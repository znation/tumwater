**Problem.** A kept patch under `.tumwater/salvage/` is deleted by the session-retention pass (`pruneOldFiles(salvageDir(root), days)`, src/files/files.ts, driven by `RetentionPruner.poll(root, liveConfig.sessionRetentionDays)`, src/orchestrator/retention.ts), and every surface that shows the operator the patches says only when each was saved: `tumwater salvage` prints `1. a.patch — saved 3h ago, 38 B` (`renderSalvageRows`, src/cli/cli-salvage-command.ts) and the dashboard's Salvaged patches card prints `saved <fmtAgo>, <size>` (`renderSalvage`, src/ui/gui/gui-client-settings.ts). Neither says when the row goes, and the `## Planned` doctor entry's clause covers only the doctor row's *oldest* patch — right for a one-line alert (which names only three patches, `SALVAGE_NAMED_CAP`, and only their oldest), wrong for a list that numbers every kept patch, where the one the operator has to act on is the old row, not the new one.

**Approach.** One clause, phrased once, computed from each row's own `savedAt` and the window the team runs.

- **One home for the clause:** `prunePhrase(savedAt: number, retentionDays: number, now: number): string` exported from `src/text/datetime.ts`, beside `humanUntil` (it is a future-direction countdown with two special cases). Exactly three shapes, and a caller holding a patch never gets an empty string:
  - `retentionDays > 0`, deadline ahead (`due = savedAt + retentionDays * DAY_MS`, `DAY_MS` already exported there): `` `prune deadline in ${humanUntil(due, now)}` `` — e.g. `prune deadline in 7d`, `prune deadline in 23h`.
  - `retentionDays > 0`, deadline past (a team that never starts runs no pass, so the patch is still there): `prune deadline passed, goes at the next prune pass` — never the `0s` `humanUntil` returns once the instant has passed.
  - `retentionDays === 0`: `retention is off, so this patch is never pruned`. `0` is retention's off switch — `RetentionPruner`'s constructor starts a pass only `if (retentionDays > 0)` and `poll()` gates the same way — so under `0` nothing ever deletes the patch, and `pruneOldFiles(dir, 0)` (which would remove every file older than `now`) is never reached with that value.
- **Window source, one rule at both call sites:** `liveConfig(root).sessionRetentionDays` (src/config/config.ts) — the stat-cached last-known-good read that degrades to `defaultConfig()` (`sessionRetentionDays: 7`), and the exact value `orchestrator-poll.ts` feeds `ctx.retentionPruner.poll(root, liveConfig.sessionRetentionDays)`, so a live edit is honored without a restart and an unconfigured repo answers `prune deadline in 7d` instead of failing. Both new call sites are synchronous, so `liveConfig` fits unchanged.
- **The clause is a row display field, not a `SalvagePatch` field.** `SalvagePatch` and `grepSalvagePatches` (src/status/status-salvage.ts) keep their shapes and signatures — this entry changes no code there. `{position,file,savedAt,bytes}` and `collectSalvagePatches` keeps its signature: it serves from `cachedByStat(salvageDirCache, …)`, so a clause computed inside it would be cached against the directory's stat and go stale in a poll that changes only the clock or the config, and the same array is what `status --json`'s `salvagePatches` carries and the standing `salvage-patches` alert counts. Each list caller adds `prune` to its own row copy instead.
- **CLI list and `--json`** (src/cli/cli-salvage-command.ts): `readSalvageRows` resolves the window once per frame from `liveConfig(root)` and its rows become `{ position, file, savedAt, bytes, prune }` — for `--grep` the rows are `grepSalvagePatches`'s copies with `prune` spread on, so a filtered row still carries the whole-list `position`. `renderSalvageRows`'s row template gains `, ${p.prune}` after the size, and `sayJsonOrRender`'s payload `{ patches: result.rows }` gains the key with no other change. The empty list still prints `no salvaged workspace patches are kept for you` and `--json` still prints `{ patches: [] }`; `--show` keeps its INV-SV1-pinned `{position,file,savedAt,bytes,size,stat,patch}` exactly (no `prune` there), and `--drop`, `--apply`, `-f/--follow` and every exit code are untouched.
- **Dashboard** (src/gui/gui-salvage-commands.ts, src/ui/gui/gui-client-settings.ts): `handleSalvageList`'s record gains `prune: prunePhrase(p.savedAt, liveConfig(root).sessionRetentionDays, now)` beside the existing `size`, so `GET /api/salvage` answers `{position,file,savedAt,bytes,size,prune}`; `handleSalvageShow` is untouched. `renderSalvage` appends one span to the row's existing `<span>saved …, …</span>`: `, ${esc(p.prune)}` — the card keeps one row per patch, its View/Apply/Drop buttons, and the empty-state sentence.
- **Docs:** docs/cli.md's `Read a kept patch` row gains one clause saying each list row names when that patch is pruned and that `sessionRetentionDays: 0` means never; `src/cli/cli-help-text.ts`'s `tumwater salvage` stanza gains the same sentence. No other docs file (the window's own semantics stay in docs/config.md, which the `## Planned` doctor entry claims).

**Acceptance criteria.**

1. In a repo with no `tumwater.json`, with `a.patch` (38 B, 3 h old) and `b.patch` (17 B, now), `tumwater salvage` prints `1. a.patch — saved 3h ago, 38 B, prune deadline in 7d` and `2. b.patch — saved 0m ago, 17 B, prune deadline in 7d` — the default window, and nothing before the new clause moved.
2. With `{ sessionRetentionDays: 1 }` written to `tumwater.json`, the 3-hour-old row prints `prune deadline in 21h` (24 h − 3 h, still in `humanUntil`'s hour bucket); with `{ sessionRetentionDays: 4 }` the same row prints `prune deadline in 4d` (93 h rounds into the day bucket) — a configured window changes the figure from the default `7d`. Given a patch whose mtime predates the window, its row prints `prune deadline passed, goes at the next prune pass`. Given `{ sessionRetentionDays: 0 }`, every row prints `retention is off, so this patch is never pruned`. A row that read `defaultConfig().sessionRetentionDays` instead of the loaded config answers the `1` case with `7d` and fails it; a branch that tested the passed deadline before the `0` window prints a passed deadline under `0` and fails the `0` case; a countdown built as `humanSeconds(due - now)` in milliseconds instead of `humanUntil(due, now)` prints a figure no case expects.
3. `tumwater salvage --json` rows carry `prune` with byte-identical wording to the row of the same position, and `tumwater salvage --show 1 --json` prints no `prune` key — its keys stay exactly `{position,file,savedAt,bytes,size,stat,patch}` (INV-SV1). The `{ patches: [...] }` envelope, the `{ patches: [] }` empty shape, and `--grep`'s whole-list `position` numbering are otherwise unchanged.
4. `GET /api/salvage` records carry `prune`, and `renderSalvage` paints one clause per row in the same row element as that patch's View/Apply/Drop buttons; with `patches: []` the card still paints `no salvaged workspace patches are kept for you`. A response that omitted `prune` renders no clause, so a per-row assertion fails.
5. `status --json`'s `salvagePatches` array keeps its exact `{position,file,savedAt,bytes}` shape — no `prune` key — and `collectSalvagePatches`'s signature and stat-cache contract are unchanged, so a second read after a config edit reflects the new window (the clause is never served from the directory cache).
6. docs/cli.md's `Read a kept patch` row and the `tumwater salvage` help stanza each name the deadline and the `0`-means-never case, and every anchor that matches the row's existing text still matches it (nothing removed).
