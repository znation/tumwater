### Backlog archive and quarantine filing: a BUGS.md or archive file that cannot be read skips the move instead of deleting or overwriting it (planned 2026-10-20 by the plan role; independent of every eligible plan; touches src/backlog/backlog-archive.ts + test/backlog-archive.test.ts + docs/invariants.md)

**Goal.** src/backlog/backlog-archive.ts rewrites backlog files in the primary checkout and in run worktrees. It reads them through `readTextOrNull` (src/files/files.ts), which returns null for every error. So a file that exists but cannot be read (EMFILE under fd pressure, EIO) is treated as absent, and the write that follows destroys it:
- `fileQuarantineBugsOnMain` reads `before` with `readTextOrNull`. When BUGS.md cannot be read, `before` is null. `appendBugEntryLocked` then throws, because its `appendEntryLocked` reads through `readTextIfExists`, which rethrows. The catch runs `restoreBugs`, and that calls `fs.rmSync(file, { force: true })` because `before === null`. **Reproduced 2026-10-20** against dist: a committed BUGS.md, with `fs.readFileSync` of BUGS.md throwing EMFILE, returns `skipped` ("a BUGS.md entry could not be written: EMFILE…") and leaves ` D BUGS.md` in the primary checkout. After that, every later filing skips with "BUGS.md has uncommitted changes", and every reader sees no open bugs.
- `planArchiveAll` (used by `archiveFinishedOnMain` and `liveFinishedHistory`) and `archiveNewFinishedEntries` pass `readTextOrNull(<archive>)` to `archiveFinishedText`. That function replaces a null archive with `archiveTemplate(spec)`. `writeMove` then overwrites an existing but unreadable PLANS-DONE.md or BUGS-FIXED.md with only the entries being moved. `archiveFinishedOnMain` commits that on main, because `created` is computed with `fs.existsSync`, so the file counts as tracked rather than new. `archiveNewFinishedEntries` writes the same truncation into the run's commit.

**Approach.** One theme, one file: treat "missing" and "unreadable" differently on these read-modify-write paths, as `readTextIfExists` (src/files/files.ts) already does for backlog-write.ts and the inbox.
1. Import `readTextIfExists` from `../files/files.js` in src/backlog/backlog-archive.ts. Switch to it in four places: both reads in `planArchiveAll`, both reads in `archiveNewFinishedEntries`, and the `before` read in `fileQuarantineBugsOnMain`. Keep `readTextOrNull` in `liveFinishedHistory`'s own `live` read: it only measures bytes, and `planArchiveAll` runs before it and already throws on an unreadable file.
2. `fileQuarantineBugsOnMain`: put the `before` read in a `try`. On a throw, return `{ status: "skipped", reason: ... }` with the reason "`BUGS.md could not be read: ` followed by `errorFirstLine(err)`", before anything is written. `restoreBugs` stays as it is: `before === null` now means the file really did not exist.
3. `archiveFinishedOnMain`: wrap both `planArchiveAll(root, keep)` calls (the pre-check outside the locks and the re-plan under them). On a throw, return `skipped` with the reason "`a backlog file could not be read: ` followed by `errorFirstLine(err)`". A small local helper that returns the plan or the skip is fine. That gives `cmdArchive` (src/backlog/backlog-cli.ts) its one-line `fail(...)` and `archiveAtTeamStart` its existing skipped warning, with no change to either.
4. `archiveNewFinishedEntries` may throw. Its only caller (src/run/run-stage.ts) already ends in `.catch(() => [])`, so the run commits with the entry still in the live section, which is legal and gets swept later. `liveFinishedHistory` may throw too. Doctor's runner (src/doctor/doctor.ts) turns that into "the check threw: …", which is the right signal for an unreadable PLANS.md or BUGS.md. Update the doc comments of `fileQuarantineBugsOnMain` and `archiveFinishedOnMain` to say that an unreadable file skips the call.

### Conflict-marker check: a changed file that cannot be read counts as still conflicted, so the gate never merges markers it could not see (planned 2026-10-20 by the plan role; independent of every eligible plan; touches src/merge/merge-git.ts + test/merge-git.test.ts + test/review.test.ts + docs/invariants.md)

**Goal.** `hasConflictMarkers` (src/merge/merge-git.ts) reads each file through `readTextOrNull`, which returns null for every error. A null counts as "resolved", because a deleted file means the resolver chose the deletion. So a file that exists but cannot be read (EMFILE under fd pressure, EIO) passes as free of markers. That check is the only deterministic guard against raw `<<<<<<<` lines reaching main. Three callers rely on it: the review gate (`conflictMarkerReason` in `reviewAttempt`, src/review/review.ts), where an md-only diff then takes the exempt fast path and merges unreviewed; the stage check (`stageCheckFindings`, src/run/stage-check.ts); and the merge resolver's acceptance test in src/merge/merge-to-main.ts (`if (!pi.ok || hasConflictMarkers(wt, remaining))`), which would continue the rebase over a resolution it never read. **Reproduced 2026-10-20** against dist with a scratch .mjs: a file holding a full conflict block gives `hasConflictMarkers` → true. With `fs.readFileSync` patched to throw EMFILE for that path, it gives false, and `conflictMarkerReason` gives undefined.

**Approach.** One file, fail closed. Only "this path holds no file" counts as resolved.
1. In src/merge/merge-git.ts, add a non-exported `markerState(wt: string, f: string): "clean" | "marked" | "unreadable"`. Read with `fs.readFileSync(path.join(wt, f), "utf8")` inside a try (`fs` is already imported). The error codes ENOENT, ENOTDIR and EISDIR give `"clean"`: deleted, a parent replaced, or a directory/gitlink path, none of which can hold a text marker. Get the code with `errCode` from `../errno.js`. Any other error gives `"unreadable"`. Text that matches `MARKER_EDGE` gives `"marked"`, otherwise `"clean"`.
2. `hasConflictMarkers` returns true when any file's state is not `"clean"`. Update its doc comment: a missing path still counts as resolved, but an unreadable one counts as conflicted, because a check that cannot read a file cannot vouch for it.
3. `conflictMarkerReason` keeps its exact wording for marked files (`conflict markers remain in: ` followed by the comma-joined list). It lists unreadable files separately as `could not be read to check for conflict markers: ` followed by the comma-joined list. When both lists are non-empty, join the two clauses with `; `. Return undefined only when every file is `"clean"`. Compute the states once per file instead of calling `hasConflictMarkers` per file.
4. Leave `conflictedFileHunks` on `readTextOrNull`. It only builds prompt text, and an unreadable file listing no hunks is harmless. Leave `markerBearingFiles` in src/runner/runner-run.ts unchanged. It inherits the fail-closed answer, so a hand-off note may name an unreadable file, which is accurate enough.
