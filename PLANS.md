### Run transcript search: `tumwater history <role> <n> --transcript --grep <text>` keeps only that run's transcript entries that contain the text, each under its agent run's separator (planned 2026-10-20 by the plan role; independent of every eligible plan; touches src/ui/transcript-run.ts + src/run/run-detail.ts + src/cli.ts + src/cli/help.ts + docs/cli.md + test/run-detail.test.ts + test/transcript-run.test.ts)

**Goal.** `logs --transcript <id> --grep <text>` and `GET /api/transcript?grep=` narrow a role's live transcript through one shared keep rule, `createTranscriptFilter` (src/ui/transcript.ts). The one-run view, `history <role> <n> --transcript`, has no such filter. To find where a past run's agent hit a given error, an operator has to page through the whole run's transcript. This plan gives the trail form the same `--grep <text>`, with the same keep rule and case-insensitive match. When planned, `RUN_DETAIL_USAGE` (src/run/run-detail.ts) did not name `--grep`; `runTrailCommand` (src/cli.ts) admitted only `--json --last --stat --patch --transcript --prompt`; and `grep -n 'history <role>.*--grep' PLANS.md PLANS-DONE.md` printed nothing.
Out of scope, unchanged: the TUI History trail's Ctrl+R transcript (src/ui/tui/tui-pane-history.ts) and `GET /api/run?transcript` (src/gui/gui-endpoints.ts). Both call `runTranscriptLines` without the new option and keep their output.

**Approach.**
1. src/ui/transcript-run.ts `readRunTranscript`: `opts` becomes `{ includePrompts?: boolean; grep?: string }`, where `grep` is an already-lowercased needle. Replace `return formatTranscript(kept, opts).flat();` with: format the entries once. When `opts.grep` is undefined, return `entries.flat()`, so today's output is unchanged. Otherwise make `const keep = createTranscriptFilter(opts.grep)`. Feed the entries oldest first and push each non-null result, then return the flattened list. Import `createTranscriptFilter` beside `formatTranscript`. Extend the function's doc comment with one sentence: `grep` keeps only the entries containing it, through the filter `logs --transcript --grep` uses.
2. src/run/run-detail.ts:
   - `RUN_DETAIL_USAGE` becomes `"tumwater history <role> [<n>] [--last] [--stat] [--patch] [--transcript [--prompt] [--grep <text>]] [--json]"`. Make the same change to `cmdRunDetail`'s doc-comment synopsis.
   - `runTranscriptLines`'s `opts` gains `grep?: string`, the raw pattern. Leave the `detail.startTs === null` branch as it is. Otherwise pass `{ includePrompts: opts.includePrompts, grep: opts.grep?.toLowerCase() }` to `readRunTranscript`. When `opts.grep !== undefined`, the `note` becomes `` `(no transcript entries matching "${opts.grep}" in ${role} run ${runNumber})` `` in place of the rotated-out note.
   - `cmdRunDetail`'s options object gains `grep = null` typed `grep?: string | null`. Right after the `prompt && !transcript` check, add `if (grep !== null && !transcript) fail(\`history --grep needs --transcript on a one-run trail (usage: ${RUN_DETAIL_USAGE})\`);`. Pass `grep: grep ?? undefined` in the `runTranscriptLines` options. `--json`'s `transcript` array then carries the filtered lines with no further change.
3. src/cli.ts `runTrailCommand`: before `peelPositionals`, run `const { rest: ungrepped, pattern: grep } = parseGrepFlag(args, HISTORY_GREP_VALUE_ERROR);`. That call removes the pattern token, so `history bugfix 2 --grep two` cannot read "two" as a third positional. Then call `peelPositionals(ungrepped)`. Add `{ names: ["--grep"] }` to the `rejectUnknownArgs` list. It is valueless because the value is already gone, and the gate's once-only rule still refuses a second `--grep`. Pass `grep` in `cmdRunDetail`'s options. Get `HISTORY_GREP_VALUE_ERROR` from "./history/history.js" through the same dynamic `await import` idiom the function already uses for run-detail.js. Check with grep whether `parseGrepFlag` is already imported into cli.ts from "./cli/cli-args.js", and add it if not. `historyTrailForm` (src/cli/cli-command-args.ts) already skips `--grep`'s value, so it needs no change. Update the function's doc comment list to "(only --json, --last, --stat, --patch, --transcript, --prompt, --grep)".
4. src/cli/help.ts: the trail stanza's synopsis becomes `tumwater history <role> [<n>] [--last] [--stat] [--patch] [--transcript [--prompt] [--grep <text>]] [--json]`. After its `--prompt (with --transcript) also shows each run's exact prompt text;` line, add `--grep <text> (with --transcript) keeps only the transcript entries containing the text, case-insensitively, under their run's separator (like logs --transcript --grep);`. Wrap it to the stanza's column.
5. docs/cli.md, "Watch run history" row: after "`--prompt` with it also shows each agent run's exact prompt", insert "; `--grep <text>` with it keeps only the transcript entries containing the text (case-insensitive, each under its agent run's separator, like `logs --transcript --grep`)". Keep the rest of the sentence as it is.

### Pending overlaps in the dashboard: `GET /api/diff?overlaps=1` serves `tumwater diff --overlaps`'s document, and the Pending view paints it as an "Overlapping files" card (planned 2026-10-20 by the plan role; independent of every eligible plan; touches src/gui/gui-endpoints.ts + src/ui/gui/gui-client-pending.ts + docs/how-it-works.md + docs/invariants.md + test/gui-endpoints.test.ts + test/gui-client-pending.test.ts)

**Goal.** `tumwater diff --overlaps` (`collectChangeOverlaps`, src/change/change-data.ts) lists each file that two or more roles' pending changes touch. The dashboard's Pending view shows each role's change and the merge queue, but not these collisions. An operator watching ten feature instances in the browser has to switch to the CLI to see two changes heading for a conflict. This plan adds the endpoint form and a card in the Pending view. When planned, `handleDiff` (src/gui/gui-endpoints.ts) read only `role`. `grep -n overlap src/ui/gui/*.ts src/gui/*.ts` matched no overlap feature (its only hits were the word "overlap" in unrelated comments). No PLANS.md or PLANS-DONE.md entry covered a dashboard overlaps view, and PLANS-DONE.md's `diff --overlaps` entry declared `/api/diff` out of scope.

**Approach.**
1. src/gui/gui-endpoints.ts `handleDiff`: before the `role` read, when `q.get("overlaps") !== null`, do the following. If `q.get("role") !== null`, call `badRequest(res, "overlaps reads every role; drop role")` and return. This mirrors `cmdDiff`'s "diff --overlaps reads every role; drop --role". Otherwise call `sendJson(res, 200, await collectChangeOverlaps(root))` and return. Import `collectChangeOverlaps` beside `collectTeamChanges`. Extend the doc comment with one sentence: `?overlaps=1` serves `collectChangeOverlaps` (exactly `tumwater diff --overlaps --json`'s `{ mainBranch, state, overlaps }`), and with `role` it is a 400. Any value of `overlaps` counts, because only the parameter's presence is read.
2. src/ui/gui/gui-client-pending.ts, inside the `// pending-table:start` … `// pending-table:end` region, after `pendingQueueHtml`: add a pure `pendingOverlapsHtml(view)`. It returns `"<div class='card-head'><h2>Overlapping files</h2></div>"` followed by a body:
   - `view && view.state === "no-base"` → `"<div class='empty'>Main branch " + esc(view.mainBranch) + " does not exist</div>"`;
   - when `view` is not an object, or `view.overlaps` is not a non-empty array → `"<div class='empty'>No file is touched by two pending changes</div>"` (the CLI's `renderChangeOverlaps` text, capitalised);
   - otherwise `"<div style='padding:10px 16px 12px'>"`, then one `"<div class='mono clamp1' style='padding:3px 0'>" + esc(o.path) + ": " + esc(roles.map(roleLabel).join(", ")) + "</div>"` per overlap, then `"</div>"`. `roles` is `Array.isArray(o.roles) ? o.roles : []`, and a non-string `o.path` renders as `"?"`. Each line mirrors the CLI's `path: role, role` line, with roles shown through `roleLabel` like the rest of the page.
   Put a two-line comment above it in the module's style.
3. Same file: add `let pendingOverlaps = null;` beside `pendingTeam`. In `buildPendingView`, add `"<div class='card' id='pendingoverlaps'><div class='empty'>Loading…</div></div>"` between the `pendingqueue` card and the `pendingbody` card. Add `async function fetchPendingOverlaps()`. It runs `try { pendingOverlaps = await getJson("/api/diff?overlaps=1"); } catch (err) { const card = $("pendingoverlaps"); if (card) card.innerHTML = errorPanel("Overlaps unavailable", err); return; }`, then sets `$("pendingoverlaps").innerHTML = pendingOverlapsHtml(pendingOverlaps)` when the card exists. In `fetchPending`, right after `buildPendingView();`, call `fetchPendingOverlaps();` without awaiting it. That way a failed overlaps read never blanks the roster, a failed roster read never blanks the card, and the Refresh button (which calls `fetchPending`) refreshes both. Update the module's top doc comment: the view also paints the overlapping-files card from `/api/diff?overlaps=1`.
4. docs/how-it-works.md, the dashboard paragraph: after "the Pending view also paints the merge queue as a card mirroring `tumwater queue`," insert "and the files two or more roles' pending changes touch as an Overlapping files card mirroring `tumwater diff --overlaps` (`GET /api/diff?overlaps=1`),". Keep the rest of the sentence as it is.
