### Poll-loop runner state: a skip-reason, claim-release or main_red re-queue save that fails warns and moves on instead of throwing out of the poll loop, and docs/invariants.md gains a section for it (planned 2026-10-20 by the plan role; independent of every eligible plan; touches src/runner/runner-state.ts + src/orchestrator/orchestrator-scheduling.ts + src/merge/merge-slot.ts + test/orchestrator-scheduling.test.ts + test/merge-requeue.test.ts + docs/invariants.md)

**Goal.** The orchestrator's poll loop (`while (!signal.aborted)` in src/orchestrator/orchestrator.ts) runs inside a `try`/`finally` with no `catch`, so any throw from a poll step ends the team (`stopCause` stays `"error"`). Three poll-step writes of a runner's state file call `saveRunnerState` (src/runner/runner-state.ts, a `writeJsonAtomic`) with no guard:
- `noteSkip` in src/orchestrator/orchestrator-scheduling.ts, which `pollRunnerReasons` calls whenever a role's skip reason changes;
- the claim-release save in `pollRunnerReasons` (`r.state.claim = undefined; saveRunnerState(root, r.state)`);
- both saves in `requeueMainRedPin` (src/merge/merge-slot.ts), which `pollMergeDrain` (src/orchestrator/orchestrator-poll.ts) calls for every runner, plus its `enqueueRetry` → `enqueueMerge` queue write.
On 2026-10-20 the plan role confirmed with a scratch test (since deleted): in the existing claim-hold setup ("a sibling held by an unclaimed mid-entry runner records claim-hold, cleared once admitted"), making the rename of `statePath(root, "feature-2")` fail with `failRenameSyncOn` (test/helpers/fs-faults.ts) makes `pollRunnerReasons` reject with that error. A full disk (ENOSPC), a read-only `.tumwater/state` (EACCES) or a state path replaced by a directory reaches the poll loop the same way. The in-memory state is already updated before each of these saves, and the next successful save of that runner (its run end, or the next change) writes it, so a failed save loses nothing the team needs to keep running. The events feed beside these saves is already best-effort ("a claim release survives an unwritable events feed").

**Approach.**
1. src/runner/runner-state.ts: add `export function saveRunnerStateBestEffort(root: string, state: RunnerState): void` beside `saveRunnerState`. It calls `saveRunnerState` in a `try`; the `catch` calls `warnEventBestEffort(root, state.role, \`could not save the role's state: ${errorMessage(err)}\`)` (import `warnEventBestEffort` from ../events/events.js and `errorMessage` from ../text/text.js; events.ts does not import runner-state, so there is no cycle). Doc comment: for writes in the orchestrator's poll loop, which has no catch; the in-memory state stays ahead of the file until the runner's next successful save. Leave `saveRunnerState` itself strict: run-end and CLI callers keep their errors.
2. src/orchestrator/orchestrator-scheduling.ts: `noteSkip` and the claim-release save in `pollRunnerReasons` call `saveRunnerStateBestEffort` instead of `saveRunnerState`. If `saveRunnerState` is then unused in the file, drop it from the import.
3. src/merge/merge-slot.ts, `requeueMainRedPin`: both `saveRunnerState(root, state)` calls become `saveRunnerStateBestEffort`. Wrap the final `enqueueRetry(root, retryEntry(kept.entry, sha, "main_red"))` in `try`/`catch` that calls `warnEventBestEffort(root, kept.entry.role, \`the kept main_red change could not be re-queued: ${errorMessage(err)}\`)` (import what is missing; check the file's existing imports first). Do not restore `state.mainRedRetry` on that failure: the role's leftover recovery re-queues a kept pin with no record, as `requeueKeptChange`'s doc says ("leftover recovery stays the backstop"). Extend `requeueMainRedPin`'s doc comment with one sentence: it never throws, since the poll loop calls it with no catch. Leave `requeueKeptChange` alone: it runs when a merge settles, not in the poll body.
4. test/orchestrator-scheduling.test.ts: import `failRenameSyncOn` from ./helpers/fs-faults.js and `eventsOfType` from ./fixtures/log-fixtures.js (that module is already imported for `unwritableEvents`/`writeEvents`). Append two tests; undo each fault in a `finally`:

It resolves and `feature2.state.claim` is undefined. `failRenameSyncOn` fails only the first matching rename, so do not assert on the file's contents.
