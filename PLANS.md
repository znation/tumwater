## Planned

### The post-merge review floors its own wall at the 3600 s reviewer floor when its resolved model is free, so a slow local default is not killed mid-run and re-queued (planned 2026-11-14 by the plan role; implements Option B of the user's 2026-11-14 answer to QUESTIONS.md "post-merge review on a slow local model", and fixes the open BUGS.md entry "The post-merge review times out while still progressing… no floor reaches the post-merge review path")

**Goal.** A merged commit's post-merge review runs on the live config's `strong`/`review` model — on this host a slow local model — and its wall comes from `reviewRunConfig` (src/config/config-views.ts): a 900 s base (`REVIEW_TIMEOUT_S`) stretched up to 2× under host load and up to 2× for a large diff. A *free* (typically local) model needs the same number of turns as a paid one but runs far slower per turn, so the load stretch alone (1800 s for a59a20af; 3555.9 s for a4d55b7d once the diff stretch engages) kills a *progressing* review mid-run and the drain re-queues it, burning ~15–60 min of dead compute per attempt until an attempt happens to finish. The `FALLBACK_REVIEW_TIMEOUT_S` (3600 s) floor exists for exactly this, but only in the budget-fallback view (`fallbackReview`, src/config/config-fallbacks.ts), which the post-merge review never uses. Generalize the floor to the live post-merge path: when the reviewer's *own* resolved seam is free, floor its budget at `FALLBACK_REVIEW_TIMEOUT_S` *before* the load/diff stretch, so a slow local default gets the floor (not the 900 s fast-default budget) while a paid reviewer keeps today's value exactly. The load/diff stretch and the quiet watchdog are untouched.

**Approach.**
- `src/config/config-views.ts`, `reviewRunConfig`: add a fourth parameter `slowReviewer: boolean = false` and a floor step — when true, the budget's base is `Math.max(config.review.timeoutSeconds ?? REVIEW_TIMEOUT_S, FALLBACK_REVIEW_TIMEOUT_S)` before the existing `starvedDeadlineMs` × `diffScaledMs/base` stretch and the existing `Math.min(cfg.runTimeoutSeconds, …)` cap, all unchanged. `FALLBACK_REVIEW_TIMEOUT_S` is already declared in this file, so no new import. **Do not** import `seamFree` here: `pi-models.js` imports `config-views.js` (`configForRole`/`reviewConfig`/`resolverConfig`), so a reverse import would cycle — the free-ness verdict is computed by the caller and passed in as a plain boolean.
- `src/review/post-merge-review.ts`, `reviewMergedCommit`: at the point it builds the reviewer config, resolve the reviewer seam with the existing `reviewConfig(config)` and judge it free with `seamFree` (src/pi/pi-models.ts) over `readPiProviders(piModelsPath())`, a `readAccount`-backed account reader (src/agent/subscription-account.ts; a missing account file reads null and the subscription arm returns the safe false), and `readOpencodeCache(root)` (src/agent/opencode/opencode-catalog.ts) — then pass that boolean as the fourth `reviewRunConfig` argument. These three are lower-level modules that do not import `post-merge-review.ts`, so no cycle. Make the verdict injectable (an optional `slowReviewer?: boolean` parameter on `reviewMergedCommit` that defaults to the computed value) the way `load` is already injectable in `reviewRunConfig`, so the offline test forces free/not-free without a real model catalog.
- Existing callers and tests are unchanged: `merge-slot.ts` (`reviewRunConfig(author.config)`), `config-fallbacks.ts` (`reviewRunConfig(config)`, whose budget-fallback view keeps flooring its own `timeoutSeconds` in `fallbackReview`), `role-view.ts`, and `orchestrator-scheduling.ts` all pass no fourth argument and read `slowReviewer = false`.

**Files touched.** src/config/config-views.ts, src/review/post-merge-review.ts, test/config-views.test.ts, test/post-merge-review.test.ts.

**Acceptance criteria.**
- With the reviewer free, a quiet host (load1 ≤ cpus) gives the post-merge reviewer a 3600 s wall, not 900 s; a starved host (load1 > cpus) stretches it above the floor up to the 2× cap (≤ 7200 s); and a large reviewed diff (above `REVIEW_DIFF_REFERENCE_BYTES`) stretches it toward the 4× ceiling — each still bounded by the run's own budget, so a wedged review's quiet-watchdog wall is untouched.
- With the reviewer *not* free (the default `slowReviewer = false`), a quiet host gives exactly today's 900 s and a starved host exactly today's ≤ 1800 s — the floor engages only for a free reviewer, so a paid reviewer's wall is byte-identical to before.
- A configured `review.timeoutSeconds` above the floor stands unchanged when the reviewer is free; one below the floor is raised to the floor — the same rule `fallbackReview` already applies.
- Offline, forcing the free-ness verdict true makes the gate run the post-merge review with `runTimeoutSeconds` ≥ `FALLBACK_REVIEW_TIMEOUT_S`; forcing it false keeps the pre-floor value. The existing `config-views.test.ts` `reviewRunConfig` tests (own-budget, starved stretch, smaller-run-budget-wins) and the `post-merge-review.test.ts` load-robust diff-stretch tests all pass unmodified.
- **Known precondition (the 2026-11-13 selfcheck confirmation, still open):** the floor engages when the reviewer's *resolved* seam is free per `seamFree`. On this host that requires the slow local model to resolve to a seam `seamFree` calls free (a pi seam listed price-0 in models.json, or a subscription account that is not over-billing). If the reviewer instead resolves to a local endpoint `seamFree` does not recognize as free, the floor will not engage — the implementer should confirm the resolved seam is free on a real catalog before treating the bug as resolved; the QUESTIONS.md Option-B decision (detect via the existing `seamFree`) governs, so this is a precondition to verify, not a redesign.
