**Goal.** The file-based ref reads in src/git/git.ts — the `"Ref reads from files"` block behind `isGitRepo`, `hasCommits`, `headOf`, `refSha`, `branchExists` and `hasWorktreeRegistrations` — each ask `repoFiles(dir)` first and answer from the repository's files only when the files *settle* the read, otherwise they spawn git. `repoFiles` gates that on `filesBackendTrusted`, a guard whose job is to decide whether the files may be trusted at all: this process's user owns both the checkout dir and its git dir, the shared dir's `objects` dir and the git dir's `HEAD` are present, and no `reftable` store shadows the loose/packed refs. When the files are untrusted every probe must fall back to git. No test drives this gate: the suite only builds same-user, complete, non-reftable repositories (the trusted path) and one redirect-env case, so the branch that makes an *untrusted* repository fall back to git has no failing test. A change to the ownership comparison, the `objects`/`HEAD` presence checks, or the `reftable` shadow check would silently let a planted or incomplete layout answer a ref SHA from files with no test to catch it. Pin the gate's untrusted branches through the exported `refShaFromFiles` (which calls `repoFiles`) and one real probe (`hasCommits`, to confirm the spawn fallback), so the trust decision itself is part of the suite.

**Approach.** One file, test-only, no src change and no invariant edit: in test/git-ref-files.test.ts (which already imports `refShaFromFiles`, `hasCommits`, `setEnv` from test/helpers/env.js, and `makeRepo`, `gitInit`, `commitIn`, `sh`, `tmpdir` from test/fixtures/repo-fixtures.js, and holds the `richRepo()` fixture) add `test(...)` cases that build a real same-user repository — a `makeRepo()` primary checkout, where `git init -b main` leaves no `commondir` pointer, so `resolveCommondir` resolves the shared dir to `.git` and the guard reads `.git/objects`, `.git/HEAD` and `.git/reftable` directly — then mutate one layout condition and assert the gate refuses the files. Cases: (1) the *complete trusted* baseline — a `makeRepo()` checkout with a commit — answers `refShaFromFiles(root, "HEAD")` (or `"main"`) with the SHA that `git rev-parse` prints, establishing the positive contract the untrusted cases fall back from; (2) *objects missing* — `fs.rmSync(path.join(root, ".git", "objects"), { recursive: true, force: true })` — `refShaFromFiles` returns `undefined` (the files do not settle it), so the read falls back to git; (3) *HEAD missing* — `fs.rmSync(path.join(root, ".git", "HEAD"), { force: true })` — `refShaFromFiles` returns `undefined`; (4) *reftable shadows* — `fs.mkdirSync(path.join(root, ".git", "reftable"))` — `refShaFromFiles` returns `undefined` even though `objects` and `HEAD` are present; (5) *redirect env* — `t.after(setEnv("GIT_DIR", path.join(other, ".git")))` on a real repo — `refShaFromFiles` returns `undefined` (this branch is already asserted in the file for `HEAD`; a distinct full `refs/…` read through `refSha` or `hasCommits` confirms the gate bails on the environment regardless of the ref shape); and (6) the *spawn fallback* — against the objects-missing repo, `await hasCommits(root)` still resolves to `true`, proving an untrusted files-backend read defers to a git spawn rather than answering from files. No source file and no other test file change. Where a case mutates a shared `makeRepo` output, build a fresh `makeRepo()` per case so the mutations do not leak between tests.

**Files touched.** test/git-ref-files.test.ts.

**Acceptance criteria.**
- A `makeRepo()` primary checkout (a same-user, complete, non-reftable repository with a commit) answers `refShaFromFiles(root, "HEAD")` with the exact SHA `git rev-parse --verify HEAD` prints — the trusted path is the positive contract the untrusted cases fall back from.
- In a `makeRepo()` checkout whose `.git/objects` has been `rm -rf`'d, `refShaFromFiles(root, "HEAD")` returns `undefined` — the guard refuses the files when the objects dir is absent, and the read is left to git.
- In a `makeRepo()` checkout whose `.git/HEAD` has been removed, `refShaFromFiles(root, "HEAD")` returns `undefined` — the guard refuses the files when HEAD is absent.
- In a `makeRepo()` checkout whose `.git` holds a `reftable` directory, `refShaFromFiles(root, "HEAD")` returns `undefined` — a reftable store shadows the loose/packed refs even when `objects` and `HEAD` are otherwise present, and the read is left to git.
- With a git-redirecting environment variable set (e.g. `GIT_DIR`), a real repository's `refShaFromFiles` returns `undefined` — the environment forces every read back to git regardless of the ref shape or the files' completeness.
- Against an objects-missing repository, `await hasCommits(root)` resolves to `true` — an untrusted files-backend read defers to a git spawn and the probe still answers, rather than erroring or reading a planted layout.
- Every pre-existing test in test/git-ref-files.test.ts passes unmodified; no source file and no test file other than this one change; the project's declared check is green.

### `nearestTumwaterRoot`'s ancestor-walk branches are pinned in test/paths.test.ts, so a regression that would mint a phantom team root from a nested directory, or read a non-directory `.tumwater` entry as a root, is caught by the suite (planned 2026-11-15 by the plan role; `nearestTumwaterRoot` in src/paths.ts walks up to 64 ancestors from `sessionDir` and returns the first directory that holds a `.tumwater` *directory* — `isDirectory` from src/files/files.js — or `undefined` when none does; it is the lookup every team-root resolution builds on, and `owningTeamRoot` (src/paths.ts, which both init and the gated commands call to refuse a team workspace) and `teamRootOf` (the OpenCode read-back root) each call it first; it is exported and yet `grep -rn 'nearestTumwaterRoot' test/` prints nothing — no test drives it directly; the only live test, `"owningTeamRoot names the team root only for a directory inside its worktrees"` (test/paths.test.ts:147), exercises `owningTeamRoot`, whose output is `nearestTumwaterRoot`'s *collapsed* result (a slot is `root`, a root or a dir-under-root is `undefined`), so the three branches of `nearestTumwaterRoot` itself — return the directory itself, return a *nested* ancestor, return `undefined` — are never distinguished: a change to the `isDirectory` shape check, the 64-ancestor bound, or the self-return would silently let `owningTeamRoot`/`teamRootOf` read the wrong root or mint a phantom one (the 2026-10-18 `$TMPDIR/.tumwater` bug) with no failing test; the walk is pure path logic — `isDirectory` plus `path.dirname`, no git, shell or file read — so the pin is test-only and needs no invariant edit, docs/invariants.md binding src/paths.ts to `owningTeamRoot` and other symbols but never `nearestTumwaterRoot`; independent in file of the other `## Planned` entry, which is test/git-ref-files.test.ts over src/git/git.ts, so feature can take either)

**Goal.** `nearestTumwaterRoot` (src/paths.ts, exported) is the one lookup that answers "which team root owns this directory?" by walking up the filesystem until it finds a `.tumwater` directory. Both `owningTeamRoot` (the team-workspace refusal init and the gated CLI commands rely on) and `teamRootOf` (the OpenCode/notes read-back root) delegate the actual search to it, so it is the load-bearing core of team-root resolution. Its three outcomes — the given directory *itself* when it directly holds `.tumwater`, a *nested* ancestor when only an ancestor does, and `undefined` when none within 64 levels does — are each the answer to a different real question, but no test drives it directly: the existing `owningTeamRoot` test only sees the collapsed `{root, undefined}` that `owningTeamRoot` computes *from* it, so it cannot catch a regression in the walk's self-return, its ancestor climb, its `isDirectory`-vs-`exists` shape check, or its no-match termination. The `undefined` branch is the safety pin — BUGS.md 2026-10-18 was a phantom `.tumwater` minted in a shared directory that then read back as a root; a walk that returned a directory for a non-directory `.tumwater`, or that stopped at the wrong ancestor, reproduces it. Pin all three branches plus the shape check through the exported function so the team-root search itself is part of the suite.

**Approach.** One file, test-only, no src change and no invariant edit (docs/invariants.md binds src/paths.ts to `owningTeamRoot` and other symbols but never `nearestTumwaterRoot`): in test/paths.test.ts add `nearestTumwaterRoot` to the existing named-import block from `../src/paths.js`, and add `import fs from "node:fs"` (the file currently imports only `node:test`, `node:assert/strict`, and `node:path`). Each case builds a throwaway tree under the file's existing `tmpdir()` helper (test/fixtures/repo-fixtures.ts — one `fs.mkdtempSync` directory under the per-run root, so a fresh call gives a directory whose only ancestors are that mkdtemp dir, the shared per-run root, and the OS tmp mount, none of which hold a `.tumwater` directory — the same isolation the existing `owningTeamRoot` test already assumes) and lays out real entries with `fs.mkdirSync`/`fs.writeFileSync`, then drives `nearestTumwaterRoot` against it. Cases: (1) *returns itself* — `fs.mkdirSync(path.join(dir, ".tumwater"))` where `dir` is a fresh child under `tmpdir()` — `nearestTumwaterRoot(dir)` returns `dir`; (2) *returns a nested ancestor* — a `<team>` dir holding a `.tumwater` directory, with a nested `<team>/.tumwater/worktrees/_slot-1` (the real role-worktree shape) — `nearestTumwaterRoot(nested)` returns `<team>`, not the nested dir, proving the walk climbs to the nearest ancestor that holds the store; (3) *no match* — a fresh empty `tmpdir()` child with nothing created — `nearestTumwaterRoot(dir)` returns `undefined`, the no-phantom-root safety; (4) *a non-directory store is not a root* — `fs.writeFileSync(path.join(dir, ".tumwater"), "x")` (a `.tumwater` *file*, plus a nested child for good measure) — `nearestTumwaterRoot(dir)` returns `undefined`, pinning that the walk tests `isDirectory`, not mere existence. No source file and no other test file change.

**Files touched.** test/paths.test.ts.

**Acceptance criteria.**
- Given a directory that holds a `.tumwater` subdirectory, `nearestTumwaterRoot(dir)` returns `dir` itself — a directory is its own team root the moment it holds the store.
- Given a nested directory (a `<team>/.tumwater/worktrees/_slot-1` whose nearest ancestor holding a `.tumwater` directory is `<team>`), `nearestTumwaterRoot(nested)` returns `<team>` — the walk climbs to the nearest ancestor that holds the store rather than answering with the nested dir.
- Given a fresh empty directory whose ancestors hold no `.tumwater` directory, `nearestTumwaterRoot(dir)` returns `undefined` — a team root is never minted from an absent store (the 2026-10-18 phantom-root safety).
- Given a directory that holds a `.tumwater` *file* (not a directory), `nearestTumwaterRoot(dir)` returns `undefined` — a non-directory `.tumwater` entry is not read as a team root, so the walk keys on `isDirectory`, not on existence.
- Every pre-existing test in test/paths.test.ts passes unmodified; no source file changes; the project's declared check is green.
