## Planned

### `scanPositionArgs`'s five edge-flag branches are pinned in test/cli-args.test.ts, so a regression in the one home of the position-flag command shell's scan loop is caught by the suite (planned 2026-11-15 by the plan role; `scanPositionArgs(args, flag, example, extraBooleans = [])` in src/cli/cli-args.ts is the shared scan every queue-style command shell repeats: it classifies each token as `--json` (a once-settable boolean), a named extra boolean edge flag (each once-settable, collected in `flags`), the single valued position flag (parsed through `parsePositionFlag` with the caller's `example`, its value token consumed, and a repeat refused), a tolerated `--help`/`-h` (dropped), or an unknown token (collected in `rest` for the caller's `rejectUnknownArgs`), and returns `{ json, flags, position, rest }`. It is the one home of the at-most-once wording, the position value-consumption, and the help-tolerance rule the ten `--cancel`/`--top`/`--release`/`--retire`/`--show`/`--accept`/`--drop`/`--apply` shells share — cli-backlog.ts, cli-salvage-command.ts, cli-review-commands.ts, cli-query-commands.ts and cli-backlog-view.ts all call it, and `--done` (backlog `--show`) and the `--dry-run` (salvage `--apply`) arrive as `extraBooleans`; `grep -rn scanPositionArgs test/` prints nothing, so the scan itself is untested — the command shells' tests reach it only through a full `cli()` child-process path and no test drives the function directly, and the archive records no pin of it — while its constituents are already pinned: `flagValue` and `parsePositionFlag` in test/cli-args.test.ts, `parseDurationMs`/`parseDurationFlag` in the same file and the duration family, and the `rejectRepeatFlag` wording the command shells' tests assert; the loop is genuinely multi-branch, not a 1-line composition over a pinned fn — the `json`/`flags` accumulation, the skip-the-value `i++`, the help-drop, and the `rest` collection are its own, and the at-most-once and value-consumption rules compose `rejectRepeatFlag`/`parsePositionFlag` but those are the parts, not the whole; the test is test-only — no source change — and docs/invariants.md binds no `cli-args.ts` symbol (`grep -n cli-args docs/invariants.md` prints nothing), so no invariant edit is needed)

**Goal.** Pin `scanPositionArgs`'s five branch rules directly, through its exported function in test/cli-args.test.ts. The position-flag shells share it so the at-most-once, position-value-consumption, and help-tolerance rules cannot drift, but no test drives the scan itself — only the shells' e2e paths do. A one-line change to any branch (a `flags` key spelled wrong, the skip removed, a `--help` that stops dropping, a repeat accepted) is invisible to the current suite.

**Approach.** In test/cli-args.test.ts, import `scanPositionArgs` alongside the file's existing `parsePositionFlag`/`flagValue` import and drive the function directly through the `expectFail`/`expectOk` helpers from test/helpers/exit-capture.js (the same in-process capture the file's `--port`/`--since` fail tests already use), returning `{ json, flags, position, rest }` on success or throwing `ExitError` on a `fail()`. Work each expected value out of the input, never from the function's output, and pin only where the text is the operator-facing contract.

**Files touched.** test/cli-args.test.ts (test-only; no source change). src/cli/cli-args.ts is read as the source of the exact wording but is not modified.

**Acceptance criteria.**

- `scanPositionArgs(["--cancel", "2", "--json"], "--cancel", "--cancel 2")` returns `{ json: true, position: 2, flags: {}, rest: [] }` — the valued flag's value token is consumed (it does not reach `rest`), `--json` sets the boolean, and no extra booleans were named.
- `scanPositionArgs(["--show", "3", "--done", "--json"], "--show", "--show 2", ["--done"])` returns `{ json: true, position: 3, flags: { "--done": true }, rest: [] }` — the extra boolean is collected in `flags` and `--json` set in the same pass.
- `scanPositionArgs(["--show", "3", "--help"], "--show", "--show 2")` returns `{ json: false, position: 3, flags: {}, rest: [] }` — `--help` is dropped from `rest`; `[-h]` behaves the same.
- `scanPositionArgs(["--show", "3", "extra"], "--show", "--show 2")` returns `rest` containing `"extra"` — an unrecognised token survives for the caller's `rejectUnknownArgs`; and `scanPositionArgs(["--show", "3"], "--show", "--show 2")` returns `position: 3, json: false, flags: {}, rest: []` — a lone valued flag.
- A repeated `--json` (`["--json", "--json"]`) fails with the wording containing `--json may only be given once`; a repeated extra boolean (`["--done", "--done"]` with `extraBooleans = ["--done"]`) fails with `--done may only be given once`; and a repeated position flag (`["--show", "1", "--show", "2"]`) fails with `--show may only be given once` — the three repeat forms each reach their own once-rule, in token order.
- A valued flag with no value — `--cancel` as the final argument — fails with `--cancel needs a position number`; a flag-shaped value in the slot (`["--cancel", "--json"]`) fails naming the slipped flag, not a malformed number; and a non-integer value (`["--cancel", "x"]`) fails with `--cancel needs a positive integer` — the value-consumption and `parsePositionFlag` wording compose through the scan.
- After this entry `grep -rn scanPositionArgs test/` matches test/cli-args.test.ts (today it prints nothing); the project's check is green, so the ten command shells that read `scanPositionArgs` are unchanged.
