### GUI report charts: show a label on each bar segment at the cursor on mouse hover (planned 2026-09-14, requested by user)

**Goal.** In the GUI's report tab, hovering the mouse over any bar segment shows a label with that segment's exact value, immediately and in the dashboard's own style. Today each segment only carries an SVG `<title>` — the browser's native tooltip, which appears after a ~1 s delay, cannot be positioned or styled, and is invisible in some viewing contexts. The user asked for hover labels on the chart data; this plan ships the standard immediate cursor-following tooltip.

**Design (decided, with rationale).**
- **One shared tooltip element, created in JS, not in the static HTML.** A single `<div id="report-tip">` is created idempotently at script init (`document.getElementById` before creating) and appended to `document.body` with `position:fixed; pointer-events:none`. It lives outside `#report` because `fetchReport()` replaces `#report`'s innerHTML on every tab activation — a tip inside it would be destroyed and re-created per fetch — and it must not appear in the static markup because the existing page-structure test pins `</div>\n<div id="report" hidden></div>\n<script>` verbatim. `pointer-events:none` stops the tip from intercepting the pointer (which would flicker it away the instant the cursor reaches it).
- **The label text is read from the segment's existing `<title>` — no markup change to `reportSvg`.** The delegated handler takes `e.target.closest("rect")` (guarded with `instanceof Element` so non-Element targets are skipped), then `rect.querySelector("title")?.textContent`; no rect or an empty title hides the tip. This reuses the exact raw-value strings the builders already produce and escape — `2026-09-14: 14000` for tokens/commits, `2026-09-14 feature: 7` for a role segment (per-segment, NOT the day's total, in the stacked chart) — with zero new escaping surface and zero diff to `reportSvg` (the existing builder test's `parseRects` regex keeps pinning the rect markup byte-for-byte). The `<title>` elements are KEPT: they remain the accessible name of each segment, the fallback where pointer events are unavailable, and the anchor of the existing tests. The native tooltip may still appear after the browser's delay alongside the immediate one — accepted; the styled overlay is the primary affordance.
- **One delegated `pointermove` handler on the persistent `#report` container, plus `pointerleave` to hide.** Delegation on `#report` (the element itself is never replaced — only its innerHTML) survives every re-render, so the listener is attached exactly once at init. `pointermove`: resolve the rect/title as above; when present, set the tip's `textContent`, make it visible, and position it at `clientX + 12, clientY + 12` in viewport coordinates (matching `position:fixed`), measuring the tip via `getBoundingClientRect()` AFTER showing it so the flip is exact — if `left + width` exceeds `window.innerWidth`, place it at `clientX - width - 12`; same for the bottom edge (`clientY - height - 12`). When absent (svg background, gaps between bars, axis text, legend, stats row), hide it. `pointerleave` on `#report` hides it for the pointer leaving the panel entirely — switching to the fleet tab is covered by the same event, since the nav-link click necessarily moves the pointer out of `#report` first; no `switchView` hook.
- **Hover cue + chip styling, matching the dashboard's existing palette.** CSS next to the other report rules: `#report svg rect:hover { opacity:.8 }` (the only hover affordance on the charts; legend/stats/axis untouched), and for the tip: `background:#0b0e12; border:1px solid #2a3642; border-radius:6px; padding:4px 8px; font-size:12px; color:#d6dde4; white-space:nowrap; display:none; z-index:10` — the same colors as `#feed`/`#transcript` and the input borders. The tip's initial `display:none` is set in CSS; JS toggles it.
- **New marked region.** The tooltip JS lives in its own `// report-tip:start … // report-tip:end` region in the report section, beside the existing `report-chart` region, following the page's marker convention (`loop-sort`, `last-tick-fmt`) so tests can extract and pin it.

**Approach.**
- src/ui/gui-page.ts — (a) two CSS rules in the `<style>` block beside `#report svg text` (the `#report-tip` chip and `#report svg rect:hover`); (b) in the report section, a new `// report-tip:start … // report-tip:end` region immediately after the `report-chart` region (before `reportSummary`) holding: `reportTipElement()` (idempotent create + append to `document.body`) and `attachReportTip()` (the `pointermove`/`pointerleave` handlers on `document.getElementById("report")`, delegating to the hovered rect's `<title>`); (c) one call to `attachReportTip()` at the script's init point alongside the existing wiring — after the four listener-attachment blocks, immediately before the final `refresh(); setInterval(refresh, 1000);` (the `#report` container exists in the static HTML, so init-time attachment is safe); (d) a comment update in `reportSvg`'s doc comment noting the `<title>` doubles as the hover-label text source. `reportSvg`, the three chart builders, `fetchReport`, and the API are untouched.

The existing chart-builder test is left as-is — it already pins that every rect's `<title>` carries the exact raw value, which is exactly the text the tooltip now displays, and its `parseRects` regex pins that the rect markup did not change.

### Merge queue 4/5 — surface the land queue on status and both dashboards (planned 2026-09-08, requested by user, refined 2026-09-13)

**Goal.** Make queued and in-flight landings visible: after 3/5 a productive tick reports `"queued"` and its change lands seconds-to-minutes later, so an operator needs to see the depth of the queue and which change is landing right now. Depends on `Merge queue 3/5`; architecture: plans/merge-queue.md.

**Design (decided, with rationale).** One payload field, three renderers — the pattern the budget badge and the inbox count already follow. `snapshot()` gains `landQueue: { depth, inFlight?: { role, sha, summary, startedAt } }`, unconditionally (depth 0 when empty), so `status --json` consumers see one stable shape.

- **The in-flight record is a state file, not orchestrator memory.** The TUI, GUI, and `status --json` are separate processes that read `.tumwater/state/`; the drain task's in-memory promise is invisible to them (the OrchestratorInfo precedent — observers never depend on the scheduler module). The orchestrator writes `.tumwater/state/landing.json` (`{ role, sha, summary, startedAt }`) when it starts a landing and removes it after every outcome. `snapshot()` reports `inFlight` only when three things agree: the marker exists, a queue entry with that sha still exists (entries are dropped only AFTER an outcome — 3/5 — so in-flight always implies depth ≥ 1), and the orchestrator is alive (`snap.running`). The cross-check makes every crash ordering self-healing: a stale marker without a matching entry never displays, and no cleanup pass is needed.
- **The per-loop label is marker-driven, not phase.** During an async landing the authoring role has `running = false` (its tick ended with `"queued"`), and loopPhase renders its in-flight labels only for running loops — so a persisted phase can never show a landing. The label comes from the snapshot: loopPhase gains one optional parameter and renders `landing <elapsed>` (elapsed from the marker's startedAt, via the file's private duration helper) when it is passed this role's in-flight record.
- **Badge text.** `· land queue: N` while depth > 0, empty otherwise — produced by one exported pure helper landingBadge beside budgetBadge/buildBadge and shipped preformatted (the buildBadge precedent), so gui-page.ts renders the payload field rather than mirroring the rule. A merely queued role shows its normal sleep/queue state with its `queued` last result for free.

**Approach.**
- src/paths.ts — `landingStatePath(root)` → `.tumwater/state/landing.json`, beside orchestratorStatePath.
- src/state.ts — `LandingInFlight { role; sha; summary; startedAt }` interface and `readLandingMarker(root): LandingInFlight | null` (readJsonFile, never throws) beside the OrchestratorInfo/readOrchestratorInfo pair. No phase changes: the label is marker-driven (see Design).
- src/ui/status.ts — snapshot gains `landQueue`: one `queuedLandings(root)` pass per poll (3/5's land-queue.ts; its internal stat cache keeps an unchanged queue at one stat per file) serves depth, and inFlight = running && marker && a queued entry with the marker's sha.
- src/orchestrator.ts — inside 3/5's drain task: `writeJsonFile(landingStatePath(root), { role, sha, summary, startedAt: Date.now() })` before starting landChange; `removeQuiet` it after every outcome (including aborted and merge_blocked); on the no-run drop path (sha already in main) also delete a matching stale marker.
- src/ui/status-render.ts — exported pure `landingBadge(lq)` per Design; loopPhase gains a trailing optional parameter `landing?: { startedAt: number } | null` checked right after the stopped case (`if (landing) return \`landing ${duration(Date.now() - landing.startedAt)}\`;`); stateCell threads it through — its existing guard already returns the bare label for non-running loops, so no work-item leak. renderStatus's header line appends `${landingBadge(snap.landQueue)}` immediately after the running/pid+build part (`${header}`), before the inbox badge — that is where the TUI and `tumwater status` get it (both render through renderStatus); empty string when idle keeps every existing byte-identical pin intact.

### Merge queue 5/5 — coalesce the build check across queued landings (planned 2026-09-08, requested by user, refined 2026-09-15)

**Goal.** Stop paying one full `npm test` per landing when several are queued. Review each queued change individually as today, then stack the approved changes into one lander worktree, run the declared check once over the combined tree, and fast-forward main through all of them when it is green — abandoning to one-at-a-time landings (each re-verified by its own gate) when the stack is red or cannot be assembled. Depends on `Merge queue 3/5` (and transitively 2/5); architecture and invariants: plans/merge-queue.md.

**Design (decided, with rationale).**
- **Coalescing is only ever cross-role** (invariant 3 caps a role at one in-flight change), so a stack is N changes from N distinct roles — exactly the case the queue was built for. Reviews run sequentially in queue order: the single landing slot is occupied for the whole batch, and parallel reviewer runs would complicate abort/stop semantics.
- **The model reviewer is never coalesced, only the deterministic check.** Each change still gets its own gate run over its own `main...<sha>` diff (2/5's reviewAheadOfMain in that role's own `_land-<role>` worktree): an adversarial review of a stack would blur which change a criticism applies to, and the reviewer's per-change verdict is what `state.lastReview` feeds back to one author. What is shared is the expensive, deterministic half — exactly one check run over the combined tree in the common case.
- **Stacking = cherry-pick, not rebase.** After 2/5 a role branch sits at main and each landing lives only in its pinned ref as a single commit (one tick = one `commitAll`). A stack is assembled by checking out the head change's sha detached in `_land-<S[0].role>` and `git cherry-pick`ing the remaining shas in queue order, capturing each post-pick sha — those captured shas are what main fast-forwards through and what the per-change merged events carry.
- **Red or un-assemblable means abandon to one-at-a-time, not blame-the-batch.** When the stack check is red (or a cherry-pick conflicts), the batch gives up coalescing: every approved change lands through 2/5's existing single-change path (`landChange`) in queue order. That gate short-circuits on `state.lastApprovedHead === head` before any model run or pre-check, so each fallback landing costs git + ff only (plus one bounded scope-`landing` check when main moved under a change since its Phase A gate — 7ce70ae's in-lock re-check; during a batch that can only be a human commit, the single landing slot being occupied for the whole batch); conflict resolution and the full ref lifecycle come for free, and main is never left red — a change that cannot be rebased cleanly keeps its ref for next-tick recovery exactly as today. Bounded: one stack check plus N ordinary landings (the dropped bisect design cost up to N+1 checks in the same case — see Refined note 3).
- **One `merged` event per landed change.** report.ts counts `merged` events as commits; one ff through N stacked commits must emit N merged events (each with its own role, captured post-pick sha, and summary) or the usage report undercounts a batch by N−1. The question_posted diff stays one-shot around the single ff.
- **A green stack check seeds the red-main baseline.** A passed check ran on exactly the future main tip — `noteGreenBaseline(tip)` after a successful ff (the idiom verifyLanding uses for its own landing checks) so the red-main gate does not re-run the suite once per batch-landed SHA. Only the stacked tip is seeded: one ff moves main straight to it, so intermediate shas never become main's head and need no cache entry; seeding after (not before) the ff means a merge_blocked stack seeds nothing. Skips never seed, and when `detectBuildCheck` finds no declared check the batch skips the stack check entirely and lands directly — consistent with the gate skipping its pre-check.
- **The stack ff carries no rebase and no in-lock re-check — 7ce70ae's invariant holds by construction.** Since `7ce70ae`, tryMerge re-verifies inside the merge lock (`verifyLanding`) because its rebase can rewrite the checked commits into new bytes. The batch path has neither hole: nothing rewrites between the green stack check and the ff (the cherry-picks precede the check, and there is no rebase at all), so under the lock `ffMainTo(tip)` either succeeds — main becomes byte-identical to the checked tip, exactly what 7ce70ae requires of a landing — or fails because main moved under us (`merge --ff-only` on diverged history) and every S change keeps its ref with result `"merge_blocked"`, where leftover recovery re-lands each one through its own gate + tryMerge, which carries the in-lock check. During a batch no other harness landing can interleave (the single slot is occupied for the whole batch; after 3/5 even the director drains through it), so divergence means a human commit to the primary checkout — rare, and bounded at one stack check plus N ordinary landings. ffStackToMain therefore adds neither a redundant in-lock suite run (it would double-pay the common case) nor a rebase (a rewrite would invalidate the very check that just passed).
- **Cap the stack** (`landBatchMax`, default 3 — the fleet's realistic concurrent-role count) so the worst case stays bounded and a busy queue cannot build an arbitrarily long stack. Integer ≥ 1, where 1 reproduces 3/5's single-landing behavior exactly (no zero-knob).

### TUI/GUI auto-reload when a newer build lands on disk (planned 2026-09-13, requested by user, refined 2026-09-15)

**Goal.** `tumwater tui` and `tumwater gui` keep running their startup code forever: when the fleet redeploys itself onto a fresh main build (redeploy.ts swaps `dist/`), both dashboards keep serving stale UI code until someone restarts them. Make each auto-reload — like the core engine does for itself — as soon as it is stale, i.e. as soon as a newer compiled tree than its own startup stamp exists on disk.

**Approach.**
- New src/ui/self-reload.ts (~100 lines) — all logic lives here so TUI and GUI share one implementation:
  - `captureStartupBuild(): BuildInfo | null` — calls the existing `readBuildInfo()` (src/build-info.ts) exactly once at process start. The in-memory startup stamp is the only correct reference: after a redeploy swap, the on-disk stamp already reads as fresh and the orchestrator's published `BuildStatus` flips to `stale: false` under the NEW orchestrator — both would tell an old UI process it is fine while it still executes old modules. Never re-derive "am I stale" from either.
  - `shouldReload(startup, disk): boolean` — pure: true iff both stamps exist and `disk.sha !== startup.sha`. A differing on-disk stamp means a newer compiled tree is available (redeploy's swap or a manual `npm run build`); re-exec will load it. Deliberately NOT git-based: while main is merely ahead with no new dist yet (restart pending, blocked, or inside the 12 h cooldown) there is nothing to reload onto, and the STALE header already covers that state.
  - `reexecSelf(spawnImpl?)` — spawn `process.execPath` with `process.argv.slice(1)` and `{ stdio: "inherit" }`, then exit with the child's code when it exits (child fails fast on a broken new build → parent surfaces its non-zero code; operator re-runs manually). Injectable spawner for tests. TUI/GUI are user-launched processes, not supervisor children — no interaction with RESTART_EXIT_CODE.
  - `createReloadWatch({ root, startupInfo, readDisk?, isSelfHostedImpl?, spawnImpl?, intervalMs = 1000, onTrigger })` → `{ start, stop }`, with `start(): Promise<void>` resolving once the one-time gate settles. The gate: null `startupInfo` ⇒ never reload (checked BEFORE calling `isSelfHosted(root, startup)` — it is async and takes a non-null `BuildInfo`, not `BuildInfo | null`); else `await isSelfHosted(...)` false ⇒ never reload; only when self-hosted does the interval start, re-reading the disk stamp every `intervalMs` (default 1 s) and calling `onTrigger()` at most once when `shouldReload` holds. All seams injectable so tests need no real timers, git, or dist — `intervalMs` is the orchestrator's documented pollMs idiom (tests pass a short value).
- src/ui/tui.ts — in `runTui(root)` (line ~197): immediately after its TTY guard (which throws `tuiTerminalError` for a non-TTY start — a process that is about to throw arms no reload watch), capture the startup build and `await` the watch's `start()`; the watch's `onTrigger` sets a local `reloadRequested` flag and calls the main keypress await's `resolve` (captured in its executor), and the executor itself resolves immediately if the flag is already set — the exact same path Ctrl+C takes either way, so the existing teardown (`clearInterval(timer)`, `setRawMode(false)`, `stdin.pause()`) runs unchanged. At the very end of the function, after the teardown block's `process.stdout.write("\n")` (line ~510), call `reexecSelf()` when the flag is set; otherwise return as today.
- src/ui/gui.ts — in/after `startGui(root, port, allInterfaces)` (line 233): capture the startup build once and keep it for the payload; start the watch with `onTrigger` closing the server (`server.close()`) then calling `reexecSelf()`. When sending `/api/status` (line 241 — `sendJson(res, 200, statusPayload(root))`), spread one extra field onto the existing payload: `serverBuildSha` — the serving process's own startup sha (string or null). Add it in gui.ts at send time, not in status-payload.ts, so `status --json` and its tests are untouched.
- src/ui/gui-page.ts — in the page's 1 s `/api/status` poll (`refresh()`, line ~335): declare the remembered sha next to `let lastStatus = null;` (line ~247), and in `refresh()`'s try block immediately after `lastStatus = d;` (line ~339) — before any render, so a newer build reloads before it paints a frame — remember the first non-null `serverBuildSha` seen (the failed-poll catch path never touches it, so it is kept across failed polls while the server is down); when a later successful poll returns a different value, `location.reload()`. ~8 lines of inline JS; the page cannot import TypeScript.

**Design (decided, with rationale).**
- **Durable file queue, inbox.ts idiom.** `.tumwater/land-queue/<ts>-<seq>-<pid>.json`, one entry per file: `{ role, sha, tick, summary, body?, highFriction?, enqueuedAt }`. No attempt counter in the file — retry bookkeeping is `state.unreviewFailures`, which already persists in LoopState and governs the strike cap (Refined note 1). Filenames order the queue across processes; a crash loses nothing and `tumwater status` can read it without the scheduler. Same reasons the director's inbox is a directory of files.
- **New `TickResult` value `"queued"`**, scheduled in `applyTickOutcome` exactly like `"changed"` (backoff reset, next run at `minTickInterval`) *minus* the commit count — `commits` increments when the change actually lands, so the counter keeps meaning "landed on main".
- **One in-flight landing per role, enforced in the orchestrator's eligibility pass** (invariant 3): a role whose queue has an entry is skipped before it reaches `reasons` — not inside `isEligible`, which stays pure over LoopState and its arguments (queue state lives in files, deliberately). This is what keeps `state.lastReview`'s rejection reasons ahead of the author's next prompt and stops a role stacking two commits. The director obeys the same rule — its prompt is not finished until it lands — so there is one rule, not two.
- **The lander runs outside the author semaphore, one landing at a time.** A single in-process landing slot (not a new semaphore capacity knob): the orchestrator starts the head entry when no landing is in flight and does not await it in the poll loop. Author slots and the landing slot are independent, which is the entire point.
- **Write-back into the authoring role's `LoopState`.** The lander already mutates `lastReview`/`lastApprovedHead`/`unreviewFailures` through the gate; on completion the orchestrator folds the landing's usage into that role's counters (invariant 5), increments `commits` on success, refreshes `lastResult`/`lastSummary` with the landing outcome, saves, and logs. The orchestrator resolves the authoring state object — its runner's when one exists (runners are never removed from the array on disable; only a warning event fires) else `loadLoopState(root, role)` — calls `applyLandingOutcome` on it and saves: the same in-place discipline `resetCounters` documents, for the same reason.
- **Three new events, `land_queued` / `landed` / `land_failed`**, carrying role, sha, result, and the landing's `durationMs` and usage. `merged` still fires from merge.ts, so nothing that reads the feed for landings today breaks.
- **The queue holds only unattempted landings; failures drop to ref-recovery.** The orchestrator drops the head entry after EVERY landing outcome — terminal or not. Non-terminal outcomes (`aborted`, under-cap `review_error`, `merge_conflict`, `merge_blocked`) keep 2/5's landing ref, so retry rides leftover.ts's existing recovery on that role's next fresh tick: same gate, same strike cap, normal tick cadence instead of a fast-retry policy the queue would otherwise have to invent (Refined note 1). - **Recovery on start.** Such entries are drained on the next start like any other entry (invariant 7); the drain first skips an entry whose sha is already contained in main (`isMergedInto`) — the crash-between-ff-and-drop case — dropping it without a landing run, the same stale-ref cleanup idiom 2/5 pins for leftover.ts. A crash mid-review leaves both the entry and the ref: the drain re-runs `landChange`, i.e. re-reviews — the established crash semantics.

**Goal.** Both dashboards show each loop's cumulative `gen` tokens but not how fast the model is generating for that loop right now — an operator watching a long tick cannot tell whether the fleet is at full speed or crawling (slow local server under load, KV thrashing, a wedged engine). Add one column per loop to both dashboards: output tokens generated over the trailing 5 minutes divided by the window's elapsed time — a moving average that smooths turn granularity and tool-call gaps. Shown for loops with an in-flight tick; `-` otherwise.

**Design (decided, with rationale).**
- **Source: assistant `message_end` events in each loop's raw pi log.** Usage arrives only at turn granularity — streaming deltas (`message_update`) carry no usage and progress.ts already ignores them. The existing live-progress tail (src/ui/progress.ts) incrementally parses exactly these lines for `outputTokens`, so the rate rides that mechanism: no new state file, no loop/orchestrator change, display-only.
- **Sample ring inside LiveProgress.** Each assistant message_end with `usage.output > 0` appends `{ t, tokens }`, where `t` is the line's own `message.timestamp` (epoch ms — transcript.ts already relies on that field for run separators) falling back to parse time when absent. Samples older than the window are pruned at each append. The ring survives `session` resets: `freshProgress` omits the field, so the session case's `Object.assign` leaves it untouched — a 5-minute window legitimately spans tick boundaries (back-to-back ticks, review runs), and tail seeding rebuilds the ring from per-line timestamps.
- **Rate = tokens in [now−300 s, now] ÷ min(300 s, now − oldest sample's t).** Dividing by the full 5 minutes would under-report a young window (a tick that started one minute ago at 100 t/s would read ~20); dividing by elapsed time since the first in-window sample converges to the true rate immediately and becomes exactly the 5-minute moving average once samples span the whole window. No samples in the window → null → `-`.
- **Shown only for running loops** (`s.running`, set at tick start, cleared at end): matches "each running loop", keeps idle loops' tail-read pattern unchanged (progress.ts deliberately does not combine an idle loop's log tail with persisted counters), and no stale rate lingers on a sleeping loop. Review-gate runs count toward their loop's rate — they are that loop's generation.
- **One window constant, no knob.** `TOKEN_RATE_WINDOW_MS = 5 * 60_000` in progress.ts (opinionated default; "let's say 5 minutes" was a suggestion, not a requirement).

### Make the daily cost budget editable from the TUI/GUI (planned 2026-09-07, done 2026-09-12)

**Goal.** The fleet's daily spend cap (`maxDailyCostUsd`, default $50, 0 = disabled) can today only be changed by hand-editing tumwater.json while the harness runs. Both dashboards already show the budget badge (TUI header via renderStatus; GUI header from /api/status), but neither offers a way to change it — an operator who hits the cap mid-day must leave the dashboard, find the file, edit JSON, and come back. Make the cap editable in place on both surfaces: the TUI through a key-driven edit mode on its existing input line, the GUI through an inline editor on the budget badge. Both write through one shared setter that persists to tumwater.json — so the change is durable (survives restarts), applies live within ~2 s via the orchestrator's existing config poll, and needs no new reload machinery or event types: raising/disabling the cap while paused already flips the gate on the next poll and emits the existing `budget_resumed` transition.

**Design (decided, with rationale).**
- **One shared setter; both surfaces call it.** New `setDailyBudgetUsd(root, value)` in src/config.ts beside `saveConfig`: fresh `loadConfig` (no stat cache — a writer must see the latest file), validate, mutate only that key, write atomically (tmp file + rename over tumwater.json). Atomicity matters because this is the first in-harness *writer* of the config while readers poll it every ~2 s (the orchestrator) and two dashboards could save concurrently; today's `saveConfig` is a plain `writeFileSync` and stays as-is for init. Validation: finite number ≥ 0, fractional dollars allowed (the display rule already renders cents — $12.34). Invalid input returns an actionable error string instead of throwing, so both UIs can flash it without try/catch plumbing. Read-modify-write preserves every other key.
- **The budget badge becomes always present.** Today `snapshot().budget` is null when the cap is 0 (disabled) and neither dashboard shows a badge — which would leave no affordance to *set* a cap from a disabled fleet. Change: the snapshot/payload carries `{ spentUsd, capUsd, free }` unconditionally (`free` = `fleetModelsFree(cfg, modelsPath)` from src/pi-models.ts, already computed while enabled since e0b817a); one display rule in both dashboards with three cases, `free` first: `free` → today's exact text `· budget: n/a today`, byte-identical in every cap state (spend can never accumulate against a cap that cannot be reached); else `capUsd > 0` → `· budget: $X/$Y today`; else `· budget: $X today · no cap`. The editable affordance sits on the badge either way. This is a deliberate small display change (the disabled case gains a line; both enabled cases stay byte-identical) and it changes `status --json`'s `budget` from null to an object when disabled — pinned in acceptance so JSON consumers are aware.
- **TUI: Ctrl+B budget-edit mode on the existing input line.** The TUI has exactly one interactive surface (the prompt line), and its keys follow a pinned pattern (Ctrl+T cycles views; arrows/PgUp-PgDn act only in project-status entry mode). Ctrl+B is free — verified no ctrl+b handler today — and mnemonic for *b*udget. Pressing it switches the input line into budget-edit mode pre-filled with the current cap (`""` when disabled — empty means "no cap" on save) and flashes a hint; from then on printable keys/backspace/edit as usual (applyKey unchanged), Enter parses + saves (flash `budget set to $25` / `budget disabled`, or the validation error — an invalid Enter stays in edit mode so the operator can fix it), Esc cancels back to prompt mode with the previous text restored. Budget mode is orthogonal to view cycling: Ctrl+T still cycles and exits budget mode; every other key/view behaves exactly as today.
- **GUI: click-to-edit on the badge.** The header's budget fragment becomes a link-styled span; clicking swaps just that fragment for `<input type="number" min="0" step="0.01">` (pre-filled with the current cap, empty when disabled) plus `set`/`cancel` buttons. Enter or `set` POSTs `/api/budget`; success flashes and the badge re-renders from the next 1 s poll — no optimistic local state, the badge stays payload-driven like everything else on the page; a failed response flashes the server's error. No new polling or websocket: the existing 1 s refresh shows the new cap within one orchestrator poll of the save.

**Design (decided, with rationale).**
- **Sources = events.jsonl + two markdown files.** `tick_end` events carry `{ ts, loop, tick, result, summary, tokens?, costUsd? }` (src/loop.ts ~line 405; `tokens` is the run's output tokens, same value as the status table's "gen" column) and `merged` events carry `{ ts, loop, commit, summary }` (src/merge.ts:73). ### Prioritize loops by need — defer unneeded maintenance ticks and order work roles first (planned 2026-09-08, requested by user, refined 2026-09-09, done 2026-09-10, perf-refined 2026-09-12)

**Goal.** Today every enabled loop ticks on its own clock regardless of whether there is anything for it to react to: after a quiet stretch in which no feature or bugfix landed, the maintenance roles (readme, organize, coverage, clean, dry, perf, qa, improve, steward) keep burning model runs re-deriving "nothing to do", and when `maxConcurrent` slots are contended they can claim them ahead of loops that actually ship work. Make scheduling need-aware with two mechanisms: (1) a maintenance role's due tick is **deferred** while no feature/bugfix/human commit has landed on main since its last tick AND its own last tick did nothing; (2) slot allocation in `fairOrder` orders the work roles (**feature, bugfix, plan**) ahead of every maintenance role. The user's words: "if no feature or bugfix work has landed since the last tick, and the last tick had nothing to do, the readme, organize, coverage, clean, dry, perf, qa, improve, and steward roles probably don't need to run at all; we could instead prioritize the feature, bugfix, and plan roles."

**Design (decided, with rationale).**
- **Two tiers plus exemptions.** Work tier: `feature`, `bugfix`, `plan` — never deferred, always scheduled ahead of maintenance in slot allocation. Maintenance tier (deferrable): exactly the nine built-ins named above. The director is exempt from both mechanisms (unchanged). Unknown/custom roles (the planned user-defined loops) are **never deferred** — the harness cannot judge what an arbitrary custom role needs — but they sort into the maintenance tier for `fairOrder` (they never outrank work).
- **"Work landed" definition.** A commit on main whose subject starts with `tumwater(feature):`, `tumwater(bugfix):`, or `tumwater(director):` — a director commit is human intent of unknown kind (code, config, docs), so it counts like a human commit — **plus any commit whose subject does not start with `tumwater(` at all** (a human commit — the world changed in a way the fleet cannot generate itself). Commits from every other tumwater role do NOT count: plan/readme/steward land markdown, and organize/clean/dry/coverage/perf/qa/improve land hygiene — none of those give a maintenance role new work to react to. Waking them on their own kind of landing is exactly the cascade this feature removes (a readme commit today wakes every sleeping loop via "main moved"). The subject prefix `tumwater(<role>):` is composed by the harness at its two commit sites (loop.ts's tick path and refusal.ts; `buildCommitMessage` in src/commit-message.ts only formats — director commits included, since the director runs through LoopRunner), so attribution needs no new metadata.
- **Deferral rule.** A maintenance role's due tick — eligibility reason `"scheduled"` or `"main moved"` — is skipped when ALL of: its `lastResult === "no_change"`; its `lastMainHead` is non-empty (it has seen main before); and no work landed in `(lastMainHead, main]`. Only `no_change` defers: every other outcome carries pending business (retry an error, address recorded review-rejection reasons, recover a merge failure) that must not stall until unrelated work lands. A never-ticked role (`ticks === 0`, empty `lastMainHead`) always runs its first tick — the fleet still gets one baseline pass per role at startup. `resume` wakes (interrupted-tick recovery) are never deferred; they precede this check in `isEligible`. When the git range cannot be evaluated (unknown head, error), treat it as work landed — conservative: run the tick.
- **Deferral mechanics.** A deferred role's `nextRunAt` is left untouched: it stays due and re-checks every poll (~2 s) until a qualifying commit lands, then starts within one poll. The per-head git check caches verdicts in two bounded in-memory structures owned by the orchestrator (each cleared past 200 entries): a `Set<sinceHead>` of **true** verdicts — monotone, since once work has landed in `(sinceHead, main]` it stays there as main advances via fast-forward merges — and a `Map<sinceHead, main-head-at-check>` of **false** verdicts, valid exactly while main sits at the head checked: the range cannot grow until main moves, so a cached false skips git entirely and re-evaluates once when main's head changes (a *false* can flip to true only on such movement — caching it unconditionally would defer a role forever after the very commit that should wake it, since its `lastMainHead` never advances while deferred). Steady-state cost in a quiet fleet is therefore zero git spawns: one local `git log` per due-deferred role only when main actually moves. No new tumwater.json knob: one opinionated policy, per the principles.
- **Observability.** One `tick_deferred` event (loop = role) per deferral episode — logged on the transition into deferred-due state, tracked in an in-memory `Map<string, boolean>` (role → currently deferred-due) local to `runOrchestrator` — the per-role sibling of the fleet-scope `prevBudgetPaused`/`prevUserPaused` locals; not persisted, so a restart mid-episode can re-log at most one event; no event when the episode ends (the tick's own events cover it). New union member in `HarnessEvent["type"]` plus one formatting case in src/ui/event-format.ts (`<time> <loop> deferred — no work landed since last tick`), so logs/TUI/GUI show why a loop is quiet.
- **fairOrder.** Director first (unchanged); then tier 0 before tier 1; within a tier, least-recently-ticked first (the existing LRU tie-break). So with `maxConcurrent: 2`, a just-finished feature and an overdue steward compete for one slot — feature takes it.
