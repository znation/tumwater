The state the 14 helpers close over is 10 named vars that group the same three ways, so it becomes one shared state object the extracted functions take as a parameter instead of closing over.

### `setOwn`'s `__proto__`-stays-an-own-property rule is pinned in test/json-object.test.ts, so a regression in the one home of the `__proto__`-safe store the untrusted-JSON family shares is caught by the suite (planned 2026-11-15 by the plan role; `setOwn(obj, key, value)` in src/files/json-object.ts is the `__proto__`-safe **write** twin of `validEntries` (the read side, pinned 2026-11-15 by the feature role). Its own doc comment names the hazard it exists for: a plain `obj[key] = value` under a `__proto__` key hits `Object.prototype`'s setter — a non-object value is silently dropped and no own key is added, so the value vanishes from every reader and the persisted JSON; `setOwn` stores with `Object.defineProperty(obj, key, { value, enumerable: true, writable: true, configurable: true })` instead, making `__proto__` an OWN data property that shadows the accessor, and is the single home of that descriptor so the three flags cannot drift between its call sites — the qa coverage ledger (src/observer/qa-coverage.ts, storing under a model name and a flow name), the account's windows map (src/agent/subscription-account.ts), and the per-pair spend map (src/budget/budget.ts) — exactly the untrusted-key / external-boundary keys the `addTo` sibling's doc documents as the `constructor`/`__proto__` poison class. `setOwn` is unpinned: `grep -rn setOwn test/` matches nothing, and no archive heading pins it (the only `setOwn` mention in PLANS-DONE.md is the `validEntries` parenthetical above, which named `setOwn`'s write half "a separate entry"); the single-value reads are already pinned through the INV-AF1/AF3 guarantees in test/json-object.test.ts, but the map-level write half — the one with no single-value twin — is not. It is the write twin, not a 1-line composition over a pinned fn: the `__proto__` safety is in the `Object.defineProperty` store itself, which a bare index-assignment loses. Independent of the other `## Planned` entry (`createMainWatch` takes src/baseline/, never src/files/ or test/json-object.test.ts), so feature may take this one alone. docs/invariants.md's "Untrusted JSON" section binds the *read* half only (INV-AF1/AF3/AF4 name `isJsonObject`/`objectOrEmpty`/`parseJsonObject`/`stringList`/`finiteNumber`/`nonNegativeNumber`, not `setOwn`), so no invariant edit is needed; touches test/json-object.test.ts)

**Goal.** Pin the one unpinned member of the untrusted-JSON *write* half in src/files/json-object.ts. `setOwn(obj, key, value)` is the single home of the rule that stores one own property under a key that may cross an external boundary: the value is defined as an own property with `enumerable/writable/configurable: true`, so a `__proto__` key becomes an own property that shadows the prototype accessor (a plain `obj[key] = value` under `__proto__` would either rewrite the prototype with an object value or silently drop a non-object value, polluting or losing the entry for every reader and for the persisted JSON). Its call sites — the qa coverage ledger's model/flow maps, the account's windows map, the per-pair spend map — all store under a key read from untrusted input, so a regression that would drop a `__proto__` entry or rewrite `Object.prototype` is the class of bug a corrupt-key writer can carry into a coverage or a budget total. Pin its two branches with plain `assert` in the existing test file.

**Approach.** One file, test-only, no src change and no invariant edit: add `setOwn` to the existing named-import block in test/json-object.test.ts (which already imports `canonicalUsageBlock, finiteNumber, isJsonObject, nonNegativeNumber, objectOrEmpty, parseJsonObject, stringList, validEntries` from `../src/files/json-object.js`) and add pure `test(...)` cases. No repo, worktree, fs, git or clock — each is a few assertions on a freshly built object. The `__proto__` cases use a fresh `{}`; the object-valued `__proto__` case is what separates `Object.defineProperty` from a plain assignment, because a plain assignment of an object to `__proto__` sets the prototype whereas `setOwn`'s `defineProperty(value: …)` creates an own data property and leaves the prototype alone.

**Files touched.** test/json-object.test.ts (new `setOwn` import + cases only).

**Acceptance criteria.**
- A normal key stores an own property with the three flags and round-trips the value: `setOwn({}, "a", 1)` yields an object where `o.a === 1`, `Object.keys(o)` deep-equals `["a"]`, and `Object.getOwnPropertyDescriptor(o, "a")` has `enumerable === true`, `writable === true`, `configurable === true` (so the entry serializes in `JSON.stringify` and copies in a spread — the `enumerable/writable/configurable: true` descriptor the doc calls the single home for).
- An inherited key is shadowed by an own property, never the inherited value: `setOwn({}, "constructor", 5)` yields `o["constructor"] === 5` and `Object.keys(o)` deep-equals `["constructor"]` — the own property wins over `Object.prototype.constructor`, so a key that names an `Object.prototype` member is a real entry, not a read of the prototype.
- A `__proto__` key becomes an OWN data property and does not rewrite the prototype — the sharp `defineProperty`-vs-assignment discriminator: for `setOwn(o, "__proto__", marker)` where `marker` is a fresh object literal, `o["__proto__"] === marker` (the own data property shadows the accessor) AND `Object.getPrototypeOf(o) === Object.prototype` (the prototype is unchanged — a plain `o["__proto__"] = marker` would set the prototype to `marker` and fail this assertion). Also `Object.keys(o)` deep-equals `["__proto__"]`.
- A non-object `__proto__` value is stored, not dropped: `setOwn(o, "__proto__", 7)` yields `o["__proto__"] === 7` and `Object.keys(o)` deep-equals `["__proto__"]` (a plain `o["__proto__"] = 7` is ignored for a non-object and would leave no own key — failing the `Object.keys` assertion).
- Overwriting an existing key replaces it in place with no duplicate: `setOwn(o, "a", 1); setOwn(o, "a", 2)` yields `o.a === 2` and `Object.keys(o)` deep-equals `["a"]`.
- Storing an `undefined` value still defines the own property: `setOwn(o, "a", undefined)` yields `"a" in o` true, `Object.getOwnPropertyNames(o)` deep-equals `["a"]`, and `o.a === undefined`.
- Every pre-existing test in the file passes unmodified; no source file, no other test file, and no docs file change; the project's declared check (`npm run test`) is green.

### `validEntries`'s keep-passing / drop-foreign / `__proto__`-stays-an-own-property rule is pinned in test/json-object.test.ts, so a regression in the one home of the map-level untrusted-JSON read the untrusted-JSON family shares is caught by the suite (planned 2026-11-15 by the plan role; `validEntries(value, guard)` in src/files/json-object.ts is the shared "keep only the well-formed entries of an untrusted map, drop the foreign ones" read its two call sites apply — the per-pair daily spend map's heal (src/runner/runner-state-load.ts `healPairCosts`) and the opencode catalog cache's models map (src/agent/opencode/opencode-catalog.ts). Independent of the other `## Planned` entry (which pins src/config/config-keys.ts through test/config-keys.test.ts): these touch different src files and different test files, so feature may take either. docs/invariants.md binds nothing to `validEntries` — the "Untrusted JSON" section's INV-AF1/AF3/AF4 name `isJsonObject`/`objectOrEmpty`/`parseJsonObject`/`stringList`/`finiteNumber`/`nonNegativeNumber` and `readJsonFile`/`writeJsonAtomic`, not the map-level read — so no invariant edit is needed) — done 2026-11-15 by the coverage role

**Goal.** Pin the one unpinned member of the untrusted-JSON read family in src/files/json-object.ts. `validEntries(value, guard)` is the single home of the rule that decides which entries of an untrusted map survive a heal or load: keep the entries that pass the caller's `guard`, drop the foreign ones, and — because it rebuilds with `Object.fromEntries` — keep a `__proto__` key as an own property instead of a bare index-assignment reaching into `Object.prototype`. Every map-typed read of a persisted or wire value that runs through it (the per-pair daily spend map's heal, the opencode catalog's models map) is exposed to that same rule, so a regression that would keep a poison entry or corrupt the prototype is the class of bug a corrupt-cache reader can carry into a budget comparison or a catalog model. Pin its three behaviors with plain `assert` in the existing test file.

**Approach.** One file, test-only, no src change and no invariant edit: add tests to the existing test/json-object.test.ts (which already imports from `../src/files/json-object.js`) importing `validEntries` (and `nonNegativeNumber` for the number-guard case). Drive each branch in isolation. No repo, worktree, fs, git, or clock. The `__proto__` input must be built with `JSON.parse` — an object literal `{"__proto__": x}` triggers the assignment trap at creation and does not model what the callers actually receive (a value read back from disk via `readJsonFile`, i.e. `JSON.parse`).

**Files touched.** test/json-object.test.ts (new `validEntries` cases only).

**Acceptance criteria.**
- Given a non-object `value` — a scalar `5`, `null`, or an array `[1,2,3]` — `validEntries(…, anyGuard)` returns `{}` (the map is not an object, so there is nothing to keep). The guard is never the reason; the shape is.
- Given an object whose entries all pass a number guard — `validEntries({ a: 1, b: 2 }, (v): v is number => nonNegativeNumber(v, -1) >= 0)` — the result is `{ a: 1, b: 2 }` (every passing entry kept, in source order).
- Given a mixed object — `validEntries({ a: 1, b: { x: 1 }, c: "s" }, (v): v is number => nonNegativeNumber(v, -1) >= 0)` — the result is `{ a: 1 }`: the object entry `b` and the string entry `c` are dropped for failing the guard, the number `a` survives. (The same rule under an object-valued guard keeps the object entry instead, so the drop is the guard's call, not `validEntries`'s.)
- Given a map whose value is a JSON `__proto__` key — the input `JSON.parse('{"__proto__":7,"a":1}')` under a guard that keeps numbers — the result exposes `__proto__` as an own property: `Object.keys(result)` is `["__proto__","a"]`, `result["__proto__"]` is `7` (not `Object.prototype`), `result.a` is `1`, and `Object.prototype` is left untouched — `Object.prototype.a` stays `undefined`.
- Given an empty object, `validEntries({}, guard)` returns `{}`.
- Every pre-existing test passes unmodified; no source file, no other test file, and no docs file change; the project's declared check is green.
