### `normalizeDiffPath`'s traversal-refusing branches are pinned in test/change-data.test.ts, so a regression that would let a `diff --path` / dashboard `?path=` argument read outside the repo — through a `..` segment or an absolute path — is caught by the suite (planned 2026-11-15 by the plan role; `normalizeDiffPath(raw: string): string | null` in src/change/change-data.ts strips leading `./` pieces and trailing `/`, then returns `null` when the normalised form is empty, a lone `.`, `isAbsolute` (node:path), or carries a `..` segment — otherwise it returns the normalised relative path; it is the one rule both user-facing path scopes route a user-supplied path through: `diffPathArg` (src/cli/cli-query-commands.ts, the `diff --path` flag) calls it and `fail`s with a repo-relative example on `null`, and `handleDiff` (src/gui/gui-backlog-endpoints.ts, the dashboard `GET /api/diff?path=` arm) calls it to scope the diff — so a guard that stopped refusing `..`/absolute would let either surface scope or read outside the intended directory; `grep -rn normalizeDiffPath test/` prints nothing — no test drives it directly — and the archive records only a *move* of the rule from `diffPathArg` into change-data.ts (PLANS-DONE.md, the `--overlaps --path` scoping split), never a coverage pin, so the rule is untested on its own; the function is pure string logic — two `replace`s plus `===`/`isAbsolute` and a `split`/`includes` — with no git, fs or shell, so the pin is test-only: no source change, and docs/invariants.md names `normalizeDiffPath` only in the change-data prose, binding no guarantee to it, so no invariant edit is needed; independent in file of the two other `## Planned` entries, which are test/git-ref-files.test.ts over src/git/git.ts and test/paths.test.ts over src/paths.ts, so feature can take any of the three)

**Goal.** `normalizeDiffPath` (src/change/change-data.ts, exported) is the shared rule that turns a user-supplied `--path` / `?path=` argument into a safe in-repo scope: it strips leading `./` pieces and trailing slashes, and refuses anything that is not a safe repo-relative path — an empty result, a lone `.`, an absolute path, or any `..` segment — by returning `null`. Two surfaces a user types a path into route through it: the CLI `diff --path` (via `diffPathArg`, which `fail`s with a repo-relative example when it gets `null`) and the dashboard's `GET /api/diff?path=` arm (via `handleDiff`). It was extracted out of `diffPathArg` by the `--overlaps --path` scoping split, so the *caller* moved with it, but the rule itself has no direct test: `grep -rn normalizeDiffPath test/` is empty, and the existing test/change-data.test.ts drives the sibling `collect*` functions, not the guard. Because the guard is a path-traversal boundary — the thing that stops a `..` or absolute argument from climbing out of the scope — pin each of its accept and refuse branches through the exported function so the boundary itself is part of the suite.

**Approach.** One file, test-only, no src change and no invariant edit (docs/invariants.md names `normalizeDiffPath` only in the change-data prose, binding no guarantee to it): in test/change-data.test.ts add `normalizeDiffPath` to the existing named-import block from `../src/change/change-data.js` (the file already imports the sibling `collect*` functions from that module), then add pure `test(...)` cases that call it directly with the string inputs below and assert the exact return — no repo, worktree, fs, git or clock needed, so each case is a single `assert.equal` against a literal. Cases cover every branch: accept a plain relative path ("src/cli.ts" → itself) and a nested one ("a/b" → itself); strip a leading `./` ("./src/x.ts" → "src/x.ts"), repeated leading pieces ("././x" → "x"), and a trailing `/` ("src/" → "src", "src/x/" → "src/x"); and return `null` for each refuse — an empty string (""), a `./` that collapses to empty ("./"), a lone dot ("."), a lone `..` (".."), a middle `..` segment ("src/../secrets"), a trailing `..` ("src/.."), and an absolute path ("/etc/passwd", absolute under node:path on the POSIX suite host). No source file and no other test file change.

**Files touched.** test/change-data.test.ts.

**Acceptance criteria.**
- Given a plain repo-relative path, `normalizeDiffPath("src/cli.ts")` returns `"src/cli.ts"` — a normal relative path is returned as the scope.
- Given a nested relative path, `normalizeDiffPath("a/b")` returns `"a/b"` — internal separators are preserved.
- Given a path with a leading `./` ("./src/x.ts") or repeated leading pieces ("././x"), `normalizeDiffPath` returns the normalised relative form ("src/x.ts", "x") — leading `./` pieces are stripped before the refusal checks run.
- Given a path with a trailing slash ("src/", "src/x/"), `normalizeDiffPath` returns the slash-stripped form ("src", "src/x") — a trailing slash does not survive, and is not mistaken for a segment.
- Given an empty string, a `./` that collapses to empty, or a lone `.`, `normalizeDiffPath` returns `null` — there is nothing to scope to, so the caller refuses.
- Given a `..` segment — a lone `".."`, a middle `"src/../secrets"`, or a trailing `"src/.."` — `normalizeDiffPath` returns `null` — a parent-segment path is refused rather than normalised, so it cannot climb out of the scope.
- Given an absolute path ("/etc/passwd"), `normalizeDiffPath` returns `null` — an absolute argument is refused rather than read.
- Every pre-existing test in test/change-data.test.ts passes unmodified; no source file and no other test file change; the project's declared check is green.

### `rejectFlagLookingValue`'s flag-shaped-value refusal and its pass-through branches are pinned in test/cli-args.test.ts, so a regression that would let a `--` token swallow the next argument as a value — or a single-dash value be mistaken for a flag — is caught by the suite (planned 2026-11-15 by the plan role; `rejectFlagLookingValue(flag, value): string | null | undefined` in src/cli/cli-args.ts returns `value` unchanged unless it is a string that starts with `--`, in which case it `fail`s (src/terminal.ts — writes `tumwater: <flag> needs a value (the next token "<value>" is a flag, not a value)` to stderr, exits 1); it is the one rule every user-facing valued-flag slot applies so a `--token` in a value position cannot be read as a secret: `rejectFlagLookingValue` is called from cli-backlog.ts (`--retire --reason`), cli-operator-commands.ts (`pause --reason`), cli-prompt-file.ts (`--file`), cli-config-commands.ts (`--file`), cli-command-args.ts (`--template`, `--attach`), cli-query-commands.ts (`--path`), and history/history.ts (`--result`/`--model`/`--by`), and is also the internal `guardFlagValue` arm of `takeValuedFlag` (parsePortFlag, parseDurationFlag, parseBranchFlag, parseRoleFlag); `grep -rn rejectFlagLookingValue test/` prints only comment mentions — the five hits in test/cli-args.test.ts and test/cli-command-args.test.ts are each a `//` prose note naming the shared wording, none a call — so no test drives the guard itself; the function is pure in-memory string logic — one `startsWith("--")` plus `JSON.stringify`, no git, fs, shell or clock — so the pin is test-only and needs no invariant edit, docs/invariants.md binding no src/cli/cli-args.ts symbol; independent in file of the two other `## Planned` entries, which are test/change-data.test.ts over src/change/change-data.ts and test/paths.test.ts over src/paths.ts, so feature can take any of the three)

**Goal.** `rejectFlagLookingValue` (src/cli/cli-args.ts, exported) is the shared boundary that stops a valued flag from swallowing a *flag* as its value: `history --model --last` used to read `--last` as the model name (silently matching no rows) and `--result --last` failed downstream with a misleading "needs --last" wording when the operator *did* write `--last`. It is the one rule every user-facing valued-flag slot applies so `--token --all-interfaces` cannot serve with the literal secret `"--all-interfaces"`. Its two outcomes — refuse a `--`-prefixed value (fail, exit 1) and pass everything else through unchanged (a normal string, a *single-dash* value like `-5`/`-f`, `null`, `undefined`) — are each load-bearing: the refusal is the guard, and the pass-through of single-dash tokens is what keeps intentional one-dash filters and negative numbers working. The existing test/cli-args.test.ts drives the *callers* (parseCountFlag, parseDurationFlag, parsePortFlag, parseBranchFlag, …) which reach `rejectFlagLookingValue` indirectly, but never calls the guard directly, so a regression in the `startsWith("--")` shape check — refusing single-dash values, or accepting `--` tokens — would only surface through whichever caller happened to exercise it, not the guard itself. Pin the guard directly through its exported signature so the boundary is part of the suite.

**Approach.** One file, test-only, no src change and no invariant edit (docs/invariants.md binds no src/cli/cli-args.ts symbol): in test/cli-args.test.ts add `rejectFlagLookingValue` to the existing named-import block from `../src/cli/cli-args.js` (the file already imports `flagValue, parseBranchFlag, parseCountFlag, parseDurationFlag, parsePortFlag, parsePositionFlag, parseRoleFlag, parseRoleListFlag` from it and `expectFail, expectOk` from `./helpers/exit-capture.js`). Add pure `test(...)` cases that call it directly — no repo, worktree, fs, git or clock, so each is a single assertion. Because the `--`-prefixed branch `fail`s (exit 1 + a stderr line) while the non-`--` branch simply returns the value, drive the two outcome families with the two capture helpers the file already imports: `expectFail(() => rejectFlagLookingValue(flag, "--…"))` asserts the fail and returns the captured stderr (assert it equals the exact contract string, which embeds `JSON.stringify` of the value), and `expectOk(() => rejectFlagLookingValue(flag, value))` asserts the return value. Cases: *refuse* a `--`-prefixed value — `rejectFlagLookingValue("history --result", "--last")` and `rejectFlagLookingValue("--file", "--x")` fail with exit 1 and stderr `tumwater: <flag> needs a value (the next token "<value>" is a flag, not a value)` (the `fail` prefix is `tumwater: ` from src/terminal.ts, and `<value>` is `JSON.stringify`'d, so the quoted token is the double-quoted form). *Pass a normal string* — `rejectFlagLookingValue("--branch", "release/2.0")` returns `"release/2.0"`, and `rejectFlagLookingValue("--x", "a b")` returns `"a b"` — a non-`--` value is returned as-is. *Pass a single-dash value* — `rejectFlagLookingValue("history --since", "-5")` returns `"-5"` and `rejectFlagLookingValue("--by", "-f")` returns `"-f"` — only a `--` token reads as a flag, so one-dash values (negative numbers, `-f` filters) are not refused. *Pass absent* — `rejectFlagLookingValue("--x", undefined)` returns `undefined` and `rejectFlagLookingValue("--y", null)` returns `null` — an absent value is neither refused nor fabricated. No source file and no other test file change.

**Files touched.** test/cli-args.test.ts.

**Acceptance criteria.**
- Given a `--`-prefixed value, `rejectFlagLookingValue(flag, "--last")` fails with exit 1 and writes to stderr the exact line `tumwater: <flag> needs a value (the next token "--last" is a flag, not a value)` — a flag-shaped token in a value slot is refused, and the operator is told the flag, so a `--token --all-interfaces` is not served with the literal secret `"--all-interfaces"`.
- Given `rejectFlagLookingValue("--file", "--x")`, the captured stderr is exactly `tumwater: --file needs a value (the next token "--x" is a flag, not a value)` (a trailing newline) — the `fail` prefix `tumwater: ` is written by src/terminal.ts, and the value is `JSON.stringify`-quoted, so a `--`-prefixed value appears in the message in double quotes; the same message carries whichever `<flag>` the caller named, so the wording is shared and names the caller's own flag.
- Given a normal (non-`--`) string, `rejectFlagLookingValue("--branch", "release/2.0")` returns `"release/2.0"` — a plain value passes through untouched.
- Given a single-dash value, `rejectFlagLookingValue("history --since", "-5")` returns `"-5"` and `rejectFlagLookingValue("--by", "-f")` returns `"-f"` — one-dash values are not mistaken for a flag, so negative counts and one-dash filters keep working.
- Given `null` or `undefined`, `rejectFlagLookingValue` returns the argument unchanged (`null` → `null`, `undefined` → `undefined`) — an absent value is neither refused nor invented.
- Every pre-existing test in test/cli-args.test.ts passes unmodified; no source file and no other test file change; the project's declared check is green.
