### Dashboard Activity window picker: a `#feedwindow` select (Recent / Last hour / Last 6 hours / Last day) on the Activity card serves the feed of a trailing window through `GET /api/logs?sinceMs=` (planned 2026-10-20 by the plan role; independent of every eligible plan. It touches src/ui/gui/gui-client-feed.ts, src/ui/gui/gui-page.ts, test/gui-client-team.test.ts and docs/how-it-works.md's Activity paragraph. "Dashboard window end on the last two windowed endpoints" touches only server files (gui-args.ts, gui-endpoints.ts, test/gui-endpoints.test.ts). "Dashboard History past windows" touches gui-client-history.ts, its test, and a different docs/how-it-works.md paragraph, the one starting "The dashboard's History drill-down adds…")

**Goal.** "Dashboard event-log window" (PLANS-DONE.md) taught `handleLogs` (src/gui/gui-endpoints.ts) to answer `?sinceMs=S[&grep=][&role=]` with `{ events, covered, note }`, the twin of `tumwater logs --since`. That plan named the feed's window picker as later work, and the dashboard's Activity card still cannot ask for "every event in the last 6 hours": `feedLogsQuery` (src/ui/gui/gui-client-feed.ts) only ever builds `/api/logs?grep=&role=` (the `n`-scanned slice), and only once a Role or Search filter is set. This plan adds a window select to the card head. A chosen window fetches `/api/logs?sinceMs=…` even with no filter, and the card paints that window instead of the carried status-poll events. The change is client-only.

**Behavior, decided:**
- Choices: `const FEED_WINDOWS = [["", "Recent", ""], ["3600000", "Last hour", "the last hour"], ["21600000", "Last 6 hours", "the last 6 hours"], ["86400000", "Last day", "the last day"]];` (value, option label, phrase), the dashboard's REPORT_SINCE_CHOICES lengths. `""` is today's behavior.
- State: `let feedWindow = …` recalled from `"feed-window"`. A recalled value that is not a `FEED_WINDOWS` value falls back to `""`. It persists through `store("feed-window", …)` like feed-role/feed-grep/feed-type.
- `feedLogsQuery()`: when `feedWindow` is set, `"sinceMs=" + feedWindow` is the first param, followed by grep and role in their current order. So role qa + grep boom + 1h gives `/api/logs?sinceMs=3600000&grep=boom&role=qa`, and 1h alone gives `/api/logs?sinceMs=3600000`. With no window the URL is exactly what it is today.
- `searchFeed()`'s early return becomes `if (!feedRole && !feedText && !feedWindow) return;`. renderFeed's re-arm key becomes `feedRole + "\u0000" + feedText + "\u0000" + feedWindow`.
- Live window: a server search today is fetched once per filter change. A window must not freeze, so add `let feedTailTs = 0;`. In renderFeed, take `tail` = the `ts` of the last element of `d.eventItems` (oldest-first), or 0 when there is none. When the key changed, set `feedTailTs = tail` before `searchFeed()`. Otherwise, when `feedWindow` is set, `feedResults !== null` and `tail !== feedTailTs`, set `feedTailTs = tail` and `void fetchFeedSearch(++feedSeq)`. This refetch skips the debounce and does not clear `feedResults`, so the old slice stays painted until the new answer lands, and a poll with no new event fetches nothing. A filter-only search (no window) keeps today's fetch-once behavior.
- Sparse note: add `let feedNote = "";`. `fetchFeedSearch` sets `feedNote = (d && d.note) || ""` on success. `searchFeed` and the catch branch reset it to `""`. renderFeed paints `"<li class='empty muted feed-note'>" + esc(feedNote) + "</li>"` first in the panel, ahead of the tally chips, when `feedNote` is non-empty and `feedResults !== null`.
- Empty states when `feedWindow` is set and the server slice is empty, with phrase P = the window's FEED_WINDOWS phrase: no role/grep/type gives `emptyFeedRow("No events in " + P, "Pick a longer window to look further back. ")`. Otherwise it gives `emptyFeedRow("No events match this filter in " + P, "Widen the Search or Role picker, clear the type chip, or pick a longer window. ")`. With no window, every empty state keeps its current wording.
- Row cap: a day of All events can run to thousands of rows. Add `const FEED_MAX_ROWS = 500;`. renderFeed paints `shown.slice(0, FEED_MAX_ROWS)` (shown is newest-first). When `shown.length > FEED_MAX_ROWS` it appends `"<li class='empty muted'>Showing the newest 500 of " + shown.length + " events — narrow the window or add a filter.</li>"`. The tally chips still count every pre-type row. Today the slice is at most `LOGS_SEARCH_EVENTS` (500) scanned rows, plus the carried window, so no current render reaches the cap.
- Control: gui-page.ts ships `<label><span class="sr-only">Window</span><select class="field" id="feedwindow"></select></label>` between the `#feedrole` and `#feedgrep` labels. The activity region fills it at load: `$("feedwindow").innerHTML = FEED_WINDOWS.map(([v, label]) => "<option value='" + v + "'>" + label + "</option>").join("")`, then `$("feedwindow").value = feedWindow`. Its `change` listener validates `ev.target.value` against FEED_WINDOWS (falling back to `""`), stores it, and calls `renderFeed(lastStatus)` when `lastStatus` is set, mirroring the `#feedrole` listener.
- `clearFeedFilter()` also resets `feedWindow = ""`, stores it, and sets `$("feedwindow").value = ""` when the element exists, so the empty state's Clear button returns the card to its default feed.

**Approach.** All of the logic lives in src/ui/gui/gui-client-feed.ts, inside the `// activity:start` / `// activity:end` region. Update the region's head comment and the module doc comment so they name the window select. In src/ui/gui/gui-page.ts, add the one `<label>` described above. In docs/how-it-works.md, in the Activity sentence that ends "…persisted like the Notable/All choice", add a clause: a Window picker (last hour / 6 hours / day) shows that trailing window's events through `/api/logs?sinceMs=`, the twin of `tumwater logs --since`, refreshing when a new event arrives.

**Tests** (test/gui-client-team.test.ts, through the existing `feedScope` helper and `feedSettle`):
- "a chosen window fetches /api/logs?sinceMs= even with no filter": `feedScope({ "feed-window": "3600000" }, { getJson: (records path, returns { events: [{ ts: 1, source: "qa", type: "merged", message: "window row" }], covered: true, note: "" }), lastStatus: payload })`, where payload carries one "carried row". After `renderFeed` and `feedSettle()`, `calls` deep-equals `["/api/logs?sinceMs=3600000"]`, the panel matches /window row/, and it does not match /carried row/.
- "the window composes with Role and Search in the query": recalled feed-window 21600000, feed-role qa and feed-grep boom give `["/api/logs?sinceMs=21600000&grep=boom&role=qa"]`.
- "a recalled unknown window falls back to Recent": `{ "feed-window": "999" }` with no filter makes no getJson call after `feedSettle()`. `els["feedwindow"].value === ""`.
- "a windowed feed refetches only when a new event arrives": window 1h. Render a payload whose eventItems' last ts is 10, then settle (1 call). Render the same payload again and `sleep(10)` (still 1 call). Render a payload whose last ts is 11 and `sleep(10)` (2 calls). Between the second render and the answer, the panel still matches the first slice's row.
- "a sparse window names its note and an empty window names its span": getJson answering `{ events: [], covered: false, note: "SPARSE" }` with window 1h. The panel matches /SPARSE/ and /No events in the last hour/. With feed-grep x as well, it matches /No events match this filter in the last hour/.
- "the feed paints at most FEED_MAX_ROWS rows and says so": feed "all", window 1d, getJson answering 501 events (`ts: i`, distinct messages `row i`). The panel holds exactly 500 `<li class='feed-item` matches and matches /Showing the newest 500 of 501 events/.
- "Clear filter resets the window": recalled window 1h plus grep x. `scope.clearFeedFilter()` sets `stores["feed-window"] === ""` and `els["feedwindow"].value === ""`.
- Extend "the Activity filter persists its choices and the page ships the controls in the card head": `GUI_CLIENT_FEED_JS` matches `/store\("feed-window"/`, and the card head matches `/id="feedwindow"/`.
- Every existing Activity feed test passes unchanged. In particular the no-window query URLs and the "with neither filter set … byte-for-byte" render stay as they are.

**Acceptance criteria.**
- The Activity card head has a Window select (Recent, Last hour, Last 6 hours, Last day) that persists across reloads. With a window chosen, the card fetches `/api/logs?sinceMs=<ms>[&grep=][&role=]` and paints that window's events, with the Notable/All cull and the type chips applied as for any server slice. It refetches without a debounce flash when a status poll carries a new event, and never on a poll without one.
- A sparse window shows the server's note. An empty window names its span in the empty state. More than 500 shown rows are capped at the newest 500 with a count line.
- With the window at Recent, every request URL and render matches today's, and Clear filter also resets the window.
- No server file changes. `npm run test:gate` passes.
