### docs/invariants.md gains a review-verdict and revision-finality section, and two tests pin that only a leading `(prior N)` with N ≥ 1 is a repeat tag and that a tag with no matching prior count still counts one revision (planned 2026-10-20 by the plan role; independent of every eligible plan; touches docs/invariants.md, a comment in src/merge/merge-core.ts + a new test/revision-prior-tags.test.ts)

**Goal.** The review gate depends on two things. First, src/review/review-verdict.ts's `parseVerdict` turns the reviewer's reply into a verdict and its reasons. It fails closed when no verdict line exists, and the last VERDICT line wins. It caps the reasons at `MAX_REASONS` and drops a leading prior-objection resolution from a rejection. Second, src/merge/merge-core.ts's `recordRejectedChange` uses `priorObjectionNumber` to decide when a revision chain ends. Each reason gets a persistence count: 0 for an untagged reason, and `1 + prior[n - 1] ?? 0` for a `(prior N)` restatement. The rejection is final when any count reaches `REVISION_FINAL_ON_REPEAT` or the round reaches `REVISION_BACKSTOP` (both in src/runner/revision.ts). Before this entry, docs/invariants.md named none of `parseVerdict`, `priorObjectionNumber`, `recordRejectedChange` or the two constants. Two edges are untested:
- No test calls `priorObjectionNumber` directly. Its only coverage is the `(prior 1)` reply in test/revision.test.ts's "a rejection whose objection has survived two revisions is final and deletes the rejected ref". Nothing pins the `^` anchor (a tag mid-line is not a tag), the case-insensitive match, the leading-whitespace trim, or the `n >= 1` guard.
- Two cases are untested: a `(prior N)` tag whose N is beyond the prior list, and a tag with no `priorCounts` at all (a recovery merge, or a first rejection). In both, `prior[n - 1] ?? 0` gives a count of 1. That is not final this round, but one more restatement makes it final. The doc comment on `recordRejectedChange` says such a tag "reads as a fresh objection", which a reader takes to mean count 0. The code gives 1, so the comment is corrected to match the code. The behavior does not change.

**Approach.**
1. New test/revision-prior-tags.test.ts (node:test + `node:assert/strict`). Do not edit test/revision.test.ts or test/review-verdict.test.ts: the waiting "Plain terms code cleanup" parts may touch test files. Import `priorObjectionNumber` from ../src/review/review-verdict.js. Import `verifyRequest` from ../src/merge/merge-batch.js, `refSha` from ../src/git/git.js, `rejectedRefName` from ../src/paths.js and `freshRunnerState` from ../src/runner/runner-state.js. Import `withPi` from ./fakes/fake-pi.js, and `batchWiring`, `makeCtx`, `pinnedFixture`, `request`, `reviewerPi` and `ROLE` from ./fixtures/merger-fixtures.js. These are the same imports test/revision.test.ts uses.
