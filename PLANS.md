### Dashboard window end on the last two windowed endpoints: `GET /api/failures?sinceMs=&untilMs=` and `GET /api/logs?sinceMs=&untilMs=` serve a bounded past window that ends before now, the twins of `report --failures --since --until` and `logs --since --until` (planned 2026-10-20 by the plan role; independent of every eligible plan. "TUI History trail transcript search" touches only TUI files, none of these. Touches src/gui/gui-args.ts (doc comment only) + src/gui/gui-endpoints.ts + test/gui-endpoints.test.ts)

**Goal.** "Dashboard API window end" (PLANS-DONE.md) gave `/api/report` and `/api/history` an `untilMs` bound through `untilMsQuery` (src/gui/gui-args.ts). It left `/api/failures` alone until "Failure digest window" (PLANS-DONE.md) landed. That plan has now landed: `collectFailureReportSince(root, sinceMs, role?, untilMs?)` (src/failure/failure-data.ts) takes the bound, and `renderFailureMarkdown` prints the bounded `boundedWindowLine` header. `/api/logs?sinceMs=` (PLANS-DONE.md "Dashboard event-log window") said its `untilMs` would be a later plan. The CLI already bounds it: `cmdLogs` (src/cli/log-commands.ts) filters `readEventsSince`'s events with `e.ts < cutoff + ms - untilMs`. Today `handleFailures` and `handleLogs` (src/gui/gui-endpoints.ts) never read `untilMs`. A script asking `/api/failures?sinceMs=345600000&untilMs=259200000` or `/api/logs?sinceMs=…&untilMs=…` silently gets the whole window up to now. Fixing both endpoints is one theme: the same helper applied to the two windowed endpoints still missing it. After this, `grep -n untilMsQuery src/gui/gui-endpoints.ts` shows a call in every handler that calls `sinceMsQuery` or `reportScope`.

**Approach.**
1. `handleFailures`: right after `reportScope`, add `const untilMs = untilMsQuery(q, res, scope.sinceMs); if (untilMs === null) return;`. This is the same two lines `handleReport` uses. Then pass `untilMs` as the 4th argument of `collectFailureReportSince`. The days shape has no `sinceMs`, so `?days=7&untilMs=…` becomes the helper's "requires sinceMs" 400 instead of being ignored. Add `[&untilMs=<ms>]` to the doc comment's sinceMs shape.
2. `handleLogs`, in the `sinceMs` branch: after `sinceMsQuery`, add `const untilMs = untilMsQuery(q, res, sinceMs); if (untilMs === null) return;`. Destructure `cutoff` from `readEventsSince` as well. When `untilMs` is defined, keep only events with `e.ts < cutoff + sinceMs - untilMs` before `keep`, the CLI's exact edge. `covered` and `note` are unchanged, because coverage is about the window's far edge either way, as in handleHistory. In the count branch, call `if (untilMsQuery(q, res, undefined) === null) return;` before the `n` parse, so `?n=5&untilMs=…` and a bare `?untilMs=…` are 400s, the handleHistory count-branch rule. Update the handler's doc comment to show `sinceMs=S[&untilMs=U]`.
3. src/gui/gui-args.ts `untilMsQuery` doc comment: change "the report and history endpoints'" to name all four endpoints (report, failures, history, logs). The code does not change.
4. No dashboard client change. gui-client-feed.ts keeps calling `?n=`, and the Failures tab keeps its trailing windows. A past-window UI is a separate later plan, and it is a design choice that plan must settle.

**Tests** (test/gui-endpoints.test.ts, using the existing `serveFailures`/`serveLogs` helpers and `writeEvents`, placed beside "handleFailures serves the windowed digest as { markdown } when ?sinceMs is set" and "handleLogs ?sinceMs serves the trailing window's events, composing grep and role"):
- New test "handleFailures' ?untilMs ends the since window that long ago". Seed a `run_end` `result: "error"` event for `bugfix` at now−30 min (`error: "recent boom"`) and one for `feature` at now−3 h (`error: "old boom"`). `?sinceMs=14400000&untilMs=3600000` → 200, and `markdown` matches `/window: 4h to 1h ago/` and `/feature/` and does not match `/bugfix/`. The digest table names each role that ran (the existing sinceMs test asserts `/bugfix/`), and bugfix's run lies in neither the window nor its prior window `[now − 7 h, now − 4 h)`. Compare shapes, not bytes: each call reads its own `Date.now()`. 400 cases, each with the error matched: `?untilMs=3600000` and `?days=7&untilMs=3600000` → /requires sinceMs/; `?sinceMs=3600000&untilMs=3600000` → /must be shorter than sinceMs/; `?sinceMs=3600000&untilMs=abc` → /untilMs/.
- New test "handleLogs' ?untilMs drops the window's newer events". Seed the same three events as the existing sinceMs test (now−3 h, now−30 min, now−20 min) plus one at now−5 min. `?sinceMs=3600000&untilMs=600000` → `events` ts are `[now − 30 min, now − 20 min]`, with `covered: true` and `note: ""`. `&role=bugfix` added → `[now − 20 min]`. 400s: `?untilMs=600000`, `?n=5&untilMs=600000` → /requires sinceMs/; `?sinceMs=600000&untilMs=600000` → /must be shorter than sinceMs/.

**Acceptance criteria.**
- `/api/failures?sinceMs=S&untilMs=U` (U < S) serves `{ markdown: renderFailureMarkdown(collectFailureReportSince(root, S, roles, U)) }`, with the bounded header and only the failures in `[now − S, now − U)`.
- `/api/logs?sinceMs=S&untilMs=U` serves `{ events, covered, note }` holding only the window's events older than `now − U`, and `grep` and `role` still compose.
- `untilMs` without `sinceMs`, with `days` or `n`, `untilMs >= sinceMs`, or a non-positive-integer `untilMs` is a 400 on both endpoints. Nothing ignores it silently.
- Requests without `untilMs` answer as before: the existing handleFailures and handleLogs tests pass unchanged.
- `npm run test:gate` passes.
