### Refusal-note merge: a merge check holding merge.lock no longer errors the refusing run (planned 2026-10-20 by the plan role; independent of every eligible plan; touches src/merge/merge-to-main.ts + src/runner/runner-run.ts + src/verdict/refusal.ts + src/paths.ts + src/backlog/backlog-cli.ts + test/merge-to-main.test.ts + test/refusal.test.ts + docs/invariants.md)

**Goal.** A run that refuses its plan or bug merges its Refused note itself. The path is `handleRefusal` (src/verdict/refusal.ts) → `RefusalContext.merge` → `mergePhase` (src/runner/runner-run.ts) → `mergeToMain` → `tryMerge` (src/merge/merge-to-main.ts). `tryMerge` waits for `merge.lock` through `withLock(mergeLockDir(ctx.root), …)` with `withLock`'s default timeout of 120 s. The merge pipeline holds that same lock through its in-lock check (`verifyMerge`), which runs the full suite and routinely takes longer. The timeout error escapes `handleRefusal`, even though its doc comment says "Never throws", so the run ends `error`. The note merges only when the next run's leftover recovery re-queues it, and that recovery never logs `entry_refused`, so the operator is never paged. **Seen in the live feed:** over the 7 days to 2026-10-20 there were 5 `refused` runs plus 2 runs that ended `error: timed out after 120s waiting for lock …/merge.lock (held by pid …)`: feature-3 on 2026-10-17 11:05 and on 2026-10-20 15:25. In the second, feature-2's merge check (`build_check` scope `merge`) ran for 151 s while holding the lock, and the refusal merged 21 s later as "recovered leftover work from feature-3: refuse — …". `tumwater archive` already waits out this case with `ARCHIVE_LOCK_WAIT_MS` (15 min, src/backlog/backlog-cli.ts), and its comment gives the same reason: "a merge holds it through its in-lock check, which can run several minutes".

**Approach.** One theme: an out-of-queue merge-lock waiter waits out an in-lock merge check, and the refusal never throws.
1. src/paths.ts: beside `mergeLockDir`, add `export const MERGE_LOCK_WAIT_MS = 15 * 60_000;` with a doc comment taken from `ARCHIVE_LOCK_WAIT_MS`'s: this is how long a merge-lock taker outside the merge queue waits, because a merge holds the lock through its in-lock check, which can run several minutes. A dead holder is still broken early by `tryBreakStale`. In src/backlog/backlog-cli.ts, delete `ARCHIVE_LOCK_WAIT_MS` and make `cmdArchive` pass `{ lockTimeoutMs: MERGE_LOCK_WAIT_MS }`.
2. src/merge/merge-to-main.ts: add an optional `lockTimeoutMs?: number` to `MergeContext`, documented as the merge-lock wait, defaulting to `withLock`'s. In `tryMerge`, pass it as `withLock`'s third argument (`withLock(mergeLockDir(ctx.root), async () => …, ctx.lockTimeoutMs)`; `undefined` keeps the default). The queue's callers set nothing, so their behaviour stays the same.
3. src/runner/runner-run.ts `mergePhase` (its only caller is the refusal verdict): add `lockTimeoutMs: MERGE_LOCK_WAIT_MS` to the context it builds, and say in its doc comment why the refusal path waits longer.
4. src/verdict/refusal.ts `handleRefusal`: wrap `await ctx.merge(wt, \`refused: ${reason}\`)` so that a throw (a lock timeout, or `cannot acquire lock`) is handled like a non-`"changed"` result. Set `state.lastError = \`refusal note merge failed: ${errorMessage(err)}\``, log no `entry_refused`, leave the rejection uncleared, and still return `{ result: "refused", summary: reason, commit }`. The committed note stays on the branch for leftover recovery, as it does today for `merge_conflict`. Make the doc comment's "Never throws" true by naming the thrown-merge case.
5. Leave unchanged: `withLock`'s 120 s default, the merge queue's own lock use (`ffStackToMain`, the queued `mergeToMain`), `fileQuarantineBugsOnMain` and the main-watch revert in src/baseline/main-revert.ts. The revert runs on the main watch, where a 15-minute wait would stall the watch, and none of these appears in the feed as a lock timeout.

**Files.** src/paths.ts, src/backlog/backlog-cli.ts, src/merge/merge-to-main.ts, src/runner/runner-run.ts, src/verdict/refusal.ts, test/merge-to-main.test.ts, test/refusal.test.ts, docs/invariants.md.

**Acceptance criteria.**

Commit a branch edit as "a fast-forward that git refuses reports merge_blocked without merge" does, but leave the primary checkout clean. Hold the lock with `withLock(mergeLockDir(root), () => new Promise((r) => setTimeout(r, 1_000)))`, not awaited, then assert that `mergeToMain({ ...ctx, lockTimeoutMs: 200 }, wt, "branch edit")` rejects with /timed out after 0\.2s waiting for lock/ and that main has not moved. Await the holder, hold the lock again for about 300 ms, and assert that `mergeToMain({ ...ctx, lockTimeoutMs: 10_000 }, wt, "branch edit")` resolves `"changed"`.

Assert that `handleRefusal` resolves (it does not reject), that `outcome.result === "refused"`, that `outcome.commit` is set, that `state.lastError === "refusal note merge failed: timed out after 120s waiting for lock /x/merge.lock"`, and that no `entry_refused` event was logged.

### Event log search: `tumwater logs --grep <text>` composes with `--since <duration>` (planned 2026-10-20 by the plan role; independent of every eligible plan; touches src/cli/log-commands.ts + src/cli/help.ts + docs/cli.md + test/cli-logs-filtering.test.ts + test/log-commands-views.test.ts)

**Goal.** An operator who wants to find something in the event log over a time window, such as "every warning naming merge.lock in the last 24h", cannot ask for it today. `cmdLogs` (src/cli/log-commands.ts) rejects `logs --grep x --since 1h` through `failRivalShapes("logs --grep", "--since", "--since is a filter of its own; --grep filters the -n view and its follow")`. The other filters already work with a window: `--type` and `--role` filter the `--since` window, and `history --grep` works with `history --since`. So the remaining option is to guess an `-n` count, which bounds the scan and not the time span, or to pipe `--since … --json` through a script. The plan role's own feed mining does that on every run. `--grep` is a filter like `--type`, and the window is a window. The rival rule is left over from before `--type` and `--role` were added.

**Approach.** One change in `cmdLogs`; the `-n` view, the follow and the transcript view stay the same.
1. In `cmdLogs`, inside the `if (grepPattern !== null)` block, delete the `--since` rival check (`if (rest.includes("--since")) failRivalShapes(...)`). Keep `rejectTranscriptViewRival(rest, "--grep", true)`. `--grep` with `-f`, `-n` and `--transcript` keeps today's behaviour, and `--since` keeps its own rivals (`-f`, `-n`, `--transcript`).
2. In the `--since` branch, filter the window with the composed rule: `const filtered = events.filter(feedFilter);`. This replaces the inline `typeFilter`/`roleFilter` lambda. The window, the `-n` tally and the follow then share the one predicate that the `feedFilter` comment already promises, and `--grep` matching still goes through `eventMatchesGrep` (INV-A3, which needs no change).
3. Empty-window prose in that branch. JSON mode stays silent. The text branch picks, in this order: when both `grepPattern` and `type` are set, `no events matching "<pattern>" or ${typeEmpty(type, typePieces)}`, the same line the `-n` view prints; when only `type` is set, `typeEmpty(type, typePieces)` as today; when only `grepPattern` is set, `no events matching "<pattern>" in ${durationLabel(ms)}`; otherwise the role/plain lines as today.
4. Update the comments that state the old rule: the `parseGrepFlag` preamble comment ("and --since is a filter of its own rather than a window to filter"), the `--type` comment ("Unlike --grep it composes with --since"), the `--role` comment ("Unlike --grep it composes with --since"), the `--since` branch comment ("it is NOT the --since rival --grep is"), and the `rejectTranscriptViewRival` doc comment. After the change each one should say that `--grep`, `--type` and `--role` all filter the `--since` window.
5. src/cli/help.ts `logs` synopsis text: in the `--grep` sentence, add that it composes with `--since`, the way the `--type` sentence says "(it composes with --since)". docs/cli.md "Check state" row: after `` `tumwater logs --grep <text>` `` add `(composes with `--since`, `--type`, `--role` and `--json`)`.

**Files.** src/cli/log-commands.ts, src/cli/help.ts, docs/cli.md, test/cli-logs-filtering.test.ts, test/log-commands-views.test.ts.
