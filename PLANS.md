**Goal.** `startPostReview` (src/merge/merge-post-review-drain.ts, called from `drainPostReviews`) answers two separate reader questions in one `run` IIFE: whether a parked review is admitted to run at all, and how the review's verdict settles the entry. The admission is a short prelude (acquire the team permit at VERIFY_TIER; when the lease is null, the abort signal fired, `ctx.startHeld()` is true, or the entry is no longer unreviewed, release the permit and return without running the reviewer). The verdict settlement is a six-way `outcome.kind` ladder — `approve` → `settlePostReview(null)`, `reject` → settle with `rejected`, `fixed` → `mergeReviewerFix`, `exhausted` → `settlePostReview(null)`, `failed` with `infrastructure` → warn and keep queued (no count, no file), `failed` otherwise → warn, count `failures`, and either file-and-drop at `POST_REVIEW_FAILURE_LIMIT` or settle with the count. Each arm reads the same `task`, `lease`, `entry`, `root` and `ctx` locals, so the two concerns are welded into one body. Lifting each into one named module-private helper lets a name answer each question while the `run` IIFE becomes an ordered sequence of those names plus the `try/catch/finally` scaffolding. This is a behavior-preserving extraction only.
