### `readPromptImageFiles`'s on-disk guards — the not-a-regular-file check, the oversize-file refusal, and the count-cap-before-read — are pinned in test/inbox-attachments.test.ts, so a regression in the shared `--attach` read core is caught by the suite (planned 2026-11-14 by the plan role; `readPromptImageFiles` in src/inbox/inbox-attachments.ts is the throwing core both attach surfaces share — the CLI's `readPromptImages` in src/inbox/prompt-commands.ts and the TUI's prompt-line attach in src/ui/tui/tui-editor-attach.ts — and it is the only on-disk reader for an `--attach` image list; the three rule helpers it calls (`promptImagesCountProblem`, `promptImageExtensionProblem`, `promptImageSizeProblem`) and the endpoint validator `promptImagesProblem` are already pinned in test/inbox-attachments.test.ts, but the reader itself is exercised only indirectly through the TUI editor flow in test/tui-attach.test.ts, which never feeds it a non-regular file, an oversize file, an over-count list, or an invalid-extension path; independent in file of the other `## Planned` entry (test/secret-leaks.test.ts, which tests src/review/secret-leaks.ts), so feature can take either; docs/invariants.md names the file for the sibling/move shapes (INV-AK1/AK2) but never `readPromptImageFiles`, so this test-only change needs no invariant edit)

**Goal.** `readPromptImageFiles` (src/inbox/inbox-attachments.ts, exported) is the single on-disk read-and-validate path for a `--attach` image list, shared by the CLI `tumwater prompt` submit/`--edit` forms and the TUI prompt-line attach. It carries three guards its own test file never drives directly. The *not-a-regular-file* check: after it stats each path, `if (!stat.isFile())` throws, so a directory, a FIFO, or a device node named like an image is refused with a path-naming message instead of being `readFileSync`'d — a guard the code documents as keeping a caller from reading a FIFO that would block indefinitely. The *on-disk oversize* refusal: a file whose `lstat` size exceeds `PROMPT_IMAGE_MAX_BYTES` (5 MiB) is refused through `promptImageSizeProblem` before it is read, so an oversized image can never be slurped into memory. The *count cap before read*: the `PROMPT_IMAGES_MAX_COUNT` (4) bound is checked from the raw path list before any file is statted or base64-encoded, so a glob that expanded past it is refused without touching disk. These guards are the `--attach` core's read-safety contract; a change to the `isFile()` test, the `stat.size > MAX` comparison, or the `count > MAX` order would silently weaken it with no failing test. Pin all three (plus the invalid-extension refusal and the happy path) so the shared reader's own behavior is part of the suite.

**Approach.** One file, test-only, no src change and no invariant edit (the three rule helpers and the endpoint validator are already pinned; this adds only the on-disk reader cases): in test/inbox-attachments.test.ts add the import of `readPromptImageFiles` to the existing named-import block from `../src/inbox/inbox-attachments.js`, and add five `test(...)` cases beside the existing ones. Each case builds a fresh directory from the file's existing `tmpdir()` helper (test/fixtures/repo-fixtures.ts) and writes real files with node:fs, then drives `readPromptImageFiles` against paths into that directory: (1) a directory created with `fs.mkdirSync` and named `x.png` — a valid `.png` extension that is not a regular file; (2) a sparse file written with `fs.ftruncateSync(handle, 5 * 1024 * 1024 + 1)` — a 5 MiB + 1 byte regular file whose content is never read because the size guard fires first; (3) five distinct small valid `.png` files (the count cap is 4); (4) a single `note.txt`; and (5) one or two small valid `.png` files as the happy path, carrying the file's existing minimal `PNG` payload so the reader's final `promptImagesProblem` re-validation of the decoded images passes. For the oversize, over-count, extension, and not-a-regular-file cases assert each thrown `Error`'s `message` with `assert.match` on the stable rule wording the reader surfaces; for the happy path assert `assert.deepEqual` on the returned `{ name, dataBase64 }` shape. No source file and no other test file change.

**Files touched.** test/inbox-attachments.test.ts.

**Acceptance criteria.**
- `readPromptImageFiles([a directory named like an image])` throws an `Error` whose message contains `is not a regular file` and the path's JSON-quoted basename — the directory is refused by its `isFile()` shape, not read.
- `readPromptImageFiles([a regular file whose size exceeds PROMPT_IMAGE_MAX_BYTES])` throws an `Error` whose message matches the size wording — `is 5242881 bytes — at most 5242880 (5 MiB) per image` for a 5 MiB + 1 byte file — the file is refused before it is read.
- `readPromptImageFiles([five valid .png files])` throws the count wording (`at most 4 images per prompt (got 5)`) — refused on the raw path list before any file is read.
- `readPromptImageFiles([one .txt file])` throws an `Error` whose message contains `unsupported image type` — the extension is refused before the file is read.
- `readPromptImageFiles([one or two small valid .png files])` returns one or two `{ name, dataBase64 }` objects (the basenames and the base64 of the written bytes) and throws no error — the documented happy path through the reader.
- Every pre-existing test in test/inbox-attachments.test.ts passes unmodified; no source file and no test file other than this one change; the project's declared check is green.
