### `GET /api/run?role=<id>&last=1[&result=<class>[,...]][&model=<selector>[,...]]` serves the role's newest matching run: the dashboard API twin of `tumwater history <role> --last [--result] [--model]` (planned 2026-10-20 by the plan role; independent of every eligible plan: the `/api/diff?overlaps&role` plan edits `handleDiff` in the same file, a different function; touches src/run/run-detail.ts src/gui/gui-endpoints.ts docs/how-it-works.md test/gui-endpoints.test.ts test/gui-server-api.test.ts)

**Goal.** `tumwater history <role> --last` opens a role's newest completed run, and `--result <class>[,...]` / `--model <selector>[,...]` pick the newest run in those outcome classes or on those models (PLANS-DONE.md "`history <role> --last --model`"). `GET /api/run` (`handleRun`, src/gui/gui-endpoints.ts) only takes an explicit `run=N`, so a script or the dashboard has to fetch `/api/history` and pick a row itself to answer "show me feature's newest failed run". This plan adds `last` to `/api/run`. The run is resolved by the same code the CLI uses, so the two cannot pick different runs. When this was planned, `grep -n '"last"' src/gui/gui-endpoints.ts` printed nothing.

**Approach.**
1. src/run/run-detail.ts:
   - Extract the `last` branch of `cmdRunDetail`'s `runNumber` expression into `export function newestRunNumber(root: string, role: string, classes: HistoryResultClass[] | null, models: string[] | null): number | null`. Move the expression as it stands: `readRunRows(root, 1, role)[0]` when both lists are null, else the HISTORY_MAX_RUNS scan through `runRowsOnModels` when `models` is set, then `.find` on `historyClass`; return `?.run ?? null`. `cmdRunDetail` calls it, and its output does not change.
   - Export `runNotFoundLastMessage` and rewrite its doc comment. It currently says the 404 "only ever serves the numbered form, so this wording has no second consumer"; it gets a second consumer here.
2. src/gui/gui-endpoints.ts `handleRun`. Keep the `rejectBadRole` check first. Then set `const last = q.get("last") !== null` (the flag's presence, whatever its value, like `patch`/`transcript`).
   - When `!last`: `q.get("result") !== null` → `badRequest(res, "result needs last")`, and `q.get("model") !== null` → `badRequest(res, "model needs last")` (the CLI's "--result needs --last" rule). Otherwise the existing `intQuery(q, res, "run", "positive")` path runs unchanged.
   - When `last`: `q.get("run") !== null` → `badRequest(res, "last cannot be combined with run (a number and the newest run are rival selectors)")`. `result` is parsed with `splitCommaList` (src/text/text.ts) plus `parseHistoryResultClass` (src/history/history-data.ts), deduplicated. A piece that is not a class → `badRequest` with `` `result must be one of ${Object.values(HISTORY_RESULT_FLAG_NAMES).join(", ")}${gotSuffix(piece)}${typoSuffix(piece, Object.values(HISTORY_RESULT_FLAG_NAMES))}` ``, which is the CLI's `parseHistoryResultList` wording without the `history --` prefix. `model` is parsed with `splitCommaListUnique`. For both, an absent value, `""`, or a list with no non-empty piece means null (filter nothing), as `handleHistory`'s `model` does. Do not call `parseHistoryResultList`/`parseHistoryModelList` (src/history/history.ts): they `fail()` (exit the process).
   - Call `newestRunNumber(root, role, classes, models)`. A null result → 404 `{ error: runNotFoundLastMessage(role, classes, models) }`. Otherwise use that number as `run` for the rest of the handler: `readRunDetail`, the existing 404, and `transcriptText`. The 200 payload has the same shape as the numbered form; the resolved number is in `detail.run`.
   - Extend `handleRun`'s doc comment with the `last`/`result`/`model` contract.
3. docs/how-it-works.md: after the "Its search box (applied on Enter) reloads it through `GET /api/run?…&transcript=1&grep=<text>` … toggling prompts clears it." sentence, add: "`GET /api/run?role=<id>&last=1` serves the role's newest completed run instead of a numbered one, and `&result=<class>[,...]` / `&model=<selector>[,...]` narrow it to the newest run in those outcome classes or on those models, the run `tumwater history <role> --last [--result] [--model]` opens (`newestRunNumber`, shared)." `grep -n 'api/run' docs/invariants.md` printed nothing when this was planned, so the plan claims no invariant ID.

No client change: the dashboard's drill-down keeps fetching by number.

**Acceptance criteria.**

Seed clean run 3 with `run_start` model `m-a` and result `changed`, then clean run 4 with `run_start` model `m-b` and result `error`, then a feature run 5 (`no_change`). Assert:
  - `?role=clean&last=1` → 200 with `run` 4. Its body `deepEqual`s `serveRun(root, "?role=clean&run=4")`'s body.
  - `&result=merged` → run 3, and so does the hidden class alias `&result=changes` (`parseHistoryResultClass` accepts both); `&result=problems` → run 4; `&model=m-a` → run 3; `&model=m-b&result=merged` → 404 whose error equals `runNotFoundLastMessage("clean", ["changes"], ["m-b"])`; `&result=` → run 4.

### `tumwater diff --overlaps --path <path>` keeps only the shared files at or under a repo-relative file or directory, and `GET /api/diff?overlaps=1&path=<path>` does the same: `diff --overlaps --path src/cli` answers "which files under src/cli will two pending changes meet in?" (planned 2026-10-20 by the plan role; independent of every eligible plan. The `/api/run?last` plan edits `handleRun` in src/gui/gui-endpoints.ts, a different function. The `prompt --list --grep` plan touches src/cli/help.ts and docs/cli.md only in the prompt command's stanza and row, so rebase onto it if it lands first. Touches src/change/change-data.ts src/change/change-render.ts src/cli/cli-query-commands.ts src/gui/gui-endpoints.ts src/cli/help.ts docs/cli.md docs/how-it-works.md test/cli-diff.test.ts test/gui-endpoints.test.ts)

**Goal.** `tumwater diff --overlaps` lists every file two or more roles' pending changes touch, and `--role` keeps the files a listed role holds (PLANS-DONE.md "`tumwater diff --overlaps --role`"). On a team with 10 feature instances the list is long. An operator who owns one area, such as `src/gui`, cannot ask for only that area's collisions. `--path` already scopes `diff --role` to a file or directory through `normalizeDiffPath` and `inPath` (src/change/change-data.ts). But `cmdDiff` (src/cli/cli-query-commands.ts) refuses it with `--overlaps` ("diff --overlaps reads every file; drop --path"), and `handleDiff` (src/gui/gui-endpoints.ts) refuses `?overlaps=1&path=` the same way ("overlaps reads every file; drop path"). This plan replaces both refusals with a filter. Overlaps are still computed across every file, so each kept line still names every holder. Only the printed set narrows, as `--role` does today. The scope rule is the same `inPath` rule `diff --role --path` uses, so the two forms cannot disagree about what is "under" a path.

**Approach.**
1. src/change/change-data.ts: add `export function scopeChangeOverlapsToPath(view: ChangeOverlapsView, path: string): ChangeOverlapsView`, defined as `{ ...view, overlaps: view.overlaps.filter((o) => inPath(o.path, path)) }`. Place it beside `scopeChangeOverlaps` with a one-line doc comment that cites `inPath`. `inPath` stays private.
2. src/change/change-render.ts `renderChangeOverlaps(view, scope?, path?)`: add an optional third parameter. It only changes the empty-list wording:
   - `scope` and `path` both set → `no file under <path> held by <a, b> is touched by another pending change`.
   - `path` only → `no file under <path> is touched by two pending changes`.
   - Neither, or `scope` only → today's two strings, unchanged.
   Update the doc comment. Existing one- and two-argument callers (`cmdDiff`, the TUI's `pendingOverlapsText`) are unaffected.
3. src/cli/cli-query-commands.ts `cmdDiff`, `--overlaps` branch: delete the `--path` refusal and keep the `--stat` refusal. Read the path with the existing `diffPathArg(args)`, which already fails on an empty, absolute, `.` or `..`-bearing value with the "diff --path takes a repo-relative path…" wording. The repeat check `rejectRepeatFlag` already runs before the branch. Apply `scopeChangeOverlaps` when `--role` is given, then `scopeChangeOverlapsToPath` when a path is given. Render with `(v) => renderChangeOverlaps(v, scope ?? undefined, path)`. With neither flag, keep calling `renderChangeOverlaps` with one argument, as today. Update `cmdDiff`'s doc comment (`--path` keeps the files at or under that path).
4. src/gui/gui-endpoints.ts `handleDiff`, `overlaps` branch: replace the `rawPath !== null` 400 with a parse through `normalizeDiffPath`. A null result → `badRequest(res, "path takes a repo-relative path such as src/cli.ts (as overlaps lists it)")`, which is the wording the role branch already sends. Then `roleListQuery`, then `collectChangeOverlaps`, then scope by roles (when given) and by path (when given). Extend the doc comment: "`&path=<path>` keeps the files at or under that path, exactly `tumwater diff --overlaps --path <path> --json`."
5. src/cli/help.ts: change the stanza line to `tumwater diff --overlaps [--role <id>[,<id>...]] [--path <path>] [--json]`. Add to its description: "--path keeps only the files at or under that repo-relative file or directory". Completion already offers file completion after `--path` (`PATH_FLAGS`, src/cli/completion.ts), so no completion edit is needed.
6. docs/cli.md, the "See a role's pending change" row: after the `--role` parenthetical on `diff --overlaps`, add "`--path <path>` keeps only the files at or under that file or directory, combining with `--role`". docs/how-it-works.md: change the `GET /api/diff?overlaps=1[&role=<ids>]` mention to `GET /api/diff?overlaps=1[&role=<ids>][&path=<path>]`. When this was planned, `grep -n 'overlaps' docs/invariants.md` printed nothing, so the plan claims no invariant ID.

No dashboard client change: the Pending view keeps fetching the unscoped list.

**Acceptance criteria.**
- test/cli-diff.test.ts, new test "diff --overlaps --path keeps the shared files at or under the path". Build on `seededFeatureRepo` (feature has committed `widget.md`). In feature's worktree write `docs/b.md` and `commitIn` it. Create clean's and bugfix's worktrees with `ensureWorktree`. Clean writes `widget.md` and `docs/a.md`, bugfix writes `docs/a.md` and `docs/b.md` (`fs.mkdirSync(..., { recursive: true })` for `docs/`), and each role `commitIn`s its own worktree. Committing matters: `changedFiles` (src/git/git-diff.ts) reads plain `git status --porcelain`, which collapses a wholly untracked `docs/` into one `docs/` entry, while committed files come through `aheadOfMainFiles` one path each.
