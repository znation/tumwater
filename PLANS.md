### Every post-merge rejection reaches one accounted terminal state: the revert chain holds its plan at exhaustion like a rejection's does, and the forwarded hand-back carries the same round and backstop counters (reported by the user 2026-10-24)

**Goal.** Every post-merge rejection ends somewhere operator-visible when it never converges, and every hand-back path counts rounds the same way. Two gaps make that false today. (1) The plan hold: `recordRevertedChange` (src/merge/merge-core.ts:401-424) counts rounds and clears the chain at `REVISION_BACKSTOP` but never calls `holdEntryAfterExhaustion`, so an exhausted post-merge chain leaves its plan eligible for a fresh pick that restarts the same cycle — the asymmetry against `recordRejectedChange` (src/merge/merge-core.ts:354-390, which holds at its exhaustion via the call at :387). (2) The forwarded path: `sendReviewToRole` (src/merge/merge-drain.ts:129-140) enqueues an inbox prompt and records nothing — no `state.lastReview`, no round — so a rejection that keeps being handed back has no backstop and no terminal state. Design: plans/post-merge-fix-forward.md, "What could land" item 2.

**Approach.**
- src/merge/merge-core.ts: `recordRevertedChange` calls `holdEntryAfterExhaustion(root, role, state.claim, reasons)` in its exhaustion branch, beside the existing `revision exhausted` log, exactly as `recordRejectedChange` does at :387 — so a post-merge chain that stops converging holds its PLANS.md plan for the plan role instead of re-picking. The existing "a BUGS.md claim is never held" rule inside `holdEntryAfterExhaustion` (no role resolves a Needs-review hold on a bug) stays the one home of that exemption.
- src/merge/merge-core.ts: add the one home of the forwarded record — `recordForwardedChange(root, role, state, commit, reasons)` — set beside `recordRevertedChange` and sharing its round arithmetic (the commit's `Revision` trailer read from `git log -1 --format=%B`, + 1) and its `REVISION_BACKSTOP` handling, so the two hand-back paths cannot drift on the counter. Its `state.lastReview` verdict must say what happened — the commit is still on main, not reverted — so no surface reads a revert that never ran (the BUGS-FIXED.md:24-31 class of defect).
- src/merge/merge-drain.ts `sendReviewToRole`: route through `recordForwardedChange` the way `handBackReverted` (:106) routes a revert — the commit's own runner when it is free, else the first free runner of the same base role — keeping the inbox prompt only for the no-free-runner case, where the round is counted at assignment (`assignPendingReverts`, :142) rather than at the first hand-back.
- Terminal state: an exhausted forwarded chain must be visible where rejections already are (`tumwater report`'s per-role maps, src/report/report-fold.ts) — a `revision exhausted` event is already logged for the reverted chain; the forwarded one logs the same event with its own action, so both read the same way on the report's revision line.
- No change to `POST_MERGE_REJECT_WARN`/`postMergeRejectionCounts` here: BUGS.md's filed churn entry (filed 2026-10-24, `tumwater bug`) owns the alert's row folding.

### A post-merge rejection stops reverting: the reviewer's reasons become a fix-forward by the commit's authoring role on top of main, leaving runMainRevert to a red main (reported by the user 2026-10-24)

**Needs review 2026-10-24 by feature: too large for one run (held 1)** — this entry routes through code ("the forwarding path (`recordForwardedChange` + the runner routing that plan adds)") and a round/backstop that only the accounting plan (`## Planned` "Every post-merge rejection reaches one accounted terminal state…") provides, and its **Requires** clause says that plan must land first; it is still under `## Planned`, so this entry cannot be implemented yet, and the surfaced change is itself a 15-file, four-test-suite port. Revisit after the accounting plan merges.

**Goal.** A post-merge rejection costs one follow-up fix, not a revert cycle. Today `drainPostReviews` (src/merge/merge-post-review.ts:25-44) turns a rejected entry into a revert slot item, so the rejection pays a revert commit, a full `check.gateCommand` run on that revert inside the single merge slot (src/baseline/main-revert.ts:118-121), an authoring run that re-applies the whole patch from `refs/tumwater/rejected/<role>`, and then the follow-up's own gate, merge and second reviewer run. The reviewer-as-role.md payoff — the class "a post-merge review converts from hours of serial rework into one follow-up fix" — is only reached if the reasons go to the author as a fix on top of main, where the commit already is. Design: plans/post-merge-fix-forward.md, arms C.

**Requires** the accounting plan (`PLANS.md` ## Planned, "Every post-merge rejection reaches one accounted terminal state…") landed: the forwarded hand-back must carry a round and a backstop before it becomes the normal path, or the cycle it replaces becomes an uncounted loop.

**Approach.**
- src/merge/merge-post-review.ts `drainPostReviews`: a rejected entry hands the reviewer's numbered reasons to the commit's authoring role through the forwarding path (`recordForwardedChange` + the runner routing that plan adds) and settles the entry out of `post-review.json` once the reasons are handed over — the entry exists to carry them to a fix, not to wait for a revert. The revert-slot arm, its `skipChecks` guard and the `p.revert = culprit` assignment go; the review slot's own one-at-a-time behaviour is unchanged.
- src/baseline/main-revert.ts: `MainCulprit.postReview` (:31-33), `runMainRevert`'s rejection wording (:110-112) and `reason: c.postReview ? "post-review" : "main-red"` (:134) are deleted with every caller migrated — `main_revert` then has one cause and one value, a commit that turned main red, which is what `main-guardrails.ts`'s revert rules (:204-215) and docs/invariants.md:266-270 already assume.
- src/merge/merge-drain.ts: `revertReasons`' post-review branch (:76-77), the `toReviewer`/`onFailed` routing in `runMainRevert`'s failure handler (:92) and `sendReviewToRole`'s "it could not be reverted (reason)" wording collapse into one forward text — "A review after merging rejected your commit <sha> on main. It is still on main. Fix what the reviewer found in a new change:" + the reasons — which is now the only path, not a fallback.
- Every surface that says "reverted" or "waiting to revert" for a post-merge rejection says "still on main, awaiting the follow-up" instead: the rejected-entry status label's one home (src/review/post-review-render.ts:24, shared by the TUI pane, `tumwater reviews` and the dashboard), the dashboard's own copy (src/ui/gui/gui-client-pending.ts:234), the help text (src/cli/help.ts:255) and docs/cli.md:50, `post-merge-churn`'s detail (src/ui/team-alerts.ts:872-877 — coordinate with BUGS.md's churn-entry fix, which folds its rows to base role there), docs/how-it-works.md:263-274, docs/invariants.md's INV-BT2 pin list (whose "a rejecting post-merge review reverts the commit and hands it back as a revision" test is deleted with the path), docs/cli.md's `tumwater revert` wording.
- `tumwater report`'s post-merge-rejection table, the churn alert's trigger/window and `POST_MERGE_REJECT_WARN` are unchanged: the rejection still happened and is still the operator's signal.
- The revert machinery itself is untouched for its other job — a red main's culprit — along with the red-main watch, the revert ceiling and bugfix's heal prompt.

**Accepted tradeoff.** The rejected commit stands on main until the follow-up lands. A behavioral rejection that breaks what a test covers is caught by the existing red-main path (culprit bisect → revert → bugfix heal); one that no test covers (BUGS.md's churn entry names `ec36ff29`, reverted by `beac3bd1e` because it "drops `gitTryStarted`'s `gitCouldNotStart` throw and breaks `pickBase`'s documented contract") stands on main, green but wrong, until the fix lands. Measure after landing: how many forwarded rejections later needed a red-main revert, and whether a day's `post-main_revert` count falls when the revert commit, the merge-slot hold and the patch re-apply leave the cycle. If that measurement shows the forwarded fix standing too long or too often, the levers are plans/post-merge-fix-forward.md's arm D (the reviewer's verdict declares the cause, and behavioral findings revert) or arm F (narrow `review.afterMerge` for the noisy role) — not a silent return of this path.

### A re-queued merge carries how many times it has bounced, shown wherever its retry reason is, so a change stuck retrying is not mistaken for a fresh one (planned 2026-10-24 by the plan role; independent of every eligible plan — the high-friction plan edits src/merge/merge-queue-render.ts, src/status/status-data.ts, src/ui/gui/gui-client-pending.ts, docs/how-it-works.md and its queue tests, and this plan shares those first three files and test/merge-queue.test.ts / test/gui-client-pending.test.ts as neighbouring additions (that plan inserts a `high friction` tag before the retry tag in `renderMergeQueue`; this appends a count inside `retryNote`), the `reviews --role` plan edits src/review/post-review-render.ts, src/cli/cli-review-commands.ts, src/cli/help.ts and their tests, the `post-merge churn` doctor plan edits src/review/post-merge-review.ts, src/ui/status-payload.ts and src/doctor/*, the event-feed plan edits src/events/event-format.ts, and the two post-merge-rejection plans edit src/merge/merge-core.ts, src/merge/merge-drain.ts, src/merge/merge-post-review.ts, src/baseline/*, src/ui/team-alerts.ts and their surfaces; neither this plan nor any waiting plan touches src/merge/merge-queue.ts or src/merge/merge-requeue.ts, whose `MergeEntry`/`retryEntry` edits are the one home of the count; touches src/merge/merge-queue.ts src/merge/merge-requeue.ts src/merge/merge-queue-render.ts src/status/status-data.ts src/ui/gui/gui-client-pending.ts docs/cli.md test/merge-requeue.test.ts test/merge-queue.test.ts test/status-data-inbox.test.ts test/gui-client-pending.test.ts)

**Goal.** A `MergeEntry` the pipeline re-queues after a retriable result names its result in `retry` (`merge_blocked`, `review_error`, `merge_conflict` or `main_red`, `retryEntry` in src/merge/merge-requeue.ts) but not how many times the change has bounced, and every re-queue resets `enqueuedAt` to now (`retryEntry`) so it also loses its queue age. A change re-queued once and one re-queued forty times read identically on `tumwater queue`, the dashboard Pending card and the TUI Pending pane. On the day one dirty primary `PLANS.md` produced ~300 `merge_blocked` refusals across five roles (BUGS.md's 2026-10-23 entry), the surfaces showed a succession of apparently fresh single retries, not a change stuck in a loop; the landed `primary-overwrite` alert names that one cause after the fact, but nothing names a repeated bounce itself. Carry a count on the entry and show it wherever the retry reason is already shown, so "this change keeps coming back" is visible at a glance.

**Approach.**
- src/merge/merge-queue.ts: add `retryCount?: number` to `MergeEntry` beside `retry`, doc-commented as how many times the pipeline has re-queued this change (absent for a fresh entry and a recovery's entry; informational, not an ordering key — the filename still orders the queue by the current attempt's `enqueuedAt`). Add `(e.retryCount === undefined || nonNegativeNumber(e.retryCount, null) !== null)` to `isMergeEntry` beside the `retry` guard, so a hand-edited non-number is skipped like any malformed field.
- src/merge/merge-requeue.ts `retryEntry`: add `retryCount: (from.retryCount ?? 0) + 1` to the returned object. `from` is the settled entry, so the count survives every retry; a `main_red` pin re-queues through `state.mainRedRetry.entry` (the stored `rest` carries the count) with the same arithmetic. A first re-queue gets 1.
- src/merge/merge-queue-render.ts `retryNote`: widen the `Pick` to `"retry" | "notBefore" | "retryCount"`, and when `(entry.retryCount ?? 0) > 1` append `` ` · ×${entry.retryCount}` `` after `re-queued after ${entry.retry}` and before the `eligible in` clause. A fresh entry (no `retry`) and a first re-queue (count 1) render byte-identically to today, so no existing queue line moves.
- src/status/status-data.ts: add `retryCount?: number` to the `mergeQueue.entries` element type and `...(typeof e.retryCount === "number" ? { retryCount: e.retryCount } : {})` to the `merges.map`, so the key stays absent for a fresh entry and the dashboards receive it.
- src/ui/gui/gui-client-pending.ts `queueEntryLineHtml`: inside the existing `retry` clause, append `(Number.isFinite(e.retryCount) && e.retryCount > 1 ? " · ×" + e.retryCount : "")` after the result and before the `eligible in` clause, matching `retryNote`'s wording.
- docs/cli.md, the `tumwater queue` clause (the sentence that already says a re-queued entry names why it is back): add that a change re-queued more than once also names how many times it has bounced (`re-queued after merge_blocked · ×3`).
- No change to `settleMergeOutcome`, `requeueKeptChange`'s re-queue decision, the event log, or `enqueuedAt`'s meaning; an implementation that finds itself editing those has gone off-plan.
