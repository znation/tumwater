### `parseGrepFlag`'s value-token removal and its valueless/empty-value refusal are pinned in test/cli-args.test.ts, so a regression that would let a `--grep` value token read as a rival flag or a positional — or a flag-shaped pattern be mistaken for a flag, or a valueless `--grep` be accepted — is caught by the suite (planned 2026-11-15 by the plan role; `parseGrepFlag(args: string[], missingValueError: string): { rest: string[]; pattern: string | null }` in src/cli/cli-args.ts is the shared `--grep <text>` parser the filtering views use: it removes the flag's value token from `rest` (the `--grep` flag token itself stays) so a flag-shaped pattern cannot be read as a rival flag or a positional, and `fail`s with the caller's own wording when the flag is valueless or its value is empty; it deliberately KEEPS a flag-shaped or single-dash token as the pattern text rather than refusing it — the inverse of `rejectFlagLookingValue`, the sibling plan — because `logs --grep -f` greps for the text "-f"; `grep -rn parseGrepFlag test/` prints nothing — no test drives it directly — and the archive records only the addition of `--grep` to the views (backlog, quarantine, help, salvage, reviews, logs, history), never a coverage pin, so the value-removal and valueless branches are untested on their own; the function is pure in-memory `args`-array logic — `indexOf`, `filter`, `flagValue`, one `fail` — with no git, fs, shell or clock, so the pin is test-only; docs/invariants.md binds no src/cli/cli-args.ts symbol, so no invariant edit is needed; independent of the other `## Planned` entry, which is test/cli-args.test.ts over src/cli/cli-args.ts — same file, different exported function — so feature may take either)

**Goal.** `parseGrepFlag` (src/cli/cli-args.ts, exported) is the shared `--grep <text>` parser behind the filtering views (`logs`, `backlog`, `quarantine`, `help`, `salvage`, `reviews`, `history`). Two branches are load-bearing and untested on their own: the value token leaves `rest` (so a flag-shaped pattern like `logs --grep -f` cannot impersonate a rival flag or be read as a positional by the caller's later scans), and a valueless or empty value `fail`s with the caller's own wording (each view names its command). It is the deliberate inverse of `rejectFlagLookingValue`: a `--`- or `-`-token in the grep slot is the *text* to search, never refused. No test calls it directly (`grep -rn parseGrepFlag test/` is empty; the views drive it only indirectly through their own commands), so pin both branches through the exported function.

**Approach.** One file, test-only, no src change and no invariant edit (docs/invariants.md binds no src/cli/cli-args.ts symbol): in test/cli-args.test.ts add `parseGrepFlag` to the existing named-import block from `../src/cli/cli-args.js` and drive the cases with the `expectOk`/`expectFail` helpers already imported from `./helpers/exit-capture.js` — each case is a single `assert` against a literal, no repo, worktree, fs, git or clock. Cases: *remove the value token* — `expectOk(() => parseGrepFlag(["--grep", "two", "-n"], err))` returns `{ rest: ["--grep", "-n"], pattern: "two" }` (the value "two" is dropped from `rest`; the `--grep` token and the trailing `-n` remain). *keep a flag-shaped pattern as text* — `expectOk(() => parseGrepFlag(["--grep", "--since"], err))` returns `{ rest: ["--grep"], pattern: "--since" }`. *keep a single-dash pattern* — `expectOk(() => parseGrepFlag(["--grep", "-f"], err))` returns `{ rest: ["--grep"], pattern: "-f" }`. *absent* — `expectOk(() => parseGrepFlag(["-n", "5"], err))` returns `{ rest: ["-n", "5"], pattern: null }`. *valueless fails* — `expectFail(() => parseGrepFlag(["--grep"], err))` returns `{ code: 1, stderr }` where `stderr` is `tumwater: ` + `err` + `\n`. *empty value fails* — `expectFail(() => parseGrepFlag(["--grep", ""], err))` returns code 1 with the same `stderr` (both branches call the one `fail(missingValueError)`). No source file and no other test file change.

**Files touched.** test/cli-args.test.ts.

**Acceptance criteria.**
- Given `--grep` with a plain value, `parseGrepFlag(["--grep", "two", "-n"], err)` returns `{ rest: ["--grep", "-n"], pattern: "two" }` — the value token is removed from `rest` so it cannot be read as a positional, while the `--grep` flag token and the trailing `-n` remain.
- Given `--grep` with a flag-shaped value, `parseGrepFlag(["--grep", "--since"], err)` returns `{ rest: ["--grep"], pattern: "--since" }` — a `--`-token in the grep slot is searched as the pattern text and is not refused (the deliberate inverse of `rejectFlagLookingValue`), and it is removed from `rest` so it cannot impersonate a rival flag.
- Given `--grep` with a single-dash value, `parseGrepFlag(["--grep", "-f"], err)` returns `{ rest: ["--grep"], pattern: "-f" }` — a `-`-token is likewise kept as pattern text and not refused.
- Given no `--grep` in `args`, `parseGrepFlag(["-n", "5"], err)` returns `{ rest: ["-n", "5"], pattern: null }` — an absent filter leaves `rest` unchanged and reports no pattern.
- Given a valueless `--grep` (the flag is the final token), `parseGrepFlag(["--grep"], err)` fails with exit 1 and writes the exact line `tumwater: <err>` (a trailing newline), where `<err>` is the caller's wording — a `--grep` with no value is an error, not a no-op.
- Given an empty value, `parseGrepFlag(["--grep", ""], err)` fails with exit 1 and writes the same `tumwater: <err>` line (a trailing newline) — a zero-length pattern is refused like a missing one.
- Every pre-existing test in test/cli-args.test.ts passes unmodified; no source file and no other test file change; the project's declared check is green.
