### The post-merge review floors its own wall at the 3600 s reviewer floor when its resolved model is free, so a slow local default is not killed mid-run and re-queued (planned 2026-11-14 by the plan role; implements Option B of the user's 2026-11-14 answer to QUESTIONS.md "post-merge review on a slow local model" (Option B confirmed 2026-11-14); the floor itself shipped on main in b911d4e4 but no test exercises its free-ness-verdict path, so the remaining close is the offline free-ness-verdict tests — this entry is done only when those tests land)

**Goal.** A merged commit's post-merge review runs on the live config's `strong`/`review` model — on this host a slow local model — and its wall comes from `reviewRunConfig` (src/config/config-views.ts): a 900 s base (`REVIEW_TIMEOUT_S`) stretched up to 2× under host load and up to 2× for a large diff. A *free* (typically local) model needs the same number of turns as a paid one but runs far slower per turn, so the load stretch alone (1800 s for a59a20af; 3555.9 s for a4d55b7d once the diff stretch engages) kills a *progressing* review mid-run and the drain re-queues it, burning ~15–60 min of dead compute per attempt until an attempt happens to finish. The `FALLBACK_REVIEW_TIMEOUT_S` (3600 s) floor exists for exactly this, but only in the budget-fallback view (`fallbackReview`, src/config/config-fallbacks.ts), which the post-merge review never uses. Generalize the floor to the live post-merge path: when the reviewer's *own* resolved seam is free, floor its budget at `FALLBACK_REVIEW_TIMEOUT_S` *before* the load/diff stretch, so a slow local default gets the floor (not the 900 s fast-default budget) while a paid reviewer keeps today's value exactly. The load/diff stretch and the quiet watchdog are untouched.

**The floor is implemented and shipped (b911d4e4, on main).** `reviewRunConfig` (src/config/config-views.ts) takes a fourth parameter `slowReviewer: boolean = false` and, when true, raises the budget's base to `Math.max(config.review.timeoutSeconds ?? REVIEW_TIMEOUT_S, FALLBACK_REVIEW_TIMEOUT_S)` before the unchanged load/diff stretch and run-budget cap. `reviewMergedCommit` (src/review/post-merge-review.ts) resolves the reviewer seam with `reviewConfig` and judges it free with `seamFree` (a module-private `reviewerSlowFree`; a missing catalog reads the safe false), and accepts an optional `slowReviewer?: boolean` override that defaults to the computed verdict so an offline test can force free/not-free without a real model catalog. Every other `reviewRunConfig`/`reviewMergedCommit` caller passes no fourth/fifth argument and reads `slowReviewer = false`, so a paid reviewer's wall is byte-identical to before the floor.

**Remaining close (this plan).** The floor shipped (b911d4e4) with no test exercising its *free-ness-verdict* path: `test/config-views.test.ts` held only the fallback-view floor test (the `applyFallbackModel` view, line 233), and `test/post-merge-review.test.ts` held only the load/diff stretch — neither calls `reviewRunConfig` with the fourth `slowReviewer` argument, nor passes `reviewMergedCommit` a forced verdict. This plan is the remaining work: write the missing coverage offline (no real model, per the project's offline-fake-pi rule) and stamp the entry Done.

**Approach.**
- `test/config-views.test.ts`: add one `reviewRunConfig` test that calls with the fourth argument. Free (`slowReviewer = true`): quiet host (`load1 ≤ cpus`) gives exactly `FALLBACK_REVIEW_TIMEOUT_S` (3600 s), a starved host (`load1/cpus = 2`) gives `2 × FALLBACK_REVIEW_TIMEOUT_S` (7200 s), a quiet + large diff (`4 × REVIEW_DIFF_REFERENCE_BYTES`, capped at 2×) gives `2 × FALLBACK_REVIEW_TIMEOUT_S`, and starved + large diff gives `4 × FALLBACK_REVIEW_TIMEOUT_S` — with a high `config.runTimeoutSeconds` so the run cap is inert. A configured `review.timeoutSeconds` above the floor (7200 s) stands unchanged when free; one below it (120 s) is raised to the floor. Not free (`slowReviewer = false`): quiet gives exactly `REVIEW_TIMEOUT_S` (900 s) and starved gives exactly `2 × REVIEW_TIMEOUT_S` (1800 s) — the floor never engages for a priced reviewer.
- `test/post-merge-review.test.ts`: add two load-robust tests through the `runGatePi` config the review hands the run (the existing diff-stretch capture pattern), passing the `reviewMergedCommit` `slowReviewer` override. Forcing it `true` (free): the run's `runTimeoutSeconds` is `≥ FALLBACK_REVIEW_TIMEOUT_S` and `≤ 4 × FALLBACK_REVIEW_TIMEOUT_S`, and the review still settles on the approving verdict (emptying the queue). Forcing it `false` (not free): the run's `runTimeoutSeconds` stays `≤ 2 × REVIEW_TIMEOUT_S` and `< FALLBACK_REVIEW_TIMEOUT_S` — the floor is a minimum on the stretched budget, so the bound holds whatever the host's load is, and the not-free budget never reaches the floor.

**Files touched.** test/config-views.test.ts, test/post-merge-review.test.ts. (The floor's source files, src/config/config-views.ts and src/review/post-merge-review.ts, already carry the shipped behavior; no src change and no invariant change — the only invariant binding `reviewMergedCommit` is INV-BT3, the git-diff path, which these tests do not touch.)

### `secretLeakReason`'s two untested changed-file guards — the most-files-named bound and the per-file size cap — are pinned in test/secret-leaks.test.ts, so a regression in the secret-leak gate's own finding limits is caught by the suite (planned 2026-11-14 by the plan role; the secret-leak gate src/review/secret-leaks.ts is live — called by the review gate and the stage check, src/review/diff-rules.ts, src/review/review.ts and src/stage/stage-check.ts — and its happy path, merge-base exclusion, symlink non-following, credential sources and unreadable-file findings are all already pinned in test/secret-leaks.test.ts, but its two changed-file *limits* are not: the most-files-named bound and the per-file size cap; independent in file of the one waiting `## Planned` entry, which tests src/review/post-merge-review.ts and src/config/config-views.ts, so feature can take either)

**Goal.** `secretLeakReason` (src/review/secret-leaks.ts, the exported async gate) has two changed-file guards that its own test file never exercises. The *most-files-named* bound: after it gathers one finding per leaked/unreadable file, it names only the first `MAX_NAMED` (10) of them, `slice(0, MAX_NAMED)`, and appends `moreSuffix(leaks.length - MAX_NAMED)` — a ` (+N more)` for the overflow — so a change that dumps the same secret into a dozen files reports "ten named, and N more" rather than an unbounded reason string. The *per-file size cap*: `readFileForScan` skips any regular file whose `lstat` size exceeds `MAX_SCAN_BYTES` (8 MiB) instead of reading it, so a hostile or accidental huge file can never be slurped into the scan. Both guards are pure and cheap to drive from a repo fixture, and neither is covered: a reviewer who changes `MAX_NAMED`, `moreSuffix`'s wording, or the `size > MAX_SCAN_BYTES` test has no test that fails. Pin both so the gate's own output limits and its read-safety rule are part of the suite's contract.

**Approach.** One file, test-only, no src change and no invariant edit (the gate's finding *rules* — names the variable never the value, merge-base exclusion, unreadable-file reporting — are already pinned; this adds only the two *limit* cases): add two `test(...)` cases to test/secret-leaks.test.ts beside the existing ones, reusing the file's existing `worktree(base, edit)` helper (a `makeRepo` + `ensureWorktree(root, "improve", "main")` worktree) and its `VALUE`/`ENV` constants (one secret, `$HF_TOKEN`, so every leaking file names the same variable). For the most-files-named case, write a base with a few non-secret files and an edit that puts `VALUE` into eleven distinct files, then assert the reason names exactly `MAX_NAMED` of them and ends with the ` (+${overflow} more)` suffix. For the size-cap case, write one file whose size exceeds the 8 MiB cap containing `VALUE` and one small file containing it, and assert the oversized one is not reported while the small one is. Both read through the real git fixtures, so they also keep the real `changeBaseRev`/`fileContentAt` merge-base path exercised at scale.

**Files touched.** test/secret-leaks.test.ts.

**Acceptance criteria.**
- With a change that puts the same known secret value into eleven changed files, `secretLeakReason(wt, "main", <all eleven files>, ENV)` returns a string that contains a finding for exactly ten of those files (the first `MAX_NAMED` in the `files` order) and ends with ` (+1 more)` immediately before the ` — delete the file or remove the value;` closer, and does not name the eleventh file (the bound and the `moreSuffix` wording are the contract).
- With a changed file whose size exceeds `MAX_SCAN_BYTES` (8 MiB) containing the value alongside one small changed file containing it, the returned string names the small file and does not contain a finding for the oversized one — the oversized file is skipped before it is read, not read and then filtered.
- Every pre-existing test in test/secret-leaks.test.ts passes unmodified; no source file and no test other than this one change; the project's declared check is green.
