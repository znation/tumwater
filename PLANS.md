### Event log window: `tumwater logs --since <duration> --until <duration>` shows a bounded past window that ends before now (planned 2026-10-20 by the plan role; independent of every eligible plan; touches src/cli/cli-args.ts + src/cli/cli-flag-specs.ts + src/cli.ts + src/cli/log-commands.ts + src/cli/help.ts + docs/cli.md + test/cli-logs-filtering.test.ts)

**Goal.** `tumwater logs --since <duration>` always ends its window at now. To look at an incident from 3 days ago (say, a connection-error storm), an operator has to ask for `--since 4d`, which also prints every later event, often thousands of rows. `-n` cannot help, because it counts back from now and is a rival shape to `--since`. This plan adds `--until <duration>`, which ends the `--since` window that long ago. `--since 4d --until 3d` then shows one past day, and it composes with `--grep`, `--type`, `--role`, `--count` and `--json` exactly as the plain window does. `grep -rn -- '--until' src docs/cli.md` printed nothing when planned, and `grep -n -- '--until' PLANS-DONE.md BUGS-FIXED.md` printed nothing. `history --since` stays as it is; this plan is `logs` only.

**Approach.**
1. src/cli/cli-args.ts `parseSinceFlag(args, label, maxMs)`: add a fourth parameter `flag = "--since"` and read `flagValue(args, flag)`. Existing callers are unchanged. Update its doc comment to say the flag defaults to `--since`.
2. src/cli/cli-flag-specs.ts: beside `sinceFlagSpec`, export `LOGS_UNTIL_FLAG: FlagSpec = { names: ["--until"], value: true, valueName: "<duration>", missingValue: "logs --until needs a value", validate: (value) => { parseDurationFlag("logs --until", value); } }`, with a one-line doc comment. `parseDurationFlag` is already used there by `sinceFlagSpec`. src/cli.ts `case "logs"`: add `LOGS_UNTIL_FLAG` to the `rejectUnknownArgs("logs", …)` list right after `sinceFlagSpec("logs --since")`, and import it from ./cli/cli-flag-specs.js beside the other specs.
3. src/cli/log-commands.ts `cmdLogs`: right after `const ms = parseSinceFlag(rest, "logs --since", LOGS_SINCE_MAX_MS);`, add `const untilMs = parseSinceFlag(rest, "logs --until", LOGS_SINCE_MAX_MS, "--until");`. Then:
   - `if (untilMs !== null && ms === null) fail("logs --until requires --since");`. This one rule also covers `-f`, `-n` and `--transcript` without `--since`.
   - `if (untilMs !== null && ms !== null && untilMs >= ms) fail(`logs --until (${durationLabel(untilMs)}) must be shorter than --since (${durationLabel(ms)})`);`. Both checks run before any read.
   - Inside the `if (ms !== null)` branch, after `readEventsSince` returns, keep only `e.ts < cutoff + ms - untilMs` when `untilMs !== null`. Use destructured `cutoff`, so the upper edge is the same `now` the lower edge used. Apply this before `feedFilter`, so `--count`, the filters and the empty-window prose all see the bounded window.
   - Replace the three `in ${durationLabel(ms)}` phrases in the empty-window prose with one `windowPhrase`. It is `in ${durationLabel(ms)}` without `--until`, and `between ${durationLabel(ms)} and ${durationLabel(untilMs)} ago` with it. The no-`--until` output stays as it is.
   - `covered` and `SPARSE_WINDOW_NOTE` are unchanged: coverage is about the window's far edge, which `--until` does not move.
   - Add `[--until <duration>]` to the doc comment's synopsis on `cmdLogs`.
4. src/cli/help.ts: in the `tumwater logs` stanza's synopsis, add `[--until <duration>]` right after `[--since <duration>]`. After "events of the past window (capped at 7d)", add `; --until ends that window the given duration ago (requires --since)`, re-wrapped to the column. Shell completion reads flags from the help stanzas (`helpStanzas`, src/cli/completion.ts), so it needs no separate edit.
5. docs/cli.md, "Check state" row: change `` `tumwater logs --since <duration>` `` to `` `tumwater logs --since <duration> [--until <duration>]` (`--until` ends the window that long ago, so `--since 4d --until 3d` shows one past day; it requires `--since`, must be shorter than it, and composes with every filter `--since` does) ``.

**Files.** src/cli/cli-args.ts, src/cli/cli-flag-specs.ts, src/cli.ts, src/cli/log-commands.ts, src/cli/help.ts, docs/cli.md, test/cli-logs-filtering.test.ts. src/events/event-window.ts is unchanged. INV-A3 in docs/invariants.md binds `cmdLogs` only for the feed's shape and grep rule, which this plan does not change, so it claims no invariant ID.

**Acceptance criteria.** All the tests are new, in test/cli-logs-filtering.test.ts, and use its existing `seedEvents(repo, agesMs)` helper.

### The pre-queue self-check flags a word doubled by a word-swap rename ("role role", "merge merge") in added comment and doc prose (planned 2026-10-20 by the plan role; independent of every eligible plan; touches src/run/stage-path-checks.ts + src/run/stage-check.ts + test/stage-check.test.ts + test/gui-operator.test.ts + src/git/worktree-use.ts)

**Goal.** Every plain-terms rename pass has left words doubled in comments, and reviewers rejected the change for each one. Between 2026-10-17 and 10-20, `review_rejected` reasons quote "The merge merge's conflict resolver", "eight newly introduced "role role(s)" artifacts", "a role role's bare nothing-to-do" (split across a line break), "an idle role role shows why…" and "(config, roles, roles, running, …)". `garbledWordingFindings` (src/run/stage-path-checks.ts) already catches this for "run" (`GARBLED_WORDING`'s `\bruns?\s+run(?:s|ning)?\b`), but not for any other word, so the next rename (`loop` → `role`, `landing` → `merge`) reaches review with it. This plan adds a word-agnostic doubled-word pattern that runs only on comment and doc prose, so the authoring session gets the finding in its fix-up turn instead of losing a review round. `grep -n -iE 'doubled word|repeated word|role role' PLANS-DONE.md BUGS-FIXED.md` printed nothing when planned. The closest finished plans are the two garbled-wording entries ("…flags the garbled wording a word-swap rename leaves…" and "…catches "run" stacked on "run"…"), and both cover "run" only.

**Approach.** All in src/run/stage-path-checks.ts, beside `GARBLED_WORDING`:
1. Add `const DOUBLED_WORD = /(?<![-./\w])(?!(?:that|had)\b)([A-Za-z]{2,})\s+\1\b(?![-:])/;` with a doc comment. It is case-sensitive on purpose, so `[object Object]` and "plans PLANS" do not match. The lookbehind skips a word after `-`, `.` or `/` ("team-wide wide-shallow", "built-in in", "Readable.read read", "chars/line line"). The trailing lookahead skips "NaN NaN:NaN" and "not not-ready". "that that" and "had had" are grammatical and are let through.
2. Add `function proseOf(file: string, line: string): string | null`. It returns the whole line for a `.md` file and for a line whose trimmed start is `//`, `/*` or `*`, and the text from the first ` // ` onward for a trailing comment. Otherwise it returns null. Code is never checked, because class strings like `"btn btn-sm"` would match.
3. `spanningGarbled(joined, joinAt)` gets a third parameter `patterns: readonly RegExp[]`. The existing call passes `GARBLED_WORDING`.
4. In `garbledWordingFindings`, when no `GARBLED_WORDING` pattern hit the line and `proseOf(file, cur)` is not null, test `DOUBLED_WORD` against that prose. A match is pushed as `${file}:${lineNo} "${m[0]}"`, like the existing hits. In the split-line branch, when the `GARBLED_WORDING` spanning check finds nothing and both `proseOf(file, prevAdded)` and `proseOf(file, cur)` are non-null, call `spanningGarbled(joined, head.length, [DOUBLED_WORD])` and report a hit as `${file}:${lineNo - 1}-${lineNo}`. Record prose stays skipped through the existing `isRecordProse` guard. A line still yields at most one hit.
5. Change the finding's lead to `'added lines carry garbled rename wording (reword them; a rote word swap such as "tick" → "run" reads wrong here or leaves a word doubled): '`. Keep the `// vocabulary-ok` marker on that line and the "garbled rename wording" substring, which existing tests filter on.
6. Doc comments: in the module comment of src/run/stage-path-checks.ts, change "garbled run wording" to "garbled run wording or a doubled word in comment and doc prose". In src/run/stage-check.ts, extend the "seventh check" paragraph with one sentence: it also reports any word doubled back to back in comment or doc prose (case-sensitive, not after `-`, `.` or `/`, "that that" and "had had" excepted).

Fix the two hits this pattern finds on the tree today. test/gui-operator.test.ts has the comment "every idle role role as `waiting: budget spent`", which becomes "every idle role as …". src/git/worktree-use.ts has "process that runs runs and merges" in its module comment, which becomes "process that launches runs and merges". When planned, a node script that applied `DOUBLED_WORD` through `proseOf` to every line of the .ts/.tsx/.md files under src, test and docs, plus README.md and DEVELOPMENT.md, found exactly these two hits in 64,117 prose lines.
