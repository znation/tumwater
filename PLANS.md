### A post-merge review that keeps failing names its last failure reason in `tumwater reviews` and the dashboards, so the operator can act on the at-risk advice (planned 2026-10-23 by the plan role; independent in files — the at-risk plan reads `readPostReviews`/`POST_REVIEW_FAILURE_LIMIT` from src/review/post-merge-review.ts and the accept plan reads `readPostReviews`/`settlePostReview` there, neither editing the module, and the post-merge-review-keeping-authoring plan edits src/merge/merge-pipeline.ts, merge-verify.ts and merge-drain.ts, not src/merge/merge-post-review.ts; docs/cli.md's `tumwater reviews` clause is shared with the accept plan, so whichever lands second rebases that one clause; touches src/review/post-merge-review.ts src/merge/merge-post-review.ts src/review/post-review-render.ts src/ui/gui/gui-client-pending.ts docs/cli.md test/post-merge-review.test.ts test/post-review-render.test.ts test/gui-client-pending.test.ts)

**Goal.** `drainPostReviews` (src/merge/merge-post-review.ts) retries a post-merge review that ends without a verdict and logs the reason each time as a free-text warning: `the post-merge review of <sha> failed (<detail>)`. The entry itself keeps only the count (`failures`), so `tumwater reviews` and the dashboard/TUI Pending views print `[N failed review runs]` and the at-risk doctor row/alert planned in PLANS.md advises "fix the reviewer backend or accept the commit unreviewed deliberately" without naming what is failing. The operator has to grep `.tumwater/log/events.jsonl` for the sha to learn why. Store the latest run's `outcome.detail` on the entry and render it beside the count, so the place that raises the alarm also carries the reason to fix.

**Approach.**
- src/review/post-merge-review.ts: add `lastFailure?: string` to `PostReview` (doc-comment: the most recent verdict-less run's detail, replaced on each failed run and cleared when the entry is settled or removed). In `readPostReviews`, after the `failures` parse, `if (typeof lastFailure === "string") entry.lastFailure = lastFailure;` — a torn-file field of any other type is dropped like the others. Update the "torn or hand-edited entry" doc comment to name it.
- src/merge/merge-post-review.ts, `drainPostReviews`'s verdict-less arm: the below-limit `settlePostReview(root, entry.commit, { ...entry, failures })` becomes `{ ...entry, failures, lastFailure: outcome.detail }`. The drop-at-limit branch and its two warnings are unchanged (the entry is removed, so nothing renders its reason). The rejected arm's `{ ...entry, rejected: outcome.reasons }` spread keeps carrying any older `lastFailure`, which the rejected label already outranks.
- src/review/post-review-render.ts, `postReviewStatusLabel`: when `lastFailure` is a non-empty string, the failures branch returns `` `[${plural(entry.failures, "failed review run")} — last: ${squash(entry.lastFailure, 80)}]` `` instead of the bare count. `squash` is already imported; the rejected branch is unchanged. This one helper is what `renderPostReviews` (the CLI and the TUI Pending pane, src/ui/tui/tui-pane-pending.ts) already calls, so both get the reason with no further plumbing. Update the helper's doc comment to name the reason.
- src/ui/gui/gui-client-pending.ts, the hand-kept browser twin `postReviewStatusLabel`: mirror the same suffix using the file's `squashText(e.lastFailure, 80)`, so the dashboard's Post-merge reviews card matches the CLI. The card already paints `status.postReviews`, which statusPayload fills from `readPostReviews` (src/ui/status-payload.ts), so the new field reaches it with no server change.
- docs/cli.md, the `tumwater reviews` clause: after the `[N failed review runs]` description, state that the suffix names the last failure's reason (squashed) and that `--json` carries it as `lastFailure`. Do not touch docs/invariants.md: the field changes no guarantee in the `## Post-merge reviews` section, and the accept plan edits that section in the same window.

**Acceptance criteria.**
- After a verdict-less run below `POST_REVIEW_FAILURE_LIMIT`, `tumwater reviews` prints the entry with `[N failed review runs — last: <detail>]`, the same text appears in the dashboard's Post-merge reviews card and the TUI Pending pane's review block, and `reviews --json` carries the entry's `lastFailure` string; the detail is squashed to at most 80 characters with the same `squash`/`squashText` used elsewhere.
- A later failed run replaces `lastFailure` with that run's detail; an approve removes the entry and a reject keeps rendering the `[rejected — waiting to revert: …]` label without the reason.
- `readPostReviews` preserves a string `lastFailure` and drops a non-string one, so a hand-edited or older file still reads; `tumwater reviews` on an entry with only `failures` (no `lastFailure`) prints the unchanged `[N failed review runs]`, and the drop-at-limit behavior and its warnings are unchanged.
- `npm run test:gate` passes.

### A dropped post-merge review — the commit it leaves on main unreviewed — raises a standing amber alert on the dashboard, the TUI and `tumwater status` (planned 2026-10-23 by the plan role; independent — it edits no src/review, src/merge, src/doctor, src/cli or src/orchestrator file and reads only the existing `warning` event the drain's drop branch writes, so the in-flight accept plan (src/review, src/cli) and last-failure plan (src/review, src/merge) do not collide; it shares docs/how-it-works.md with the in-flight Interlock 4/4 docs plan, so whichever lands second rebases one line; touches src/ui/status-payload.ts src/ui/team-alerts.ts src/ui/status-render.ts src/ui/tui/tui.tsx docs/how-it-works.md test/status-payload.test.ts test/team-alerts.test.ts)

**Goal.** `drainPostReviews` (src/merge/merge-post-review.ts, `startPostReview`) counts each verdict-less run in the entry's `failures`; at `POST_REVIEW_FAILURE_LIMIT` (3, src/review/post-merge-review.ts) it drops the entry (`settlePostReview(root, entry.commit, null)`) and writes only a `warning` — `dropping the post-merge review of <sha> after N failed runs; it stays on main unreviewed`. The landed `post-merge-risk` alert and `post-merge reviews` doctor row (src/ui/status-payload.ts `postReviewRiskAlert`, src/doctor/doctor-backlog.ts `atRiskPostReviews`) fire while the entry is still in `.tumwater/state/post-review.json` at `failures >= POST_REVIEW_FAILURE_LIMIT - 1`; once the next failed run drops it, the entry is gone, so `tumwater reviews`, the dashboard's Post-merge reviews card and the TUI Pending block list nothing and no surface names the unreviewed commit. The commit is permanently on main beyond the review gate with only an event-log line, and the at-risk alert can be missed entirely when the team runs unattended. Add the after-the-fact judgement: read the drop `warning` off the trailing day of events — the `primaryOverwriteBlocks` precedent (src/ui/status-payload.ts) — and raise the same standing amber alert on all three status surfaces.

**Approach.**
- src/ui/status-payload.ts: beside `PRIMARY_OVERWRITE_WINDOW_MS` add `export const DROPPED_POST_REVIEW_WINDOW_MS = 24 * 60 * 60_000;`, `const DROPPED_POST_REVIEW_MARKER = "dropping the post-merge review of";` (doc-commented: the exact substring the drain's at-limit branch writes at src/merge/merge-post-review.ts, so it matches a drop and not the per-run `the post-merge review of <sha> failed (…)` warning the at-risk alert already covers), `export interface DroppedPostReviews { count: number; latestTs: number; latestMessage: string }`, and `export function droppedPostReviewsAlert(root: string, now = Date.now()): DroppedPostReviews | null`. The function is `const hits = eventsSince(root, DROPPED_POST_REVIEW_WINDOW_MS, now, (e) => e.type === "warning" && typeof e.message === "string" && e.message.includes(DROPPED_POST_REVIEW_MARKER)); const latest = hits[hits.length - 1]; return latest ? { count: hits.length, latestTs: latest.ts, latestMessage: String(latest.message) } : null;`. `eventsSince` already degrades an unreadable log, so no `try`/`catch` is needed; it is one bounded event scan like the other event-reading alerts.
- src/ui/team-alerts.ts: add `type DroppedPostReviews` to the existing `import type { … } from "./status-payload.js"` group; append `droppedPostReviews: DroppedPostReviews | null = null` as the **last** parameter of `teamAlerts` (after `postReviewRisk`); and push one amber block after the `post-merge-risk` block: `key: "dropped-post-reviews"`, tone `amber`, title `` `${plural(droppedPostReviews.count, "post-merge review was dropped", "post-merge reviews were dropped")} in the last day — ${plural(droppedPostReviews.count, "the commit sits", "the commits sit")} on main unreviewed` ``, detail `` `most recently ${humanAgo(droppedPostReviews.latestTs, now)}: ${squash(droppedPostReviews.latestMessage, 160)} — the reviewer kept failing past \`POST_REVIEW_FAILURE_LIMIT\`, so the commit is beyond the review gate; fix the reviewer backend so later commits are reviewed` ``, `actions: [{ label: "See failures", act: "view", arg: "failures" }]`. `plural`, `humanAgo` and `squash` are already imported. Append only, never insert: the trailing parameter's position is load-bearing for every existing caller and test. Update the module doc comment's alert list to name a dropped post-merge review.
- src/ui/status-render.ts and src/ui/tui/tui.tsx: import `droppedPostReviewsAlert` from ./status-payload.js (../status-payload.js in the TUI) and append `droppedPostReviewsAlert(root)` as the **last** `teamAlerts` argument, after `postReviewRiskAlert(root)`. Append, never insert.
- docs/how-it-works.md: the dashboard alert list (the parenthetical beginning "a failing or stuck role, …") gains "a post-merge review dropped after repeated failures, leaving its commit on main unreviewed"; the Pending view's post-merge reviews card sentence ("A review one failed run from the `POST_REVIEW_FAILURE_LIMIT` drop raises the standing amber post-merge-risk alert…") adds that a review the drain actually drops raises the standing amber `dropped-post-reviews` alert describing the unreviewed commit.
- The drain's retry/drop behavior, the drop warning text, `post-merge-risk`, `post-merge-churn`, the `post-merge reviews` doctor row and `tumwater reviews` are unchanged — this reads the event log only.

**Acceptance criteria.**
- After the drain drops a post-merge review (`failures >= POST_REVIEW_FAILURE_LIMIT`), `tumwater status`, the dashboard and the TUI each raise exactly one amber alert keyed `dropped-post-reviews`, whose title names the count of drops in the trailing day and says the commit(s) sit on main unreviewed, and whose detail carries the latest drop warning squashed to 160 characters with the fix-the-reviewer-backend advice and the Failures-view action.
- The alert fires only on the drop warning: a day whose only post-merge warnings are per-run `the post-merge review of <sha> failed (…)` lines raises no `dropped-post-reviews` alert, and a drop older than `DROPPED_POST_REVIEW_WINDOW_MS` under the pinned `now` raises none.
- The production `statusPayload` path and `renderStatus`/the TUI call `droppedPostReviewsAlert` in the last `teamAlerts` position; the alert and the feed use the one `DROPPED_POST_REVIEW_MARKER`, so the feed and the drain's warning cannot drift on what a drop is (pinned by the status test seeding the drain's exact warning text, and by the per-run `failed (…)` line raising none).
- The drain, `post-merge-risk`, `tumwater reviews` and every existing `teamAlerts` caller behave as before (the new parameter defaults to `null`); their existing tests pass unedited.
- `npm run test:gate` passes.
