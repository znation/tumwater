### `tokenValueProblem`'s valueless/empty-secret refusal and its flag-shaped-secret refusal are pinned in test/cli-args.test.ts, so a regression that would let a `--token <flag>` swallow the next argument as the dashboard secret — or accept an empty secret — is caught by the suite (planned 2026-11-15 by the plan role; `tokenValueProblem(args: string[], example: string): string | null` in src/cli/cli-args.ts is the one validation of a `--token <secret>` value, shared by `tumwater gui` (`cmdGui`, src/gui/gui-command.ts) and `tumwater start --gui` (`cmdStart`, src/cli/cli-start.ts) so the wording cannot drift between the two: it returns `null` when the token is absent or fine, the constant `TOKEN_VALUE_ERROR` when the `--token` value is empty or the flag is valueless, and a flag-looking-value message when the value starts with `--` — so `--token --all-interfaces` does not serve with the literal secret "--all-interfaces"; it builds on `flagValue` (already directly pinned in test/cli-args.test.ts) and is pure in-memory `args`-array logic — `indexOf` + one `startsWith("--")` — with no `fail`, no git, fs, shell or clock, so the pin is plain return-value assertions; `grep -rn tokenValueProblem test/` prints one hit, a `//` prose comment in test/cli-start-guards.test.ts, none a call, so no test drives the guard itself; docs/invariants.md binds no src/cli/cli-args.ts symbol, so no invariant edit is needed; independent of the other `## Planned` entry, which is test/cli-args.test.ts over a different exported function in the same src/cli/cli-args.ts — both add to the one shared named-import block, but the tests are disjoint and neither edits src — so feature may take either)

**Goal.** `tokenValueProblem` (src/cli/cli-args.ts, exported) is the single home for validating the `--token <secret>` value that opens the dashboard to the network. It is the inverse-complement of the `--grep`/`--type` text filters: a `--`-token in the secret slot is *dangerous* (it would be served as the literal secret) and is refused, while a single-dash secret is legitimate. It guards a real security behavior, is called from two independent commands, and yet no test drives it directly. Pin its four returns through the exported function.

**Approach.** One file, test-only, no src change and no invariant edit (docs/invariants.md binds no src/cli/cli-args.ts symbol): in test/cli-args.test.ts add `tokenValueProblem` to the existing named-import block from `../src/cli/cli-args.js` and pin the branches with plain `assert.strictEqual` / `assert.equal` against string literals — the function returns `null` or an error string and never calls `fail`, so no exit-capture helper is needed; each case is a single assert, no repo, worktree, fs, git or clock. Cases: *absent* — `tokenValueProblem(["--port", "80"], "tumwater gui")` is `null` (no `--token` in `args`). *valid* — `tokenValueProblem(["--token", "s3cret"], "tumwater gui")` is `null`. *empty* — `tokenValueProblem(["--token", ""], "tumwater gui")` is the constant `TOKEN_VALUE_ERROR`. *valueless* — `tokenValueProblem(["--token"], "tumwater gui")` is the same `TOKEN_VALUE_ERROR` (the flag is the final argument, so the next token is absent). *single-dash* — `tokenValueProblem(["--token", "-x"], "tumwater gui")` is `null` (a `-`-secret is a valid secret; only `--` reads as a flag). *flag-shaped* — `tokenValueProblem(["--token", "--all-interfaces"], "tumwater gui")` is the flag-looking message with `tumwater gui` in its example slot. *example interpolation* — `tokenValueProblem(["--token", "--port"], "tumwater start --gui")` is the same flag-looking message but with `tumwater start --gui` in the example slot, so the fix names whichever command the operator typed. No source file and no other test file change.

**Files touched.** test/cli-args.test.ts.

**Acceptance criteria.**
- Given no `--token` in `args`, `tokenValueProblem(["--port", "80"], "tumwater gui")` returns `null` — an absent secret is fine, not a problem.
- Given a non-empty, non-flag secret, `tokenValueProblem(["--token", "s3cret"], "tumwater gui")` returns `null`.
- Given an empty value, `tokenValueProblem(["--token", ""], "tumwater gui")` returns the exact line `--token requires a non-empty secret (e.g. `--token s3cret`)` — the constant `TOKEN_VALUE_ERROR`.
- Given a valueless `--token` (the flag is the final token), `tokenValueProblem(["--token"], "tumwater gui")` returns the same `TOKEN_VALUE_ERROR` line — a `--token` with no value is a problem, not a no-op.
- Given a single-dash value, `tokenValueProblem(["--token", "-x"], "tumwater gui")` returns `null` — a `-`-prefixed secret is accepted; only a `--`-token reads as a flag.
- Given a flag-shaped value, `tokenValueProblem(["--token", "--all-interfaces"], "tumwater gui")` returns `--token got the flag-looking value "--all-interfaces" instead of a secret — write the secret as its own argument (e.g. `tumwater gui --token s3cret --all-interfaces`)` — a `--`-token in the secret slot is refused, and the named flag is quoted back in the message.
- Given the same flag-shaped value under the other caller, `tokenValueProblem(["--token", "--port"], "tumwater start --gui")` returns the same flag-looking message with `tumwater start --gui` in the example slot — the copyable fix names the command the operator actually typed, so the two callers' wording stays correct and distinct.

### `parseDurationMs`'s composite-grammar acceptance and rejection are pinned in test/cli-args.test.ts, so a regression in the one home of the `<n><unit>` duration grammar — the parser the CLI `--for/--since` values, the TUI send-later input, and the GUI prompt defer all validate through — is caught by the suite (planned 2026-11-15 by the plan role; `parseDurationMs(raw: string): number | null` in src/text/duration.ts is the one home of the `<n><unit>` duration grammar — one or more components in strictly descending unit order d→h→m→s, each a plain-decimal count with no leading zero or zero count — and the one parser `parseDurationFlag` (src/cli/cli-args.ts) delegates its malformed-value check to, the TUI send-later input (src/ui/tui/tui-input.ts) reads through, and the GUI prompt defer (src/gui/gui-prompt-commands.ts) validates with, so its acceptance and every surface's echoed `durationLabel` form cannot drift; its sibling `durationLabel` is already pinned in test/cli-args.test.ts, so this pin extends that file's existing `import { durationLabel } from "../src/text/duration.js"` line by adding `parseDurationMs`; `grep -rn parseDurationMs test/` prints nothing, so no test drives the grammar itself — every caller's test hits it only through a wrapper or an e2e path; docs/invariants.md's "Local time" section names the grammar in prose but its `**Binds.**`/`**Pinned by.**` lines name only `src/text/datetime.ts` symbols, so no invariant edit is needed; independent of the other `## Planned` entry, which pins a different exported function in a different src module (src/cli/cli-args.ts) through test/cli-args.test.ts — this one pins src/text/duration.ts, and the two add disjoint named imports — so feature may take either)

**Goal.** `parseDurationMs` (src/text/duration.ts, exported) is the single home of the `<n><unit>` duration grammar: it accepts `45s`, `90m`, `1h30m`, `1h30m15s`, `2d` (and composites in strictly descending d→h→m→s order) and returns the total in milliseconds, and it returns `null` for every other spelling — a zero count (`0s`, `0h30m`), a gap or any non-numeric junk between or at the edges, an out-of-order or repeated unit, a value past `Number`'s range that would overflow to `Infinity`, a unit-less number, a bare unit, or the empty string. It is the grammar the CLI duration flags, the TUI send-later input, and the GUI prompt defer all validate through, and it is a pure in-memory text→ms read that returns `number | null` and never calls `fail`, yet no test drives it directly — only its callers' tests reach it, and none pins the grammar's own accept/reject boundary. Pin that boundary through the exported function.

**Approach.** One file, test-only, no src change and no invariant edit (docs/invariants.md's `**Binds.**`/`**Pinned by.**` lines name no `src/text/duration.ts` symbol; the grammar appears only in the section's prose): in test/cli-args.test.ts extend the existing `import { durationLabel } from "../src/text/duration.js"` line to also import `parseDurationMs`, then pin the grammar with plain `assert.equal` against the numbers and `null` it actually returns — it returns `number | null`, never `fail`, so no exit-capture helper is needed; each case is a single assert, no repo, worktree, fs, git or clock. Valid cases assert the exact millisecond total: `45s`→45000, `90m`→5400000, `30m`→1800000, `1h30m`→5400000, `1h30m15s`→5415000, `2d`→172800000, `1d12h`→129600000. Reject cases assert `null`: a zero count (`0s`, `0h30m`), a gap (`"1h 30m"`), leading or trailing whitespace (`" 45s"`, `"45s "`), trailing junk after a component (`"1s0"`), an out-of-order unit (`"30m1h"`), a repeated unit (`"1h30m1h"`, `"1h1h"`), a digit run past `Number`'s range (a 400-`9` string + `"s"`), and the no-component forms (`""`, `"abc"`, `"1"`, `"s"`). No source file and no other test file change.

**Files touched.** test/cli-args.test.ts.

**Acceptance criteria.**
- Given a valid single-unit duration, `parseDurationMs("45s")` returns `45000`, `parseDurationMs("90m")` returns `5400000`, and `parseDurationMs("30m")` returns `1800000` — the component's count times its unit's milliseconds.
- Given a valid composite in strictly descending order, `parseDurationMs("1h30m")` returns `5400000`, `parseDurationMs("1h30m15s")` returns `5415000`, `parseDurationMs("2d")` returns `172800000`, and `parseDurationMs("1d12h")` returns `129600000` — the components' totals summed, largest unit first.
- Given a zero count, `parseDurationMs("0s")` returns `null` and `parseDurationMs("0h30m")` returns `null` — a `0` count is not a valid component (write `30m`), even when a nonzero component follows.
- Given a gap, `parseDurationMs("1h 30m")` returns `null` — whitespace between components is not a valid duration.
- Given leading or trailing whitespace, `parseDurationMs(" 45s")` returns `null` and `parseDurationMs("45s ")` returns `null` — the spelling must fill the whole string, not just contain a valid duration.
- Given trailing non-component junk, `parseDurationMs("1s0")` returns `null` — a bare digit with no unit after a component is not a duration.
- Given an out-of-order unit, `parseDurationMs("30m1h")` returns `null` — units must descend d→h→m→s, so a smaller unit before a larger one is refused.
- Given a repeated unit, `parseDurationMs("1h30m1h")` returns `null` and `parseDurationMs("1h1h")` returns `null` — a unit never reappears in one spelling.
- Given a digit run past `Number`'s range, `parseDurationMs` of a 400-character run of `9` followed by `"s"` returns `null` — an overflowing sum is refused, not returned as `Infinity`.
- Given no valid component at all, `parseDurationMs("")` returns `null`, `parseDurationMs("abc")` returns `null`, `parseDurationMs("1")` returns `null` (a number without a unit), and `parseDurationMs("s")` returns `null` (a unit without a number).
- Every pre-existing test in test/cli-args.test.ts passes unmodified; no source file and no other test file change; the project's declared check is green.
