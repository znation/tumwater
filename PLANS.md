### Dashboard window end on the last two windowed endpoints: `GET /api/failures?sinceMs=&untilMs=` and `GET /api/logs?sinceMs=&untilMs=` serve a bounded past window that ends before now, the twins of `report --failures --since --until` and `logs --since --until` (planned 2026-10-20 by the plan role; independent of every eligible plan. "TUI History trail transcript search" touches only TUI files, none of these. Touches src/gui/gui-args.ts (doc comment only) + src/gui/gui-endpoints.ts + test/gui-endpoints.test.ts)

**Goal.** "Dashboard API window end" (PLANS-DONE.md) gave `/api/report` and `/api/history` an `untilMs` bound through `untilMsQuery` (src/gui/gui-args.ts). It left `/api/failures` alone until "Failure digest window" (PLANS-DONE.md) landed. That plan has now landed: `collectFailureReportSince(root, sinceMs, role?, untilMs?)` (src/failure/failure-data.ts) takes the bound, and `renderFailureMarkdown` prints the bounded `boundedWindowLine` header. `/api/logs?sinceMs=` (PLANS-DONE.md "Dashboard event-log window") said its `untilMs` would be a later plan. The CLI already bounds it: `cmdLogs` (src/cli/log-commands.ts) filters `readEventsSince`'s events with `e.ts < cutoff + ms - untilMs`. Today `handleFailures` and `handleLogs` (src/gui/gui-endpoints.ts) never read `untilMs`. A script asking `/api/failures?sinceMs=345600000&untilMs=259200000` or `/api/logs?sinceMs=…&untilMs=…` silently gets the whole window up to now. Fixing both endpoints is one theme: the same helper applied to the two windowed endpoints still missing it. After this, `grep -n untilMsQuery src/gui/gui-endpoints.ts` shows a call in every handler that calls `sinceMsQuery` or `reportScope`.

**Approach.**
1. `handleFailures`: right after `reportScope`, add `const untilMs = untilMsQuery(q, res, scope.sinceMs); if (untilMs === null) return;`. This is the same two lines `handleReport` uses. Then pass `untilMs` as the 4th argument of `collectFailureReportSince`. The days shape has no `sinceMs`, so `?days=7&untilMs=…` becomes the helper's "requires sinceMs" 400 instead of being ignored. Add `[&untilMs=<ms>]` to the doc comment's sinceMs shape.
2. `handleLogs`, in the `sinceMs` branch: after `sinceMsQuery`, add `const untilMs = untilMsQuery(q, res, sinceMs); if (untilMs === null) return;`. Destructure `cutoff` from `readEventsSince` as well. When `untilMs` is defined, keep only events with `e.ts < cutoff + sinceMs - untilMs` before `keep`, the CLI's exact edge. `covered` and `note` are unchanged, because coverage is about the window's far edge either way, as in handleHistory. In the count branch, call `if (untilMsQuery(q, res, undefined) === null) return;` before the `n` parse, so `?n=5&untilMs=…` and a bare `?untilMs=…` are 400s, the handleHistory count-branch rule. Update the handler's doc comment to show `sinceMs=S[&untilMs=U]`.
3. src/gui/gui-args.ts `untilMsQuery` doc comment: change "the report and history endpoints'" to name all four endpoints (report, failures, history, logs). The code does not change.
4. No dashboard client change. gui-client-feed.ts keeps calling `?n=`, and the Failures tab keeps its trailing windows. A past-window UI is a separate later plan, and it is a design choice that plan must settle.

**Tests** (test/gui-endpoints.test.ts, using the existing `serveFailures`/`serveLogs` helpers and `writeEvents`, placed beside "handleFailures serves the windowed digest as { markdown } when ?sinceMs is set" and "handleLogs ?sinceMs serves the trailing window's events, composing grep and role"):
- New test "handleFailures' ?untilMs ends the since window that long ago". Seed a `run_end` `result: "error"` event for `bugfix` at now−30 min (`error: "recent boom"`) and one for `feature` at now−3 h (`error: "old boom"`). `?sinceMs=14400000&untilMs=3600000` → 200, and `markdown` matches `/window: 4h to 1h ago/` and `/feature/` and does not match `/bugfix/`. The digest table names each role that ran (the existing sinceMs test asserts `/bugfix/`), and bugfix's run lies in neither the window nor its prior window `[now − 7 h, now − 4 h)`. Compare shapes, not bytes: each call reads its own `Date.now()`. 400 cases, each with the error matched: `?untilMs=3600000` and `?days=7&untilMs=3600000` → /requires sinceMs/; `?sinceMs=3600000&untilMs=3600000` → /must be shorter than sinceMs/; `?sinceMs=3600000&untilMs=abc` → /untilMs/.
- New test "handleLogs' ?untilMs drops the window's newer events". Seed the same three events as the existing sinceMs test (now−3 h, now−30 min, now−20 min) plus one at now−5 min. `?sinceMs=3600000&untilMs=600000` → `events` ts are `[now − 30 min, now − 20 min]`, with `covered: true` and `note: ""`. `&role=bugfix` added → `[now − 20 min]`. 400s: `?untilMs=600000`, `?n=5&untilMs=600000` → /requires sinceMs/; `?sinceMs=600000&untilMs=600000` → /must be shorter than sinceMs/.

**Acceptance criteria.**
- `/api/failures?sinceMs=S&untilMs=U` (U < S) serves `{ markdown: renderFailureMarkdown(collectFailureReportSince(root, S, roles, U)) }`, with the bounded header and only the failures in `[now − S, now − U)`.
- `/api/logs?sinceMs=S&untilMs=U` serves `{ events, covered, note }` holding only the window's events older than `now − U`, and `grep` and `role` still compose.

- Requests without `untilMs` answer as before: the existing handleFailures and handleLogs tests pass unchanged.

### Dashboard History past windows: "◀ Earlier" and "Later ▶" buttons step the History view's window back one window length at a time through `/api/history?sinceMs=&untilMs=` (planned 2026-10-20 by the plan role; independent of every eligible plan. "TUI History trail transcript search" touches only TUI files and docs/cli.md, and "Dashboard window end on the last two windowed endpoints" touches only src/gui/gui-args.ts, src/gui/gui-endpoints.ts and test/gui-endpoints.test.ts)

**Goal.** "Dashboard API window end" (PLANS-DONE.md) taught `/api/history` to serve a bounded past window (`sinceMs` plus `untilMs`, both validated by `untilMsQuery`, src/gui/gui-args.ts), but no dashboard control uses it. The History toolbar's `#histcount` select (src/ui/gui/gui-client-history.ts, `HIST_WINDOWS`) offers only trailing windows: "the last day" can never become "yesterday". This plan adds two step buttons next to that select. They shift the chosen window back or forward by its own length, so `1d` stepped back once asks for `?sinceMs=172800000&untilMs=86400000`, the browser twin of `tumwater history --since 2d --until 1d`. This plan changes only the client. The endpoint already serves the shape.

**Approach** (all in src/ui/gui/gui-client-history.ts):
1. View state: add `let histStep = 0;` beside `histModel`. It counts how many window lengths back the window ends. It is view state and is not persisted, like `histModel`, so a reload returns to the trailing window.
2. Inside the `history-table:start`/`:end` region, add these pure helpers next to `HIST_WINDOWS`:
   - `const HIST_MAX_MS = 604_800_000;` — the server's `LOGS_SINCE_MAX_MS` (src/events/event-window.ts), the cap `/api/history`'s `sinceMs` rides. Add a comment saying the two must agree. A test pins it.
   - `histSpan(ms)`: `"1 day"`/`"N days"` when `ms` is a whole number of days (`ms % 86_400_000 === 0`), otherwise `"1 hour"`/`"N hours"`. Every window and step length is a whole number of hours.
   - `histCanStepEarlier(sinceKey, step)`: true exactly when `HIST_WINDOWS[sinceKey]` exists and `(step + 2) * w[0] <= HIST_MAX_MS`. That means the next earlier window's `sinceMs` is still under the cap. So `7d` never steps, `1d` steps up to 6 times, and `1h` up to 167.
   - `histWindowPhrase(sinceKey, step)`: `HIST_WINDOWS[sinceKey][1]` when `step` is 0 (for example "the last day"). Otherwise `"between " + histSpan((step + 1) * w[0]) + " and " + histSpan(step * w[0]) + " ago"`, which mirrors cmdLogs' `between X and Y ago` wording (src/cli/log-commands.ts). Returns `""` for an unknown key.
   - `historyQuery(count, role, sinceKey, grep, model, step)`: when a window is set and `step > 0`, the window part becomes `"/api/history?sinceMs=" + (step + 1) * w[0] + "&untilMs=" + step * w[0]`. Otherwise the URL is exactly what it is today. Role, grep, model and `&summary=1` follow in their current order.
   - `historyStepHtml(sinceKey, step)`: `""` when `step` is 0 or the key is unknown. Otherwise `"<p class='muted window-note'>Showing runs " + histWindowPhrase(sinceKey, step) + ".</p>"`.
3. In `historyTableHtml`, add a trailing `step` parameter. The empty-window branch then says `"No runs " + (step ? histWindowPhrase(sinceKey, step) : "in " + w[1])`, so step 0 keeps the current text unchanged.
4. Toolbar (`buildHistoryView`): right after the `#histcount` label, add `<span id='histstep' style='display:none'>` holding `<button type='button' class='btn btn-sm' id='histearlier'>◀ Earlier</button>` and `<button type='button' class='btn btn-sm' id='histlater'>Later ▶</button>`. The click handlers do `histStep += 1` (earlier) or `histStep = Math.max(0, histStep - 1)` (later), then `fetchHistory()`. The `#histcount` change handler resets `histStep = 0` before it fetches. Role, grep, model, refresh and the status-poll refetch keep the step.
5. `fetchHistory` passes `histStep` to `historyQuery`. `renderHistory` passes it to `historyTableHtml` and paints `historyNoteHtml(histNote) + historyStepHtml(histSinceKey, histStep) + bodyHtml`. It also sets `$("histstep").style.display` to `""` exactly when `HIST_WINDOWS[histSinceKey]` exists, `$("histearlier").disabled = !histCanStepEarlier(histSinceKey, histStep)` and `$("histlater").disabled = histStep === 0`.
6. docs/how-it-works.md: in the paragraph that starts "The dashboard's History drill-down adds…", add one sentence before it: on a trailing window, the dashboard History toolbar's ◀ Earlier / Later ▶ buttons step that window back by its own length, through `/api/history?sinceMs=&untilMs=`, the twin of `history --since --until`. Extend the module's top doc comment the same way.

**Tests** (test/gui-client-history.test.ts, using `clientScope(HISTORY_REGIONS, …)` and `iconStub` as the neighbouring tests do):
- "historyQuery steps a window back by its own length with untilMs": `historyQuery(50, "", "1d", "", "", 1)` → `"/api/history?sinceMs=172800000&untilMs=86400000&summary=1"`. `historyQuery(50, "clean", "1h", "x", "", 2)` → `"/api/history?sinceMs=10800000&untilMs=7200000&role=clean&grep=x&summary=1"`. Step 0 and step `undefined` with `"1d"` → `"/api/history?sinceMs=86400000&summary=1"`. `historyQuery(50, "", "", "", "", 3)` → `"/api/history?n=50&summary=1"` (no window, so the step is ignored).
- "histCanStepEarlier stops at the server's sinceMs cap": import `LOGS_SINCE_MAX_MS` from `../src/events/event-window.js` and assert it equals the scoped `HIST_MAX_MS`. Then `("7d", 0)` → false, `("1d", 5)` → true, `("1d", 6)` → false, `("6h", 26)` → true, `("6h", 27)` → false, `("", 0)` → false.
- "histWindowPhrase and historyStepHtml name a stepped window": `("1d", 0)` → `"the last day"`, `("1d", 1)` → `"between 2 days and 1 day ago"`, `("6h", 1)` → `"between 12 hours and 6 hours ago"`, `("6h", 4)` → `"between 30 hours and 1 day ago"` (30 h is not a whole day, 24 h is). `historyStepHtml("1d", 0)` → `""`. `historyStepHtml("1d", 1)` contains `Showing runs between 2 days and 1 day ago.`
- "historyTableHtml's empty stepped window names its bounds": `historyTableHtml([], "all", new Set(), "", "1d", "", 1)` matches `/No runs between 2 days and 1 day ago/`. The same call with step 0 still matches `/No runs in the last day/`.
- Extend the toolbar test "the History toolbar carries the four trailing-window options in the #histcount select" (or add a sibling built the same way) so it asserts that the built toolbar HTML contains `id='histearlier'` and `id='histlater'` inside `id='histstep'`.

**Acceptance criteria.**
- With a trailing window chosen, the History toolbar shows ◀ Earlier / Later ▶. Earlier refetches `/api/history?sinceMs=(k+1)·len&untilMs=k·len`. Later steps back toward the trailing window and is disabled at step 0. Earlier is disabled once the next step's `sinceMs` would pass the server's 7-day cap. With a run count chosen, the buttons are hidden.
- Changing the window select resets the step to 0. Role, search, model chip, Refresh and the status-poll refetch keep the step.
- A stepped window shows "Showing runs between X and Y ago." above the table, and its empty state names the same bounds. Step 0 renders exactly as today, and the existing gui-client-history tests pass unchanged.
- No server file changes. `npm run test:gate` passes.
