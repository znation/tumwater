**Goal.** `tumwater prompt --list --grep <text>` keeps only the queued prompts whose text contains the text, case-insensitively, each under its unfiltered per-role number (`cmdPrompt`'s list mode, src/inbox/prompt-commands.ts, which filters `row.text.toLowerCase().includes(needle)` inline). The TUI's Inbox pane (`createQueuedPane`, src/ui/tui/tui-pane-queued.ts, view `roleIds.length + 6`) lists every queued prompt with no way to narrow it. The shared `/` search editor (`createSearchEditor`, src/ui/tui/tui-editor-search.ts) already serves Activity, History, Backlog and a role's Transcript. Add the Inbox pane as its fifth target, so an operator with a long queue can find the prompt to cancel (Ctrl+X), edit (Ctrl+E) or move to the top (Ctrl+V).

**Approach.**
1. src/inbox/inbox.ts: add `export function queuedRowsMatching(rows: readonly QueuedListRow[], grep: string | null): QueuedListRow[]`. `null` returns a copy of `rows`; otherwise it keeps the rows whose `text.toLowerCase()` includes `grep.toLowerCase()`. In prompt-commands.ts, replace the inline `needle` filter with `queuedRowsMatching(scoped, parsed.grep ?? null)`. Output is unchanged.
2. tui-pane-queued.ts: add `let queuedGrep: string | null = null;`. `refreshQueued` builds `queuedRows` as `queuedRowsMatching(queuedListRows(...), queuedGrep)`, so `renderQueuedList` prints each kept row under its own `position` (its unfiltered per-role number). Ctrl+X, Ctrl+V and the Ctrl+E editor (tui-editor-queued.ts reads `ctx.queuedRows`) keep addressing the right role and position with no change. Add `applySearch(pattern)`: set `queuedGrep`, set `selectedQueued = null`, call `refreshQueued()`, and request a render. `state()` also returns `queuedGrep`. Add `applySearch` to the `satisfies` type. `reset()` stays as is, so the pattern persists across Ctrl+T cycles, as `backlogGrep` does.
3. Plumbing, mirroring `backlogGrep`/`applyBacklogSearch` at each site: `queuedGrep` in `TuiEditorCtx` (tui-editor-ctx.ts), in tui-panes.ts `editorCtx()` and its state object (`que.queuedGrep`), and in the state type in tui-keys.ts. `applyQueuedSearch` goes in the session deps interface and its wiring (tui-editor-session.ts), in the tui-editors.ts deps doc, in tui-panes.ts's return (`queued.applySearch`), and in tui-keys.ts's deps wiring.
4. tui-editor-search.ts: add `ctx.view === ctx.roleIds.length + 6` to the `/` open guard. Add `"queued"` to the `searchFor` union and pick it on that view. Add `queued: ctx.queuedGrep` to the pre-fill map and `queued: "inbox"` to the noun map. On Enter, call `session.applyQueuedSearch(applied)`. Update the comments that list the targets.
5. Render: in tui-frame.ts the `queued` `TuiView` becomes `{ kind: "queued"; grep?: string | null }`. tui.tsx passes `grep: s.queuedGrep`. The queued footer in `hintLine` adds `["/", view.grep ? `search: ${view.grep}` : "search"]` after Ctrl+X. In tui-pane.ts's `queued` branch, list mode with `pane.grep` set prepends a `search: "<grep>"` line. When no row matches, the body is that line plus `(no queued prompt matches "<grep>")`, so the operator can see why the pane is empty. With no grep and in selection mode, rendering is unchanged.
6. Docs: in docs/cli.md, the `/` row of the TUI keys table adds Inbox to its views column, plus the clause "on Inbox, keep only the queued prompts containing the text, each under its unfiltered number, like `prompt --list --grep`". In docs/how-it-works.md, the Inbox pane paragraph gets one sentence on the `/` search.

### `GET /api/run?last=1` with no `role` serves the newest completed run of any role, and `result`/`model` narrow it the same way: the dashboard API twin of bare `tumwater history --last` (planned 2026-10-20 by the plan role; independent of every eligible plan: none of them edits `handleRun` or src/run/run-detail.ts. Touches src/run/run-detail.ts src/gui/gui-endpoints.ts docs/how-it-works.md test/gui-endpoints.test.ts test/gui-server-api.test.ts)

**Goal.** `tumwater history --last` with no role opens the newest completed run of any role, and `--result`/`--model` narrow it (PLANS-DONE.md "`tumwater history --last` with no role"). `cmdRunDetail` (src/run/run-detail.ts) resolves it with `newestRunRow(root, null, classes, models)` and takes the role from the row. `GET /api/run` (`handleRun`, src/gui/gui-endpoints.ts) cannot do this. Its first step is `rejectBadRole(root, res, role)`, so `?last=1` with no role is a 400 "role required". A script asking "what was the newest failed run, whoever ran it" has to fetch `/api/history` and pick a row itself. This plan lets `last` stand without a role. It resolves the run through the same `newestRunRow`, so the CLI and the endpoint cannot pick different runs. It is API-only. A dashboard button that uses it is a separate, later plan.

**Approach.**
1. src/run/run-detail.ts: export `newestRunRow` (today it is module-private). Do not change its body. Extend its doc comment's last sentence with: "Also GET /api/run?last=1 with no role."
2. src/gui/gui-endpoints.ts, `handleRun`:
   - Add `newestRunRow` to the existing `../run/run-detail.js` import.
   - Change the role check to `const bareLast = role === null && q.get("last") !== null; if (!bareLast && rejectBadRole(root, res, role)) return;`. A missing role without `last` is still the shared 400. A present role, including an empty one, is still validated as today.
   - Make `role` a `let` binding typed `string | null`. In the `last` branch, replace the `newestRunNumber` call with `const row = newestRunRow(root, role, classFilter, modelFilter);`, then `if (row !== null) role = row.role; run = row?.run ?? null;`. The 404 stays `runNotFoundLastMessage(role, classFilter, modelFilter)`. With no role, `role` is still `null` there, which gives the "any role" wording `cmdRunDetail` prints.
   - After the `last`/numbered branches, `role` is a string, so the existing `role as string` casts stay valid. Remove `newestRunNumber` from the import if nothing else in the file uses it. Check with `grep -n newestRunNumber src/gui/gui-endpoints.ts`. Keep the export in run-detail.ts if any other file still imports it. Check with `grep -rn newestRunNumber src test`, and if nothing uses it, delete it.
   - Doc comment: append to the `last` paragraph: "With no `role`, `last` opens the newest completed run of any role (newestRunRow with a null role, the run bare `tumwater history --last` opens), and the payload's `role` is that run's; `result`/`model` narrow it the same way, and a miss is a 404 worded for any role."
3. docs/how-it-works.md: after the sentence ending "the run `tumwater history <role> --last [--result] [--model]` opens (`newestRunNumber`, shared)." add: "Without `role`, `GET /api/run?last=1` serves the newest completed run of any role, the run bare `tumwater history --last` opens, with the same `result`/`model` narrowing." If step 2 deleted `newestRunNumber`, change that parenthetical to `(newestRunRow, shared)`. `grep -n 'api/run' docs/invariants.md` printed nothing when this was planned, so the plan claims no invariant ID.

**Acceptance criteria.**

  - `?last=1&result=problems` answers `role` "clean", `run` 4.

  - `?last=1&model=m-b&result=merged` answers 404 with error equal to `runNotFoundLastMessage(null, ["changes"], ["m-b"])`.
  - `?last=1&result=bogus` is a 400 matching `/result must be one of/`.
  - `?last=1&run=3` is a 400.
