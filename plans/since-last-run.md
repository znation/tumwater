# Since your last run

Planned 2026-11-12 by the operator. One PLANS.md series: "Since last run, part 1/1".

## Why

Every authoring run starts a fresh agent session (`runAuthoringPi`, src/runner/runner-pi.ts).
That is deliberate, and this plan keeps it. A run never inherits a full context window, a
stale view of files, or prompt rules worn down by compaction.

The cost is orientation. The 2026-10-17 measurement over 1,213 runs found a median of 22 tool
calls and 44k tokens of context before a run's first edit. Doc reads (PLANS/BUGS/README) were
about 27% of tool output and code exploration about 48%. Much of that rediscovers what changed
on main since the role last looked.

We considered keeping one long-running conversation per role instead. The research argues
against it for this team:

- *No Reset, Emergent Behaviors* (NeurIPS 2026) ran agents through task sequences in one
  persistent session (GAIA2, SWE-Bench Pro). Frontier models held their single-task baselines
  but DeepSeek v4 Pro lost 5.9 points, and pass^K consistency fell for every model. The gain
  was efficiency: up to 60% fewer output tokens and less repeated exploration.
- *The Compaction Cliff* (arXiv 2608.22752) measured `/compact` keeping 53% of safety rules
  after one round and 10% after five. Tumwater's worst incidents were prompt-rule violations.
- Anthropic's long-running harness (2025-11) starts each session fresh and orients from a
  progress file, the git log and a feature list. Tumwater already has that shape.
- Main moves between a role's runs, so carried context would hold stale file contents.
  Runs are minutes to hours apart, beyond prompt-cache lifetimes, so the carried history
  would be re-prefilled at full cost each time.

This plan takes the efficiency gain persistence offers without carrying context: the harness
tells each run, from git, what changed since that role's last run.

## Design

A new prompt block, rendered by the harness from git, right after the role-notes block.

**Anchor.** `RunnerState.lastMainHead`. run-finalize.ts sets it to main's head at the end of
every run, and nothing else writes it. It is per runner, so `feature-2` and `feature` each have
their own.

**Content.** Read with one git call:
`git log --no-merges --format=<sha subject> --name-only <lastMainHead>..<main>`.

1. One header line: how long ago the role's last run ended (`lastRunEndedAt`), its result and
   summary (`lastResult`, `lastSummary`), and how many commits landed on main since.
2. Commit subjects, newest first, capped at 30, then "+N older". A subject starting
   `tumwater(<this role>):` is marked as this role's own merge.
3. Changed files, ranked by how many of those commits touched them, capped at 20, then
   "+N more".
4. For an assigned run (`assigned`), list first any changed file that the claimed entry's
   "touches" clause or **Files touched.** line names. These are the files most likely to have
   moved under the plan.

**Framing.** The block says it is generated by tumwater from git and is current. That
contrasts it with role notes, which the prompt labels unverified. One sentence tells the run
to use the block to skip re-reading what it already knows, and to re-read any file it
plans to edit that appears in the list.

**Omit the block when:** `lastMainHead` is empty (first run); `lastMainHead` is not an ancestor
of main (`git merge-base --is-ancestor` fails); the git call fails (never fail a run over
this); or the role is the director (it has no recurring search). When main has not moved, a
single line says so. That is useful on its own: nothing the role read last time has changed.

**Size.** Hard cap of 4,000 characters (about 1k tokens), truncating the file list first and
then the subjects. A run's first prompt is about 5k tokens, so the block stays well under a
quarter of it.

**Cost.** One git spawn per run, in run-prompt.ts beside the other collect* calls. No new
config key: the block either helps or is removed. Process creation is the host's bottleneck,
so do not add per-commit or per-file git calls.

## How we will know it worked

Compare 7 days before against 7 days after the merge, same backend and model mix, measured the
2026-10-17 way from session files under `.tumwater/sessions/<role>/`:

- tool calls before the first edit (median; was 22);
- context tokens at the first edit (median; was 44k) and peak context per run;
- input tokens and cost per run;
- `no_change` rate and review rejection rate, which must not rise.

Keep the block if orientation drops without a rise in rejections. Remove it if nothing moves.
The lab replay method in the prompt-lab memory (replay real runs from their base commits, n=3
per arm) is the fallback when live data is confounded by host load, as it was on 2026-10-19.

## Not in this plan

- Long-running per-role conversations (see "Why").
- Typed role notes, with lessons kept verbatim and an episode log that decays (ACE, Knowledge
  Triage). A separate plan once this one is measured.
- Rubric-triggered compaction or a handoff rollover inside a run (SelfCompact).
- Resume and revision runs. Their prompts come from prompt-followup.ts. Whether they should
  carry the block is a question for after the measurement.
