## Open

### A policy scan's failure is excused by test name alone, so a new offender in an already-failing scan merges as main's known failure (found by the reviewer role 2026-11-05)

- **Symptom:** when main is red on one of the repo-wide policy scans, a change that adds its own offender makes the same aggregate test fail (e.g. `every comment line in src/ and test/ fits in 100 columns…`), so the gate's failure has the same name as main's known failure. `onlyKnownMainFailures` (src/baseline/main-watch.ts:146) checks every failing test name against `knownMainFailures(root)` and, when all match, returns them as main's; the change's new offender is excused and merges, leaving main red on a line its own change introduced. Previously the scans were rarely selected at all (BUGS-FIXED.md 2026-11-05), which hid this gap; now that a budgeted gate force-runs them, it is the remaining half.
- **Reproduce:** with main red on `test/comment-width.test.ts` (one wide comment in file A), append a 125-column `//` comment to a different src file and run the gate on that change. The scan fails on the new line too, but the failure lists the same one test name, so `onlyKnownMainFailures` returns it as main's known failure and the gate does not blame the change.
- **Cause:** the excuse compares test names, not offenders. The four policy scans report one aggregate test regardless of which file or name offends, so a name match cannot distinguish main's offender from the change's.
- **Cost / why fileable:** the change's new offender lands on a red main, keeping main red and hiding which commit added it — the same failure mode the 2026-11-05 force-run fix addressed. The fix sketch: compare offenders, not test names — a scan failure that lists a line or name main's own failure does not list belongs to the change.

### Tier-1 role waiters have no age bound and no visible wait, so maintenance roles starve behind work runs for half a day (the unlanded remainder of the 2026-11-05 ci-heal entry, found by operator session 2026-11-05 from the team's event log)

- **Symptom:** the ci-heal entry's fix (BUGS-FIXED.md 2026-11-05) admits a red-main heal run at VERIFY_TIER, but every other tier-1 role still waits behind work runners. In the same incident, coverage and selfcheck parked for a permit at 10:01 on 2026-11-04 and were admitted only at 22:19 and 22:46 (`provider_wait` `waitedMs` 44,273,467 and 45,923,005), while clean, dedupe, organize, improve, steward, readme, perf, qa, security and robustness all read `due` and last started a run between 00:29 and 08:31 that day. `provider_wait` is logged only when a wait ends, so a role still parked leaves no event at all and the dashboard row shows only `due`.
- **Cause:** `roleTier` (src/roles/roles.ts) puts feature, bugfix and plan at tier 0 and every other role at tier 1, and the semaphore admits strictly by tier (`enqueue`, src/concurrency/semaphore.ts) with the work reserve also withholding permits from tier 1. With more busy work runners than permits, one work waiter is always parked, so a tier-1 waiter can be passed over indefinitely. The ci-heal fix narrows this for one prompt kind; it does not bound any other tier-1 wait and does not surface a wait in progress.
- **Expected / fix sketch:** bound how long any tier-1 waiter can be passed over (for example, promote a waiter parked longer than two hours ahead of new tier-0 arrivals), and show a wait in progress on the role row and in doctor (for example "waiting for a run slot 14h"), so starvation is visible before it costs a day.

### A post-merge reviewer's fix that conflicts with main can never merge: the resolver's resolution is always discarded, and each retry re-runs the whole review (found by operator session 2026-11-05 from the team's event log)

- **Symptom:** `28f1e703` (feature-4, "Remote CI part 2/3", merged 2026-11-04 17:57) was post-merge reviewed at 19:44. The reviewer found a real gap: the `remote CI` doctor row was not omitted when the ci role is disabled. Its fix (`37d2a4f0b`) conflicted with main in docs/how-it-works.md (lines 286–323, where main had since added the remote-CI badge paragraph). A resolver run (`.tumwater/sessions/feature-4/2026-11-05T03-56-06-740Z_…`) merged both paragraphs in 22 s, yet the landing returned `merge_conflict` ("the post-merge fix of 28f1e703 could not merge (merge_conflict); it stays queued for the next poll", 19:56). At 23:45 a second full review of the same commit wrote a new fix. It hit the same conflict, and its resolver (`2026-11-05T07-57-50-869Z_…`) was discarded again at 23:58. The entry now reads `failures: 2`, `lastFailure: "fix did not merge: merge_conflict"`. The next failure drops the review and files it here (`fileDroppedReview`, src/merge/merge-post-review-drain.ts:290), and the reviewer's fix is lost (it survives only at `refs/tumwater/review-fix/28f1e703`).
- **Cost:** each attempt spends one reviewer run plus one resolver run on a MERGE_TIER permit, which is admitted ahead of role runs. All of it is thrown away.
- **Reproduce:** queue a post-merge review of commit C, then merge a change to main that edits the same lines of a file the reviewer's fix will touch. The fix is authored on C, so its landing conflicts. Any resolution replaces main's edit, so it diverges, and the entry is retried and finally dropped.
- **Cause:** `mergeReviewerFix` passes `recheckResolved: async () => ({ verdict: "retry" })` (src/merge/merge-post-review-drain.ts:264). In `mergeToMain` (src/merge/merge-to-main.ts:106–109), a resolution whose diff leaves the fix's own lines (`resolvedDiffDiverges`, src/merge/merge-diff.ts) goes to `recheckResolved`, and `retry` returns `merge_conflict`. A resolution of lines both sides edited always leaves them: it replaces main's new wording, which the fix's own diff never deleted. The failed landing leaves the entry with neither `fixed` nor `rejected`, so `unreviewed` is true and the next drain starts a fresh review of C. That review authors its fix on C again, so it conflicts again.
- **Expected / fix sketch:** never run a resolver whose result is always discarded. Either judge the resolved tree, as `mergeApprovedChange`'s `recheckResolved` re-reviews a resolved conflict (src/merge/merge-core.ts:423), or, on a conflict, retry by rebasing the stored fix ref onto main's tip, or have the retry's review author its fix on main's tip rather than on C.
