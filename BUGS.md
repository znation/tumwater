The detector needed no code change.

- The bugfix "with the director" skip is re-derived from prose every run; no machine hold exists (filed 2026-11-11 from ~/Desktop/tumwater-no-progress-bugs.md). — fixed 2026-11-12 by the bugfix role

**Symptom.** The bugfix charter (src/roles/role-catalog.ts, bugfix `find` step 2, lines ~119–127) tells the model to skip an entry "whose newest Progress note names a director handoff" and that carries no `**Needs review … by director: …**` note. Nothing in the backlog index marks that state, so every run re-derives it from prose. One model (`codex/gpt-6-luna`) misread repeatedly: 25 consecutive `no_change` runs (00:00–01:05) while the director had already answered, `yieldMultiplier: 8`; the bug was fixed only when a later run on another model took the entry.

**Required behavior.** A machine hold at handoff time: write a hold line (e.g. `**Director handoff <date>**`) beside the request file, have the index mark the entry `[blocked: with the director]`, and clear it when the director resolves — the request-file lifecycle (src/inbox/director-request.ts) already knows when the director ran (the request file's deletion marks that event), so the index can derive the hold from that state instead of asking the model to interpret the newest Progress note.

**Suspected cause.** The handoff state exists only in prose; the entry stays eligible, so a model that misreads the note idles instead of being held.

**Fixed.** The required machine hold is in place and regression-tested: at handoff the bugfix charter (src/roles/role-catalog.ts, bugfix `find` step 2) tells the model to write a `**Director handoff <YYYY-MM-DD>**` line beside the request file, and that marker is what the index now reads. `withDirectorHold` (src/roles/role-guidance.ts) holds an entry that carries the marker with no `**Progress …**` or `**Needs review … by director: …**` line; `entryHoldAgainst` (src/backlog/backlog-eligibility.ts) maps that to the `with-director` hold and the backlog index marks the entry `[blocked: with the director]`, so a model that would misread the prose Progress note no longer keeps an answered entry eligible — the 25-run `no_change` idle it describes is gone. The hold releases the moment the director appends its resolution note. Covered by test/role-guidance.test.ts (`withDirectorHold` holds/releases) and test/backlog-eligibility.test.ts (`entryHold` → `with-director`).

**Validation gap:** no-repro — the 25-consecutive-`no_change`-runs symptom was a one-time live model misread, not reproducible on demand; the fix's hold mechanism (marker → `with-director` → `[blocked: with the director]`, releasing on a director resolution note) is unit-confirmed by those regression tests instead.

- The live-orchestrator e2e `a stale marker beside a stale pin is dropped at the drain without a merge run` (test/orchestrator-3.e2e.test.ts:273) flakes under load — it timed out waiting for the stale pin to be dropped and its marker cleared, and CI on the GitHub runner failed on it (found by the ci role 2026-11-11). — fixed 2026-11-12 by the bugfix role

**Symptom.** On a slow/loaded runner the drain path that drops an orphaned stale merge pin and clears its marker does not settle within the test's ~60 s window: the GitHub run https://github.com/znation/tumwater/actions/runs/43015260315 (main tip `ec3a65e4a`) reported the test as `timed out`. The same test passes in isolation (~0.9 s) and in the full local e2e suite at the live tip (661 ms on 2026-11-11), so it is load-sensitive, not a regression.

**Required behavior.** The stale-pin drop and its marker clear settle within the timeout under the load the hosted runner actually applies, or the test's bound is widened (and the drain's timing checked) so a slow machine does not fail the suite. A flaky live-orchestrator test in the known-flaky family (cf. the archived merge-pipeline-2 / abort entries) that only fails under load should be made deterministically fast or its bound raised — not left red at the mercy of runner speed.

**Suspected cause.** The pin-queue rework made the drain heavier (it drops pins rather than queue files), so on a loaded runner the drop-and-clear round-trip crosses the test's wall-clock bound even though the code path is correct.

**Fixed.** A load-sensitive flake, not a source defect: the drain's drop-and-clear round-trip is a handful of git spawns and the whole test settles in well under a second on a quiet host, so the code path is correct and it is the 100 ms poll loop's wall-clock cost that a loaded hosted runner stretches past the 60 s deadline. The test is now robustified like the sibling load-sensitive orchestrator e2e files (orchestrator-budget/-once/-permits/-resize): a quiet-host gate (test/helpers/wait.ts `awaitQuietHost`) defers the test with an honest skip when the host is saturated instead of running it starved, and the drop-and-clear wait's deadline is widened to the 150 s robust e2e budget (the once-round hang-guard convention) to cover a near-bar host that spikes mid-run. The quiet path is unchanged and finishes in well under a second, so the generous bound costs nothing on the success path. The gate's defer/quiet logic is unit-tested in test/wait.test.ts.

**Validation gap:** no-repro — the flake is a wall-clock timeout that reproduces only under heavy shared-host load (it timed out at a load1 of 28 on an 18-core host and passed in <1 s at load1 ~3), so it cannot be reproduced deterministically on demand; verified the robustified test passes on a quiet host and the quiet-host gate defers rather than fails under saturation.

- A director run with a queued user prompt ends on the `pinned` recovery arm, starving the prompt indefinitely while its pin cannot merge (filed 2026-11-11 from a live stuck instance). — fixed 2026-11-12 by the bugfix role

**Symptom.** The director held an unmerged pin (`refs/tumwater/merge/director` at `d524a78e`) while the merge slot's one gate-then-merge task waited on a `VERIFY_TIER` permit (all 4 held by long pi runs). Each of the director's two queued operator prompts dequeued (`prompt_taken`), then `recoverLeftoversForRun` → `recoverLeftover` found the pin and `handleRecoveredLeftover` (src/runner/runner-run.ts) ended the run through `ctx.finishRecoveryRun` **before authoring** — the only arm that falls through to authoring is `already_queued`, which requires a queue file, and pin-only writers (parts 3e/7, 3i/7) never write one. `finishRecoveryRunPhase` re-queued the dequeued prompt ("a run's dequeued user prompt goes back to its queue, since nothing ran it"), so the operator's request never ran and never will until the pin clears on its own.

**Required behavior.** A run that dequeued a user prompt (`plan.userPrompt !== null`) must not end on the `pinned`/`relief_wait` recovery arms: either run the recovery first and then author the request, or decline to dequeue while a pin recovery is pending (admit the run only when it can actually serve the prompt). The operator's request must always reach an authoring run.

**Suspected cause.** `handleRecoveredLeftover` treats every recovery arm except `already_queued` as terminal, and the director's `recoveryOnly` gate (src/runner/runner-run.ts `runOncePhase`) is computed with `ctx.pending.get() === null` before the dequeue in `runPrompt` — so a prompt-carrying run enters the recovery path and loses its prompt.

**Fixed.** A director with a kept merge pin under the conflict cap — the pin leftover recovery will END on — now runs promptless (`recoveryOnly`), declining to dequeue any queued user prompt, so the prompt stays in the inbox until the pin's drain merges it and the next eligible run serves it. The `recoveryOnly` gate now uses `pinnedRetrySha` (a live-under-cap pin) rather than `hasUnmergedPin`, so a pin at the conflict cap — which recovery hands back or discards while AUTHORING with the run's prompt — still serves the prompt instead of holding it.

**Validation gap:** no-repro — the failure needed a live stuck instance (a `VERIFY_TIER` permit wait with all four held); the offline suite had no path combining a kept pin with a queued director prompt to deterministically show the dequeue/requeue churn.
