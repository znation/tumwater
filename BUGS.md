### The main watch re-attributes an ongoing red to each later tip it re-checks, so the G1 guardrail and the ci heal prompt blame a doc-exempt commit that landed after the red opened (found by the selfcheck role 2026-10-30)

- **Symptom:** the Fast-merge-guardrail line in the selfcheck digest reads `main has had no passing full check for 36 min: red since 369b04fb at 21:27 — every comment line in src/ and test/ fits in 100 columns and opens no block inside a block; the main watch blames plan's merge 94848312`. The phrase says the red began at 369b04fb, but names 94848312 as the merge that caused it — and 94848312 (`tumwater(plan): Add PLANS.md entry splitting collectRoleRows' complexity-15 row builder`, PLANS.md-only, a `*.md`-exempt doc commit) merged 13 min AFTER the red opened. A doc-exempt commit cannot change a `src/`/`test/` comment-width verdict, so the blame is wrong; the real opener is 369b04fb (`tumwater(organize): Rename src/gates/maintenance-quota.ts → maintenance-quota-gates.ts`), whose diff re-wrapped a comment in `src/status/status-data.ts` to fit the 100-column gate.
- **Reproduce:** drive main red at commit A, then land a doc-exempt commit B on top (diff touching only `review.exemptPaths` such as `*.md`), then let the main watch re-check. The `main_culprit` event and the G1 phrase name B, not A. On the 2026-10-30 instance this is `main_check failed` + `main_culprit` at 94848312 for a red opened at 369b04fb (cluster key: the digest's `## Fast merge guardrails` line quoted above; correlated commits 369b04fb [opened red] and 94848312 [wrongly blamed]).
- **Cause:** while main is red, each new tip is re-checked and re-attributed. `inheritedGreen` (src/baseline/main-baseline.ts) only carries GREEN across doc commits; a doc commit after a red never inherits ("The nearest RED stops the walk"), so its check re-runs (or reads the red) and `reportCulprit` (src/baseline/main-watch.ts) then names that tip — a doc-exempt commit — as `main_culprit`. G1's `redSpell`/`redBlameClause` (src/baseline/main-guardrails.ts) pair the spell's `startEv` (the first red, 369b04fb) with the NEWEST in-window `main_culprit` (94848312) when the two shas match, so the one phrase both says "red since A" and "blames B". The same wrong sha reaches the ci healer via `mainRedHealPrompt` (src/baseline/main-red.ts: "The watch named 94848312 as the commit that turned it red") and the dashboard/TUI red alert (src/status/status-polls.ts reads the newest `main_culprit`).
- **Expected / fix sketch:** attribute the red to the commit that OPENED it, not to the newest red tip. Either stop re-naming the culprit once a red spell is open (the first red tip / first `main_culprit` stays the culprit until a green closes the spell), or make `reportCulprit` skip re-attribution for a tip whose diff is review-exempt (it cannot have changed the suite, so it inherits the prior culprit instead of becoming one). The G1 clause and the heal prompt must then name the opener, so the operator and ci heal toward the commit that actually broke the check.
- **Note:** the red test itself (the comment-width check) is already tracked as main's known red and was quarantined (see the BUGS-FIXED entries for "every comment line in src/ and test/ fits in 100 columns…"); this entry is only about the mis-attribution of that red, not the flake.

### `test/supervisor.test.ts` "startParentDeathWatch takes a SIGKILLed supervisor's grandchild down with it" flaked again on 2026-10-16, after its 10-01 and 10-09 Fixed entries and the 10-11 rewrite to a SIGUSR2-driven poll (found by operator session 2026-10-16 from improve's red merge check)

- **Symptom:** at 07:29:28 PDT, improve's in-lock merge check for `d4b62873` failed one test: `✖ startParentDeathWatch takes a SIGKILLed supervisor's grandchild down with it — AssertionError [ERR_ASSERTION]: the orphaned grandchild's watch fired and ran its stop path`. - **Reproduce:** no repro; one live failure under the team's normal load.
- **Cause:** unknown. After SIGKILLing `middle`, the test sends SIGUSR2 up to 200 times, 50 ms apart (about 10 s), and breaks out of the loop early if `process.kill(grandchildPid, …)` throws. The failure reads the same in two cases, and the message cannot tell them apart:

  - the grandchild had already exited without writing `gone`, so the loop broke on ESRCH.
- **Expected / fix sketch:** first make the failure name its case. Record whether the loop broke on ESRCH and how many signals were sent. Have the grandchild write the `ppid()` it saw on each poll. Then fix the case that fires. Re-check the 10-09 entry's mechanism, a watch armed against the wrong baseline, on the handed-down `expectedPpid` path.
- **Progress 2026-10-16 (bugfix):** the test's failure message now names its case: signals sent, whether the loop broke on ESRCH, the expected ppid, and the ppid the grandchild saw on each poll (a `gone.seen` file). The cause is still unknown, so the entry stays open until the next flake reads out.
- **Progress 2026-10-16 (bugfix, second):** one candidate cause closed, unconfirmed: the test treated the existence of `started` as ready, but the grandchild created it with `writeFileSync`, so the test could read an empty or partial pid and SIGUSR2 the wrong pid (ESRCH, no `gone`). The grandchild now writes `started.tmp` and renames it. No flake has been seen since, so the entry stays open until the next failure reads out.
- **Progress 2026-10-16 (bugfix, third):** no repro. 30 concurrent runs of the test beside 8 CPU-spinning node processes all passed (the `timeout` wrapper on the spinners did not exist on this host, so the spinners ran unbounded until `pkill`; the load was real). `startParentDeathWatch` (src/process/supervisor.ts:79-104) reads correctly on the handed-down `expectedPpid` path. No code change; the entry stays open until a flake's failure message (signals sent, ESRCH or not, ppids seen) names the case.
- **Progress 2026-10-16 (bugfix, fourth):** one more candidate closed, unconfirmed: the signal loop was bounded by a count (200 × 50 ms), so a grandchild starved for longer than that (the 145 s check suggests heavy load) could miss every poll and the verdict was read right after. The loop is now bounded by 60 s of wall clock. The entry stays open until a flake reads out.

**Needs review 2026-10-26 by bugfix: the failure message will show signals sent, whether the loop broke on ESRCH, the expected ppid, and the ppid the grandchild saw on each poll (`gone.seen`).**
