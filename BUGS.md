### Any reply that merely mentions `TUMWATER_REFUSED` is treated as a refusal and its code is hard-reset: `TUMWATER_REFUSED: none` discarded two finished, tested bugfix ticks (found by human log analysis 2026-09-23)

**Symptom:** Four commits on 2026-09-22 are refusal notes whose "reason" is a negation: `9cea8c3` (`bugfix: refuse — none`, 01:17), `e420415` (`bugfix: refuse — (none — no entry refused this run)`, 02:49), `cd0f477` (`telemetry: refuse — (none — bug filed normally)`, 03:19) and `4037522` (`steward: refuse — none`, 07:03). None of these runs refused anything: each ended a normal SUMMARY/WHY/RISK/VERIFIED reply with a trailing `TUMWATER_REFUSED: none` line, treating the sentinel as one more report field. The two bugfix runs had done real, verified work that the harness then destroyed:
- 01:17 (session `.tumwater/sessions/bugfix/2026-09-22T07-57-23-814Z_*.jsonl`): edited src/build-check.ts, src/pi.ts and test/build-check.test.ts — the build-check tree-kill fix — and reported `npm test` 1275/1275 passing. Only its BUGS.md move-to-Fixed landed.
- 02:49 (session `…/2026-09-22T09-42-15-778Z_*.jsonl`): edited src/lander.ts, src/landing-slot.ts, src/orchestrator.ts, src/review.ts, src/ui/progress.ts, src/ui/status-model.ts and three test files — the user-reported landing-cell fix — reporting 1292/1292 passing. Only BUGS.md/README.md landed; that bug is re-opened below because its Fixed record describes code that does not exist.
The steward later found the first phantom record and diagnosed it as a tick that *fabricated* a Fix paragraph (the "fix narrative can land on main without its fix" entry under Fixed); the code was in fact written, tested, and discarded by the harness. The `falseFixReason` guard added for that entry now blocks the orphaned note, but the code is still thrown away.

**Repro:** Deterministic, no model needed: a fake-pi shim whose final assistant message makes an ordinary src/ edit and ends `SUMMARY: x` / `TUMWATER_REFUSED: none`. The tick ends `result: "refused"` with summary `none`, the src edit is gone from the worktree, and only markdown (if any) is committed. On the live log: `git log --grep='refuse — ' --format='%h %s' main`.

**Expected:** A refusal is a deliberate, affirmative declaration, and treating it as one must not depend on the model never naming the sentinel. Detect it only from an anchored `TUMWATER_REFUSED: <reason>` line in the FINAL assistant message, and treat reasons that negate the refusal (`none`, `n/a`, `(none …)`, empty) as no refusal. A reply that carries both a SUMMARY and a refusal line with real work in the diff is contradictory and should be surfaced (warning event), not resolved by destroying the work. The prompt should say explicitly that the line is emitted only when refusing.

**Suspected cause:** `PiStream` sets `refused = true` on `text.includes(REFUSED_SENTINEL)` for any assistant message (src/pi-stream.ts:225) — deliberately looser than the anchored `extractRefusal`, by analogy with the nothing-to-do sentinel, where a false positive costs only a no_change. Here a false positive routes the tick through `handleRefusal` (src/refusal.ts:34, from src/loop.ts:609), which commits only `.md` files and discards everything else via reset --hard/clean. `extractRefusal` then accepts `none` as a valid reason. The prompt (src/prompt.ts:110) lists the refusal line right next to the reply-contract fields, which invites a model to fill it in on every reply. The pi sessions above still contain both runs' edit tool calls and could be replayed to recover the lost diffs until `sessionRetentionDays` prunes them (~2026-09-29).

### A live `tumwater.json` that disappears mid-run hot-reloads as built-in defaults: plan 4b's own landing deleted the config and the fleet ran 8.6 hours with zero successful ticks (found by human log analysis 2026-09-23)

**Symptom:** At 2026-09-22 14:05:32 `48b3474` ("Land plan 4b/7 — ffMainTo preserves the live tumwater.json across an untracking landing") merged. That one commit both added the preservation code to src/merge.ts and `git rm`'d `tumwater.json`, but the live orchestrator was build `03edeba` (10:12), which predates the preservation, so its fast-forward of the root checkout deleted the operator's config. One second later the log shows `config_changed` with keys `fallbackModel, idleBackoff, maxDailyCostUsd, model, provider, quietTimeoutSeconds, tickTimeoutSeconds`, plus `max_concurrent_changed 3 → 6`. That is exactly the set of keys the file had that the defaults lack. The fleet then ran on `defaultConfig()`: no provider/model, so pi's default (local oMLX Qwen instead of `huggingface`/`zai-org/GLM-5.3-Flash`, confirmed from the pi logs' per-message provider); `maxConcurrent` 6 (7 ticks in flight with the director, against an oMLX server configured for 3 concurrent requests); `tickTimeoutSeconds` 1800 instead of 54000. From 14:05 to the 22:42 restart: **97 `error` ticks (all `timed out after 1800s`), 4 aborted, 0 successful ticks, 1 landing**, $0.00 spend. The only signals were per-role `3 consecutive tick failures` warnings. Nothing said the config file was gone. The user's 14:13 report that "landing doesn't count as active for maxConcurrent" (the first Open entry) came eight minutes after the cap silently doubled.

**Repro:** Deterministic: with a fleet running, `mv tumwater.json /tmp/` — the next poll logs `config_changed` naming every non-default key and the fleet continues on defaults with no warning. `loadConfigCached` (src/config.ts:212) returns `{ config: defaultConfig() }` for a missing file, the same as a first run.

**Expected:** Once a fleet has loaded a config, the file vanishing is an incident, not a reconfiguration. Keep the last-known-good config (as a *broken* file already does) and emit a warning naming the missing file until it returns. Separately, a landing that changes how landings themselves behave must not also depend on that change: a self-hosted fleet lands every commit with the *previous* build, so the untracking should have been a follow-up commit after the preservation code was running (plan-sizing rule for PLANS.md).

**Suspected cause:** The "missing ⇒ defaults" rule was written for startup and first-run convenience and reused unchanged in the hot-reload path, where it turns a deleted file into a silent full reset. Plan 4a/4b made the file untracked, so deleting it became an ordinary git side-effect for the first time. The self-hosting build lag (the running build is always behind main) was not considered when 4b bundled the code with the `git rm`.

### A self-redeploy whose new generation fails a startup precondition takes the whole fleet down with no event: 4 h 44 m of silence after the 2026-09-22 22:42 restart (found by human log analysis 2026-09-23)

**Symptom:** `events.jsonl` shows `restart` (from `03edeba` to `0f284a8`) and `orchestrator_stop` at 2026-09-22 22:42:30, then nothing until a manual `orchestrator_start` at 2026-09-23 03:26:58. The respawned child hit `requireReadyRepo` (src/cli.ts:123): `tumwater.json` was missing (see the entry above), so it failed with `NOT_INITIALIZED_MESSAGE` and exited non-75. `superviseRun` (src/supervisor.ts:58) treats any exit other than `RESTART_EXIT_CODE` as final and returns, so the supervisor exited too. No event recorded the failure: the last generation's stderr went only to the operator's terminal. Recovery required a human to notice, run `tumwater init` (which itself refused until `59bba02`), restore the config by hand and restart.

**Repro:** Deterministic: in a running self-hosted fleet, remove `tumwater.json` and land any `src/` commit so a redeploy fires. After the drain, the new child exits with the not-initialized message, the supervisor exits, and events.jsonl ends at `orchestrator_stop`.

**Expected:** The redeploy should refuse to swap onto a generation that cannot start: run the same preconditions the child will run (config present and valid, git/pi on PATH) before the swap, and record `restart_refused` with the reason if they fail. Or the supervisor should treat a fast non-75 exit right after a respawn as a failed deploy, log an event, and keep or restore the previous generation instead of exiting. Also, startup and hot reload disagree about a missing file: reload says "use defaults" (src/config.ts:212), startup says "not initialized". One rule should apply to both.

**Suspected cause:** The redeploy's readiness check is "main is green and compiles" (src/redeploy.ts). "Can this generation boot in this repo's current state" is a separate question that nothing asks. The supervisor was written assuming only the new code could be broken, and a green check rules that out, not the environment.

### The restart drain's `hold` does not stop ticks already parked in the semaphore: they start fresh pi runs mid-drain and are the ticks the restart then aborts (found by human log analysis 2026-09-23)

**Symptom:** The orchestrator documents `hold` as "starts no new ticks at all" (src/orchestrator.ts:489). That holds only for ticks not yet scheduled. A tick scheduled in an earlier poll sets `running = true` and parks in `semaphore.acquire`. When a slot frees during the drain, `runTimedRoleTick` (src/orchestrator.ts:63) takes it and starts `runner.tick()` after checking only `signal.aborted`. Drain windows from the log: the 2026-09-22 10:12 restart (957 s) saw **6** role ticks start mid-drain (plan, dry, improve, readme, telemetry, qa), and aborted 2 of them (qa and telemetry, started 10:04–10:06); the 22:42 restart (full 1800 s window) saw dry, improve and perf start at 22:12–22:22 and **all three were among the 4 aborted**. The ticks that start mid-drain are what keep the drain from finishing and are then the work thrown away. Separately, `abortedTicks` (src/redeploy.ts:385) reports `roleInFlight.size`, which counts parked waiters: the 2026-09-21 21:54 restart reported `abortedTicks: 12` while only 3 `tick_end aborted` events exist.

**Repro:** Live fleet, `maxConcurrent` well below the number of due roles, so several ticks sit in the semaphore queue. Land a `src/` commit to trigger `restart_pending`, then compare `tick_start` events between `restart_pending` and `restart`: new ticks start inside the window. At the unit level: park a second `runTimedRoleTick` behind a held permit, flip the redeploy into `hold`, release the permit, and the parked tick runs.

**Expected:** While a restart is pending, a parked waiter that gets a permit should release it without starting (and clear `running`, so it re-schedules on the new build). `roleInFlight` for the drain decision and `abortedTicks` should count only ticks that actually hold a permit.

**Suspected cause:** The same conflation as the first Open entry: `runner.state.running` and the in-flight sets mean "reserved", not "running", so the drain waits for ticks that have not started and lets them start. The hold was implemented at scheduling time only, and nothing re-checks it at the point where a parked tick gets its slot.

### The landing state cell shows only elapsed time: a landing renders bare `landing <elapsed>` while working/reviewing carry turns, context, and tool (reported by user 2026-09-22; re-opened by human log analysis 2026-09-23 — the recorded fix never landed)

**Re-opened 2026-09-23:** the 2026-09-22 Fixed record is false. The fixing bugfix run did write and test this code (session `.tumwater/sessions/bugfix/2026-09-22T09-42-15-778Z_*.jsonl`: edits to src/lander.ts, src/landing-slot.ts, src/review.ts, src/ui/progress.ts, src/ui/status-model.ts and tests, 1292/1292 passing), but its reply ended `TUMWATER_REFUSED: (none — no entry refused this run)`, so the harness handled it as a refusal (see the refusal-sentinel entry above), discarded every non-markdown change, and landed only the BUGS.md move as `e420415`. On main, `setLandingStage` exists nowhere in src/, and `loopPhase` still returns bare `landing <elapsed>` (src/ui/status-model.ts:121). The **Discarded fix (design reference, not on main):** paragraph below is kept as a design reference for the re-implementation, not as a description of main.

**Symptom:** While a role's commit is landing, its row in `tumwater status`, the TUI, and the GUI reads `landing <elapsed>` and nothing else — although the same landing spends most of its time in a reviewer pi run whose turns, live context, current tool call, and current work are all already observable. A landing routinely runs for many minutes (the full `npm test` pre-check plus an adversarial review), and during all of it the operator cannot tell whether the reviewer is making progress or hung — the exact detail an in-flight tick's cell carries (`reviewing 2m · turn 3 · ctx 18k · bash npm test`). A landing is an active state; it is displayed as a featureless countdown.

**Fix:** The 4/5 landing marker (`LandingInFlight`) carries a `stage` the landing path advances as it progresses (`setLandingStage` in landing-slot.ts: lander.ts opens the marker at `merging` for the checkout/rebase steps, review.ts moves it to `build-check` before its pre-check and `reviewing` before the reviewer run, back to `merging` on a mid-batch reject so a finished reviewer's turns cannot accrue a false stall flag, and lander.ts returns it to `merging` for the merge). `loopPhase` renders the stage: `reviewing` shows the reviewer run's live detail exactly like a reviewing tick — the gate accumulator, whose reset now happens at the run's `tumwater_run label=review` label line (written before pi spawns), so a previous review's turns/context can never bleed into the next landing's cell; `build-check`/`merging` render honest stage labels and never read the log; a stage-less record (an older writer mid-upgrade) keeps the bare elapsed label. The elapsed is the LANDING's (marker.startedAt), never the authoring tick's start.

**Validation gap:** real-run-needed — the symptom only exists mid-landing in a live fleet, and the unit suite not only never covered the landing cell's detail, it pinned the bare `landing <elapsed>` label as the correct output, so nothing reddened until a human watched a real landing.

### The active-state rows an operator counts against `maxConcurrent` do not track the real permit holders: a tick parked in the semaphore queue renders as `working`, so a landing that holds a permit looks like it runs outside the cap (reported by user 2026-09-22)

**Symptom:** Watching a live fleet, the number of loops in active states (working/reviewing/landing) visibly exceeds `maxConcurrent`, and a `landing <elapsed>` row coexists with a full complement of `working` rows — so the landing appears not to count as active for the cap on parallel loops, when the user's expectation (and the documented contract) is that it should. The harness's real accounting says otherwise: since 2eee180 (2026-09-18) the landing slot's whole body — reviewer run, build check, conflict resolution — holds one `maxConcurrent` permit (`withLandingSlot`, src/orchestrator.ts:184, tier −1), and the display sorts landing as active (`isActivePhase`, src/ui/status-model.ts:181). The visible discrepancy comes from the display, not the permit: `runner.state.running` is set to true BEFORE the semaphore wait (src/orchestrator.ts:749, "Reserve before the semaphore wait so we don't double-schedule"), and `loopPhase` renders every `running` loop as `working <elapsed>` (src/ui/status-model.ts:122) with no distinction between a tick that holds a permit and one parked in the semaphore queue. With the default cap of 6 (src/config.ts:36) and a dozen roles due in one poll, several parked waiters display as `working` beside the permitted ticks — and the landing, which holds a real permit and genuinely limits the fleet, rows up next to them, making the cap look unenforced and the landing look free. The same flag serves two meanings: "this loop has business in flight" (what `isEligible`'s `if (s.running) return { run: false }` needs so a parked waiter is not double-scheduled) and "this loop's pi is running right now" (what the dashboards render as an active state).

**Repro:** Live fleet, no model needed. Set `maxConcurrent: 2` with several roles enabled at short intervals and keep one role authoring changes so a landing runs. During the landing, `tumwater status` shows the landing row plus two or more `working` rows — more active states than the cap — while the backend actually serves at most 2 streams. Correlated history: the permit invariant itself is pinned only in the e2e tier since the split (test/orchestrator.e2e.test.ts:741, "a landing's reviewer run takes the same maxConcurrent permit as a role tick"); the gating suite has no pin, and no test renders a fleet whose active-state rows exceed `maxConcurrent`, so nothing reddened while the display drifted from the limit it mirrors.

**Expected:** The operator-visible active set must equal the real permit holders, so a landing visibly counts toward the cap. A tick parked in the semaphore queue holds no permit and runs no pi: it should display a distinct label (e.g. `awaiting slot <elapsed>` — its true state) instead of `working <elapsed>`, so the active rows — permitted working ticks, reviewing ticks, and the in-flight landing — add up to at most `maxConcurrent` (plus the director, whose documented bypass is a state of its own). Keep the landing's permit behavior unchanged; if the fix touches the semaphore seam, add a gating-suite pin for the landing-holds-a-permit invariant so it stops living only in the e2e tier.

**Suspected cause:** The merge-queue work (3/5) split the tick — permit held from start to end, label `working` — from the landing — permit held by the orchestrator's slot, label `landing` — but nothing revisited the display contract that maps loop states onto the concurrency limit. `running` was never split into "scheduled/parked" and "permit held", so the parked-waiter reservation made before the semaphore wait (needed against double-scheduling) leaked into the active-state rendering, and the user-visible count stopped tracking the limit it is supposed to mirror.

**Context added 2026-09-23:** the user's report was enqueued at 2026-09-22 14:13:16, eight minutes after the live `tumwater.json` was deleted and the fleet hot-reloaded defaults (`max_concurrent_changed 3 → 6` at 14:05:33; see the missing-config entry above). With the cap silently doubled, up to 7 ticks were really in flight against a configured cap of 3, which by itself produces the observation "more active loops than maxConcurrent". The display conflation described here is real, but re-check the symptom against a fleet whose config is intact before sizing the fix.

### A 429 storm still has no fleet-wide hold: each tick now retries its own 429, but concurrent loops keep hammering a rate-limited provider instead of backing off together (found by human investigation 2026-09-21; spun out of the fixed 429-retry entry 2026-09-22)

### The failure digest's `## Outcome by role` separator row has no cell delimiters, so the table never renders (found by human investigation 2026-09-21)

**Symptom:** `tumwater report --failures` emits `| --- | ---: ---: ---: ---: ---: ---: |` as the separator under a header with N+1 cells. Every markdown renderer needs the separator's cell count to match the header's; with two cells against seven the block is not a table at all and falls through as a paragraph of pipes and dashes. The section is the digest's primary per-role summary, and it is the one table in the document that is broken — `## Deltas vs the preceding N days`, two lines below, hardcodes its separator correctly and renders fine.

**Repro:** `node dist/src/cli.js report --failures --days 2` and read the fourth line of `## Outcome by role`; or `renderFailureMarkdown(collectFailureReport(root, 2))` in a scratch root with any two roles' `tick_end` events.

**Expected:** `src/failure-report.ts:474` builds the row as `` `| --- |${cols.map(() => " ---:").join("")} |` ``; the join needs the delimiter — `join(" |")` — to produce `| --- | ---: | ---: | … |`. A test asserting the separator's pipe count equals the header's would pin it.

**Suspected cause:** The row was written by analogy with the header line one line above, which interpolates `cols.join(" | ")` into a template that supplies the outer pipes. Copying that shape with a `.map()` in front drops the inner delimiter, and the digest is read almost exclusively as plain text in a terminal or in an event feed, where a broken table looks nearly identical to a working one.

### The build check's 300 s timeout does not bound it: skipped checks recorded 331–1158 s (found by human investigation 2026-09-21)

**Symptom:** `BUILD_CHECK_TIMEOUT_MS` is 300 s (`src/build-check.ts:156`) and is the only timeout passed to `runBuildCheck` on every path, including the un-parameterised call at `src/main-baseline.ts:148`. Yet **every** `build_check` event with `status: "skipped"` in the last two days records a duration well past it: 331 s, 373 s, 415 s, 571 s, 741 s, 1028 s, 1037 s, 1045 s on 09-21, up to 1158 s on 09-20. The durations are honest — `src/build-check.ts:396` measures `Date.now() - startedAt` around `runBuildCheck` alone, and `checkMainBaseline`'s `onRun` hook (`src/main-baseline.ts:148`) fires only for the real run, never for a deduped waiter, so neither queueing nor the in-flight dedupe is being counted. So `execFileAsync`'s promise really is settling up to 12 minutes after its own timeout should have fired, and the operator-facing string `build check timed out after 300s` is false by a factor of 2–4 in the data. ### The test suite has never deleted a temp dir: 1.68M abandoned `tumwater-test-*` directories make every `mkdtemp` 9,145× slower and time out the build check (found by human investigation 2026-09-21, fixed 2026-09-22)

**Symptom:** `$TMPDIR` (`/private/var/folders/b9/…/T` — what `os.tmpdir()` returns) held **1,683,621** `tumwater-test-*` directories on 2026-09-21, **76% of the directory's 2,226,568 entries**, the oldest 31 days old. `test/util.ts:13` `tmpdir()` is `fs.mkdtempSync(path.join(os.tmpdir(), prefix))` and nothing in the suite ever removes the result: no `after()` hook, no `rmSync`, no per-run root anywhere in `test/`. Measured on the live machine: `fs.mkdtempSync` takes **357.276 ms/call** in that directory against **0.039 ms/call** in a freshly created one, a factor of **9,145**. At ~470 calls that is **~168 s of pure `mkdtemp`** before a single test does any work, on a suite `src/test-runner.ts:9` documents as "the full ~40 s suite". It is self-amplifying: every run adds ~500 more entries, so every later run is slower. Build-check durations track it exactly — median 91 s / p90 124 s on 09-19, median 464 s / p90 1079 s on 09-20 — and the 300 s `BUILD_CHECK_TIMEOUT_MS` now fires routinely (9 skipped checks on 09-20, 7 on 09-21), dropping the fleet's deterministic verification on those ticks and, through the two sibling bugs filed below, leaking process trees and falsely reddening main.

**Repro:** Count on the live machine with `ls -f "$TMPDIR" | grep -c '^tumwater-test-'` — an unsorted `ls` is the only fast read, because `find` and `os.scandir` over 2.2M entries take minutes (a 45 s time-boxed `scandir` covered only 3% of the directory and undercounted by 30×). The slowdown standalone: time `fs.mkdtempSync` 60 times in `$TMPDIR` and 60 times in a directory created for the purpose. The leak itself: run one test file and count `tumwater-test-*` entries before and after — none is ever removed.

**Expected:** A test that creates a temp directory removes it. One per-run root (`mkdtempSync` once per process, every `tmpdir()` nested inside it) torn down in a process-exit hook bounds the footprint at one directory per run no matter how many call sites there are, and keeps `mkdtemp` O(1) forever — a smaller change than auditing 469 sites, and it cannot regress when a new site is added. The existing 1.68M directories need a one-off sweep; until that lands every measurement of suite runtime on this machine is measuring the leak.

**Suspected cause:** `tmpdir()` was a one-line convenience written when a handful of tests each leaked one directory into a location the OS was assumed to clean. Nothing revisited it as the suite grew to ~470 call sites and began running on every gate, landing, batch and baseline check — 189 build checks in the last two days alone, each abandoning a few hundred more. macOS reaps `/var/folders` only on a periodic schedule this machine's 33-day uptime has never reached, so the assumption has been false for the whole life of the project.

**Fix:** `test/util.ts`'s `tmpdir()` now creates one `tumwater-test-run-*` root per process on first use — registered with a `process.once("exit")` hook that `rmSync`es it recursively, best-effort with retries — and nests every `tmpdir()`/`makeRepo()` result inside it. A suite run (one worker process per test file) therefore abandons at most one directory per file instead of ~500 per run, and every `mkdtemp` inside the root is O(1) against a near-empty directory regardless of how polluted `$TMPDIR` already is. `test/tmpdir.test.ts` pins it: it spawns a child that calls `tmpdir()` and `makeRepo()` and exits, then asserts the run root and everything under it are gone. Full suite after the fix: 1264/1264 pass in ~120 s. Residual, machine state not repo state: the ~1.74M directories already in `$TMPDIR` need a one-off operator sweep — they live outside any worktree, so no repo change can remove them; runs no longer add to the pile and no longer pay the per-call scan cost.
