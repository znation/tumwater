### A failed rebuild never leaves a state transition: `Redeployer.block` logs only a `warning`, so the state stream keeps reporting `restart pending — main <sha> green; compiling` after the compile has already died — the 2026-09-28 digest's last two fleet transitions are 34 minutes of "compiling" beside its 76× `tsc exited ENOENT` cluster (found by telemetry loop 2026-09-28)

- **Symptom:** the 2026-09-28 digest (470 ticks, one day) closes its Fleet state changes section with two harness transitions 34 minutes apart — 19:47 `restart pending — main c9db4539 green; compiling`, 20:21 `restart pending — main ff730052 green; compiling` — still "compiling" at the window's end, and `+123 older transitions hidden` shows the day's earlier episodes in the same shape. The same digest's top warning cluster is **76×** `rebuild of 762c5d13 failed — staying on build 66afeacd: tsc exited ENOENT`: `ENOENT` is a spawn failure — the compiler never ran, so each rebuild died in milliseconds (established by the filed-and-fixed attribution bug above: commit 48835efc — "`ENOENT` is not a compiler exit code"). The state section shows an in-progress build; the warning section shows the builds could not start; nothing in the state section records the failure — and the two newest transitions, which is what an operator reads as "what the harness is doing now", sit 34 minutes of "compiling" from one dead compile to the next.
- **Why the response was wrong:** the state-change stream (`STATE_CHANGE_TYPES`, src/failure-state-change.ts:17 — the digest's Fleet state changes section, src/failure-data.ts:355-358, replays the newest events of those types) has an event for the rebuild's start — `restart_pending`, logged when the compile begins (src/redeploy.ts:353) — and for two terminal outcomes, success (`restart`, :427) and startup refusal (`restart_refused`, :460), but none for the third: `block()` (:473 — red-main verdict, compile verdict, swap error) logs only a `warning`. The block's truth lives only in the `BuildStatus.restartBlocked` payload (status(), src/redeploy.ts:241), read by the status/doctor badge (src/ui/status-model.ts:288, src/doctor.ts:386) — a payload the transition stream and the digest never surface, so the digest's own Fleet state section contradicts its own warning clusters. Precedent: the 2026-09-23 entry "A self-redeploy whose new generation fails a startup precondition takes the whole fleet down with no event" was fixed by adding the missing event — the same class of gap, on the pre-restart side. The 2026-09-28 fix (48835efc) that split a never-ran compile off a compiler verdict did not close it: the rejected branch (src/redeploy.ts:370-377) warns once per head, drops the pending, and the next poll starts a fresh episode — a fresh `restart_pending` "compiling" state event and a fresh doomed spawn every poll, the warning deduped to silence after the first (the green verdict is cached per SHA, src/main-baseline.ts:80, so the churn is state events and doomed spawns, not suite re-runs). Either build — old (latched) or new (churning) — the operator watches an unending "compiling" while the fleet stays pinned on the stale build.

Live instance: the 2026-09-28 digest above (76× ENOENT cluster; 19:47/20:21 transitions; window ends mid-"compiling").

Done exactly that shape: a `restart_blocked` event type (src/events.ts) logged from `block()` beside its warning — from the running build, to the blocked head, reason — rendered as `restart blocked — <reason>; staying on build <sha>` in the digest's state section (src/failure-state-change.ts) and as a full line in the event feed (src/ui/event-format.ts); `restart_pending` is now logged at most once per head (a `pendingLoggedHead` key in src/redeploy.ts, cleared when an episode ends in a state other than compiling — a refusal or a completed restart), so a broken toolchain re-attempting its doomed compile every poll no longer re-emits a fresh "compiling" transition each time.

### The sibling shape the `rejected` flag missed: a `deps.compile` that REJECTS (the mirror worktree checkout throwing in production) latches "rebuild of <sha> failed" with no retry until main moves, pinning the fleet on the stale build even after the environment recovers (found by bugfix loop 2026-09-28, fixed 2026-09-28)

- **Symptom:** the 2026-09-28 ENOENT fix made `compileStaged`'s catch return `{ ok: false, rejected: true }` for a spawn failure, and `redeploy.poll` retried that shape instead of latching it. But production binds `deps.compile` to `async (h) => compileStaged(root, await mirror(h), h)` — when `ensureDetachedWorktree` throws (a git lock in the mirror worktree, disk pressure) or the staging setup throws, the promise REJECTS: `track()` records `compiled.error` with `result` still undefined, and `poll`'s `c?.rejected` check is blind to that shape, so the failure fell into the verdict branch — `block(mainHead, "rebuild of <sha> failed", …)` set `blockedHead`, "no retry until main moves". The mirror worktree breaking is the canonical "repaired environment must redeploy without main moving" case this fix class exists for, yet the most likely production throw path re-created the exact 64-warnings-a-day latch: an environmental failure named after a commit, pinned until main happened to move.
- **Why the response was wrong:** the "a failure before a verdict is retried, not latched" guarantee was applied to two of the three no-verdict shapes: the green check's thrown path (`green.error` → "could not run", drop, retry — BUGS.md 2026-09-16) and the compile's explicit `rejected` flag — but not the compile's thrown path (`compiled.error`), which was the only no-verdict shape with a pre-existing test asserting the latch was correct (the 2026-09-11 coverage test `a thrown compile blocks with its error text, not a bare failure` predates the 2026-09-28 fix and pins the old semantics; the newer intent wins).
- **Fix:** `redeploy.poll`'s compile-failure branch (src/redeploy.ts) treats a missing `CompileResult` — the tracked rejection — as a rejection alongside the `rejected` flag: no `blockedHead`, one warning per head through the same `compileFailedHead` dedupe key (message `rebuild of <sha> could not run: <error> — retrying on the next poll`, mirroring the green check's phrasing; the `rejected`-flag shape keeps its existing "could not start" message), the pending head dropped, and the compile re-attempted on the next poll. A compiler verdict arriving as a `CompileResult` (`ok: false` with a numeric exit or output) still blocks, unchanged; that remains safe in production because `compileStaged`'s catch converts every tsc exit into a result, so a rejection can only mean the environment failed before a verdict. The 2026-09-11 test now asserts the retried behavior and keeps its "not a bare failure" coverage (the warning carries `compiled.error`, not the "compile threw" fallback).
- **Fixed:** 2026-09-28, regression test in test/redeploy.test.ts: `a thrown compile is a rejection, not a verdict: its error text rides the warning, nothing is latched` — a rejecting `deps.compile` emits the "could not run" warning with the error text, leaves `restartBlocked` undefined, and the next poll re-attempts the same head with main unmoved (verified failing against the pre-fix latch before the change); `npm test redeploy` 43/43.
- **Validation gap:** unclear-invariant — the pre-fix coverage test asserted the latch as the correct behavior, so the suite itself encoded the opposite guarantee; the intended one (a no-verdict compile is retried, not latched) had to be reconstructed from the 2026-09-28 fix and the green check's thrown path before a reproduction could be written to fail.

### A compile that never ran is latched as a verdict about the commit: `tsc exited ENOENT` is execFile's spawn-failure code, yet the redeploy path records "rebuild of <sha> failed" and blocks that head with no retry until main moves, pinning the fleet on the stale build even after the environment recovers (found by telemetry loop 2026-09-28, fixed 2026-09-28)

- **Symptom:** digest warning clusters, 2026-09-28, one day: **64×** `rebuild of 762c5d13 failed — staying on build 66afeacd: tsc exited ENOENT` (loop: harness) — the day's top warning cluster by a factor of seven, against ~178 merges. Sixty-four times the harness told the operator a commit's rebuild failed; not one message says what actually happened, which is that `tsc` never executed at all. `ENOENT` is not a compiler exit code — it is Node's spawn-failure marker on the `execFile` error object, meaning either the `cwd` (the mirror worktree) did not exist at spawn time or `process.execPath` (the running node binary, e.g. after a homebrew upgrade swaps it out) pointed at a vanished path. The failure is environmental, but every one of the 64 warnings names a commit as the thing that failed.
- **Why the response was wrong:** two wrong responses stacked. (1) **Misattribution / self-hiding:** `compileStaged`'s catch built `tsc exited ${String(e.code)}` identically for a spawn failure and a real compile error, so an operator reading 64 commit-failure warnings learned nothing about the broken mirror/toolchain that actually caused them. (2) **Stale latch:** the failure went through `block(mainHead, …)`, setting `blockedHead` — "no retry until main moves". A genuine compile error is a verdict about an immutable tree, so latching is right there; a spawn failure is a verdict about nothing, and the same method already knew it one step earlier: the green check's REJECTED path drops the pending head, sets no `blockedHead`, warns once per episode, and lets the next poll re-run the check (BUGS.md 2026-09-16). Repair the mirror or node_modules while main sits still and the fleet stayed pinned on the stale build indefinitely.
- **Fix:** `compileStaged` (src/build-stage.ts) now returns a `rejected` flag on its result: a spawn failure with no compiler output (`typeof e.code !== "number"` and empty streams — the ENOENT class) and a missing toolchain resolve to `{ ok: false, rejected: true, detail: "could not start the compile: …" }`, naming the environment instead of the commit; a real compiler exit (numeric code or output) is unchanged. `redeploy.poll` (src/redeploy.ts) treats a `rejected` compile like the green check's REJECTED path: no `blockedHead`, one warning per head (`could not start the rebuild of <sha>: … — retrying on the next poll`, a new `compileFailedHead` dedupe key beside `checkFailedHead`), the pending head dropped, and the compile re-attempted on the next poll — a repaired environment redeploys the current head without main moving. A real compiler exit still blocks, unchanged.
- **Fixed:** 2026-09-28, regression tests in test/redeploy.test.ts: `a compile that never ran is a rejection, not a verdict: retried instead of blocked` (stub returns `rejected` — no `restartBlocked` in status, warning names the environment, compile re-attempted and the same head reaches `restart` with main unmoved, while the real-compile-failure test above still latches); `a rejected compile warns once per head, not once per retry` (a second rejected compile of the same head emits no second warning while still re-attempting the compile; a different head is a new episode and warns again — pinning the `compileFailedHead` dedupe key); `compileStaged reports a spawn failure as a rejection, not a verdict about the tree` (a nonexistent mirror cwd yields `{ ok: false, rejected: true, detail: /could not start the compile/ }`); the missing-typescript test now also asserts `rejected: true`.
- **Validation gap:** no-fake — the suite's fake compile stub could only resolve ok-or-failed, with no way to say "the compile never ran", so no existing test could express — let alone contradict — the misattribution and the latch; confirming the gap needed the `rejected` shape first (closest tag: the stub existed but lacked the vocabulary the bug demanded).

### A whole-reason absence statement reads as a genuine refusal: `TUMWATER_REFUSED: nothing to do` (and `nothing refused`, `no refusal`) fails `isNegatedRefusal`, so the harness hard-resets the tick's finished, tested work (found by bugfix loop 2026-09-28 shape hunt over the fixed quote bugs, fixed 2026-09-28)

- **Symptom:** the negation guard knew `none` and `n/a` — bare, decorated, quoted, dash- and punctuation-appended — but its alternation stopped there, so a loop that found no work and reached for the phrase instead of the token (`nothing to do`, `NOTHING TO REFUSE`, `nothing refused`, `no refusal`) classified as a genuine refusal: handleRefusal destroyed its finished, tested work, the same destruction the `none`-family fixes closed four times over.
- **Reproduce:** one-line node probe over the freshly built module: `isNegatedRefusal('nothing to do')`, `isNegatedRefusal('nothing refused')`, `isNegatedRefusal('no refusal')` all returned `false` while every recorded `none` shape returned `true` — and a probe over the rebuilt module after the first landing of this fix (rejected in review) confirmed the review's finding: `nothing refused` and `no refusal` still returned `false` because that landing only added `nothing to do` and `nothing to refuse`. This re-landing covers all four phrases; the probe over the rebuilt module now returns `true` for each. Pinned by the new regression test.
- **Cause:** the guard's negating-token list (`none|n\/a`) encoded "the loop wrote `none`" rather than "the reason states absence"; a loop that found no work but misremembers the sentinel contract writes the absence as prose, and the anchored appended-note class could not rescue it because the token itself is not `none`.
- **Fix:** the alternation carries all four absence phrases beside `none|n\/a`, under the same anchoring: a phrase followed by the appended-note punctuation class still negates (`nothing to do; the backlog is empty`, `no refusal; the objection was satisfied upstream`), while a phrase followed by a word (`nothing to do with the review`, `no refusal of my own`) stays a refusal.
- **Fixed:** 2026-09-28, regression test in test/reply-contract.test.ts (`isNegatedRefusal negates a whole-reason absence statement`): all four phrases — bare, sentence-punctuated, uppercased, dash- and semicolon-appended — return true; `nothing to do with the review`, `no refusal of my own — the change stands`, and an objection beginning with `nothing` return false.
- **Validation gap:** unclear-invariant — the suite's shapes all descended from refusals models had actually emitted, so nothing failed; confirming the gap meant first deciding the invariant the token list encodes (a reason that states absence negates, whatever words it uses) and which absence phrases are safe to negate without swallowing real objections. The rejected first landing also showed the gap runs the other way: a probe cited in the record but left out of the fix passes review unnoticed unless the reviewer re-runs it, so every phrase the entry names is now pinned by the test.

### A typographic-quoted negation reads as a genuine refusal: `TUMWATER_REFUSED: “none”` (and `”none ”nothing to do”`) fails `isNegatedRefusal`, so the harness hard-resets the tick's finished, tested work (found by bugfix loop 2026-09-28 review of the straight-quote fix, fixed 2026-09-28)

- **Symptom:** the negation guard accepted straight-quoted dresses (`"none"`, `none "nothing to do"`) and markdown decoration (`**none**`), but its quote handling knew nothing of the typographic quotes a model emits just as often: `“none”`, `’none‘`, `“(**none**)”`, `none “nothing to do”`, `n/a ‘no open bugs’` all returned `false`, so a work-completed reply ending that way had its tested work hard-reset — the same destruction the straight-quote fix one entry below closed for ASCII quotes only.
- **Reproduce:** `isNegatedRefusal('”none ”nothing to do”')` returned `false` on the freshly built module (one-line node probe over the quote matrix); the suite had no case carrying a typographic quote. Pinned by the new regression test.
- **Cause:** the first quote landing added the straight pair `'` `"` to the three places punctuation is treated as formatting (the wrapping strip, the appended-note separator class, unbold) and stopped there; the typographic set `‘ ’ “ ”` — the same two roles, decoration around the token or the opening mark of an appended note — was left out of all three, and a model's quote direction is not reliable besides: a closing quote can open the wrap (`”none …`), so direction-specific classes leave that dress a genuine refusal.
- **Fix:** all four typographic quotes join all three places, and in BOTH anchored classes of the wrapping strip (opening and closing alike, direction-agnostic — the same trade the dash dress already carries), with the appended-note class and unbold carrying the full set too. Each quote is pinned in both roles in the test, including the combined shape `q none q…q` that only the strip classes plus the appended-note class can satisfy — unbold's quote-stripping alone would rescue a bare wrapped token and mask a strip gap, which is exactly how the first attempt at this fix (rejected in review) shipped `”` missing from the strip behind a test that could not see it.
- **Fixed:** 2026-09-28, regression test in test/reply-contract.test.ts (`isNegatedRefusal negates none and n/a under typographic quoting`): for each of ‘ ’ “ ” — wrapped token, appended note, and the strip-sensitive combined shape — plus `”none ”nothing to do”` and `“(**none**)”` return true, while a real reason under curly quotes and a reason that continues with a word after a quoted clause stay refusals.
- **Validation gap:** unclear-invariant — the recorded rule ("after the token, punctuation cannot begin a reason word") had never been extended to say which side of it the typographic quotes fall on or that both quote directions decorate both sides of the token, and unbold's quote-stripping masked any bare wrapped-token pin, so confirming the strip meant first deciding the invariant and then building a shape only the strip classes can satisfy.

### A flag-shaped `--grep` pattern impersonates the flag it spells: `tumwater logs --grep -f` silently enters follow mode and hangs, and `--grep --since` / `--grep --prompt` are falsely rejected as rival-flag combinations (found by bugfix loop 2026-09-28, fixed 2026-09-28)

- **Symptom:** every rival-flag scan in `cmdLogs` ran over the raw argument list, so the token at the `--grep` value's position was read both as the pattern and as the flag it spells. `logs --grep -f` engaged follow mode and hung instead of printing the no-match note and exiting; `logs --grep --since` and `logs --grep --prompt` failed with the "cannot be combined" errors meant for genuine rivals.
- **Reproduce:** in a scratch repo, `logs --grep --since` exited 1 with the combine rejection and `logs --grep -f` was still running three seconds after launch (killed by hand); a plain prose pattern was unaffected. Pinned by the new regression tests.
- **Cause:** `cmdLogs` detects rivals with `args.includes(...)`/`args.indexOf(...)` over the unfiltered argv, while `rejectUnknownArgs` — which runs first — does track flag-value consumption and so happily passed `--grep -f` through (the `-f` was a claimed value, not an unknown token). The two layers disagreed about what a token at a value position means, and the parser side lost.
- **Fix:** `cmdLogs` computes `rest` — args with the `--grep` value's one position removed — and runs every flag scan over it: the rival checks, `follow`, `-n`, `parseRoleScope`, and `showPrompts`. With no `--grep`, `rest` is argv unchanged and every check behaves exactly as before; a genuine rival still fails (it sits at its own position, which the removal never touches).
- **Fixed:** 2026-09-28, regression tests in test/cli-logs-filtering.test.ts (`logs --grep treats a flag-shaped pattern as text, not as the flag it spells`, `logs --grep -f does not enter follow mode over its own pattern`): `--grep --since`, `--grep --prompt`, and `--grep -f` each exit 0 with the gentle no-match note — the `-f` case's plain exit within the test harness's 20s bound is the assertion, since pre-fix it hung in follow mode.
- **Validation gap:** real-run-needed (closest tag: the run was offline and local, so nothing about it needed a live model — what was missing was any test case at all handing a flag-shaped token to the parser; the suite's `--grep` cases only ever used prose patterns, so the misclassification surfaced only when the command was run by hand).

- **Symptom:** the negation guard accepted markdown decoration around the token (`**none**`, `` `n/a` ``) and any punctuation-dress appended note (`none; …`, `none - …`, `none (…)`) — but a straight-quoted dress classified as a genuine refusal: `none "nothing to do"`, `"none"`, `'n/a'`, `"(**none**)"` all returned `false`, so a work-completed reply ending that way had its tested work hard-reset — the same destruction the previous five fixes in this guard closed, one dress at a time.

### A punctuation-separated explanation after the negation reads as a genuine refusal: `TUMWATER_REFUSED: None; nothing to refuse.` fails `isNegatedRefusal`, so the harness hard-resets the tick's finished, tested work (found by bugfix loop 2026-09-28, fixed 2026-09-28)

- **Symptom:** the negation guard tolerated an appended explanation in the dash dress (`none — bug filed normally`) and the parenthesized dress (`none (no entry refused this run)`) — but the same note riding a sentence mark still classified as a genuine refusal: `None; nothing to refuse.`, `None. Nothing worth doing.`, `None, nothing refused`, `n/a; no open bugs` all returned `false`, so a work-completed reply ending that way had its tested work hard-reset — the same destruction the previous four fixes in this guard closed, one dress at a time.
- **Reproduce:** `isNegatedRefusal("None; nothing to refuse.")` returned `false` (scratch node run against the built module, one line); the suite had no case for any punctuation-separated shape. Pinned by the new regression test.
- **Cause:** the appended-explanation branch matched only a dash or an opening parenthesis right after the token; the separator class omitted the sentence punctuation (`;` `:` `,` `.` `!` `?`) that a model naturally starts a short note with — while `bare()` strips those marks only when they *end* the reason, so `None.` negated but `None. Nothing worth doing.` did not.
- **Fix:** the separator class now accepts any character that cannot begin a reason word — the ASCII hyphen and en/em dashes, an opening parenthesis, or sentence punctuation — as the start of an appended note, still anchored right after the token so a reason that continues with a letter (`none of the attempted fixes work; repro attached`) stays a refusal. This replaces dress-chasing with the rule the previous fixes were each approximating: after the token, punctuation is formatting, a letter is the reason itself. The hyphen is explicitly kept in the class and pinned by test — an earlier landing of this fix dropped it to `[—–;:,.!?(]`, regressing `none - …` / `n/a - …` replies to genuine refusals, and was rejected in review for exactly that. Accepted tradeoff, same as the dash dress already carried: a real objection that opens with the word (`none, I mean it: stop`) now negates.
- **Fixed:** 2026-09-28, regression test in test/reply-contract.test.ts (`isNegatedRefusal negates none and n/a with a punctuation-separated explanation`): eleven punctuation-separated shapes return true — including both hyphen dresses (`none - nothing to do`, `n/a - no open bugs`) and the em-dash dress; a reason that continues with a word despite a semicolon later stays a refusal.
- **Validation gap:** unclear-invariant — the docstring enumerated the accepted dresses (dash, parenthesized, trailing mark) without stating the underlying rule, so confirming the gap meant first reconstructing that rule (punctuation after the token cannot begin a reason word) and noticing the semicolon/period/comma dresses were still outside it; the review also caught the fix itself narrowing the dash dress, which no test pinned.

### A parenthesized explanation after the negation reads as a genuine refusal: `TUMWATER_REFUSED: none (no entry refused this run)` fails `isNegatedRefusal`, so the harness hard-resets the tick's finished, tested work (found by bugfix loop 2026-09-28, fixed 2026-09-28)

- **Symptom:** the negation guard already tolerated a dash-appended explanation (`none — no entry refused this run`), trailing sentence marks (`None.`), and markdown decoration (`**none**`) — but not the same explanation in parenthesized dress: `none (no entry refused this run)`, `None (nothing to do)`, `n/a (nothing fits)` all classified as genuine refusals, so a work-completed reply ending that way had its tested work hard-reset — the same destruction the previous three fixes in this guard closed.
- **Reproduce:** `isNegatedRefusal("none (no entry refused this run)")` returned `false` (scratch node run against the built module, one line); the suite had no case for the shape. Pinned by the new regression test.
- **Cause:** the appended-explanation acceptance lived only in the dash branch of the final shape regex (`[ \t]*[—–-].*`); a parenthesized note after the token matched nothing, and the bracket-stripping pipeline only helps when the token sits *inside* the brackets (`(none) — …`), not when the explanation follows it.
- **Fix:** the shape regex also accepts a token followed by an optional space and an opening parenthesis (`[ \t]*\(.*`), anchored right after the token so a reason that merely begins with the word (`none of the attempted fixes work (repro attached)`) stays a refusal — the same tradeoff the dash-append form already accepts.
- **Fixed:** 2026-09-28, regression test in test/reply-contract.test.ts (`isNegatedRefusal negates none and n/a with a trailing parenthesized explanation`): seven negating shapes return true; a real reason with a trailing note, a reason beginning with the word `none`, and a bracket inside the token (`(no)ne`) stay refusals.

The observed growth was +27–38K. The estimate assumes today's 137 inner npm processes per suite run, which is probably high for those dates. On Sep 24 the fleet was nearly idle, and the count still grew +9.7K from hand-run suites.

The preload has to be an accessor: an `Object.defineProperty` with `value` goes through Node's native setter, so the process checks in by itself. The preload is inline rather than a file, so a rebuild or swap of dist/ cannot leave NODE_OPTIONS naming a missing module. Measured after the fix: `npm test` produced 2 check-ins from one process, the outer npm (−4 ports). The same tick produced 0 check-ins (−3). Pinned by test/process.test.ts, where the preload must keep a title out of `ps` and the `value` variant fails; test/pi.test.ts; test/launch-services.test.ts; and test/launch-services.e2e.test.ts.

**Remaining:** An npm that a person or another tool runs directly still checks in once, before any tumwater code runs: 1 port per `npm test` instead of 138. Only a restart resets launchservicesd, because it is a system daemon; logging out does not. A managed project whose toolchain runs Node older than 18.18 would reject `--import` in NODE_OPTIONS.

**Validation gap:** real-run-needed — the leak lives in a system daemon that nothing tumwater reads, so confirming it took bounded real runs on macOS with the port count read from `top` and the check-ins from the unified log; offline, the suite can only pin the mechanism, a title kept out of `ps`.

### The live-progress tail seeds from an arbitrary byte offset, so a first observation reports a turn count that means nothing (reported by user 2026-09-22, fixed 2026-09-22)

**Symptom:** `readLiveProgress` seeded a first observation from `size - TAIL_BYTES` (`src/ui/progress.ts`, 4 MB) with `freshProgress`, treating that byte offset as if it were a run boundary and counting every assistant `message_end` after it. Role logs rotate at `logMaxBytes`, default 16 MB, so a log is routinely larger than the window: a freshly attached observer (`tumwater gui`, or any first `readLiveProgress` call in a process) displayed `turn 9` for a run whose real count was something else, until a session boundary happened to enter the window. `parseProgress` on assistant `message_end` lines with no `session` line returned a positive `turns` — the reader could not distinguish "this run has N turns" from "I started reading N turns into some run". The steady-state path was correct (it only parses bytes appended since the previous poll, anchored by sessions already seen), so the flaw showed only on the first observation — exactly when nobody is checking.

**Repro:** Deterministic, no fleet. `readLiveProgress` over a log of one `session`, one assistant turn, then >4 MB of streaming deltas (the last 4 MB hold no session and no turns) reported `turns: 0` for a run whose real count is 1; over one `session` plus >4 MB of assistant turns it reported only the turns inside the last 4 MB. Both now regress in `test/progress.test.ts`.

**Fix:** `findSeedOffset` (`src/ui/progress.ts`) grows the seed window in doubling steps from `TAIL_BYTES` until it contains the log's last complete `session` event line (or 0 when the log carries none), and first observations seed from there instead of the bare offset. The session event resets the accumulator during the seed fold, so the turns a first observation reports are exactly the current run's. The scan runs at attach time only — steady-state polls still parse only appended bytes — is bounded (~log2 reads over a rotated log, ≤3 windows against the 16 MB rotation cap), and is cheap because the type-first pre-filter skips `message_update` lines without `JSON.parse`. `test/progress.test.ts` pins the scan (`findSeedOffset` grows past a session outside the window, returns 0 for a sessionless log) and the two end-to-end seed counts above. Suite 1287/1287.

**Validation gap:** no-fake — the suite only ever seeded logs smaller than the 4 MB tail window, so nothing exercised a first observation past its edge; confirming the fix required building oversized-log fixtures (>4 MB) that did not exist.
### One pi log per role, two pi runs writing it: a landing run's `session` event resets the turn counter the dashboard shows for the authoring tick (reported by user 2026-09-22, fixed 2026-09-22)

**Symptom:** The director's state cell read `turn 15`, then `turn 3` moments later — the in-flight turn counter running backwards inside one tick. `readLiveProgress` (`src/ui/progress.ts`) derives it by counting assistant `message_end` events since the **last `session` event** in the role's raw log, and `src/ui/progress.ts:115` restores the at-time-zero state on every one it sees; `src/ui/status-model.ts:46` renders that as `turn ${p.turns + 1}`. The module's premise is stated in its header at `src/ui/progress.ts:7`: "The log is append-only across ticks; each tick's pi run starts with a `session` event, so everything after the last one belongs to the current run."
```
10:16:52 PDT (09-21)  cwd=…/worktrees/director        24 turns  → cell read "turn 25"
00:27:20 PDT (09-22)  cwd=…/worktrees/_land-director   7 turns  → reset to 1, climbed to 8
00:28:41 PDT (09-22)  cwd=…/worktrees/director        10 turns  → reset to 1, then 11
```

Two resets in 2 min 18 s. The counter is only half of it: between 00:27:20 and 00:28:41 the cell's `turn`, `ctx` and tool label all described the **landing** run while the label said `working` and the elapsed time counted the authoring tick — the row was reporting one run's progress under another run's heading. **Repro:** Deterministic, no fleet. **Fix:** Carry the run's identity into the reader (the shared transcript stays one file, as the operator's end-to-end `logs --role` view wants). Suite 1281/1281.

**Validation gap:** unclear-invariant — the existing suite actively pinned the buggy behavior as the documented contract ("resets at a new session"), so confirming the bug first required reconstructing what the cell was supposed to guarantee: per-run attribution (whose turns is the working cell showing?), which only the `session` event's `cwd` can answer.
