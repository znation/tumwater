### `test/supervisor.test.ts` "startParentDeathWatch takes a SIGKILLed supervisor's grandchild down with it" flaked again on 2026-10-16, after its 10-01 and 10-09 Fixed entries and the 10-11 rewrite to a SIGUSR2-driven poll (found by operator session 2026-10-16 from improve's red merge check)

- **Symptom:** at 07:29:28 PDT, improve's in-lock merge check for `d4b62873` failed one test: `✖ startParentDeathWatch takes a SIGKILLed supervisor's grandchild down with it — AssertionError [ERR_ASSERTION]: the orphaned grandchild's watch fired and ran its stop path`. The check ran 145 s. Recovery re-landed it green at 07:40, and it merged. That is the same assertion as the Fixed entry "The SIGKILL-grandchild supervisor test flaked twice in one 2026-10-09 window". Since then 4ec5d729 (10-11) replaced the real poll with one driven by SIGUSR2 from the test, and its comment says a loaded host "cannot stretch" the verdict. It still fails.
- **Reproduce:** no repro; one live failure under the team's normal load.
- **Cause:** unknown. After SIGKILLing `middle`, the test sends SIGUSR2 up to 200 times, 50 ms apart (about 10 s), and breaks out of the loop early if `process.kill(grandchildPid, …)` throws. The failure reads the same in two cases, and the message cannot tell them apart:
  - the reparent was not visible to the grandchild's `process.ppid` within those signals;
  - the grandchild had already exited without writing `gone`, so the loop broke on ESRCH.
- **Expected / fix sketch:** first make the failure name its case. Record whether the loop broke on ESRCH and how many signals were sent. Have the grandchild write the `ppid()` it saw on each poll. Then fix the case that fires. Re-check the 10-09 entry's mechanism, a watch armed against the wrong baseline, on the handed-down `expectedPpid` path.
- **Progress 2026-10-16 (bugfix):** the test's failure message now names its case: signals sent, whether the loop broke on ESRCH, the expected ppid, and the ppid the grandchild saw on each poll (a `gone.seen` file). The cause is still unknown, so the entry stays open until the next flake reads out.
- **Progress 2026-10-16 (bugfix, second):** one candidate cause closed, unconfirmed: the test treated the existence of `started` as ready, but the grandchild created it with `writeFileSync`, so the test could read an empty or partial pid and SIGUSR2 the wrong pid (ESRCH, no `gone`). The grandchild now writes `started.tmp` and renames it. No flake has been seen since, so the entry stays open until the next failure reads out.
- **Progress 2026-10-16 (bugfix, third):** no repro. 30 concurrent runs of the test beside 8 CPU-spinning node processes all passed (the `timeout` wrapper on the spinners did not exist on this host, so the spinners ran unbounded until `pkill`; the load was real). `startParentDeathWatch` (src/process/supervisor.ts:79-104) reads correctly on the handed-down `expectedPpid` path. No code change; the entry stays open until a flake's failure message (signals sent, ESRCH or not, ppids seen) names the case.
- **Progress 2026-10-16 (bugfix, fourth):** one more candidate closed, unconfirmed: the signal loop was bounded by a count (200 × 50 ms), so a grandchild starved for longer than that (the 145 s check suggests heavy load) could miss every poll and the verdict was read right after. The loop is now bounded by 60 s of wall clock. The entry stays open until a flake reads out.

**Waiting for the next failure 2026-10-16 by bugfix: the failure message will show signals sent, whether the loop broke on ESRCH, the expected ppid, and the ppid the grandchild saw on each poll (`gone.seen`).**

### Two `logs -f` processes leaked out of a slot's run and stayed alive for 3½ days; the doctor only detects them, nothing reaps them (found by operator session 2026-10-19 from the running instance's `tumwater doctor`)

- **Symptom:** on 2026-10-19 13:46 `tumwater doctor` reported `fail orphans`: `2 orphaned processes (PPID 1): pid 59222 (age 03-11:24:45, cpu 0:42.79) node .tumwater/worktrees/_slot-8/dist/src/cli.js logs -f; pid 60127 (age 03-11:24:17, cpu 0:42.74) node .tumwater/worktrees/_slot-8/dist/src/cli.js logs -f — nothing reaps these`. Both were started Fri 2026-10-16 02:35:55 and 02:36:23 in `_slot-8`, reparented to launchd (PPID 1), and survived roughly a dozen orchestrator generations and the 2026-10-18 pi-stdin fix without ever being reaped.
- **Reproduce:** `tumwater doctor` on the live project reports the check red while the processes stand; `ps -o pid,ppid,lstart,etime,command -p 59222,60127` shows PPID 1 and the Oct 16 start. No scratch repo; it is a live-state leak.
- **Cause:** unknown. A `logs -f` left running after the run that launched it ended was not in the run's killed process group (detached, or reparented when its parent bash exited), and no reaper collects PPID-1 orphans — the doctor's `orphans` check is a detector only ("nothing reaps these; kill each with its descendants"). Whether the spawner is a role's bash tool backgrounding `logs -f`, an operator shell, or the harness is not established from this evidence.
- **Expected / fix sketch:** establish what spawns a detached `logs -f` in a slot (grep the sessions for the Oct 16 window), then have the run/slot teardown reap its own process group including detached children — or give the doctor/orchestrator a reclaim step for orphans it can attribute to a slot. Confirm no other orphan source before adding a general reaper.
- **Progress 2026-10-19 (bugfix):** not reproducible offline — the two processes are live-state evidence from before the doctor's run-mark attribution (`src/doctor/doctor-orphans.ts` `runMarkers`/`harnessGone`), which now names the run and the dead harness pid for an orphan that inherited a run's mark. No reaper added: the spawner is unestablished, and a general reaper before that risks killing operator processes.
- **Progress 2026-10-19 (feature):** `tumwater logs -f` (both the event feed and `--role` transcripts) now ends itself once its parent pid changes (`followUntilParentGone` in src/cli/log-commands.ts), so a follow reparented to PPID 1 stops; the spawner question below still stands.

**Waiting for the next failure 2026-10-19 by bugfix: a `fail orphans` line for a leaked `logs -f` will end with `(run <pid>-…; tumwater <pid> exited)` when it inherited a run's mark, naming the run that spawned it; a line with no such suffix means the process escaped the mark (detached with a cleared environment) and the spawner is still unknown.**

### Dashboard banner "Open backlog" does not open the entry it names: the backlog card stays on the tab it was already showing (found by operator session 2026-10-21 from the refused-entry banner) (reported by the user 2026-10-21)

- **Symptom:** with one refused entry on the board, the dashboard banner "1 refused entry waits on your decision" (alerts key `refused`, src/ui/team-alerts.ts) offers an "Open backlog" button. Clicking it opens the backlog card without changing its tab, so the operator is left looking at whatever tab the card was last on (`recall("backlog")`, src/ui/gui/gui-client-backlog.ts). On 2026-10-21 the banner's entry was the bug "Structural risk: the whole open roadmap is one 41-merge serial rename chain, so no parallel capacity exists behind the in-flight front part" — `d.bugs[1]`, mark ` [blocked: refused]` — while the card sat on Plans, so the flagged entry was visible nowhere on screen and a correct banner read as one naming an entry the UI did not have.
- **Reproduce:** on a checkout with one refused bug and no refused plan, `tumwater gui`, put the backlog card on Plans, then click "Open backlog" on the refused banner. The card stays on Plans; the entry is only on the Bugs tab, under the `Blocked (N)` divider. Verified 2026-10-21 against the live payload of this checkout: 12 plans, `planBlocked` 7 with no refused hold, `bugHolds[1] === " [blocked: refused]"`, `bugBlocked[1] === true`.
- **Cause:** the alert's action carries no target. teamAlerts pushes the refused alert with `actions: [{ label: "Open backlog", act: "backlog" }]` (src/ui/team-alerts.ts), and the dashboard's dispatch (src/ui/gui/gui-client-boot.ts) reads `act === "backlog"` as "open the card and nothing else" — `if (act !== "backlog") setBacklogTab(act)` — so the tab is never touched. The sibling alerts that do land correctly (`questions` → the Questions tab, `queued` → the Inbox tab) work only because each names one tab; the refused alert spans two files (refusedEntryTitles returns the planned plans and then the open bugs, src/backlog/backlog-eligibility.ts), so no single tab stands for it — and its detail names no kind either, leaving the entry's title as the operator's only clue.
- **Expected / fix sketch:** the alert should carry the entry it points at, not the card it opens. Cheapest honest step: hand teamAlerts the refused entries as { file, position, title } (widening refusedEntryTitles' titles-only return) and emit one alert per kind — or per entry — whose `act` names that tab and the row, so gui-client-boot.ts's backlog arm can `setBacklogTab` and scroll/highlight that row the way `.backloglink` selection does. If the one combined alert is kept, its detail must name the kind ("Refused bug …" / "Refused plan …"). Either way: a banner that says an entry waits on a decision must land the operator on that entry.

### Every role's prompt says a closing date reads "— fixed YYYY-MM-DD by the <role> role", but a finished plan's Done stamp is "done YYYY-MM-DD", so a feature role that stamps per the prompt is rejected (found by operator session 2026-10-21 from the refused Newest-failure plan's review chain) (reported by the user 2026-10-21)

- **Symptom:** the assembled run prompt (src/prompt/prompt.ts:371, `sharedPreamble`'s "Stamp it on anything you record now …") tells every role `a closing date reads "— fixed YYYY-MM-DD by the <role> role"`. A feature role that obeys it for a finished plan is rejected by the deterministic backlog-structure rule (src/backlog/backlog-structure.ts:306-320). Live case: the plan "Dashboard History gains a Newest failure button that opens the team's newest failing run, the `history --last --result problems` twin" was moved from `## Planned` to `## Done` with the heading stamp `— fixed 2026-10-20 by the feature role`, and all three review rounds rejected the change (feature-2 heads c35d9f84, cd5ef180, 8cfa830a; reason text `… files "…" directly under "## Done" with no done date`), ending in a refusal once the repeat-finality cap was reached (run 552; `REVISION_FINAL_ON_REPEAT = 2`, src/runner/revision.ts:25). The implementation itself was green and untouched.
- **Reproduce:** `PLANNED_DATE`/`DONE_DATE` read the joined heading metadata (src/backlog/backlog-structure.ts:92-93); `DONE_DATE` and the readers' `DONE_DATE_RE` (src/backlog/backlog.ts:116) match only `/done (\d{4}-\d{2}-\d{2})/`, while `FIXED_DATE_RE` (src/backlog/backlog.ts:123, `re-landed|fixed|closed|resolved`) is the BUGS.md-only spelling. `strandedPlanEntries("### X (planned 2026-10-20 by the plan role) — fixed 2026-10-20 by the feature role")` returns the entry; the same heading with `— done 2026-10-20 by the feature role` returns nothing. `tumwater plan --show --done --json` likewise reports no `completedOn` for the fixed-stamped form.
- **Cause:** that sentence is the BUGS.md `## Fixed` convention — every entry in BUGS-FIXED.md reads `— fixed <date> by the <role> role` — stated for every role instead of for the bug kind. Nothing in the prompt names the plan token. `backlogMoveGuidance` (src/roles/role-guidance.ts:31, shared by the feature and bugfix roles so the two cannot drift) says only "add the closing date to its `### ` heading", leaving the plan stamp's verb and position to guess. Placing the stamp before the existing `(planned …)` parenthetical additionally changes `planHeadingKey` (the heading text before its first ` (`, src/backlog/backlog-structure.ts:143-146), so the Planned→Done move no longer keys equal to the base heading and the gate reads it as a brand-new plan under `## Done` rather than a move.
- **Expected / fix sketch:** split the sentence by kind: a finished plan closes with `— done YYYY-MM-DD by the <role> role`, appended after the existing `(planned …)` parenthetical; a BUGS.md record keeps `— fixed YYYY-MM-DD by the <role> role`. Have `backlogMoveGuidance` name the token (and the "the heading key must not change" rule) instead of "the closing date", with the token chosen by the caller. Pin both with tests: the assembled feature prompt, and the guidance text for each kind.

### The backlog-structure gate tells an author whose finished plan is already archived to "file it under '## Planned' in PLANS.md instead", the opposite of the fix, and a revision followed that advice (found by operator session 2026-10-21 from the refused Newest-failure plan's review chain) (reported by the user 2026-10-21)

- **Symptom:** `backlogStructureReason` renders one message for PLANS.md and PLANS-DONE.md (src/backlog/backlog-structure.ts:314-319): `<file> files "<title>" directly under "## Done" with no done date — a plan written into the done section is invisible to every Planned reader; file it under "## Planned" in PLANS.md instead`. For an entry already sitting in PLANS-DONE.md the only fault is a missing `done YYYY-MM-DD` token, so the trailing clause is exactly wrong: the entry is finished and archived, and restoring it to `## Planned` is what the next review rejects. Live case: revision 2 of the Newest-failure plan (feature-2 run 549, head a6a3bbec) did that — its commit reads `Restore PLANS.md/PLANS-DONE.md to main so the plan sits under ## Planned, not DONE` — and the following review rejected the change for the opposite reason ("the finished plan is still not under PLANS.md's `## Done`"), so the chain spent a revision on the wrong repair. Revision 3 repeated the original objection, its persistence count reached the cap, and the plan was refused with a note directing the team not to re-author the theme.
- **Reproduce:** stage a change that moves a plan from `## Planned` to `## Done` with a `— fixed <date>` stamp (no `done` token): the stage check names PLANS.md and the same message. The same entry after the commit-time archive sweep is reported against PLANS-DONE.md with the identical `file it under "## Planned" in PLANS.md instead` clause, even though the entry must stay finished and archived.
- **Cause:** the branch was written for the pre-sweep view — the author pastes into the live file, the gate reads the live file — and its fix line assumes the entry was never finished. Since the commit-time sweep (`archiveNewFinishedEntries`, src/run/run-stage.ts:313-318) runs before the commit, the gate normally sees the archive, where the assumed fault and the real fault differ.
- **Expected / fix sketch:** branch the message on the file: when the offending entry is in the archive, name the real fix (add `done YYYY-MM-DD` to its `### ` heading); keep "file it under `## Planned`" only for a heading a Planned reader should have had, i.e. the PLANS.md form. Test both branches on the same fault.
