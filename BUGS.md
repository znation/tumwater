### The `## Fast merge guardrails` line's `red since <sha>` names a non-breaker code tip when the commit that broke the suite landed in the same poll batch (found by the selfcheck role 2026-11-04)

- **Symptom:** the 2026-11-04 digest's `## Fast merge guardrails` line reads `main has had no passing full check for 943 min: red since 23a2f2c9 at 07:04 — every comment line in src/ and test/ fits in 100 columns and opens no block inside a block`. It names 23a2f2c9 (`tumwater(reviewer): Fix 905ec50e`, diff touching only `src/cli/follow-view.ts` — 5 comment lines, all ≤95 columns) as the commit main has been red since. The named test is `test/comment-width.test.ts` "every comment line in src/ and test/ fits in 100 columns…". 23a2f2c9 cannot have broken it: its only diff is a ≤95-column comment in a file the test reads but does not flag, and it adds no over-100-column line.
- **Reproduce (verified by git):** the true breaker is 642a6ffed (`tumwater(feature): Add the `retired` stamp…`), the first first-parent commit whose tree fails the test: its tree has 2 over-100-column comment lines (`test/backlog.test.ts:577`, `test/stage-check.test.ts:1098`, both 103 cols), and its first-parent parent (663b9bb7a) has 0. 642a6ffed landed ~4 min before the named tip (06:57 vs 07:01 by committer date) and is a first-parent ancestor of 23a2f2c9. So the suite went red at 642a6ffed, and 23a2f2c9 is only the newest red tip the watch checked. (The current main tip is red with 10 offenders across 9 files; the spell has been growing, not the single named test.)
- **Cause:** `poll(mainHead, …)` (src/baseline/main-watch.ts:556) checks out and checks only the newest tip per poll, never each merged commit in the batch individually. When several commits land between two polls and an earlier one in the batch breaks the suite, the watch's next poll sees only the newest tip and records the first red there. `redOpener` (src/baseline/main-watch.ts:336) walks back to the breaker only when the tip's own diff is review-exempt (`isExemptDiff`); 23a2f2c9 touches `src/` (a non-exempt path, `exemptPaths = ["*.md", "docs/**"]`), so `redOpener` returns the tip at once. G1's `red since <sha>` (src/baseline/main-guardrails.ts, `startEv` = the first red `main_check` = 23a2f2c9) and the ci heal prompt then name the newest tip, not the breaker that is two first-parent commits behind it. This is the same attribution gap the 2026-11-02 redOpener fix closed (BUGS-FIXED.md 2026-11-02), but the fix's doc-exempt walk does not reach it: the tip here is a non-exempt code commit, so no walk runs at all. The gap is not pinned by any test — test/main-watch-spells.test.ts covers only the single-interval code-then-doc case ("a doc-exempt tip on top of a code commit that broke main names the code commit as the opener"); a multi-commit batch whose breaker is not the tip is untested.
- **Cost / why fileable:** the guardrail line is the operator's (and this role's) only pointer to what broke main; naming a commit that did not break it sends the ci heal prompt and any human at the wrong commit — the response to the red is wrong, which is a rule-1 bug, not weather.

### The gate's 20 s test budget leaves out the repo-wide lint scans, so changes merge new offenders and main stays red (found by operator session 2026-11-05 from the team's event log)

- **Symptom:** four repo-wide scan tests fail at main's tip (`c5086fb45`): `every comment line in src/ and test/ fits in 100 columns…` (10 lines), `no exported symbol goes unused outside its own file` (4 names), `no identifier or file name in src/ or test/ uses a retired name` (5 lines) and `scanned src modules use only plain terms` (1 line). Every offending line was merged through the gate. `git blame` puts 10 of the 13 lines after the red opened at 07:04 on 2026-11-04: `0036f32f9` 07:12 (src/report/report-main-red.ts:126, src/report/report-since-data.ts:168), `bd71c3159` 12:31 (test/reply-contract.test.ts:364, test/run-dismiss.test.ts:173, src/roles/role-catalog.ts:500), `9d5e23a90` 14:51 (src/baseline/main-watch.ts:88), `d47a9eb87` 17:21 (src/merge/merge-post-review-drain.ts:261), `604b3f149` 19:20 (src/merge/merge-pipeline.ts:76), `bff0b1de7` 19:44, a reviewer fix (src/merge/merge-post-review-drain.ts:155), and `31923cd6b` 23:45 (test/report-data.test.ts:1465, retired name `loop`).
- **The scans were not run, not excused:** on a red main, a gate that runs comment-width fails it and logs `gate check fails only main's known failures: every comment line…`. That message appears for `2fa28fbfb`, `960718fee` and `3bf28b908`, which added no wide comment. The gates of `d47a9eb87` and `604b3f149` named only `scanned src modules use only plain terms`, and those of `bd71c3159` and `9d5e23a90` logged no excuse at all, so comment-width was never selected for them.
- **Reproduce:** append a 125-column `//` comment to src/merge/merge-pipeline.ts and run the gate's test step, `node dist/test/test-runner.js --affected=HEAD --budget=20` (checked 2026-11-05 at `c5086fb45`). It reports "27 of the 157 test files that reach the 1 changed file(s) … fit the 20s budget" and passes 264/264, and none of the four scans is among them (even test/merge-pipeline.test.ts is left out). `npm test` then fails `test/comment-width.test.ts`.
- **Cause:** test/affected-tests.ts ranks every tree scanner (~60 files) at `SCANNER_DISTANCE = 2`, and `fitBudget` fills `--budget=20` by distance and then cost. Tests at distance 0 and 1 crowd the scanners out, including these four. Yet they are cheap: measured at 0.1 s, 5.0 s, 1.8 s and 0.7 s. A second, latent gap: when a gate does run one of them on a red main, `onlyKnownMainFailures` (src/baseline/main-watch.ts:146) excuses it by test name, so a new offender in an already-failing scan would pass as main's known failure.
- **Expected / fix sketch:** always run the repo-wide policy scans in the gate (a must-run set outside the budget, or rank them at distance 0 for any src/ or test/ change), or check them per changed file in `scripts/lint-changed.mjs`. For the excuse, compare offenders, not test names: a scan failure that lists a line or name main's own failure does not list belongs to the change.

### A post-merge reviewer's fix that conflicts with main can never merge: the resolver's resolution is always discarded, and each retry re-runs the whole review (found by operator session 2026-11-05 from the team's event log)

- **Symptom:** `28f1e703` (feature-4, "Remote CI part 2/3", merged 2026-11-04 17:57) was post-merge reviewed at 19:44. The reviewer found a real gap: the `remote CI` doctor row was not omitted when the ci role is disabled. Its fix (`37d2a4f0b`) conflicted with main in docs/how-it-works.md (lines 286–323, where main had since added the remote-CI badge paragraph). A resolver run (`.tumwater/sessions/feature-4/2026-11-05T03-56-06-740Z_…`) merged both paragraphs in 22 s, yet the landing returned `merge_conflict` ("the post-merge fix of 28f1e703 could not merge (merge_conflict); it stays queued for the next poll", 19:56). At 23:45 a second full review of the same commit wrote a new fix. It hit the same conflict, and its resolver (`2026-11-05T07-57-50-869Z_…`) was discarded again at 23:58. The entry now reads `failures: 2`, `lastFailure: "fix did not merge: merge_conflict"`. The next failure drops the review and files it here (`fileDroppedReview`, src/merge/merge-post-review-drain.ts:290), and the reviewer's fix is lost (it survives only at `refs/tumwater/review-fix/28f1e703`).
- **Cost:** each attempt spends one reviewer run plus one resolver run on a MERGE_TIER permit, which is admitted ahead of role runs. All of it is thrown away.
- **Reproduce:** queue a post-merge review of commit C, then merge a change to main that edits the same lines of a file the reviewer's fix will touch. The fix is authored on C, so its landing conflicts. Any resolution replaces main's edit, so it diverges, and the entry is retried and finally dropped.
- **Cause:** `mergeReviewerFix` passes `recheckResolved: async () => ({ verdict: "retry" })` (src/merge/merge-post-review-drain.ts:264). In `mergeToMain` (src/merge/merge-to-main.ts:106–109), a resolution whose diff leaves the fix's own lines (`resolvedDiffDiverges`, src/merge/merge-diff.ts) goes to `recheckResolved`, and `retry` returns `merge_conflict`. A resolution of lines both sides edited always leaves them: it replaces main's new wording, which the fix's own diff never deleted. The failed landing leaves the entry with neither `fixed` nor `rejected`, so `unreviewed` is true and the next drain starts a fresh review of C. That review authors its fix on C again, so it conflicts again.
- **Expected / fix sketch:** never run a resolver whose result is always discarded. Either judge the resolved tree, as `mergeApprovedChange`'s `recheckResolved` re-reviews a resolved conflict (src/merge/merge-core.ts:423), or, on a conflict, retry by rebasing the stored fix ref onto main's tip, or have the retry's review author its fix on main's tip rather than on C.
