## Open

### A batch reviews its changes one after another, so its wall-clock is the sum of every review and one slow reviewer holds the whole queue (found by human log analysis 2026-09-23)

**Symptom:** A batch's time in the landing slot is the sum of its Phase A gates plus one shared check. On 2026-09-23 the 03:42:00 batch took 40 minutes: feature's gate and review 03:42–04:00 (review 998 s), then organize's 04:00–04:11 (539 s), then clean's 04:11–04:19. Each gate ran its own full build check first (104 s, 116 s, and a 300 s timeout). The batch check ran last, 04:19–04:21. Everything queued behind waited for the whole chain: readme 41 minutes, improve 37.

**Repro:** Deterministic, no model needed: batch three entries with fake reviewers that each take T. The batch takes about 3T plus the check, because the Phase A loop (src/land-batch.ts:132) awaits `reviewPinnedChange` for each request in turn.

**Expected:** Each Phase A gate already runs in its own `_land-<role>` worktree with its own session and state, so the gates could run concurrently, bounded by a small limit because each one runs a full suite. Stacking would still follow queue order. That makes a batch's slot time max(review) plus the check, instead of the sum.

**Suspected cause:** The loop was written to stop early (an under-cap `review_error` leaves the rest unattempted), and running gates in parallel would need that rule rethought. Batching was introduced to save build checks, not reviewer time.

### A batched landing is displayed as the head change's landing for the whole batch: the head role reads `landing 29m` long after its own change was rejected, while the change actually being gated shows nothing (reported by user 2026-09-23)

**Symptom:** On 2026-09-23 at 03:42:00 the landing slot picked up a `landBatchMax: 3` batch: feature `da13291`, organize `cc96b31`, clean `6079c16`. Feature's gate check passed at 03:43:44, and its review ran 998 s and ended `review_rejected` at 04:00:22. Organize's gate and review ran 04:00–04:11 (approved), then clean's gate started at 04:11:17. Throughout, `.tumwater/state/landing.json` still named `role: "feature"`, `sha: da13291…` with `startedAt` 03:42:00. The feature row showed `landing 29m` and climbing, and the user asked why feature was stuck on landing. Feature's change was finished (rejected) eleven minutes earlier, and the roles whose changes were actually in review and build check (organize, then clean) did not show a landing state.

**Repro:** Deterministic, no model needed: queue ≥ 2 entries from different roles with `landBatchMax ≥ 2` and a fake reviewer that rejects the first and takes a while on the second. While the second is in review, `readLandingMarker` returns the first entry, and `loopPhase` renders `landing <elapsed>` on the first role's row only (`landingForRole` filters by `marker.role`, src/ui/status-model.ts:78–121), with elapsed measured from the batch's start.

**Expected:** The display should show which change the slot is working on right now, and the elapsed time for that change. Either the batch arm advances the marker to each request as Phase A reaches it (role, sha, per-change `startedAt`), or the marker carries the whole batch (every role plus the current index) so each batched row can show `landing` / `queued in batch` / `rejected, awaiting batch` honestly. A role whose change already reached a terminal verdict must not keep a live `landing` label.

**Suspected cause:** The batch arm writes the marker once, for `batch[0]`, before `landBatch` runs, and removes it only in its `finally` (src/orchestrator.ts:602 and :674). The code comment calls this a deliberate choice ("The 4/5 marker names the HEAD request … the other batched roles show their queued state in the queue itself"), because the startup cross-check validates the marker against a still-queued entry. Nothing in `landBatch` (src/land-batch.ts) touches the marker per request. The per-stage marker from the landing-cell entry above would not fix this by itself, since it adds a stage but keeps one role per batch.

### A change rejected early in a batch keeps its role blocked for the rest of the batch: the author cannot start the fix tick until every other batched change finishes review, build check, and merge (found by human investigation 2026-09-23, fixed 2026-09-24)

**Symptom:** In the 03:42 batch of the batched-landing display entry ("A batched landing is displayed as the head change's landing"), feature's review rejected `da13291` at 04:00:22. That verdict is final: Phase A records `rejected`, and the gate has already deleted the landing ref and reset the worktree to main. But feature's land-queue entry (`.tumwater/land-queue/1790159851127-000004-35472.json`) stayed on disk, so the merge-queue interlock kept feature from ticking. At 04:15 feature was still blocked, with clean's gate, clean's review (organize's took 9 min, feature's 16.6 min), the shared stack build check, and the fast-forward still ahead. The role with the most urgent work (a concrete three-point rejection to address) is the one held longest, and the wait grows with each change batched behind it.

**Repro:** Deterministic, no model needed: batch two entries, the first rejected quickly and the second held in a slow fake review. After the first verdict, `queuedLandingFiles` still lists the first entry and the first role's due tick is skipped every poll (src/orchestrator.ts:695, :714) until the second review returns.

**Expected:** A request whose Phase-A outcome is terminal (`rejected`, a strike-cap `review_error` discard, `error`) should have its outcome written and its entry dropped as soon as that verdict is persisted, so its role becomes eligible immediately. Approved entries should still stay queued until the stack lands, because their authors must not tick on top of an unlanded change.

**Suspected cause:** The batch arm calls `writeLandingOutcome` (which calls `dropLanding`) only for all outcomes together, in `outcomes.forEach` after `landBatch` returns (src/orchestrator.ts:623–660). `landBatch` already persists each verdict right away "so a mid-batch crash must not lose what the batch earned" (src/land-batch.ts:150), but the queue write-back was never moved alongside it. The single-entry path never showed this, because there the terminal verdict and the end of the landing are the same moment.

**Fix:** A final Phase-A outcome now leaves the batch the moment it is persisted. `landBatch` (src/land-batch.ts) takes an optional per-request hook, `BatchContext.onFinal(index, result)`, which Phase A fires (via `settleFinal`) for a rejection, a strike-cap `review_error` discard — `reviewPinnedChange` (src/lander.ts) now marks that return `discarded: true` — and an `error` for an uncheckable pin (its `lastError` already on the state); never for an approved/exempt change (queued until the stack lands or fails), `aborted`, or an under-cap `review_error`, deliberately: that one keeps its ref, so dropping it early would free its author to run leftover recovery against this batch's fast-forward. The batch arm (src/landing-drain.ts) answers the hook at once: `writeLandingOutcome` → `dropLanding` through a `written`-guarded `writeBack`, so the end-of-batch `outcomes.forEach` never applies, logs, or drops an outcome twice; the role is spliced out of `landing.roles`, so `abort --role` for its new tick no longer kills the batch and a user-aborted batch no longer discards that role's next pin; and when the dropped entry is the one the 4/5 marker names, the marker is re-pointed at the first batched entry still queued (the queue head, keeping the batch's `startedAt` and the stage the marker already shows — the new subject's own gate then advances it through `setLandingStage`), so the snapshot cross-check still validates a queued sha. The drop precedes the re-point, as in `landQueuedEntry`: a crash between them leaves a marker naming a dropped sha, which the cross-check never displays and the next landing overwrites; a crash after the drop can neither resurrect the entry (its ref is gone too) nor lose its outcome (already saved and logged). The catch branch now records an unexpected throw on the queue head's role rather than a head role that may already be ticking again; the comments the change made false are updated (landing-drain.ts, landing-slot.ts's `writeLandingOutcome`, land-batch.ts). Pinned by test/landing-drain.test.ts "a batched change rejected early drops its entry at its verdict…" — the Repro: alpha rejected at once, beta's reviewer parked on a release file; mid-batch `queuedLandingFiles` holds only beta, alpha's `rejected` is saved and logged once, `landing.roles` is `["beta"]`, and the marker names beta at its `reviewing` stage (it failed on that first assertion with the drain fix reverted); two landBatch tests in test/lander.test.ts (`onFinal` fires for a rejection before the next gate runs and never for an approval; for a strike-cap discard and an uncheckable pin, not for an under-cap `review_error`); and test/orchestrator-3.e2e.test.ts "a batched role rejected early ticks again while the rest of its batch is still in review" (a live orchestrator runs the rejected role's due tick while dry's review is parked). landing-drain + lander + landing-slot 51/51, orchestrator-3 20/20.

**Validation gap:** none — the existing fake-pi shim reproduced it deterministically once a reviewer parked on a release file held the batch open; nothing had reddened because every earlier batch test asserted only end-of-batch state.

### The self-redeploy's shutdown awaits an in-flight batched landing with no deadline — the generation handoff lagged its own swap by 97 minutes (found by telemetry loop 2026-09-23, fixed 2026-09-24)

**Symptom:** The 2026-09-23 digest's fleet transitions: `restart pending — main a2de089d green; compiling` and `restarting onto build a2de089d` at 10:42, then `orchestrator stopped` / `orchestrator started (pid 61046, build a2de089d)` at 12:19 — 97 minutes later, with no transition in between (the newest-6 window holds none between 10:42 and 12:19). The `restart` event logs only after `swapDist` succeeded (src/redeploy.ts, post-drain), so dist/ already held the new build from 10:42 while the old generation kept working for 97 minutes — against the restart path's own promises: "a restart lands within minutes" (src/orchestrator.ts, the `hold` comment) and "the landing is one reviewer run plus a bounded merge, not a fleet-wide drain" (the shutdown comment). The batch in flight explains the gap: main moved from a2de089d to 0ae5dab1 (3 commits — coverage `d5c3441`, organize `ffbdacd`, clean `0ae5dab1`) inside the window, and two of those batch roles (clean, organize) are exactly the ones that logged `build check timed out after 300s` twice — the shutdown sat through their serial build checks and reviewer runs, silently.

**Repro:** Deterministic, no model needed: with `landBatchMax ≥ 2`, put a multi-entry batch in flight (fake reviewers that each take a while) and trigger a self-redeploy whose drain lapses so poll returns `restart` while `landingInFlight` is set. Observe the shutdown's `await Promise.allSettled([…, landingInFlight.promise])` (src/orchestrator.ts, the `finally` of runOrchestrator) wait out the whole batch — N reviewer runs plus N build checks, serially — before `orchestrator_stop` logs, with no event marking the lag.

**Expected:** The shutdown await should carry a deadline (the drain's window or a fixed cap); past it, stop the batch the way the drain gives up on ticks, log a warning naming what was still awaited, and hand off. A batched landing is a fleet-wide drain in disguise, and the restart comment that says otherwise should not survive it.

**Suspected cause:** The shutdown `finally` bets everything on the harness signal aborting every awaited run promptly — but a batch's merge steps run to completion regardless (the abort semantic is per-pi-run), and each batched change re-enters build check and review. The drain caps ROLE ticks at its window; the landing promise, deliberately awaited beside them, has no such bound — and since the swap has already happened, the operator sees `restarting onto build …` and then silence for as long as the batch takes.

**Fix:** The restart hand-off now carries a deadline and says what it waits on. On a restart, the shutdown `finally` of `runOrchestrator` (src/orchestrator.ts) routes an in-flight landing through the new `awaitLandingForHandoff`: it warns the moment it starts waiting (`restart hand-off waiting on the in-flight landing of <roles> (deadline …)`), gives the landing `HANDOFF_LANDING_WINDOW_MS` to finish, then aborts it through the harness's internal stop — the drain's own give-up mechanism, which reaches the landing's controller and its conflict-resolution runs (those watch only the harness signal) — warns naming the roles still awaited, and waits one more window for the step in progress to end before handing off. The window is one build check's bound plus a minute (`BUILD_CHECK_TIMEOUT_MS` + 60 s), justified in its comment: a landing's unbounded part is model work (review, a gate build-fix run), its deterministic part is at most one check plus git, so the first window lets a landing already past its model runs land, and the second keeps the hand-off from leaving a build check running in a lander worktree the next generation is about to reset; the drain's window (the p75 of whole ticks, over an hour here) would have been the lag itself. The landing now stops between its steps, not only where a pi run notices: `reviewPinnedChange` (src/lander.ts) returns `aborted` before a gate starts once the signal has fired — an approved-head short-circuit runs no pi, so an aborted batch used to sail through its gates into the shared check and the fast-forward — `landApprovedChange` (the batch's one-change and fallback landings, which run no gate of their own) returns `aborted` before it starts, and `landBatch`'s re-stack loop (src/land-batch.ts) checks the signal before every attempt, the first included, so no stack is assembled or checked after a stop; a shared check already running is followed through to its fast-forward, the batch's bounded commit point. A stopped landing records the ordinary shutdown abort — `aborted`, pins kept, entries dropped, 4/5 marker removed — so each role's leftover recovery re-lands it on the new build (the queue's rule that an attempted landing's retry rides recovery, never the queue); only a landing still running a window after its abort is left behind, and then the hand-off clears its marker itself (the process exits the moment it returns) while its entries and pins survive as after a crash, for the next generation's first drain — and stops waiting on reserved role ticks too, since a waiter parked behind the permit that landing still holds would never be granted it (since drain-parked-ticks, a restart aborts only permit holders, so such a waiter can exist). An operator stop still waits its already-aborted landing out — returning early would remove orchestrator.json while this process still lands, letting a second `tumwater run` start a concurrent lander — but now warns what it is waiting on. The quoted comments are rewritten: the `hold` comment says a restart lands within the drain's window plus a bounded hand-off, the shutdown comment says why a batch is not one reviewer run, and drainLandingQueue's hold rationale no longer promises minutes. Tests: test/orchestrator-3.e2e.test.ts `a restart's hand-off aborts a batched landing that outlives its deadline instead of waiting it out` (the Repro — a two-entry batch whose fake reviewers take a minute, a restart with no role tick in flight; before the fix the shutdown waited the reviewer out, 62 s, with no event; now it returns in ~3 s with the wait and lapse warnings between `restart` and `orchestrator_stop`, both changes `aborted` with pins kept, nothing landed, no marker left); test/lander.test.ts `an aborted batch lands nothing even when every gate would short-circuit on an approved head` and `an abort after the last gate approved stops the batch before its shared check`, and `an abort after the gate stops a one-change batch before it lands` (each landed its batch before the fix); test/orchestrator-seams.test.ts pins `awaitLandingForHandoff`'s three outcomes (finished in time, aborted and settled, abandoned with its marker cleared within two windows). Each new test failed before the fix (the e2e case after waiting out the 62 s reviewer). Results, after rebasing onto the re-stack loop and main 026f6a3: `npm test lander landing orchestrator-seams` 64/64, `npm test orchestrator-3` 20/20, `tsc --noEmit` clean; the full suite runs at integration.

**Validation gap:** no-observability — the hand-off logged nothing between `restart` and `orchestrator_stop`, so the 97-minute lag was visible only as a gap between two fleet transitions and its cause had to be inferred from the batch's own events; offline, the existing fake-pi reviewer, scripted redeployer and seeded land queue reproduced it deterministically once combined.

### A batch whose base main moves during its build check is discarded wholesale as `merge_blocked`: leftover-recovery landings run outside the land queue and race it (found by human log analysis 2026-09-23, fixed 2026-09-24)

**Symptom:** On 2026-09-22 the 11:55:00 batch (clean `9fce01b`, dry `bde4040`, readme `2c6a521`) spent 49 minutes on its Phase A gates, then stacked on main and started its batch check at 12:43:02. At 12:44:10 coverage's own tick landed `c6ce0a3` ("recovered leftover work from coverage …") through the tick-path lander. The batch check passed at 12:44:26, `ffStackToMain` could no longer fast-forward, and all three changes returned `merge_blocked`. Between 13:03 and 13:12 each one went through the whole gate again via leftover recovery: another full build check, another review, another landing check. The same race hit again at 13:12:55: coverage's 551 s batch came back `merge_blocked` 50 s after readme's recovery landing at 13:12:05.

**Repro:** Deterministic, no model needed: start a batch of two approved changes with a slow fake batch check. While it runs, land any commit on main through the tick path's `landChange` (src/loop.ts:305, leftover recovery). `ffStackToMain` (src/merge.ts:292) tries `ffMainTo` once under the merge lock, the ff fails, and src/land-batch.ts:249 marks every stacked change `merge_blocked`.

**Expected:** A stack that loses the fast-forward race should re-stack onto the new main tip and re-check (or, if the new commits are docs-only, just re-stack) rather than send every approved change back through leftover recovery. Better still, leftover-recovery landings should go through the land queue so there is a single writer to main. The comment at src/land-batch.ts:245 lists "a non-batched role's recovery landing" as an expected cause, which makes it routine, not a rare race.

**Suspected cause:** Merge queue 3/5 moved fresh-tick landings into the orchestrator's single slot but left leftover recovery landing from inside the tick (the "still calls it inside the tick" note in src/lander.ts's header). The batch path then assumed it has main to itself between stacking and fast-forwarding, a window that spans the whole batch check.

**Fix:** A stack that loses the fast-forward race now re-stacks instead of returning `merge_blocked` (src/land-batch.ts). The assembly moved into `assembleStack`, which `landBatch` re-runs on main's new tip after a failed `ffStackToMain`, up to `BATCH_RESTACK_ATTEMPTS` (2) times. The bound keeps a main that moves faster than a check completes from holding the single landing slot indefinitely, and the loop stops between attempts once the slot's abort signal fires (results `aborted`, refs kept). Each re-stack pays one more scope-`batch` check unless `exemptTreeDelta` finds that the re-stacked tree differs from the last tree a check ran on only in `review.exemptPaths`. That is the gate's existing doc-only test and verifyLanding's premise that a doc-only delta cannot break the build, applied to the commits main gained; it adds no new exemption rule, and such a doc-only re-stack seeds no green baseline. A re-stack cherry-pick conflict or a red re-check abandons to the existing one-at-a-time fallback, exactly like the first assembly, and only a race lost on every attempt still returns `merge_blocked` for leftover recovery. The comment that listed a recovery landing as an expected cause now describes the re-stack, and the ffStackToMain (src/merge.ts) and noteGreenBaseline (src/main-baseline.ts) doc comments follow it. **Deliberately left out:** routing leftover-recovery landings through the land queue (the entry's "better still"). It is a redesign, not a contained change: a recovery tick lands and then authors a fresh change, but a role holds one landing ref, so an enqueued recovery would have to end the tick without authoring, and that reshapes the recovery-failure error streak (`recoveryFailure`), the user-abort pin discard, and the loop's recovery tests. Main therefore still has writers outside the queue, and the re-stack is what absorbs them. Tests (test/lander.test.ts): the old test that pinned `merge_blocked` for one concurrent commit is replaced by five. (1) The Repro: a batch check parked mid-run while another role lands through the tick path's `landChange` re-stacks, re-checks once, and lands both changes on top of the racer. (2) A doc-only commit on main re-stacks with no second check. (3) Code landing on main during every check exhausts the attempts: `merge_blocked`, refs kept, nothing merged. (4) A re-stack conflict falls back to one-at-a-time. (5) An abort between attempts returns `aborted` with refs kept. With `BATCH_RESTACK_ATTEMPTS` set to 0 (the old one-shot ff), tests 1, 2, 4 and 5 fail. Results: lander 28/28, merge + landing-drain + main-baseline 44/44, orchestrator-3 e2e 17/17.

**Validation gap:** none — the existing fake build check and an in-check commit on main reproduced the race deterministically; the suite already held that exact repro, pinned as the intended `merge_blocked` outcome, so confirming the bug needed no new fixture, only the recognition that a lost race is routine rather than rare.

### The landing state cell shows only elapsed time: a landing renders bare `landing <elapsed>` while working/reviewing carry turns, context, and tool (reported by user 2026-09-22; re-opened by human log analysis 2026-09-23 — the recorded fix never landed, fixed 2026-09-24)

**Re-opened 2026-09-23:** the 2026-09-22 Fixed record is false. **Symptom:** While a role's commit is landing, its row in `tumwater status`, the TUI, and the GUI reads `landing <elapsed>` and nothing else — although the same landing spends most of its time in a reviewer pi run whose turns, live context, current tool call, and current work are all already observable. Transitions: `landQueuedEntry` and the batch arm open the marker at `merging` (checkout + rebase); `reviewAheadOfMain` (src/review.ts) moves it to `build-check` before its pre-check and to `reviewing` just before the reviewer run; `reviewPinnedChange` (src/lander.ts) returns it to `merging` as soon as the gate returns, WHATEVER it decided. That one call covers the design's mid-batch reject and the merge that follows an approval, and also the case the design missed: a batch head APPROVED in Phase A stayed on `reviewing` while the other changes' gates ran, so its finished reviewer would have accrued a false `no pi output` flag. `landBatch` (src/land-batch.ts) also sets `build-check` around the batch's shared stack check and `merging` after it. Display (src/ui/status-model.ts): `landingForRole` carries the stage, and `loopPhase` renders `landing <elapsed> · build check` / `· merging` without reading the log. `reviewing` renders `landing <elapsed> · reviewing · turn N · ctx … · <tool>`: `inFlightDetail` now takes a preformatted head, so the parts assembly (tool-stall and ≥5-min no-output flags included) is shared with the working/reviewing tick cells. It reads the gate accumulator itself, since a landing role is not running and the frame's `live` tail is null for it. A stage-less record keeps the bare `landing <elapsed>`, and the elapsed is always the marker's `startedAt`. src/ui/progress.ts resets the gate accumulator at the reviewer's `tumwater_run label=review` line, which runPi writes before pi spawns, so neither a previous review's nor this gate's build-fix run's turns/context can show in a new review's cell. Tests: the status-render test that pinned bare `landing 1m30s` as correct now pins it only for a stage-less record; new status-render tests pin each stage's label, show that build-check/merging never read a stale, silent log, show that reviewing carries live detail timed from the landing and not the tick, and show that a previous review cannot bleed in; the renderStatus row and gui-operator payload tests pin a staged cell; progress.test.ts pins the label-line reset; landing-slot.test.ts pins `setLandingStage`'s role/no-marker guard and drives `landQueuedEntry` end to end, with a fake reviewer that moves main and a configured check that records the marker's stage, observing `build-check` → `reviewing` → `merging` (the last during the in-lock re-check); lander.test.ts pins both batch cases (head rejected, head approved), where the head leaves `reviewing` before the next change's gate and the stack check runs under `build-check`. With the fix temporarily reverted, all 10 new or changed tests fail. Runs: `npm test status-render progress landing-slot lander` 122/122; `npm test review landing-drain gui tui orchestrator-3` 175/175; `npm test gui-operator status` 86/86; `npm test leftover loop-3` 38/38.

### The budget fallback has no liveness check: an unreachable free model turns the spend cap into an hour of 100% tick failure instead of a pause (found by log analysis 2026-09-20, fixed 2026-09-24)

**Symptom:** At 2026-09-19 23:00:56 the fleet reached `maxDailyCostUsd: 10` and logged `budget_fallback`. Every tick from then until local midnight's `budget_resumed` failed — **33 of 33** `tick_end` events in the window carry `result: "error"`, across nine roles (`organize`, `feature`, `bugfix`, `improve`, `coverage` 5 each; `clean`, `dry` 3; `plan`, `readme` 1). All 33 carry an oMLX HTTP 400: `oMLX prefill memory guard rejected this prompt: Prefill would require ~97.75 GB peak (current 95.54 GB + KV+SDPA 2.21 GB) but metal_cap ceiling is 96.97 GB … code: "prefill_memory_exceeded"`.
