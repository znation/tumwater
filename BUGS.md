### The backlog range reader (actionableEntryRanges) reads only `### ` headings, so `- `-bullet entries are invisible to the closed-entries index, the archive dedupe, and the bug wait-close

**Refused 2026-11-12 by bugfix: the entry's premise is false and its real symptom is a phantom-`##` archive split that no bugfix may repair — on the real archive `parseEntryDetails` and `actionableEntryRanges` both read `###`-only and return the identical 2 entries (verified offline, 2-vs-2, titles 8-133 and 134-145), so the range reader is *consistent* with the canonical reader, not blind to it, and the `-` one-line records are body content by the invariant-pinned INV-AX2 (src/verdict/fix-claim.ts `fixedSection`/`isOneLineRecord`); the ~2391 closed entries no reader walks all sit in a phantom-`##`-split section (BUGS-FIXED.md:146, a twin at PLANS-DONE.md:201) that an operator/director archive repair — not a bugfix, which may not edit archive files — must fix, and either of the entry's own "required behavior" branches rewrites that cross-cutting guarantee across twelve shared consumers in one tick, which grows complexity without justifying it.**

**Symptom.** `actionableEntryRanges` (src/backlog/backlog-index-data.ts, `line.startsWith("### ")` is the only entry-start test) is the shared entry reader for twelve modules, yet it recognizes only `### ` headings. The canonical reader `parseEntryDetails` (src/backlog/backlog-md.ts) and the date reader `eachEntryStart` (backlog-md.ts:359) both read `### ` headings AND `- ` bullets as entry-starts, and the team's roles compress most closed bugs into single-line `- ` bullets — BUGS-FIXED.md's `## Fixed` holds 1914 `-` bullets against 491 `###` headings. So the range reader is blind to the archive's majority shape.

**How to reproduce (offline, deterministic).** A scratch import over this tree: `actionableEntryRanges(BUGS-FIXED.md, "Fixed")` returns 1 range (a single `###` entry at line 43) out of 1914 bullets + 491 headings; the real newest closed entries (the `-` bullets at lines 8/20/30/…) are all skipped. Consequence 1 — the `<backlog-index>` block's `BUGS-FIXED.md ## Fixed (newest N)` (backlog-index.ts renderClosedSections, RECENT_CLOSED_MAX 5) lists stale `###` entries and never the actual newest closed bugs, in every role prompt. Consequence 2 — the archive dedupe (backlog-archive.ts entryFates, via entriesIn→actionableEntryRanges) matches selected entries against the archive's `###` entries only, so it cannot recognize a closed bug the archive already holds as a `-` bullet and will re-move it (duplicate). The same reader powers recordRecurrence (backlog-file-bugs.ts) and closeQuietWaitsText (backlog-bug-waits.ts).

**Suspected cause.** The `-` bullet is a valid one-line entry shape (parseEntryDetails and eachEntryStart read it; the team uses it for compressed closed entries), but the range walk was written for `###` headings only and never extended to the bullet shape, so every consumer of the range reader inherits the blind spot.

**Required behavior.** Decide the canonical entry shape for one-line entries and make the range reader match it. The fork: (a) make `actionableEntryRanges` read a top-level `- ` bullet as an entry-start (matching parseEntryDetails/eachEntryStart) so the closed index, archive dedupe, and bug wait-close all see the majority archive shape — the open `## Open` shape then needs a guard so a `- ` repro step inside an entry body is not misread as a sibling entry, or (b) canonicalize one-line entries to `### ` in the archive and close paths so the `###`-only reader is never blind. This is a plan-role design call (it touches twelve call sites and the entry-shape contract); the bugfix role records it, not force-picks a shape.

### The post-merge review times out while still progressing and re-queues on a slow local default model (a59a20af: 1800 s wall for ~15 turns) — no floor reaches the post-merge review path

**Symptom.** The 1d digest's top warning cluster is 5× `the post-merge review of a59a20af failed (timed out after 1800s while still making progress — the commit is kept; the next attempt reviews it from scratch)`. A single merged commit's post-merge review hit its 1800 s wall five times while still progressing and was re-queued each time, with no verdict ever recorded. a59a20af is a small change (5 files, 86+/56−, `Defer the quiet-host gate on the 5-min average`). This is the one genuine wrong response in the digest: a *budget* starvation (not a hang) re-queueing the same review until the pin is preserved.

**How to reproduce (verified 2026-11-13; the entry's original 545-branch claim is off the path).** The post-merge review receives the raw live config, not a fallback view: `drainPostReviews` → `reviewMergedCommit(root, ctx.liveConfig, …)` (src/merge/merge-post-review-drain.ts), with `ctx.liveConfig = ctx.liveReload.poll()` (src/orchestrator/orchestrator-poll.ts). It sets the reviewer's wall in `reviewRunConfig(config, sampleHostLoad, diffBytes)` (src/review/post-merge-review.ts → src/config/config-views.ts): `runTimeoutSeconds = min(cfg.runTimeoutSeconds, starvedDeadlineMs(base, load) × (diffScaledMs(base, diff)/base))` with `base = (review.timeoutSeconds ?? REVIEW_TIMEOUT_S=900) s`. `hostLoadStarved` is `load1 > cpus`; the shared `starvedDeadlineMs` factor caps at 2×, so a starved host gives `900×2 = 1800 s` — the 1800 in the log, **derived from the 900 s default, not a configured value** (the live `review` block sets neither `timeoutSeconds` nor `model`). `diffScaledMs` is a no-op at or under `REVIEW_DIFF_REFERENCE_BYTES` (20 KB). Repro: run one review on a host with `load1 > cpus`; its wall is 1800 s.

**Suspected cause (corrected).** `FALLBACK_REVIEW_TIMEOUT_S` (3600 s) is applied only inside `fallbackReview` (src/config/config-fallbacks.ts:365), reached only through `applyFallbackModel` — a budget-fallback *view* — which the post-merge review never uses (it runs on `ctx.liveConfig`, a live config). The 545 line this entry first named (`free?.(…) ? keptEntry(…) : fallbackReview(…)` in `applyFallbackModel`) is off-path for the post-merge review; its free/`keptEntry` behavior is a real but *separate* latent gap (a slow free model that is the team default would run a review with no floor through the live path). The floor exists only for the fallback view, where the model is a slow free *fallback*. So a single local default model — no cap, no fallback engaged — gets 900 s, stretched to 1800 s under load: a budget built for a fast default, not the slow local model that actually runs the review. (The event log confirms both: the reviewer inherits the local Qwen at the strong tier, and a59a20af's first run ran the full 1800 s — its second ran 1625 s and did return a verdict, so the loop self-resolves within a couple of attempts; the waste is the 1800 s wall on a model that finishes in ~15 turns.)

**Required behavior (the fork is the user's — see QUESTIONS.md "post-merge review on a slow local model").** Either (A) a **config value**: set `review.timeoutSeconds` in tumwater.json to fit the local model (~25 min) — a user/operator action, not bugfix; or (B) **code**: floor a post-merge review whose *own* resolved model is a slow free one (detect via the existing `seamFree`) in `reviewRunConfig`, so the 3600 s floor — not a per-host 2× stretch — protects a slow local default. Both keep the load/diff stretch and the wedged-run quiet watchdog intact.

**Refused 2026-11-13 by plan: the entry's named anchor (config-fallbacks.ts:545 `keptEntry`) is off the post-merge review path (the review runs on `ctx.liveConfig`, a live config, never the fallback view `applyFallbackModel` builds) and its "1800 s is a config value" premise is false (1800 = `reviewRunConfig`'s 2× load stretch of the 900 s default; the live `review` block sets neither `timeoutSeconds` nor `model`) — the real fork (generalize the floor to the post-merge path vs. a user config change) is a product/design decision the user must make (QUESTIONS.md).**

**Recurring occurrence (2026-11-13, a new commit).** A second, *larger* post-merge review of a *different* merged commit — `a4d55b7d` (`Rewrap the over-wide JSDoc line in src/prompt/since-last-run.ts`, 8 files, 471+/27−, ~35 KB default-unified diff, i.e. *above* `REVIEW_DIFF_REFERENCE_BYTES` 20 KB) — failed 7× with the same normalized key `the post-merge review of a4d55b7d failed (timed out after 3555.9s while still making progress — session and worktree …)`, the window's 7th-largest warning cluster and ~3.7 h of the "top loss causes" time. The 3555.9 s wall is *not* a new budget source: `3555.9 = 900 (base) × 2 (load stretch, host starved) × 1.976 (diff stretch, 35 KB / 20 KB capped at 2×)` — the same two bounded stretches `reviewRunConfig` applies, just with the diff stretch engaged because this diff is large. So a *large* diff under a loaded host, on the slow local default, burns ~59 min/attempt × 7 re-queues: the same budget-starvation-not-a-hang, larger and more frequent than a59a20af's 1800 s×5. (The digest's two wordings differ only because the two reviews ran under different build revisions of the `timedOutProgressing` message in src/agent/agent-settle.ts; the run-deadline budget and the `reviewRunConfig` wiring are identical.) This does not change the fork, which stays the user's in QUESTIONS.md ("post-merge review on a slow local model", asked by plan 2026-11-13, still open).

**Needs review (2026-11-13 by selfcheck):** the failure cluster recurred on a new commit (a4d55b7d) *after* this entry's filing (05fdb15c), so confirm the *resolved reviewer model/backend* for the post-merge review — whether it actually resolved to the slow local `qwenrunner/Qwen3.8-27B-MLX-Serve-4bit` via the strong tier — before treating this as confirmed for the bugfix role; that is the one claim only the live event log (outside the worktree) can settle. The QUESTIONS.md fork (floor the reviewer's own model vs. a config value) governs the fix, not this confirmation.

### A self-redeploy whose running build is self-divergent can never redeploy itself, pinning the team on the stale build until an operator restarts it (20× `the update to 14580551 failed to build — staying on version 72a0b257: tsc exited 2`)

(found by the selfcheck role 2026-11-14)

**Symptom.** After the self-redeploy compiler-split was *fixed and closed* in the window (67965f6a filed → 47657b146 re-pointed `compileStaged` at `typescript-native` 7.x → a78a5c14 closed it, all merged to main), the 1d digest still holds the self-redeploy's two signatures, and they did not stop: two `restart pending`→`restart blocked — the update to <head> f; staying on build 72a0b257` team-state transitions (11-14 03:06 for `a78a5c14` and 03:22 for `14580551`) and a 20× warning cluster `the update to 14580551 failed to build — staying on version 72a0b257: tsc exited 2` (11-13→11-14, spanning roughly a day, i.e. *after* the fix merged). `14580551` is main's tip, a one-file 100-column comment rewrap in `cli-args.ts` that merged cleanly through the green gate; `a78a5c14` is the compiler fix itself. The team is pinned at `72a0b257` — **12 commits behind** main — and the running build's *own* `compileStaged` refuses every tip it is asked to deploy, re-emitting `tsc exited 2` on each new tip.

**How to reproduce (verified 2026-11-14, offline, deterministic, against this tree).** Both TypeScript compilers are installed — `node_modules/typescript@5.9.3` (the linter's compiler) and `node_modules/typescript-native@7.0.2` (the build compiler) — and the running build `72a0b257` is *self-divergent*: its own green-check (`scripts/tsc.mjs` line 19, `resolve("typescript-native")` = 7.x) and its own `compileStaged` (`build-stage.ts` line 99, `resolveFromNodeModules(root, path.join("typescript", "bin", "tsc"))` = 5.x) resolve to *different* compilers. Against the current main tree the split reproduces exactly: `node node_modules/typescript/bin/tsc -p . --noEmit` → **exit 2** (`src/pi-extension/checkpoint.ts(286,23): error TS2345` — the `() => void` `turn_end` handler that the checkpoint feature, `990e29062`, introduced); `node node_modules/typescript-native/lib/tsc.js -p . --noEmit` → **exit 0**. `72a0b257` predates the fix (it is an ancestor of 47657b146) and carries the pre-fix `compileStaged`, so its `compileStaged` runs the 5.x compiler on a tree the 7.x green-check accepts: the green verdict (`result === true`, a *pass* — `block()` is never called here) then leads to a **failed** 5.x compile, which is a real compiler *verdict* (`!c.rejected`), so `compileStage` (src/redeploy/redeployer.ts:571) calls `block(mainHead, "the update to <head> failed to build", "…staying on version 72a0b257: tsc exited 2…")` (redeployer.ts:705), setting `blockedHead = mainHead`.

**Suspected cause.** The only self-recovery path in `poll` (src/redeploy/redeployer.ts:332) is `drainAndSwap` → `this.deps.swap(mainHead)` (a process restart onto the new head, redeployer.ts:601-605), and it is reached only after a *successful* `compileStaged`. A self-divergent running build's `compileStaged` (5.x) can never accept the 7.x-clean trees the pipeline ships, so the build can never deploy itself, `blockedHead` is set, and `poll` early-returns (`blockedHead === mainHead`, redeployer.ts:342). When main then moves to a new tip, `blockedHead` no longer matches, so the *same* self-divergent build re-runs `compileStage`, fails the *same* 5.x error on the new tip, and re-blocks — re-emitting one `restart_blocked` + `staying on version 72a0b257` warning **per new tip** (that is the 20× cluster: it counts tips, not retries, because `block()` latches per head and the early-return keeps a frozen head quiet). The bugfix's `Resolution` (BUGS-FIXED.md:8) reasoned "a one-off stale compiler exit self-heals the moment main moves" — but the self-heal requires the new head to compile under the **old build's own** `compileStaged`, i.e. under 5.x, and the shipped trees are 5.x-dirty, so it does not fire: the team stays pinned at `72a0b257` until a human runs a restart (the only thing that swaps the pre-fix binary out for one that self-heals).

**Why the 2026-11-14 compiler split (BUGS-FIXED.md:8) is a different bug, not a duplicate of it.** That entry is *closed* and its fix (47657b146) is present in main: `git show HEAD:src/build/build-stage.ts` resolves `typescript-native` (7.x), so the *current source* is self-consistent (verified). But the *running build* `72a0b257` predates the fix and is still self-divergent — the source fix can never be *deployed* onto it, because the pre-fix binary's `compileStaged` is precisely what rejects the deploy. The two are the same compiler split seen from two sides — the source's divergent `compileStaged` (fixed) vs. the *running build's* divergent `compileStaged` (not yet deployed) — but the closed entry's `Resolution` explicitly claimed the latch self-heals ("no new code" needed), which this window falsifies: the team is 12 commits behind, still failing the *same* 5.x `tsc exited 2`, and the `restart blocked … staying on build 72a0b257` transitions continued at 03:06/03:22 on 11-14.

**Required behavior.** Make a latched build that cannot compile its *own* deploy escape the latch without a human: when the running build's `compileStaged` fails on a tip that its own green-check passed (the self-divergent case — the build is red against its *own* head), the latch must not re-pin on every subsequent tip; it should escalate to the sustained-pin path (`escalateIfSustained`, redeployer.ts:681) or refuse with a *distinct* "the running build cannot verify itself" reason so the operator is told the binary is the problem, not the commit. Regression test: a running build whose `compileStaged` resolves a different (stricter/older) compiler than its green-check must self-escalate / report its own divergence and stop latching, rather than re-emitting `failed to build — staying on <build>: tsc exited 2` per tip until an operator restarts it. The compiler re-point in 47657b146 is the *first* half of the fix (the source no longer deploys divergent builds); this entry is the *second* half (a build that is already running divergent must not dead-lock the team).

**Note for bugfix (verification, offline):** the live "staying on build 72a0b257" readings and the 20× counts are from tumwater's event log (outside this worktree, injected in the digest). Everything above — the 72a0b257 self-divergence, the 12-behind staleness, the `block()`/`poll` latch path, and the 5.x-dirty / 7.x-clean split on current main — was verified offline against the tree and `git show` of the pinned build.
