## Open

### A policy scan's failure is excused by test name alone, so a new offender in an already-failing scan merges as main's known failure (found by the reviewer role 2026-11-05)

- **Symptom:** when main is red on one of the repo-wide policy scans, a change that adds its own offender makes the same aggregate test fail (e.g. `every comment line in src/ and test/ fits in 100 columns…`), so the gate's failure has the same name as main's known failure. `onlyKnownMainFailures` (src/baseline/main-watch.ts:146) checks every failing test name against `knownMainFailures(root)` and, when all match, returns them as main's; the change's new offender is excused and merges, leaving main red on a line its own change introduced. Previously the scans were rarely selected at all (BUGS-FIXED.md 2026-11-05), which hid this gap; now that a budgeted gate force-runs them, it is the remaining half.
- **Reproduce:** with main red on `test/comment-width.test.ts` (one wide comment in file A), append a 125-column `//` comment to a different src file and run the gate on that change. The scan fails on the new line too, but the failure lists the same one test name, so `onlyKnownMainFailures` returns it as main's known failure and the gate does not blame the change.
- **Cause:** the excuse compares test names, not offenders. The four policy scans report one aggregate test regardless of which file or name offends, so a name match cannot distinguish main's offender from the change's.
- **Cost / why fileable:** the change's new offender lands on a red main, keeping main red and hiding which commit added it — the same failure mode the 2026-11-05 force-run fix addressed. The fix sketch: compare offenders, not test names — a scan failure that lists a line or name main's own failure does not list belongs to the change.

### Policy-scan offenders, part 1/2: The four repo-wide policy scans print each offender on a machine-readable line, and the check outcome and main's saved verdict carry the offender lists beside the failing test names (found by the selfcheck role 2026-11-06; split 2026-11-08 by the plan role from the too-large stale-base bug below; sibling to part 2/2, which needs this capture landed; this part changes no attribution)

- **Symptom:** the four repo-wide policy scans (`POLICY_SCANS` in test/affected-tests.ts: comment width, unused exports, retired names, plain-terms vocabulary) each report one aggregate failing test whatever offended, so `parseFailingTests` keeps only the test title. `BuildCheckOutcome.failingTests` and `MainBaseline.failingTests` therefore say a scan failed, never which line or name did it, and no later attribution can tell the change's new offender from the base's or main's old one.
- **Fix:** give the scans and the check one shared offender-line contract. Add `src/build/policy-offenders.ts` exporting `POLICY_OFFENDER_PREFIX` (`tumwater-policy-offender`), `policyOffenderLine(testTitle, offender)` (one line: the prefix, the exact test title, and the offender string) and `parsePolicyOffenders(output): Record<string, string[]>` (title-keyed, in output order, deduplicated, lines without the prefix ignored). Change the four scans to emit one `policyOffenderLine` per offender through a shared test helper before their existing assertion fails, so the complete check output contains the list as well as the assertion diff. Set `BuildCheckOutcome.failingOffenders` in `runBuildCheck` (src/build/build-check.ts) from `parsePolicyOffenders(output)`, beside `failingTests` and `failingTestFiles`, and add the field to the `BuildCheckOutcome` interface. In `src/baseline/main-baseline.ts`, add `MainBaseline.failingOffenders`, fill it in `baselineFromOutcome`, and persist/restore it through `saveGreens`/`restoreRedVerdict`, treating an absent field in a saved old verdict as no offender data (the `failingTests` precedent). In `src/baseline/main-watch.ts`, carry the same map on `knownFailures` and the open red spell so a restored or inherited red keeps it; no reader outside this new plumbing may change behaviour in this part.
- **Acceptance criteria:** with a planted offender, each of the four scans' complete output contains a `tumwater-policy-offender` line naming that scan's exact test title and the offender; a clean tree emits none. `parsePolicyOffenders` returns the title-keyed lists, ignores unrelated output and deduplicates repeated offenders. A red baseline carrying `failingOffenders` reads back the same lists after `persistBaselineVerdicts`/`saveGreens`; a saved verdict without the field restores none. `onlyKnownMainFailures`, `attributeOnRedMain` and `staleBaseFailures` behave exactly as before (nothing reads the new data yet), so the existing review-precheck and main-watch cases pass unchanged.
- **Tests:** a new `test/policy-offenders.test.ts` for the line format and parser (planted offenders, duplicate, prefix-free noise, empty); extend `test/build-check-report.test.ts` for `failingOffenders` on a failed outcome; extend `test/main-baseline-persist.test.ts` for the save/restore round trip and old-file absence; add one assertion per policy scan that its offender helper prints the contracted line. Run those files and the project's gate.

### Policy-scan offenders, part 2/2: The stale-base excuse compares a change's policy-scan offenders with its base's, so an offender the base's failure never listed is rejected instead of excused (found by the selfcheck role 2026-11-06; split 2026-11-08 by the plan role from the too-large stale-base entry; requires the offender capture in part 1/2 landed, and keeps today's name-only behaviour when either side has no offender data)

- **Symptom:** when a change's git base is a red commit but main's tip is now green, a gate failure that is the change's own gets excused as its base's. The digest's 10× warning cluster picks a concrete spell: `gate check fails only tests its base 88686680 already failed, and main c8e67154 is green: every comment line in src/ …` — `88686680` is the base commit (`tumwater(feature): mergeApprovedChange …`) and `c8e67154` the green main tip. The gate names only the aggregate policy test `every comment line in src/ and test/ …` (test/comment-width.test.ts), which the base was red on and whose offenders the change's own rebased commits can add to independently.
- **Reproduce:** on a main whose tip is green and whose history holds a red base, rebase a change that adds its own 125-column `//` comment onto that base. `staleBaseFailures` (src/review/review-precheck.ts) reads the base's `watchedBaseline` verdict as red, sees every failing test name in the base's set, and returns it — even though the change's new offender is a line the base's failure never listed. The pre-check logs `gate check fails only tests its base … already failed, and main … is green` and goes on to review with no fresh run on main (`rejected: no`, `knownMainFailures`), so the offender merges.
- **Cause:** `staleBaseFailures` excuses by test **name**, never by **offender**; the four repo-wide policy scans report one aggregate test regardless of which file or line offends, so a name match cannot tell the base's old offender from the change's new one. Part 1/2 makes the base verdict carry `failingOffenders` keyed by test title, and the gate outcome carry the same for the change.
- **Fix:** in `src/review/review-precheck.ts`, thread the gate outcome's `failingOffenders` into `staleBaseFailures` from `namedFailureResult` (it already receives `outcome`). When the base verdict and the change both name offenders for a failing test, excuse that test only when every change offender is in the base's list for it; a change offender the base never listed makes `staleBaseFailures` return null, so the change is rejected through the existing `rejectionReasons` path and its own failure is named. When either side has no offender data for a test (an ordinary test, an old saved verdict, or a cut list), keep today's name-only comparison for that test so non-policy behaviour and old caches are unchanged. Do not change the red-main arm (`onlyKnownMainFailures`/`attributeOnRedMain`); its own entry remains open.
- **Acceptance criteria:** on a green main with a red base whose comment-width verdict lists `src/a.ts:10 (cols)`, a change whose gate fails comment-width only because it adds `src/b.ts:20 (cols)` is rejected, and the rejection reasons name the change's failure rather than `fails only tests its base … already failed`. A change whose only policy offender is exactly the base's listed offender still goes on to review with the stale-base warning. A non-policy stale-base failure, or a base verdict saved before part 1/2, keeps today's name-only outcome. The merge path's fresh gate sees the same rejection because it runs the same pre-check.
- **Tests:** extend `test/review-precheck.test.ts` with a base verdict carrying `failingOffenders` and a gate outcome carrying an extra offender (expect rejection), the same-offender case (expect the stale-base warning and no rejection), and the no-offender-data fallback. Run that file, the policy-offender and baseline tests, and the project's gate.
