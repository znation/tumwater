### The "N GitHub issues are fixed on main and close when you push main" banner ignores the push it asks for: the close pass runs only after the hourly scan, so pushed fixes stay open and the banner keeps asking for up to `scanIntervalMinutes` (found by an operator session 2026-11-23)

- **Symptom:** the dashboard showed the blue banner "5 GitHub issues are fixed on main and close when you push main to znation/tumwater" after main had already been pushed. `.tumwater/state/github-issues.json` had `checkedAt` 2026-11-24T05:58:01Z and `waitingPush` for #1–#5. The fixes (`51759d43`, `23be3c02`, `dd25ff5d`, `b28c127b`, `cf1a2a9b`, `880b6c5e`, `28a527ee`) first reached GitHub at 06:11:38Z (origin/main reflog: `d13725c4 … update by push`). Afterwards `gh api repos/znation/tumwater/compare/<sha>...main` answered `ahead` for all seven, but every issue stayed OPEN and the banner kept asking. The ledger said "waiting for a push" for about 47 minutes after the push, until the next hourly scan.
- **Reproduce:** with a GitHub remote and a logged-in `gh`, let a scan record a mirrored issue in `waitingPush` (its fix is on local main but not yet on GitHub). Then push main. The banner, `tumwater doctor`'s `github issues` row and `tumwater issues` keep reporting the issue as waiting for a push, and the issue stays open, until `scanIntervalMinutes` (default 60) has passed since the last scan. In a unit test: `pollGithubIssues` (src/github/issue-scan.ts:386) with `clock.nextAt` in the future, a `GhRunner` whose `compare` now answers `ahead`, and a ledger holding `waitingPush`. Expected: one `gh issue close` per waiting issue. Actual: no gh call at all.
- **Cause:** `closeFixedIssues` (src/github/issue-close.ts:277) runs from exactly one place: `pollGithubIssues`, right after `scanGithubIssues`, and only when `dueForIssueScan(clock.nextAt, now)` (src/github/issue-scan.ts:397-402). `closeOne` (issue-close.ts:236) is the only code that re-checks a `waitingPush` sha against GitHub (`onGithub`, a `compare` call) and clears the record. So the push the banner asks for never shortens the wait. The record is correct when written, since the fix really wasn't on GitHub at scan time, but no event re-checks it. The banner's wording ("close when you push") promises an immediate result that the code only delivers on the next tick of the scan clock.
- **Fix direction:** re-run the close pass, not a whole scan, when there is something for it to find. A push from this host updates `refs/remotes/origin/<branch>` (the reflog records `update by push`). So while `waitingPush` is non-empty, a poll can compare that ref with the value it saw last time and call `closeFixedIssues` when the ref moves. That costs one `compare` call per waiting sha plus the closes, and needs no issue listing. A push from another machine doesn't move the local ref until a fetch, so also keep a short, bounded re-check of `waitingPush` alone, for example every 5 minutes while it is non-empty, independent of `scanIntervalMinutes`. Whichever trigger is used, record the invariant: *a `waitingPush` record is re-checked within minutes of its fix reaching GitHub, not only on the next scan*. If the wait stays, change the banner to say the issue closes on the next scan after the push, so it doesn't promise more than the code does.

### `a suspended head another check records red is settled without waiting for the interval` fails when a sibling `culpritFixture` test ran in the same second: identical fixture commits share a SHA, so the process-wide verdict cache hands it the sibling's red (found by an operator session 2026-11-23)

- **Symptom:** GitHub CI on main `608cb8e5` (the 0.11.0 release commit, run 45339869241 attempt 1) failed only this test; the rerun of the same sha passed, and so did CI on its parent `d13725c4`, whose src/ and test/ trees are identical.

  ```
  ✖ a suspended head another check records red is settled without waiting for the interval (243.239847ms)
    AssertionError [ERR_ASSERTION]: the watch itself made no verdict yet
    actual: 2, expected: 1
        at TestContext.<anonymous> (file:///…/dist/test/main-watch.test.js:350:12)
  ```

- **Reproduce:** run it right after its sibling `a red whose bisection re-runs reach no verdict still names the tip` (test/main-watch.test.ts:326): `npm run build`, then repeat `node --test --test-name-pattern='a red whose bisection re-runs reach no verdict|a suspended head another check records red' dist/test/main-watch.test.js` — 8 of 20 runs failed on this host. Run alone, it passed 15 of 15.
- **Cause:** every `culpritFixture()` repo (test/fixtures/main-watch-fixtures.ts:55 → `baselineFixture`, test/fixtures/runner-fixtures.ts:168) commits the same tree, with the same `test <test@example.com>` identity from `gitInit` and the same messages (`seed`, then `edit bad.txt`). So two fixtures built within the same wall-clock second get byte-identical commits and the same SHAs. `baselineCache` (src/baseline/main-baseline.ts) is process-wide and keyed by SHA alone. The sibling test leaves a red verdict with `checkedAt` cached for the shared `bad.txt` SHA. When this test polls that head, `fullCheckPlan` (src/baseline/main-watch-full.ts:76-85) picks that red as its anchor, returns `skip: false` and runs the full check, which is the second `main_check` the assert sees. The file's header comment ("every fixture repo has its own, so these tests share no state", test/main-watch.test.ts:30-32) is true only while the fixture SHAs differ. The other `culpritFixture` tests in main-watch.test.ts (lines 123–383) and the `change(root, "bad.txt", "b")` tests in main-watch-mirror/main-red-heal/main-watch-spells are exposed in the same way whenever two of them in one process land in the same second.
- **Fix direction:** make each fixture's commits unique, so the SHA-keyed cache really is per repo. For example, `baselineFixture` could write a per-fixture nonce (its tmpdir path) into the seed commit's message or a tracked file. Clearing `baselineCache` between tests would also work, but it hides the shared-key assumption instead of making it true. The regression test: build two `culpritFixture`s back to back in one test, assert their `bad.txt` commits differ, and keep the pair repro above green.

### The model-check surfaces name a pi seam that declares no model `?/?`, while `status` and `role <id>` name that same seam's `pi default (<model>)`, so the alert that stops the whole team names no model the operator can act on (found by the qa role 2026-11-23)

- **Symptom:** a fresh `tumwater init` project (no `model` anywhere in `tumwater.json`) whose team starts and gets a failed model check shows the whole team stopped by a pair called `?/?`. The same running team's `status` footer and `tumwater role feature` name the model the roles actually run. The operator's only action (raise/point `model`, or wait for the re-check) has no model to reason about.
- **Reproduce:** offline, no real model. In a scratch dir: `git init -q -b main . && node <dist>/src/cli.js init "Build a tiny markdown-to-html converter CLI in Python."`, then a shim `printf '#!/bin/sh\nexit 1\n' > $TMPDIR/pi-noreply.sh; chmod +x …`, then `env -u TUMWATER_SUPERVISOR_PID -u TUMWATER_SUPERVISED TUMWATER_PI_BIN=$TMPDIR/pi-noreply.sh node <dist>/src/cli.js start --for 45s`. Within ~12s, all three surfaces print the placeholder:
  - `status`: `! ?/? failed its model check — runs on it wait — ?/? (feature, feature-2, feature-3, feature-4, +24 more) gave no reply (the agent exited 1); checking again at 22:30:41`
  - `doctor "model check"` (the name is two words, so quote it): `warn  model check  ?/? — failed: gave no reply (the agent exited 1); feature, …, +22 more wait; next check 22:30:41`
  - the event feed: `warning: model check failed: ?/? gave no reply (the agent exited 1) — runs on it wait (…)`; the ledger `.tumwater/state/model-checks.json` holds the key `"?/?"`.
  - Expected, and what the same run actually prints elsewhere: `status` footer `model (every role): huggingface/deepseek-ai/DeepSeek-V4-Flash-0731:deepinfra:low, pi default` and `role feature` → `- Model: pi default (huggingface/…:low) (default tier)`. The alert should name that model (or at minimum `pi default`), because `docs/backends.md:31-34` promises the role rows "name that default … marked `pi default`, so `tumwater status` and the dashboard still show which model each role runs", and docs/invariants.md "Cross-surface agreement" forbids two surfaces disagreeing on one fact.
- **Cause:** `modelPairName` (src/budget/budget.ts:188-190) renders missing halves as `"?"`; `seamPairName` (src/config/config-views.ts:508-512) feeds it `seamHoldKey(cfg)`, which returns `cfg.provider` for a pi seam — and a pi seam with no configured model has no provider, so the pair is `?/?`. Every model-check surface prints that raw pair: the banner `pushModelCheckAlert` (src/ui/team-alert-status.ts:155-172, `failed[0]!.pair` and `${c.pair}${on}`), the doctor row `checkModelChecks` (src/doctor/doctor-fallback-checks.ts:238-251, `${c.pair} — failed: …`), and the feed warning (src/model-check/model-check-gate.ts:370, `model check failed: ${pair} …`). The pair is a genuine identity key — it is also the cost key (`RunnerState.dayCostByPair`, per-pair `maxDailyCostUsd` at src/gates/budget-gates.ts:399,409) and a persisted ledger key — so the placeholder cannot simply be replaced in the key.
- **Fix direction.** Keep the key, fix the label: give the displayed check a label computed the way the status row already computes it, so both read one derivation. `rowModelFields` (src/status/status-roles.ts) already owns the rule (pi seam resolving neither provider nor model → `pi default (<piDefault selector>)`, else the formatted pair), and `modelLabel` (src/agent/backend-traits.ts:66-75) is a second home of the same rule that already diverges per backend (`claude backend`, `opencode/?`, `codex default`) yet still returns `?/?` for pi — pin which one the check surfaces use and add an invariant note under docs/invariants.md "Cross-surface agreement". What the surfaces have to work with: the published `ModelCheckInfo` (src/team/team-orchestrator-info-types.ts:66-80) carries only the `pair` string plus `seams`/status — no agent, no label — while the publishing side holds the resolved seam: `pairsInUse` keeps `{ seam, seams }` per pair key (src/model-check/model-check-gate.ts:80-88, `PairUse`), so the orchestrator can emit a display label without touching the key, and `status`/`doctor` each already resolve the live config (doctor's own `routing:` block in the same output prints `feature  no model declared  (pi)`). If a `label` field is added it must stay display-only: the ledger key and the cost key keep `?/?`, and `readModelCheckStore` must still parse state files written without it. Update the pins that assert the placeholder text: test/backend-traits.test.ts:21 (`modelLabel("pi", undefined, undefined) === "?/?"` — decide whether that one stays), test/transcript.test.ts:246 (`⚠ retry ?/? …`, the same placeholder through the retry warning), while test/runner-pi-retry.test.ts:247 asserts no ` on ` label at all and should stay green. One precedent already in the tree prefers prose over a placeholder: the doctor's `over-cap model` row replaces a half-resolved pair with the words `a half-resolved pair` rather than printing `?/<model>` (`pairLabel`, src/doctor/doctor-fallback-checks.ts:80, pinned at test/doctor-model-checks.test.ts:112-117) — decide which shape (the named model, or honest prose) the three check surfaces share.
- **Notes for the fixer.** A related hazard found in the same run, worth deciding in the same pass: `config set model "?/?"` is accepted verbatim (`set model to "?/?"`, then `config unset model` reports `was "?/?"`), so an operator who copies the alert's label into the remedy command gets a silently-nonsense model. If the label changes, that command still needs to refuse an unparseable selector — check whether `config set model` validates the pair at all before adding that, and keep it one entry only if the validation gap is real.
