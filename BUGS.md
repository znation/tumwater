### The backlog range reader (actionableEntryRanges) reads only `### ` headings, so `- `-bullet entries are invisible to the closed-entries index, the archive dedupe, and the bug wait-close

**Refused 2026-11-12 by bugfix: the entry's premise is false and its real symptom is a phantom-`##` archive split that no bugfix may repair — on the real archive `parseEntryDetails` and `actionableEntryRanges` both read `###`-only and return the identical 2 entries (verified offline, 2-vs-2, titles 8-133 and 134-145), so the range reader is *consistent* with the canonical reader, not blind to it, and the `-` one-line records are body content by the invariant-pinned INV-AX2 (src/verdict/fix-claim.ts `fixedSection`/`isOneLineRecord`); the ~2391 closed entries no reader walks all sit in a phantom-`##`-split section (BUGS-FIXED.md:146, a twin at PLANS-DONE.md:201) that an operator/director archive repair — not a bugfix, which may not edit archive files — must fix, and either of the entry's own "required behavior" branches rewrites that cross-cutting guarantee across twelve shared consumers in one tick, which grows complexity without justifying it.**

**Symptom.** `actionableEntryRanges` (src/backlog/backlog-index-data.ts, `line.startsWith("### ")` is the only entry-start test) is the shared entry reader for twelve modules, yet it recognizes only `### ` headings. The canonical reader `parseEntryDetails` (src/backlog/backlog-md.ts) and the date reader `eachEntryStart` (backlog-md.ts:359) both read `### ` headings AND `- ` bullets as entry-starts, and the team's roles compress most closed bugs into single-line `- ` bullets — BUGS-FIXED.md's `## Fixed` holds 1914 `-` bullets against 491 `###` headings. So the range reader is blind to the archive's majority shape.

**How to reproduce (offline, deterministic).** A scratch import over this tree: `actionableEntryRanges(BUGS-FIXED.md, "Fixed")` returns 1 range (a single `###` entry at line 43) out of 1914 bullets + 491 headings; the real newest closed entries (the `-` bullets at lines 8/20/30/…) are all skipped. Consequence 1 — the `<backlog-index>` block's `BUGS-FIXED.md ## Fixed (newest N)` (backlog-index.ts renderClosedSections, RECENT_CLOSED_MAX 5) lists stale `###` entries and never the actual newest closed bugs, in every role prompt. Consequence 2 — the archive dedupe (backlog-archive.ts entryFates, via entriesIn→actionableEntryRanges) matches selected entries against the archive's `###` entries only, so it cannot recognize a closed bug the archive already holds as a `-` bullet and will re-move it (duplicate). The same reader powers recordRecurrence (backlog-file-bugs.ts) and closeQuietWaitsText (backlog-bug-waits.ts).

**Suspected cause.** The `-` bullet is a valid one-line entry shape (parseEntryDetails and eachEntryStart read it; the team uses it for compressed closed entries), but the range walk was written for `###` headings only and never extended to the bullet shape, so every consumer of the range reader inherits the blind spot.

**Required behavior.** Decide the canonical entry shape for one-line entries and make the range reader match it. The fork: (a) make `actionableEntryRanges` read a top-level `- ` bullet as an entry-start (matching parseEntryDetails/eachEntryStart) so the closed index, archive dedupe, and bug wait-close all see the majority archive shape — the open `## Open` shape then needs a guard so a `- ` repro step inside an entry body is not misread as a sibling entry, or (b) canonicalize one-line entries to `### ` in the archive and close paths so the `###`-only reader is never blind. This is a plan-role design call (it touches twelve call sites and the entry-shape contract); the bugfix role records it, not force-picks a shape.

### The post-merge review times out while still progressing and re-queues on a slow local default model (a59a20af: 1800 s wall for ~15 turns) — no floor reaches the post-merge review path

**Symptom.** The 1d digest's top warning cluster is 5× `the post-merge review of a59a20af failed (timed out after 1800s while still making progress — the commit is kept; the next attempt reviews it from scratch)`. A single merged commit's post-merge review hit its 1800 s wall five times while still progressing and was re-queued each time, with no verdict ever recorded. a59a20af is a small change (5 files, 86+/56−, `Defer the quiet-host gate on the 5-min average`). This is the one genuine wrong response in the digest: a *budget* starvation (not a hang) re-queueing the same review until the pin is preserved.

**How to reproduce (verified 2026-11-13; the entry's original 545-branch claim is off the path).** The post-merge review receives the raw live config, not a fallback view: `drainPostReviews` → `reviewMergedCommit(root, ctx.liveConfig, …)` (src/merge/merge-post-review-drain.ts), with `ctx.liveConfig = ctx.liveReload.poll()` (src/orchestrator/orchestrator-poll.ts). It sets the reviewer's wall in `reviewRunConfig(config, sampleHostLoad, diffBytes)` (src/review/post-merge-review.ts → src/config/config-views.ts): `runTimeoutSeconds = min(cfg.runTimeoutSeconds, starvedDeadlineMs(base, load) × (diffScaledMs(base, diff)/base))` with `base = (review.timeoutSeconds ?? REVIEW_TIMEOUT_S=900) s`. `hostLoadStarved` is `load1 > cpus`; the shared `starvedDeadlineMs` factor caps at 2×, so a starved host gives `900×2 = 1800 s` — the 1800 in the log, **derived from the 900 s default, not a configured value** (the live `review` block sets neither `timeoutSeconds` nor `model`). `diffScaledMs` is a no-op at or under `REVIEW_DIFF_REFERENCE_BYTES` (20 KB). Repro: run one review on a host with `load1 > cpus`; its wall is 1800 s.

**Suspected cause (corrected).** `FALLBACK_REVIEW_TIMEOUT_S` (3600 s) is applied only inside `fallbackReview` (src/config/config-fallbacks.ts:365), reached only through `applyFallbackModel` — a budget-fallback *view* — which the post-merge review never uses (it runs on `ctx.liveConfig`, a live config). The 545 line this entry first named (`free?.(…) ? keptEntry(…) : fallbackReview(…)` in `applyFallbackModel`) is off-path for the post-merge review; its free/`keptEntry` behavior is a real but *separate* latent gap (a slow free model that is the team default would run a review with no floor through the live path). The floor exists only for the fallback view, where the model is a slow free *fallback*. So a single local default model — no cap, no fallback engaged — gets 900 s, stretched to 1800 s under load: a budget built for a fast default, not the slow local model that actually runs the review. (The event log confirms both: the reviewer inherits the local Qwen at the strong tier, and a59a20af's first run ran the full 1800 s — its second ran 1625 s and did return a verdict, so the loop self-resolves within a couple of attempts; the waste is the 1800 s wall on a model that finishes in ~15 turns.)

**Required behavior (the fork is the user's — see QUESTIONS.md "post-merge review on a slow local model").** Either (A) a **config value**: set `review.timeoutSeconds` in tumwater.json to fit the local model (~25 min) — a user/operator action, not bugfix; or (B) **code**: floor a post-merge review whose *own* resolved model is a slow free one (detect via the existing `seamFree`) in `reviewRunConfig`, so the 3600 s floor — not a per-host 2× stretch — protects a slow local default. Both keep the load/diff stretch and the wedged-run quiet watchdog intact.

**Refused 2026-11-13 by plan: the entry's named anchor (config-fallbacks.ts:545 `keptEntry`) is off the post-merge review path (the review runs on `ctx.liveConfig`, a live config, never the fallback view `applyFallbackModel` builds) and its "1800 s is a config value" premise is false (1800 = `reviewRunConfig`'s 2× load stretch of the 900 s default; the live `review` block sets neither `timeoutSeconds` nor `model`) — the real fork (generalize the floor to the post-merge path vs. a user config change) is a product/design decision the user must make (QUESTIONS.md).**
