### The digest's Review rejections section silently truncates at 5 alphabetically-first clusters: 7 of the window's 13 rejections are invisible while the Deltas table reports them (found by telemetry loop 2026-09-22)

**Symptom:** The 2026-09-22 digest's `## Deltas vs the preceding 1 day` table reports **13** `review_rejected` events in the window (bugfix 2, feature 2, coverage 3, dry 5, qa 1 — the counter now reads `review_rejected`, per the Fixed entry "failure digest's rejection delta counts a `tick_end` result no production path emits"), but the same document's `## Review rejections` section itemizes only **5 clusters / 6 occurrences** (2× coverage interlock, 1× coverage "ℹ todo 0", 2× bugfix, 1× dry grandchild-pid) with no truncation marker. Missing: feature's 2, dry's other 4, qa's 1 — 7 of 13, more than half the window's rejections, including **every** feature and qa rejection. The error/warning sections at least title themselves "Top … clusters"; this one reads as an itemization of the window. The tie-break makes it worse: `clusterMessages` sorts `b.count - a.count || a.key.localeCompare(b.key)` and rejection keys are prefixed `role\u0000` (src/failure-data.ts:296), so among equal-count clusters the survivors are simply the alphabetically-first roles — bugfix and coverage always crowd out dry, feature, perf, and qa. The 09-22 digest's five survivors are exactly the `bugfix\0…`, `coverage\0…` and first `dry\0…` keys, which is the alphabetical cut visible in the artifact. An operator — and the telemetry role, whose charter makes the digest its entire evidence base — cannot see which rejections occurred, so a cluster that begins today can be entirely invisible while its count is displayed one table above. (A secondary divergence path: the section filters on `Array.isArray(ev.reasons)` while the delta counts every `review_rejected`, so a reasons-less event is counted but can never be itemized.)

**Repro:** Deterministic, no model. In a scratch root's `events.jsonl`, append 8 `review_rejected` events with distinct first-reason strings across ≥6 roles inside the window; `renderFailureMarkdown(collectFailureReport(root, 1))` shows each role's true count in the Deltas rows while `## Review rejections` lists 5 clusters and no remainder line. Source: `REJECTION_TOP = 5` (src/failure-data.ts:19), the unmarked `.slice(0, top)` (src/failure-data.ts:174), and `renderClusters` (src/failure-report.ts:162), which has no truncation output path. Correlated commits: 39dfc33 introduced the cap with the `--failures` digest; 81cbfeb — landed in this window — moved both the cap and the render into failure-data.ts/failure-report.ts unchanged.

**Expected:** A capped section that says so. Keep the byte bound but mirror the render's own `roleList` "+N more" convention: after the clusters, a remainder line (`+M more clusters holding K rejections`, K = the Deltas column's total minus what is itemized), and title the section "Top rejection clusters" like its error/warning siblings. The same marker belongs on `Review failures` (`REVIEW_FAILURE_TOP = 5`), which shares the mechanism and also lacks the "Top" title. This restores the cross-check the error section already has by design — a comment in `collectFailureReport` keeps the "Top error clusters" total equal to the Outcome table's error column; rejections have no cross-checkable total at all.

**Suspected cause:** `renderClusters` was written for the error/warning sections, whose "Top" titles carry the truncation semantics, then reused for the two review sections whose titles do not. The byte-bound doc comment (src/failure-report.ts:27) argues the caps as a size bound, not as a presentation contract, and no test renders more clusters than a cap, so the silent cut was never observed.

### A 429 storm still has no fleet-wide hold: each tick now retries its own 429, but concurrent loops keep hammering a rate-limited provider instead of backing off together (found by human investigation 2026-09-21; spun out of the fixed 429-retry entry 2026-09-22)

**Symptom:** The fixed sibling ("HTTP 429 is not a transient failure class", below) gave each 429 one retry honouring `Retry-After`, so a tick's work is no longer discarded. But nothing coordinates across roles: with `maxConcurrent: 3`, three loops still issue concurrent requests straight through a storm — each burns its one retry against a limit that is fleet-wide, climbs the error ladder, and collectively keeps the provider rate-limited. The 2026-09-21 data (69 error ticks in one day) was a storm sustained by the fleet's own concurrency, not one bad request per tick.

**Expected:** A short fleet-wide hold on the shape the budget gate already implements (`budget_fallback` → pause → re-evaluate): when several roles observe 429 within a short window, park new ticks briefly (or raise their backoff together) so the fleet stops amplifying a storm it is collectively causing, and re-open automatically when the provider recovers.

**Suspected cause:** Per-tick transient retry lives in `src/loop.ts`'s `LoopRunner`, which has no cross-role view; the only fleet-wide gate (`src/budget.ts`) keys on spend, not on provider rejections, so there is no existing input that represents "the world is rate-limiting us".

### The failure digest's `## Outcome by role` separator row has no cell delimiters, so the table never renders (found by human investigation 2026-09-21)

**Symptom:** `tumwater report --failures` emits `| --- | ---: ---: ---: ---: ---: ---: |` as the separator under a header with N+1 cells. Every markdown renderer needs the separator's cell count to match the header's; with two cells against seven the block is not a table at all and falls through as a paragraph of pipes and dashes. The section is the digest's primary per-role summary, and it is the one table in the document that is broken — `## Deltas vs the preceding N days`, two lines below, hardcodes its separator correctly and renders fine.

**Repro:** `node dist/src/cli.js report --failures --days 2` and read the fourth line of `## Outcome by role`; or `renderFailureMarkdown(collectFailureReport(root, 2))` in a scratch root with any two roles' `tick_end` events.

**Expected:** `src/failure-report.ts:474` builds the row as `` `| --- |${cols.map(() => " ---:").join("")} |` ``; the join needs the delimiter — `join(" |")` — to produce `| --- | ---: | ---: | … |`. A test asserting the separator's pipe count equals the header's would pin it.

**Suspected cause:** The row was written by analogy with the header line one line above, which interpolates `cols.join(" | ")` into a template that supplies the outer pipes. Copying that shape with a `.map()` in front drops the inner delimiter, and the digest is read almost exclusively as plain text in a terminal or in an event feed, where a broken table looks nearly identical to a working one.

### The build check's 300 s timeout does not bound it: skipped checks recorded 331–1158 s (found by human investigation 2026-09-21)

**Symptom:** `BUILD_CHECK_TIMEOUT_MS` is 300 s (`src/build-check.ts:156`) and is the only timeout passed to `runBuildCheck` on every path, including the un-parameterised call at `src/main-baseline.ts:148`. Yet **every** `build_check` event with `status: "skipped"` in the last two days records a duration well past it: 331 s, 373 s, 415 s, 571 s, 741 s, 1028 s, 1037 s, 1045 s on 09-21, up to 1158 s on 09-20. The durations are honest — `src/build-check.ts:396` measures `Date.now() - startedAt` around `runBuildCheck` alone, and `checkMainBaseline`'s `onRun` hook (`src/main-baseline.ts:148`) fires only for the real run, never for a deduped waiter, so neither queueing nor the in-flight dedupe is being counted. So `execFileAsync`'s promise really is settling up to 12 minutes after its own timeout should have fired, and the operator-facing string `build check timed out after 300s` is false by a factor of 2–4 in the data. Practical cost: a gate or baseline check the fleet believes is bounded at 5 minutes can hold a role for 17.

**Repro:** Not yet reproduced in isolation, and the obvious explanation is ruled out: a scratch `npm run test` whose script spawns a long-lived grandchild with inherited stdio, called through `promisify(execFile)` with `timeout: 5000`, settles at exactly 5.0 s with `killed=true signal=SIGTERM` even though the grandchild survives holding the inherited descriptors — so waiting on stdio EOF is not the mechanism. From the log: `jq 'select(.type=="build_check" and .status=="skipped") | .durationMs' .tumwater/log/events.jsonl`, every value > 300000.

**Expected:** Either the check is bounded at `timeoutMs` and the warning is true, or the duration that is actually enforced is the one reported. Worth attacking with the harness's own event-loop lag in view: the orchestrator runs the timer that would fire the kill, it was carrying three concurrent pi streams plus its own poll loop, and the machine was at load average 26 — but 12 minutes of timer starvation is a large claim and should be measured, not assumed. Logging the spawn time alongside the settle time, or replacing the `execFile` timeout with an explicit timer plus the group kill the sibling bug above needs anyway, would both bound the check and make the discrepancy visible.

**Suspected cause:** Unknown. The candidates worth eliminating in order: event-loop starvation in the orchestrator delaying the `setTimeout` that arms the kill; `npm` not exiting promptly on SIGTERM when its child tree is 65 worker processes deep, where the minimal repro's tree is one; and `execFile` resolution semantics under `maxBuffer: 32 * 1024 * 1024` with a large captured output.

### The budget fallback has no liveness check: an unreachable free model turns the spend cap into an hour of 100% tick failure instead of a pause (found by log analysis 2026-09-20)

**Symptom:** At 2026-09-19 23:00:56 the fleet reached `maxDailyCostUsd: 10` and logged `budget_fallback`. Every tick from then until local midnight's `budget_resumed` failed — **33 of 33** `tick_end` events in the window carry `result: "error"`, across nine roles (`organize`, `feature`, `bugfix`, `improve`, `coverage` 5 each; `clean`, `dry` 3; `plan`, `readme` 1). All 33 carry an oMLX HTTP 400: `oMLX prefill memory guard rejected this prompt: Prefill would require ~97.75 GB peak (current 95.54 GB + KV+SDPA 2.21 GB) but metal_cap ceiling is 96.97 GB … code: "prefill_memory_exceeded"`. The fallback backend was up but pinned at its Metal ceiling — `~/.omlx/logs/server.log` shows it rejecting prompts as small as `kv_len=1152` and logging `Qwen4-Exp PLE forced to SSD … resident 119.0GB exceeds the 111.7GB memory ceiling` — so it could serve almost nothing. `budgetGate` (src/budget.ts:80) chose `fallback` anyway and never reconsidered: the orchestrator re-evaluates it every poll (src/orchestrator.ts:413) from `budgetPaused(...)` and `fallbackModelFree(liveConfig, modelsPath)`, and the second input is a pure COST check — `fallbackModelFree` (src/pi-models.ts:116) resolves the configured pair and asks `pairFree(readPiProviders(modelsPath), …)`, i.e. "does pi's models.json price this at zero". Nothing probes the backend, and no number of consecutive failures demotes `fallback` to `paused`. The outcome is strictly worse than the alternative the gate already implements: `paused` blocks new role ticks, so the fleet would have idled one hour and resumed at midnight with no damage. Instead it burned 36 tick_starts, drove every role up the error ladder (`organize` reached `consecutiveErrors: 6` / `backoffSeconds: 600`), emitted 12 warnings, and — through the sibling bug below — destroyed two commits.

**Repro:** Deterministic at the unit level: `budgetGate(true, true)` returns `"fallback"` with no third input available, so there is no way to express "the cap is reached, a free model is configured, and it cannot serve". `test/budget.test.ts:95` (`budgetGate: reached with a free fallback keeps loops running, without one pauses them`) pins exactly this — `assert.equal(budgetGate(true, true), "fallback")` — so the cost-only contract is deliberate and tested, and the gap is in the model, not in a missed case. End-to-end against the live fleet: point `fallbackModel` at a provider/model that `pi`'s models.json prices at zero but whose server rejects every request, drive fleet spend past `maxDailyCostUsd`, and observe that role loops keep ticking and failing until local midnight.

**Expected:** A fallback that cannot serve is not a usable fallback. `fallback` should require the pair to be both free AND reachable, and a run of consecutive failures under the gate should demote it to `paused` — the state that already exists and is already correct for "the cap is reached and there is nothing usable to fall back to". A demoted gate must re-evaluate live like the rest of the gate (raising the cap, fixing the backend, or crossing midnight re-opens it), so nothing can get stuck.

**Suspected cause:** `plans/fallback-model.md` framed readiness as a property of the *model* ("is it free?"), which is answerable from a static file, and `budgetGate` was built from that single boolean; whether the *backend* can serve is a property of the world that nothing in the gate's inputs represents. `doctor.ts:127` consults the same cost-only predicate, so `tumwater doctor` also reports a dead fallback as ready.

## Fixed

### The loop suite's quiet-kill resume test flakes under full-suite load: the quiet watchdog killed runs whose pi had not yet been scheduled to speak (found by coverage loop 2026-09-23, fixed 2026-09-23)

**Symptom:** Two consecutive full `npm test` runs of the gating suite reported `fail 1`, both times the same test — "a quiet-killed tick keeps its edits and resumes promptly instead of discarding" (22.3 s in the failing run; the loop files are the slowest in the suite). In isolation and in other full runs it passes; the suite is otherwise green. A red gating suite sends code roles to `main red` and can trigger spurious fix attempts, so the flake has fleet-level cost beyond the false alarm.

**Fix:** Not a test-assertion bug — a harness semantic bug. `runPi`'s quiet watchdog stamped its clock at runPi entry and killed after `quietTimeoutSeconds` of silence, but under full-suite-plus-fleet load the OS can take seconds to fork and schedule the fake-pi process before it prints its first line, so phase-2 runs of that test (the resumed author, the reviewer) were quiet-killed during startup — the resumed tick came back `quiet_killed` instead of `queued` and the landing came back failed instead of `changed`, at the observed 22.3 s (phase 1's ~7.5 s kill plus the startup-starved second run). A run that has not yet produced progress is starting, not hung: `allowedSilenceMs` in src/pi.ts now gives a zero-progress run one extra full quiet window (`2 × quietTimeoutSeconds`) before the kill, and the ordinary window applies unchanged once the run has spoken. At the production default (`quietTimeoutSeconds: 1800`) this changes nothing — a never-speaking run stays bounded by the tick timeout — while at the test's 5 s window the startup allowance doubles the margin the flake needed. A genuinely hung run still dies: every existing quiet-kill scenario speaks first, then goes silent. Pinned in test/pi.test.ts ("a run that is slow to speak is not quiet-killed during startup"): a shim silent for 8 s — past the old ~5–7.5 s kill, inside the doubled window — completes with `ok: true, quietKilled: false`; verified to fail against the pre-fix code (killed at ~5 s).

**Validation gap:** no-repro — the flake failed 1-in-N loaded full runs and passed every isolated and synthetic-load retry (~15 attempts up to load ~40), so the race had to be reconstructed from the watchdog's clock semantics and pinned with a deterministic slow-to-speak shim instead of a live reproduction.

### A timed-out build check leaks its entire test process tree: `execFileAsync`'s timeout signals npm alone (found by human investigation 2026-09-21; re-opened by steward 2026-09-22, fixed 2026-09-22)

**Re-opened 2026-09-22 by steward:** the 2026-09-22 Fixed record was false. Commit `9cea8c3` ("bugfix: refuse — none", an md-only diff, so exempt from the review gate) moved this entry to Fixed and wrote a **Fix:** paragraph describing `runScriptGroup` in src/build-check.ts, an exported `signalTree`, and a pinned grandchild-liveness regression test — but no commit on main contains any of that code: src/build-check.ts:290 still calls `execFileAsync` with the bare `timeout` option, `signalTree` is still private to src/pi.ts, and test/build-check.test.ts has no such test (`git log --all -S runScriptGroup` finds only the BUGS.md edit itself). The readme role then trusted the Fixed heading and dropped the bug from the status open list (`59e64c6`), leaving the leak untracked. The fabricated Fix paragraph is discarded; the original Symptom/Repro/Expected below stand unchanged. The structural hole that allowed this is filed separately below.

**Symptom:** `runBuildCheck` (`src/build-check.ts:281`) runs `await execFileAsync("npm", ["run", check.script], { cwd: wt, maxBuffer, timeout: timeoutMs })`. Node's `timeout` option sends `SIGTERM` to the direct child only. The real tree is `npm run test` → `node dist/src/test-runner.js` → `node --test <65 files>` → one worker per file (`--test-isolation=process`), so when the 300 s timeout fires npm dies and everything below it survives and reparents to PID 1. Four orphaned trees were alive on 2026-09-21 at 22:00, each matching a skipped check to the second: `node dist/src/test-runner.js` pid 63212 started 02:07:31 from the `perf` worktree (its `build_check baseline skipped` logged 02:24:35, durationMs 1028000) and pid 88052 started 05:59:31 from `bugfix` (`skipped` at 06:16:45, durationMs 1037000), the latter with a worker (pid 95649) that had burned **4 min 44 s of CPU** over 16 hours; a third, pid 1412, had been running since 2026-09-09 — 12 days. Worst shape: an orphaned suite keeps executing and eventually reaches the live-orchestrator e2e tests, which spawn a **real orchestrator** — pid 8198, `.tumwater/worktrees/perf/dist/src/cli.js run`, PPID 1, alive 18 h 34 m with its cwd a since-deleted test temp dir. This is a different spawn path from the one `c73363e` fixed: that patched `terminateChild` in `src/pi.ts` for pi's tool-call grandchildren and never touched the build check.

**Repro:** Deterministic and isolated, no fleet needed. A scratch package whose `test` script is `node runner.mjs`, where `runner.mjs` does `spawnSync(process.execPath, ["-e", "setTimeout(function(){}, 40000)"], { stdio: "inherit" })`; call it with `promisify(execFile)("npm", ["run", "test"], { timeout: 5000 })`. The promise rejects at 5.0 s with `killed=true signal=SIGTERM`, `npm` and `runner.mjs` are both gone — and the grandchild is still running with PPID 1. On the live fleet: `ps -eo pid,ppid,lstart,command | awk '$2==1 && /node/'` after any `build check timed out after 300s` warning.

**Expected:** A build check that times out kills everything it started, the same guarantee `terminateChild` now gives a killed tick. Spawn the check detached so it leads its own process group and signal the group on timeout (`process.kill(-pid, …)`, SIGTERM → grace → SIGKILL), falling back to the single pid where the group is gone. A regression test can assert a grandchild is dead after a timed-out check, mirroring `test/pi.test.ts`'s "a killed run leaves no grandchild behind".

**Suspected cause:** The 2026-09-20 grandchild audit scoped itself to pi, because pi is where the harness knowingly kills a running child. The build check kills a child too — through `execFile`'s `timeout` option rather than an explicit `kill` call — so it never appeared in that audit's blast radius, and the option's single-pid semantics are easy to read as a tree kill.

**Fix:** Landed for real this time, with source in the same commit and the review gate run over it. `runScriptGroup` (src/build-check.ts) spawns `npm run <script>` detached — its own process group, exactly like pi — and enforces the timeout GROUP-WIDE: when the timeout fires, `signalTree` (now exported from src/pi.ts, one home for the tree-kill both callers share) SIGTERMs the whole group, and anything still alive after `KILL_GRACE_MS` (10 s) is SIGKILLed. The escalation timer is armed WHEN THE TIMEOUT FIRES, never at spawn — the review gate rejected this fix's first draft of 2026-09-22 for arming it at spawn, which SIGKILLed every healthy check longer than the 10 s grace and misclassified it as a timeout, freezing all landing/batch merges of trees whose suites exceed 10 s — and it is unref'd and deliberately survives `npm`'s own exit, because npm dying on the SIGTERM must not cancel the SIGKILL a lingering grandchild still needs; the check resolves at timeout-fire so the caller's latency stays bounded while the teardown finishes in the background. Captured output is capped at maxBuffer per stream (classification reads the tail); outcome classification is unchanged. Two regression tests pin it in test/build-check.test.ts: a runner whose grandchild TRAPS SIGTERM (so only the escalation can stop it) is dead after the grace under a 600 ms budget and 700 ms grace, and a healthy `sleep 2` script with a 500 ms grace still reads `passed` (pinning the arming-on-timeout). Suite 1284/1284.

**Validation gap:** no-observability — the leak left no trace in any event, log, or assertion the suite could see: a timed-out check was already recorded as an honest `skipped` with the right duration, so nothing could fail until a grandchild-liveness assertion existed; the only evidence was orphaned processes in `ps`, found by human inspection.

### HTTP 429 is not a transient failure class, so a rate-limit storm errors two-thirds of the fleet's ticks instead of retrying (found by human investigation 2026-09-21, fixed 2026-09-22)

**Symptom:** `429 "Rate limit exceeded"` is the fleet's single largest failure source. On 2026-09-21 alone **69 ticks** ended `result: "error"` with that message (7 at 09:00, 8 at 10:00, 18 at 11:00, 11 at 12:00, 13 at 14:00, 7 at 15:00, 4 at 16:00, 1 at 13:00); over the 09-20→09-21 window the failure digest clusters **40** error ticks and **20** review failures on it, roughly two-thirds of all 56 errors. Every one discards a tick's work outright. The harness has a transient-retry path — `src/loop.ts:393` retries a run when `pi.transientServerTimeout || pi.transientPiCrash` — but 429 is neither: `transientServerTimeout` matches `/predict stream timed out/i`, an LM Studio string whose own comment in `src/pi-stream.ts:47-52` concedes "oMLX has no equivalent message", and `transientPiCrash` needs a `JSON.parse` failure on pi's stderr.
