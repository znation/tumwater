### `test/supervisor.test.ts` "startParentDeathWatch takes a SIGKILLed supervisor's grandchild down with it" flaked again on 2026-10-16, after its 10-01 and 10-09 Fixed entries and the 10-11 rewrite to a SIGUSR2-driven poll (found by operator session 2026-10-16 from improve's red merge check)

- **Symptom:** at 07:29:28 PDT, improve's in-lock merge check for `d4b62873` failed one test: `✖ startParentDeathWatch takes a SIGKILLed supervisor's grandchild down with it — AssertionError [ERR_ASSERTION]: the orphaned grandchild's watch fired and ran its stop path`. The check ran 145 s. Recovery re-landed it green at 07:40, and it merged. That is the same assertion as the Fixed entry "The SIGKILL-grandchild supervisor test flaked twice in one 2026-10-09 window". Since then 4ec5d729 (10-11) replaced the real poll with one driven by SIGUSR2 from the test, and its comment says a loaded host "cannot stretch" the verdict. It still fails.
- **Reproduce:** no repro; one live failure under the team's normal load.
- **Cause:** unknown. After SIGKILLing `middle`, the test sends SIGUSR2 up to 200 times, 50 ms apart (about 10 s), and breaks out of the loop early if `process.kill(grandchildPid, …)` throws. The failure reads the same in two cases, and the message cannot tell them apart:
  - the reparent was not visible to the grandchild's `process.ppid` within those signals;
  - the grandchild had already exited without writing `gone`, so the loop broke on ESRCH.
- **Expected / fix sketch:** first make the failure name its case. Record whether the loop broke on ESRCH and how many signals were sent. Have the grandchild write the `ppid()` it saw on each poll. Then fix the case that fires. Re-check the 10-09 entry's mechanism, a watch armed against the wrong baseline, on the handed-down `expectedPpid` path.
- **Progress 2026-10-16 (bugfix):** the test's failure message now names its case: signals sent, whether the loop broke on ESRCH, the expected ppid, and the ppid the grandchild saw on each poll (a `gone.seen` file). The cause is still unknown, so the entry stays open until the next flake reads out.
- **Progress 2026-10-16 (bugfix, second):** one candidate cause closed, unconfirmed: the test treated the existence of `started` as ready, but the grandchild created it with `writeFileSync`, so the test could read an empty or partial pid and SIGUSR2 the wrong pid (ESRCH, no `gone`). The grandchild now writes `started.tmp` and renames it. No flake has been seen since, so the entry stays open until the next failure reads out.
- **Progress 2026-10-16 (bugfix, third):** no repro. 30 concurrent runs of the test beside 8 CPU-spinning node processes all passed (the `timeout` wrapper on the spinners did not exist on this host, so the spinners ran unbounded until `pkill`; the load was real). `startParentDeathWatch` (src/process/supervisor.ts:79-104) reads correctly on the handed-down `expectedPpid` path. No code change; the entry stays open until a flake's failure message (signals sent, ESRCH or not, ppids seen) names the case.
- **Progress 2026-10-16 (bugfix, fourth):** one more candidate closed, unconfirmed: the signal loop was bounded by a count (200 × 50 ms), so a grandchild starved for longer than that (the 145 s check suggests heavy load) could miss every poll and the verdict was read right after. The loop is now bounded by 60 s of wall clock. The entry stays open until a flake reads out.

**Waiting for the next failure 2026-10-16 by bugfix: the failure message will show signals sent, whether the loop broke on ESRCH, the expected ppid, and the ppid the grandchild saw on each poll (`gone.seen`).**

### Structural risk: the whole open roadmap is one 41-merge serial rename chain, so no parallel capacity exists behind the in-flight front part (found by the steward role 2026-10-18)

**Refused 2026-10-18 by bugfix: a coordination watch item for the plan/feature/director runs, not a code bug — restructuring the PLANS.md roadmap is outside the bugfix role and too large for one focused change.**

- **Symptom/observation:** PLANS.md `## Planned` is 1102 lines, and the three "Plain terms code" series occupy lines 73–1101 (14 runner parts, 20 run parts, 7 cleanup parts = 41 headings) in a strict dependency chain — every part after part 1/14 is marked blocked on the previous. At any moment only the front part (1/14, in flight by feature-3) is eligible, so the reproducible roadmap strings behind one merge. The four independent in-flight plans (closed-vocabulary near-miss, plan tight-loop, GUI Validation-gap chart) are the only source of parallel progress.
- **Why it matters:** each part renames files the independent plans also edit (e.g. `src/loop/loop-tick.ts` appears in both the plan tight-loop entry and runner part 1/14), so every one of the 40 blocked parts must rebase against whatever else lands on main before it; a single stuck, superseded, or direction-changed part stalls all the parts behind it. The series' guard rails (`test/retired-names.test.ts`, the vocabulary guard) catch drift only after a part lands, not the sequencing itself.
- **Suspected cause:** the series was filed as one user request (2026-10-16) split into merge-sized parts, correct per tick but it makes the roadmap critical-path-bound for the series' whole duration.
- **Expected / watch item:** hold the series strictly serialized — do not let an independent plan land an unplanned change to a file the front part will touch without the acknowledged rebase — and if the terminology direction in plans/terminology.md changes mid-series, rewrite the pending parts in place before the front part reaches them. Not a bug to fix now; a coordination risk for the plan/feature/director runs to carry.

### Two `logs -f` processes leaked out of a slot's run and stayed alive for 3½ days; the doctor only detects them, nothing reaps them (found by operator session 2026-10-19 from the running instance's `tumwater doctor`)

- **Symptom:** on 2026-10-19 13:46 `tumwater doctor` reported `fail orphans`: `2 orphaned processes (PPID 1): pid 59222 (age 03-11:24:45, cpu 0:42.79) node .tumwater/worktrees/_slot-8/dist/src/cli.js logs -f; pid 60127 (age 03-11:24:17, cpu 0:42.74) node .tumwater/worktrees/_slot-8/dist/src/cli.js logs -f — nothing reaps these`. Both were started Fri 2026-10-16 02:35:55 and 02:36:23 in `_slot-8`, reparented to launchd (PPID 1), and survived roughly a dozen orchestrator generations and the 2026-10-18 pi-stdin fix without ever being reaped.
- **Reproduce:** `tumwater doctor` on the live project reports the check red while the processes stand; `ps -o pid,ppid,lstart,etime,command -p 59222,60127` shows PPID 1 and the Oct 16 start. No scratch repo; it is a live-state leak.
- **Cause:** unknown. A `logs -f` left running after the run that launched it ended was not in the run's killed process group (detached, or reparented when its parent bash exited), and no reaper collects PPID-1 orphans — the doctor's `orphans` check is a detector only ("nothing reaps these; kill each with its descendants"). Whether the spawner is a role's bash tool backgrounding `logs -f`, an operator shell, or the harness is not established from this evidence.
- **Expected / fix sketch:** establish what spawns a detached `logs -f` in a slot (grep the sessions for the Oct 16 window), then have the run/slot teardown reap its own process group including detached children — or give the doctor/orchestrator a reclaim step for orphans it can attribute to a slot. Confirm no other orphan source before adding a general reaper.

### A dangling `refs/tumwater/merge/feature-5` made a slot's `git checkout --detach main` exit 128 and errored organize's run (found by operator session 2026-10-19 from the running instance's doctor output and `events.jsonl`)

- **Symptom:** organize run 717 ended `error` at 2026-10-19 12:17:48, 48 ms in and before any agent work: `git checkout --detach main failed (128): fatal: bad object refs/tumwater/merge/feature-5`. `tumwater doctor` still reports `warn repeated failures: organize: 6 failed runs — last error: git checkout --detach main failed (128): fatal: bad object refs/tumwater/merge/feature-5`.
- **Reproduce:** no repro; the ref is already gone. By 13:46 `git show-ref | grep tumwater/merge` lists only `refs/tumwater/merge/organize` (`cb4d4508`), and `git for-each-ref`/`git rev-parse` no longer see the feature-5 ref, so a fresh attempt cannot fail this way until the ref is recreated and pruned again.
- **Cause:** suspected. A `refs/tumwater/merge/<role>` ref was left pointing at an object git could no longer find (pruned, or never written), and the pooled-slot reset that runs `git checkout --detach <mainBranch>` (`hardResetWorktree`, src/git/worktree.ts:252) aborts on the corrupt sibling ref rather than ignoring it — so a garbage ref in the shared common-dir ref store fails a role's tick. The ordering that let the object go before the ref is not pinned down from this single occurrence.
- **Expected / fix sketch:** make the slot reset tolerate a dangling sibling merge ref (verify each `refs/tumwater/merge/*` and drop the unreadable ones, or scope the checkout so it does not walk unrelated refs), and check the merge-ref cleanup path for an object-pruned-before-ref-deleted ordering.

### `test/cli-run-window.test.ts` "run --for boots, stops itself at the deadline, and prints the summary" flaked 14 times in five days on "the info file publishes the window's deadline", twice holding main red (found by operator session 2026-10-19 from the failure digest's `flaky:` cluster and the `main_red_hold` events)

- **Symptom:** `✖ run --for boots, stops itself at the deadline, and prints the summary — AssertionError [ERR_ASSERTION]: the info file publishes the window's deadline` (`test/cli-run-window.test.ts:100`, `assert.equal(typeof stopsAt, "number", …)`). Seen 14 times from 2026-10-16 15:25 to 2026-10-19 03:10, as gate checks (`gate check failed then passed on retry — flaky`), merge checks (`merge check failed …`, `known-flaky failure, merge kept`), and twice as `main_red_hold` (10-19 01:56:36 on `09a9329e`, 02:06:58 on `19dd179e`). `tumwater doctor` already lists it under `flaky checks` (×3/24h) — it is detected but not filed.
- **Reproduce:** no reliable repro. The test spawns `tumwater run --for 3s`, then polls `orchestratorStatePath(repo)` for `stopsAt` only until `Date.now() + 2500`; `stopsAt` is `undefined` when that window closes. I could not reproduce it under 8-way CPU load (12/12 passed, each ~3.16 s), so it needs the fuller load of a live merge check (concurrent suites, host sleep), not plain CPU spin.
- **Cause:** suspected — a startup-latency race against the fixed 2.5 s poll, not the write. `writeOrchestratorInfo` (which sets `stopsAt`) is synchronous at the top of `runOrchestrator` (src/orchestrator/orchestrator.ts), so the missing `stopsAt` means the child had not reached that line within 2.5 s of spawn (node boot + config load + redeployer/prewarm setup) under host load or a mid-check sleep.
- **Note for a reproducer:** a build without a stamp fails this test differently — the banner drops its `· build <sha>` segment, so `assert.match(s.out(), /tumwater running on branch main · for 3s ·/)` fails with `… · for 3s — Ctrl+C to stop`. Run `node scripts/stamp-build.mjs` (or `npm test`/`test:gate`) first, or that failure masks this one.
- **Expected / fix sketch:** bound the poll by readiness rather than wall clock — poll until the info file exists, then assert `stopsAt` — or raise the deadline well past a loaded boot. Keep the `stopsAt ≈ spawn + 3000` nearness assertion, which is the real contract.
