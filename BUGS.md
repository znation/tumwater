### A review that starts during its role's run renames the run's log away, so the dashboard reports the run as stuck (found by operator session 2026-11-04 from the role logs)

- **Symptom:** on 2026-11-04 the dashboard raised "bugfix looks stuck — bugfix: no agent output for 4h21m", and the bugfix row read `working 7h5m · turn 1`. Run 1840 (started 10:01:19) was healthy: it had made 85 turns, was editing `src/scheduling/scope.ts`, and was still streaming. At 12:44:15 a post-merge review of bugfix's merged `9c80d8e5` started. It opened `.tumwater/log/bugfix.pi.jsonl`, which was over `logMaxBytes` (16 MiB), so the open renamed the file to `bugfix.pi.jsonl.1` and created a new one. Run 1840 kept writing to the renamed file through its open descriptor: `lsof` showed the orchestrator (pid 71311) writing `bugfix.pi.jsonl.1` and `bugfix.pi.native.jsonl.1`. The new `bugfix.pi.jsonl` holds only the 57 s review, which ended at 12:45. The progress reader tails that file, so the row showed one turn and no output since 12:45, and `STALL_RE` raised the alert.
- **How often:** the current log generation alone shows it for five roles on 2026-11-04: feature-5 (12:18), feature (12:28), feature-2 (12:31), bugfix (12:44) and feature-3 (17:01). In each, the new `<role>.pi.jsonl` starts with a `"kind":"gate"` run marker and the `.1` was written after that marker. feature-3's run was still writing `feature-3.pi.jsonl.1` at 17:08. Rotation keeps one generation, so older cases are gone.
- **Worse case (not yet seen):** if the new file passes 16 MiB and another run opens it while the first run is still live, `rotateIfLarge` deletes the `.1` that run writes to. The rest of that run's transcript goes to an unlinked file and is lost. The run itself is not killed in either case, because its watchdogs read the in-memory stream, not the file.
- **Reproduce:** fill a role's raw log past `logMaxBytes` and start an authoring run on it. While it is live, start a second agent run with the same `rawLogFile` (a post-merge review, the merge gate's reviewer, or a conflict resolver). The first run's later output lands in `<log>.1`, and `readLiveProgress` for the role reports only the second run.
- **Cause:** `openAppendLog` (src/agent/agent-spawn.ts) calls `rotateIfLarge` (src/files/files.ts) on every open and never checks whether another run in the process still has the file open. Every agent run of a role writes `piLogPath(root, role)` (src/runner/runner-pi.ts, src/review/post-merge-review.ts), and the native log is shared and rotated the same way. Post-merge reviews run while the role's next run is live. The progress reader (src/ui/progress-data.ts) reads only the live path.
- **Expected / fix sketch:** never rename a log that another live run in this process still writes. Count opens per path in `openAppendLog`, release on stream close, and skip the rename while the count is above zero, so the first open after the last writer closes rotates it. This also prevents the `.1` deletion. A run already writing a renamed file needs no repair: its row recovers when it ends.

### A role whose change waits in the merge queue is handed the same backlog entry again, so its next run re-implements it (found by operator session 2026-11-04 from the team's event log)

- **Symptom:** on 2026-11-03 feature run 2653 queued `4901d570` ("Split runAgent's ~190-line Promise executor into five named helpers") at 17:10:03 and kept its claim. Run 2654 started at 17:14:32, and its prompt's `<assigned-entry>` named the same runAgent entry. `4254b1f1b` merged at 17:30:33, but run 2654 went on for 107 min, queued `bd1befbb9` ("Split runAgent's executor into five named module-private steps") at 19:01:43, and the merge dropped it as withdrawn at 19:02:07. The same day feature-2 run 854 started at 05:25:52 while its own `7bd1ad39` (the `cycleView` Ctrl+T split) was still queued. Its prompt assigned the `cycleView` entry again, although its role notes said "landed the `cycleView` Ctrl+T split". `7bd1ad39` merged as `00d580de1` at 05:31:06, and run 854's 68-min redo `d58fe02d` was dropped as withdrawn at 06:34:06.
- **How often:** in events.jsonl since 2026-10-30 20:30, 17 feature/bugfix runs that were not a revision or a resume started while the role's own queued change still carried the claimed entry — about 19 h of run time. 11 of them queued a second change for that entry, 5 ended no_change and 1 was aborted.
- **Before the withdrawn-entry check (b8dfa1fe6, 2026-11-02 16:06) the second change merged.** Its code was already on main, so after the rebase only the re-archived entry was left: `7afff714b` (feature-5 #286, parseWriteFlags) has a commit message describing src work but touches only PLANS.md and PLANS-DONE.md. The main watch logged eight "PLANS-DONE.md/BUGS-FIXED.md adds 1 "### " heading it already carries" warnings from 10-30 to 11-02. BUGS-FIXED.md on main still holds 7 duplicated headings (`git show main:BUGS-FIXED.md | grep '^### ' | sort | uniq -d`). Two of them come from this race: "`tumwater init` on a directory that has a README.md but no git repo…" (bugfix-2 #311) and "The main watch re-attributes an ongoing red to each later tip it re-checks…" (bugfix #1813).
- **Reproduce:** a scheduling test with a feature runner that holds `state.claim`, is not running, owes no revision or resume, and has a merge-queue entry whose `claim` key is that same entry (still listed under `## Planned` on main). `claimGroupAdmission` returns `"admitted"`, and the run's prompt assigns the entry the queued change already implements.
- **Cause:** `claimGroupAdmission` (src/scheduling/admit.ts) admits any runner that holds a claim ("its revision, resume or retry is the same entry"). `claimReleaseReason` (src/scheduling/claims.ts) keeps the claim while main still lists the entry, which stays true until the queued change merges and archives it. Nothing tells "owes the entry more work" (`owesClaimedWork`: a revision or a resume) apart from "already handed its work to the merge queue". 1c631208c (2026-10-31, "Stop the scheduler interlocking a role on its queued merge") removed the queued-merge hold and the `hasQueuedMerge` idle term, and its RISK line named this race. The 10-30 hits show that interlock-relief runs already did it before that commit.
- **Expected / fix sketch:** a runner whose queued or pinned change records its claim (`MergeEntry.claim`), and that owes the entry nothing else, does not run on that entry again. Keep the entry held, so no sibling instance takes it either, and give the runner the next free entry or let it stand down. A rejected change's revision still takes the entry. Then delete the duplicated headings in BUGS-FIXED.md, keeping one copy of each.

### A post-merge reviewer's fix lands on main with no check, so a broken repair turns main red (found by operator session 2026-11-04 from the team's event log)

- **Symptom:** on 2026-11-03 at 05:30:54 feature-6's post-merge review of `74600d2e5` logged its verdict and, in the same second, merged its repair `b2d7852a0` ("tumwater(reviewer): Fix 74600d2e — …"). No `build_check` ran for it. The next main check (05:35:30) failed 5 tests that the previous check (`15fcb70d`, red only on comment width) had passed: merger-check's "a failing pre-check on a green main rejects the merge and spends no pi run", "a failing pre-check on a red main keeps the pin, records no rejection, and spends no pi run" and "a synced rebase moves the merge ref so a failed gate keeps the tree that can merge"; merge-pipeline-watch's "a change the watch has not caught up with is kept, re-queued once the watch checks its base, then judged"; and "no exported symbol goes unused outside its own file". Main stayed red until `1969bfd53` and `bbfb996ef` (2026-11-04 01:04–01:07), about 20 h. Self-redeploy targets only a green commit, so the team ran build `1febf1af` that whole time and was 85 commits behind when main turned green.
- **Earlier case:** `33da71ae9` (feature-2's repair of `8ed0d3eec`, 2026-11-02 07:18:10) landed the same way and added 2 new failures: "the merge lock is the only merge-lock holder: …" and "no identifier or file name in src/ or test/ uses a retired name". 2 of the 13 reviewer fixes merged since 2026-11-01 added failures to main.
- **Reproduce:** queue a post-merge review whose reviewer edits a file so that a test fails, and replies with a FIX line. The post-review drain merges the fix, and the next main check fails.
- **Cause:** `mergeReviewerFix` (src/merge/merge-post-review-drain.ts) lands the fix through `mergeToMain` (src/merge/merge-to-main.ts). Since "Every commit is verified on main, part 4l/3" removed the in-lock `verifyMerge`, `mergeToMain` is a rebase and a fast-forward under the merge lock and runs no check. Only a diverging conflict resolution reaches `recheckResolved`, and this caller answers that `retry`. The gate (`reviewAheadOfMain`) runs in the merge slot before `mergeToMain` (merge-core.ts), but the reviewer-fix path calls `mergeToMain` directly. Two comments are stale since 4l/3: `mergeReviewerFix`'s doc comment says "mergeToMain, whose gate runs over the fix tree", and its `recheckResolved` comment refers to "the in-lock build check".
- **Expected / fix sketch:** before the fast-forward, run the fix tree through the same gate check a queued change gets, with its known-failure and flake handling. A failing fix never lands: it keeps the entry and its fix ref for a retry, or records the findings like an exhausted chain. Correct the two stale comments.

### The director re-runs every poll while a second commit of its waits on the branch, each run ending `skipped` (found by operator session 2026-11-04 from the team's event log)

- **Symptom:** director run 192 ended `queued` with `heldOnBranch: true` at 2026-11-03 02:08:40, while its first change `1e2c6ab39` was still in the merge queue. From 02:09:02 to 02:12:22 the director woke with reason `leftover` every 20 s and ran runs 193–203, each a `run_start` then `run_end skipped` about 10 ms later, until `56480e895` merged at 02:12:23. That is 11 runs and 33 events, and the director's run counter rose by 11. This wait was 3.5 min, but queue waits of 1–2 h happen (queuedMs 7,082,838 for `31ddc7a0a` on 2026-11-04), which would mean hundreds of skipped runs.
- **Reproduce:** let a director run commit while its previous change is still queued (the run ends `queued` with `heldOnBranch: true`). Every later poll admits it with reason `leftover`, and leftover recovery's `relief_wait` arm ends the run `skipped`.
- **Cause:** `leftoverPending` is `pinnedDirector` (src/scheduling/skip.ts). `directorGate` (src/scheduling/scheduling.ts) runs whenever `leftoverPending` is set and `now >= nextRunAt`. The `relief_wait` arm of leftover recovery (src/runner/runner-recovery.ts) returns `{ result: "skipped" }`, and run-apply.ts schedules a skipped outcome with `scheduleAtMinInterval`, the 20 s default `minRunIntervalSeconds`, so the next poll admits it again. `directorGate`'s option comment says the leftover run "is due on `nextRunAt` … never earlier, so a persistently blocked fast-forward cannot spin the merge queue", but a relief wait is a wait on the queue, not a failed merge.
- **Expected / fix sketch:** while the held commit waits on a queued change, the director is not due. Leave `leftoverPending` false for the relief-wait case, or wake the director when that queue entry settles, so a waiting second commit costs no runs.
