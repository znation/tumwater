### The stranded-plan scanner (DONE_STAMP) misreads a live `## Planned` entry as completed when its parenthetical cites another plan as `<name>, done DATE`, so the entry is stranded and the repo-checks test reds (found by the coverage role 2026-11-15)

**Note (2026-11-15, coverage role).** The live `## Planned` entry that triggered this is the git trust-gate pin (`refShaFromFiles` — `filesBackendTrusted`), which the FEATURE role has since implemented and ARCHIVED on main (`dcd87b455`); on main's live PLANS.md `strandedPlanEntries` returns nothing, so the repo-checks test is green there and the red seen in a worktree is a transient of that worktree still carrying the entry in `## Planned` (its branch predates the archive). The LATENT defect remains: ANY live `## Planned` entry whose `(planned …)` parenthetical cites a prior plan as `<name>, done DATE` will strand — the fix is to anchor the completion stamp to the entry's own trailing metadata, so a `<noun>, done DATE` reference no longer counts.
**Symptom.** `strandedPlanEntries` (src/backlog/backlog-structure.ts) reads a `## Planned` entry as finished-and-never-moved — the stranding that fails `test/backlog-structure.test.ts`'s "this repo's current PLANS.md and PLANS-DONE.md yield nothing" and blocks the plan role from archiving the entry — whenever the entry's `(planned …)` parenthetical cites ANOTHER plan as `<something>, done YYYY-MM-DD`. The trigger is `DONE_STAMP = /[—,(;]\s*done \d{4}-\d{2}-\d{2}/`: a comma followed by `done DATE` is one of its structural delimiters, so a citation of a prior completion inside a LIVE entry's parenthetical is indistinguishable from the entry's own completion stamp. The parenthetical prose is matched as a whole (the comment at backlog-structure.ts:151-156 already guards against an English *participle* like "both done DATE", but not against a `<noun>, done DATE` reference), so the entry strays from `## Planned` and the live-file test fails.

**How to reproduce (offline, deterministic).** On a worktree still carrying the trust-gate pin in `## Planned` `npm run test`'s backlog-structure file reports exactly one failing test, "this repo's current PLANS.md and PLANS-DONE.md yield nothing" — `strandedPlanEntries` returns the live `## Planned` entry `refShaFromFiles… files-backend trust gate …` (its parenthetical carries `PLANS-DONE.md, done 2026-10-28`). Verified by driving the built `strandedPlanEntries` over the pre-archive commits' `PLANS.md` (each returns that entry) and over the current main's `PLANS.md`/`PLANS-DONE.md` (each returns nothing, because the entry has since been archived): the red is a product of a live entry carrying a `<name>, done DATE` citation, not of the archive. It recurred because plan parentheticals routinely name a prior plan as `…md, done DATE` to show independence.

**Suspected cause.** `DONE_STAMP` cannot tell the entry's own completion stamp from a `<noun>, done DATE` citation embedded in its parenthetical — both are delimiter-introduced. The scanner (or `headingMetadata`'s joined text) must anchor a completion stamp to the entry's own trailing metadata (the `— done`/`, done` immediately before the closing paren), or a completion stamp that follows a plan name (not a plan's description) must not count as the entry's own.

**Required behavior.** A `## Planned` entry is stranded-done only when its OWN completion stamp is present; a citation of another plan as `<name>, done DATE` inside the parenthetical never strands it. Concretely, on a `## Planned` entry whose parenthetical carries `…PLANS-DONE.md, done 2026-10-28…` with no `— done` of its own, `strandedPlanEntries` returns no entry; a real `## Planned` entry whose heading carries `— done YYYY-MM-DD` (or `(planned …, done …)`) is still stranded-done. `test/backlog-structure.test.ts` pins both.

### The backlog range reader (actionableEntryRanges) reads only `### ` headings, so `- `-bullet entries are invisible to the closed-entries index, the archive dedupe, and the bug wait-close

**Refused 2026-11-12 by bugfix: the entry's premise is false and its real symptom is a phantom-`##` archive split that no bugfix may repair — on the real archive `parseEntryDetails` and `actionableEntryRanges` both read `###`-only and return the identical 2 entries (verified offline, 2-vs-2, titles 8-133 and 134-145), so the range reader is *consistent* with the canonical reader, not blind to it, and the `-` one-line records are body content by the invariant-pinned INV-AX2 (src/verdict/fix-claim.ts `fixedSection`/`isOneLineRecord`); the ~2391 closed entries no reader walks all sit in a phantom-`##`-split section (BUGS-FIXED.md:146, a twin at PLANS-DONE.md:201) that an operator/director archive repair — not a bugfix, which may not edit archive files — must fix, and either of the entry's own "required behavior" branches rewrites that cross-cutting guarantee across twelve shared consumers in one tick, which grows complexity without justifying it.**

**Symptom.** `actionableEntryRanges` (src/backlog/backlog-index-data.ts, `line.startsWith("### ")` is the only entry-start test) is the shared entry reader for twelve modules, yet it recognizes only `### ` headings. The canonical reader `parseEntryDetails` (src/backlog/backlog-md.ts) and the date reader `eachEntryStart` (backlog-md.ts:359) both read `### ` headings AND `- ` bullets as entry-starts, and the team's roles compress most closed bugs into single-line `- ` bullets — BUGS-FIXED.md's `## Fixed` holds 1914 `-` bullets against 491 `###` headings. So the range reader is blind to the archive's majority shape.

**How to reproduce (offline, deterministic).** A scratch import over this tree: `actionableEntryRanges(BUGS-FIXED.md, "Fixed")` returns 1 range (a single `###` entry at line 43) out of 1914 bullets + 491 headings; the real newest closed entries (the `-` bullets at lines 8/20/30/…) are all skipped. Consequence 1 — the `<backlog-index>` block's `BUGS-FIXED.md ## Fixed (newest N)` (backlog-index.ts renderClosedSections, RECENT_CLOSED_MAX 5) lists stale `###` entries and never the actual newest closed bugs, in every role prompt. Consequence 2 — the archive dedupe (backlog-archive.ts entryFates, via entriesIn→actionableEntryRanges) matches selected entries against the archive's `###` entries only, so it cannot recognize a closed bug the archive already holds as a `-` bullet and will re-move it (duplicate). The same reader powers recordRecurrence (backlog-file-bugs.ts) and closeQuietWaitsText (backlog-bug-waits.ts).

**Suspected cause.** The `-` bullet is a valid one-line entry shape (parseEntryDetails and eachEntryStart read it; the team uses it for compressed closed entries), but the range walk was written for `###` headings only and never extended to the bullet shape, so every consumer of the range reader inherits the blind spot.

**Required behavior.** Decide the canonical entry shape for one-line entries and make the range reader match it. The fork: (a) make `actionableEntryRanges` read a top-level `- ` bullet as an entry-start (matching parseEntryDetails/eachEntryStart) so the closed index, archive dedupe, and bug wait-close all see the majority archive shape — the open `## Open` shape then needs a guard so a `- ` repro step inside an entry body is not misread as a sibling entry, or (b) canonicalize one-line entries to `### ` in the archive and close paths so the `###`-only reader is never blind. This is a plan-role design call (it touches twelve call sites and the entry-shape contract); the bugfix role records it, not force-picks a shape.
