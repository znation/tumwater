## Open

### A policy scan's failure is excused by test name alone, so a new offender in an already-failing scan merges as main's known failure (found by the reviewer role 2026-11-05)

- **Symptom:** when main is red on one of the repo-wide policy scans, a change that adds its own offender makes the same aggregate test fail (e.g. `every comment line in src/ and test/ fits in 100 columns…`), so the gate's failure has the same name as main's known failure. `onlyKnownMainFailures` (src/baseline/main-watch.ts:146) checks every failing test name against `knownMainFailures(root)` and, when all match, returns them as main's; the change's new offender is excused and merges, leaving main red on a line its own change introduced. Previously the scans were rarely selected at all (BUGS-FIXED.md 2026-11-05), which hid this gap; now that a budgeted gate force-runs them, it is the remaining half.
- **Reproduce:** with main red on `test/comment-width.test.ts` (one wide comment in file A), append a 125-column `//` comment to a different src file and run the gate on that change. The scan fails on the new line too, but the failure lists the same one test name, so `onlyKnownMainFailures` returns it as main's known failure and the gate does not blame the change.
- **Cause:** the excuse compares test names, not offenders. The four policy scans report one aggregate test regardless of which file or name offends, so a name match cannot distinguish main's offender from the change's.
- **Cost / why fileable:** the change's new offender lands on a red main, keeping main red and hiding which commit added it — the same failure mode the 2026-11-05 force-run fix addressed. The fix sketch: compare offenders, not test names — a scan failure that lists a line or name main's own failure does not list belongs to the change.

### A parked run's slot wait is visible on the role row but the doctor's contention view sees only finished waits, so a live tier-1 wait leaves no doctor signal (the visible-wait half of the fixed 2026-11-08 age-bound entry, found by the bugfix role 2026-11-08)

- **Symptom:** the age-bound fix (archived in BUGS-FIXED.md 2026-11-08) stops a tier-1 role from being passed over past a two-hour starve bound. The role row already shows a parked wait: `launchDueRuns` stamps `runner.state.parkedSince` before the semaphore `acquireLease` (src/orchestrator/orchestrator-launch.ts) and `rolePhase` renders `waiting to start <duration>` from it (src/ui/status-model.ts), so a role parked for hours does not read only `due`. What is still missing is the doctor's provider-contention view: it folds only `provider_wait` events, which are logged when a wait ends (src/doctor/doctor-contention-checks.ts), so a wait still in progress has no doctor row.
- **Cause:** the row and the doctor read different signals. The row reads the per-runner `parkedSince` stamp; the doctor sums completed `provider_wait` events. The semaphore's own wait queue (each parked waiter's tier and age) is not exposed to a doctor surface, so a live wait cannot be counted or aged there.
- **Expected / fix sketch:** publish the semaphore wait in progress (the parked tier and how long it has waited) to the doctor's contention view, so a long wait is visible before it ends; the role row already carries the wait duration. This is independent of, and complementary to, the age-bound fix archived under the sibling entry.

### The gate's stale-base excuse excuses a change's own scan failure on a green main, so a change rebased past a red base merges a new offender into a green tree (found by the selfcheck role 2026-11-06)

**Needs review 2026-11-08 by bugfix: too large for one run** — the fix it demands (compare offenders, not test names) needs offender data the model does not carry and a redesign of how the four aggregate policy scans report, threaded through every attribution arm and the merge path; park for a plan-to-split.

- **Symptom:** when a change's git base is a red commit but main's tip is now green, a gate failure that is the change's own gets excused as its base's. The digest's 10× warning cluster picks a concrete spell: `gate check fails only tests its base 88686680 already failed, and main c8e67154 is green: every comment line in src/ …` — `88686680` is the base commit (`tumwater(feature): mergeApprovedChange …`) and `c8e67154` the green main tip. The gate names only the aggregate policy test `every comment line in src/ and test/ …` (test/comment-width.test.ts, the repo-wide line-width scan), which the base was red on and whose offenders the change's own rebased commits can add to independently.
- **Reproduce:** on a main whose tip is green and whose history holds a red base, rebase a change that adds its own 125-column `//` comment onto that base. `staleBaseFailures` (src/review/review-precheck.ts:45) reads the base's `watchedBaseline` verdict as red, sees every failing test name in the base's set, and returns it — even though the change's new offender is a line the base's failure never listed. The pre-check logs `gate check fails only tests its base … already failed, and main … is green` and goes on to review with no fresh run on main (`rejected: no`, `knownMainFailures`), so the offender merges.
- **Cause:** the stale-base arm and the red-main arm both excuse by test **name**, never by **offender**. `staleBaseFailures` runs whether main's tip is green or red (review-precheck.ts:265-266 has no `main.status` gate before it) and subtracts the base's failing names from the change's by name alone. The four repo-wide policy scans (comment-width among them) report one aggregate test regardless of which file or line offends, so a name match cannot tell main's old offender apart from the change's new one. The base `88686680` was additionally never post-merge reviewed (entry above), so the scan's prior offender on it is unvetted too. This is the sibling of BUGS.md 2026-11-05's red-main entry: that entry's `knownMainFailures` arm and this stale-base arm both excuse a change's own offender, the first on red main and the second on green, so the code's `onlyKnownMainFailures` fix sketch should also close this one.
- **Cost / why fileable:** the change's new offender lands on a green tree, turning it red and hiding which commit added the line — the same failure mode as the filed red-main half, at the same aggregate-test blindness. The one underlying fix for both: compare offenders, not test names — a scan failure that lists a line or name the base's (or main's) failure does not list belongs to the change and must be rejected regardless of which main state the pre-check is excusing.
