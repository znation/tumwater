# Command reference

Every `tumwater` command and the main flags it takes. `tumwater help` lists every command and
flag; `tumwater help <command>` shows one command's usage. The README's Usage section has the
short version, and [config.md](config.md) covers the settings in `tumwater.json`.

## Start the team

```bash
cd your-project             # a new or existing directory
tumwater init "Build a tiny markdown-to-html converter CLI in Python."
                            # add --template <id> to seed from a bundled starting point
                            # (blank, python-cli, node-cli, static-site); --list-templates
                            # prints the catalog
                            # add --branch <name> to name the branch a new repository starts on (it seeds a new repo only)
                            # add --file <path> to read the brief from a file
                            # add --adopt to adopt an existing repo as-is
                            # a fresh/empty project is seeded with
                            # "bootstrap": {"untilPlansDone": 5}, holding the maintenance
                            # roles until 5 plans are done; remove "bootstrap" from
                            # tumwater.json to end that early
tumwater start              # start the team (Ctrl+C to stop)
tumwater start --gui        # ... and serve the browser dashboard at http://127.0.0.1:7180 from the same process
tumwater start --tui        # ... and host the TUI in this same terminal (the `tumwater tui` view; quitting it stops the team like Ctrl+C)
tumwater start --for 2h     # run for a bounded window (capped at 90d), then finish current work, print a per-role summary of the window, and exit (one window across updates); shown as `stops in …` on status, the TUI, and the dashboard
tumwater start --once       # one full round of runs, finishes the merges it produced, and exits (for cron/CI); exits 3 if a run failed;
                            # add --role <id>[,<id>...] to scope the round to the listed roles (enabled roles only)
tumwater start --branch <name>  # merge into that branch instead of baseBranch in tumwater.json or the checked-out branch; it must exist
```

`tumwater gui --port N` serves the dashboard on another port than 7180;
`gui --all-interfaces` exposes the dashboard, and with it the director prompt, to your whole
network, so pair it with `--token <secret>`.

## Watch, check, steer, control, audit

| To | Run |
| --- | --- |
| Watch the team | `tumwater tui`, or the browser dashboard at http://127.0.0.1:7180 — `tumwater gui` on its own, or `tumwater start --gui` to boot the team and the dashboard together |
| Watch run history | `tumwater history [--role <id>[,<id>...]] [-n N] [-f/--follow] [--since <duration>] [--grep <text>] [--result <merged|none|refused|problems>[,...]] [--model <selector>[,...]] [--summary] [--by role|model]`, where `-f` prints the last N rows oldest first, then one row per run as it ends, until Ctrl+C or its parent exits (not with `--since` or `--summary`; with `--json` each row is one compact JSON object per line, like `logs -f --json`), `--result none,refused,problems` shows every run that did not merge, `--model` keeps only the runs that started on the listed models, the exact selectors `--summary --by model` prints (`--model acme/m1 --summary` tallies just that model's runs by role), a comma list keeps the rows of any listed role (`--role feature,feature-2 --summary` tallies both feature instances), `--summary` prints one line per role counting its runs by outcome class (a per-role and total `refused` column between `none` and `problems`), tallying its tokens, cost and run time, and naming its newest merged change (plus a total) instead of the rows (`--summary --by model` prints one line per model with the same columns, `(unknown)` for runs whose start the log no longer holds), or `tumwater history --json` for the rows as JSON; `tumwater history <role> <n>` for one run's full event trail (a summary header — when it ran, how long, result, usage — followed by the run's events, oldest first; a run waiting to merge shows its merge verdict and outcome line once the merge finishes, and the header names the landed sha (`merged as <sha>`, the one `tumwater revert` takes) when a rebased merge put the change on main under a different sha than the run's commit; `tumwater history <role> --last` shows the newest completed run's trail instead of numbering one; `--stat` appends the run's commit's per-file `git show --stat` summary; `--patch` appends that commit's full patch (after the `--stat` summary when both are given); clearing falls back to the team-wide `minRunIntervalSeconds`), and sets the role's instance count, writing `roles.<base>.instances` (an integer 1–8; only `feature` and `bugfix` may split), and sets the role's model triple, writing `roles.<base>.provider`/`.model`/`.thinking` (an instance id writes its base role's keys)—and the TUI's role Transcript view (Ctrl+O) edits or clears that same window—and the TUI's role Transcript view (Ctrl+L) replaces or clears the standing-instructions override from a typed file path, writing `roles.<base>.instructions` for the base id—and the TUI's role Transcript view (Ctrl+G) edits or clears the viewed role's parallel-runner count, writing `roles.<base>.instances` (an integer 1–8; only `feature` and `bugfix`; empty clears it)—and the TUI's role Transcript view (Ctrl+X) edits or clears the role's model override, writing `roles.<base>.model` for the base id (a model id or tier name like `strong`; empty clears it)—and the TUI's notes view (Ctrl+N) clears them with Ctrl+X pressed twice) |
| See a role's pending change | `tumwater diff --role <id>` (`--stat` swaps each patch for its per-file `git diff --stat` summary) — that role's branch's unmerged commits (with the patch) and its worktree's uncommitted edits (staged and unstaged); without `--role`, one line per role holding pending work; `--json` prints the payload as data |

absent when the window has no tagged fixed bug), and each `run_start`'s agent-qualified selector tallied as `Runs by model` (the exact model a team mixing providers, per-role overrides and fallbacks ran on; team report only, so a mixed-backend team sees how much of a day ran on a fallback or an override); totals include merge runs — reviewer + conflict resolution), `tumwater report --role <id>[,<id>...]` (scopes the day or `--since` report to the listed roles' runs, tokens, cost, and commits, summed with one by-role entry per listed role; merge runs and backlog tallies are team-wide and omitted; with `--failures`, scopes the failure digest to those roles too), `tumwater report --since <duration>` (totals over a trailing window, capped at 7d; with `--failures`, the failure digest over that window instead), `tumwater report --json` (the `--days`/`--since`/`--failures` reports as JSON, for scripts), `tumwater report --failures` (the failure digest: per-role outcomes, each role's time and spend by outcome, and the top five loss causes ranked by agent-hours, with a marker naming how many were cut; `--since <duration>` windows the digest over a trailing span, capped at 7d, compared against the equal-length window before it) |

`tumwater completion bash|zsh|fish` prints a shell completion script derived from that help (completing role ids after `--role` and as the first argument of `role`, `history` and `revert`, and keys after `config get|set|unset`, file paths after `--file`/`--attach`/`--notes-file`/`--instructions-file`, template ids after `--template`, result classes after `--result`, event-type codes after `--type`, summary groups after `--by`, tier names after `role <id> --model`, and check names after `doctor`); `tumwater completion --roles` and `tumwater completion --config-keys` print the role ids and config keys that script completes. Install
it with `eval "$(tumwater completion zsh)"` in your shell rc, or for fish write `tumwater completion fish > ~/.config/fish/completions/tumwater.fish`. `tumwater version` prints the version.

## TUI keys

The hint line at the bottom of the TUI names the keys the current view takes.

| Key | Where | What it does |
| --- | --- | --- |
| `Ctrl+T` | any view | next view (Activity, each role's Transcript, Backlog, Usage, Failures, History, Pending, Inbox, Health, Brief); it also leaves an open editor |
| `Ctrl+D` | any view | quit the TUI (under `tumwater start --tui` this stops the team like Ctrl+C in the shell) |
| `Ctrl+C` | any view | interrupt the director's in-flight run, as `tumwater abort --role director` does; a notice when none is in flight |
| `Enter`, `↑`/`↓`, `PgUp`/`PgDn`, `Esc` | prompt line, panes | send the prompt, prompt history (or move through entries on Backlog), scroll, cancel an editor |

| `Ctrl+B` | Activity, Transcript | edit the daily cost cap: the team's on Activity, the viewed role's (`maxDailyCostUsdPerRole.<role>`) on its Transcript; empty means no cap |
| `Ctrl+P` | Activity | edit the team's per-provider concurrency caps (`maxConcurrentPerProvider`, a JSON object like `{"anthropic":2}`; empty clears it) |
| `Ctrl+A` | Activity | edit the team's model (`model`, a model id or a JSON map by tier like `{"strong":"..."}`; empty clears it) |
| `Ctrl+X` | Activity | edit the team's agent backends (`backends`, a JSON object of per-backend `bin`/`args` such as `{"pi":{"bin":"/path/to/pi"}}`; empty clears it) — the terminal twin of the dashboard Settings Agent backends field |

| `Ctrl+R` | Activity | apply the pending self-redeploy now (the terminal twin of `tumwater restart` and the dashboard update alert's restart button) |
| `Ctrl+W` | Activity | edit the team's worktree pool size (`worktreeSlots`, an integer ≥ 1; empty restores the `maxConcurrent + 1` default) |
| `Ctrl+V` | Activity | attach an image path to the next prompt to the director (the terminal twin of `tumwater prompt --attach <path>` and the dashboard composer's drop/paste) |

| `Ctrl+X` | Transcript | edit the viewed role's model override (`roles.<base>.model`, a model id or tier name like `strong`; an empty line clears it) — the terminal twin of `tumwater role <id> --model` and the dashboard role drawer's Model overrides editor (an instance id writes its base role's key) |
