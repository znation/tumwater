# Command reference

Every `tumwater` command and the main flags it takes. `tumwater help` lists every command and
flag; `tumwater help <command>` shows one command's usage; `tumwater help --grep <text>`
prints the usage stanzas containing the text, case-insensitively (no ready repo needed, like
the topic form). The README's Usage section has the short version, and [config.md](config.md)
covers the settings in `tumwater.json`.

## Start the team

```bash
cd your-project             # a new or existing directory
tumwater init "Build a tiny markdown-to-html converter CLI in Python."
                            # add --template <id> to seed from a bundled starting point
                            # (blank, python-cli, node-cli, static-site); --list-templates
                            # prints the catalog
                            # add --branch <name> to name the branch a new repository starts on (it seeds a new repo only)
                            # add --file <path> to read the brief from a file
                            # add --adopt to adopt an existing repo as-is
                            # add --json to print one acknowledgement object (command, status
                            # initialized or already_initialized, dryRun, template, adopted,
                            # readmeExists, wasRepo, repoInitialized, branch, created,
                            # leftAlone, committed, bootstrap) instead of the prose report;
                            # --list-templates --json prints the catalog as a templates array
                            # a fresh/empty project is seeded with
                            # "bootstrap": {"untilPlansDone": 5}, holding the maintenance
                            # roles until 5 plans are done; remove "bootstrap" from
                            # tumwater.json to end that early
tumwater start              # start the team (Ctrl+C to stop)
tumwater start --gui            # ... and serve the browser dashboard at http://127.0.0.1:7180 from the same process
                                # add --port <n> to serve it on another port (the `tumwater gui --port <n>` twin)
                                # add --all-interfaces and --token <secret> to serve the LAN behind the
                                # auth gate — both forward onto the dashboard child, the `tumwater gui` twins
tumwater start --tui        # ... and host the TUI in this same terminal (the `tumwater tui` view; quitting it stops the team like Ctrl+C)
tumwater start --for 2h     # run for a bounded window (capped at 90d), then finish current work, print a per-role summary of the window, and exit (one window across updates); shown as `stops in …` on status, the TUI, and the dashboard
                            # (add --json to print that summary as one JSON object — tumwater start --for 2h --json)
tumwater start --once       # one full round of runs, finishes the merges it produced, and exits (for cron/CI); exits 3 if a run failed;
                            # add --role <id>[,<id>...] to scope the round to the listed roles (enabled roles only)
                            # add --json to print the round's totals, per-result counts, skipped roles and failures as one JSON object (only with --once or --for)
tumwater start --branch <name>  # merge into that branch instead of baseBranch in tumwater.json or the checked-out branch; it must exist
```

`tumwater gui --port N` serves the dashboard on another port than 7180;
booting with `tumwater start --gui --port N` serves it the same way from the
one-command start.
`tumwater start --gui --all-interfaces --token <secret>` forwards both onto the
dashboard child, exposing the dashboard — and with it the director prompt — to your
whole network behind the token gate, so the one-command start can serve the LAN as
`gui --all-interfaces --token <secret>` would on its own.

## Scripting the writes

Each write above takes `--json`, which prints one acknowledgement object in place of its prose line so a script can read the result as data instead of parsing the text. A refusal still fails with its prose and prints no JSON, so no partial acknowledgement is ever emitted. One entry per write form, and the fields it prints (the same fields `tumwater help` names):

- `tumwater plan "<title>" [body...] --json` and `tumwater plan --file <path> --json` file a plan into PLANS.md and print `{ file, title, stamp }` — `file` the backlog file (`PLANS.md`), `title` the entry's first line, `stamp` its filing stamp; `tumwater bug` files into BUGS.md the same way.
- `--release <n> --json` lifts the `Refused` or `Needs review` note from the Nth open entry and wakes its role, printing `{ file, title, lifted }` — `lifted` the note it lifted — plus `hold` when the entry is still held and wakes no one.
- `--top <n> --json` moves the Nth entry to the head of its section and prints `{ file, title }`, plus `hold` when the entry is still held.
- `--cancel <n> --json` removes the Nth entry and prints `{ file, title }`, plus `workingOn` when a role is working on it, and `released` when cancelling a plan frees its waiting dependant parts.
- `--edit <n> ... --json` rewrites the Nth entry in place (or `--edit <n> --file <path>`) and prints `{ file, title }`, plus `hold` when it is still held; an unchanged buffer writes nothing and prints `{ file, title, changed: false }`.
- `--retire <n> [--reason <text>] --json` moves the Nth open entry to the kind's finished section as retired — `## Fixed` for a bug, `## Done` for a plan — and prints `{ file, title, retiredOn }`, plus `reason` when one was given.
- `tumwater retire --role <id> [--force] [--dry-run] --json` removes a disabled role's workspace, branch, and per-role state; on a dry run it prints `{ role, dryRun: true, wouldRemove, skipped, objections }`, and without `--dry-run` it prints `{ role, removed, skipped }`.
- `tumwater reviews --accept <n> --json` removes the Nth queued post-merge review as deliberately accepted unreviewed, logging a warning, and prints `{ accepted: { role, commit, summary } }`.
- `tumwater quarantine --release <n> --json` releases the Nth quarantined flaky test, logging a warning, and prints `{ released: { position, test } }`.
