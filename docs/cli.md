# Command reference

Every `tumwater` command and the main flags it takes. `tumwater help` lists every command and
flag; `tumwater help <command>` shows one command's usage. The README's Usage section has the
short version, and [config.md](config.md) covers the settings in `tumwater.json`.

## Start the fleet

```bash
cd your-project             # a new or existing directory
tumwater init "Build a tiny markdown-to-html converter CLI in Python."
                            # add --template <id> to seed from a bundled starting point
                            # (blank, python-cli, node-cli, static-site); --list-templates
                            # prints the catalog
                            # add --file <path> to read the brief from a file
                            # add --adopt to adopt an existing repo as-is
                            # a fresh/empty project is seeded with
                            # "bootstrap": {"untilPlansDone": 5}, holding the maintenance
                            # loops until 5 plans are done; remove "bootstrap" from
                            # tumwater.json to end that early
tumwater run                # start the loops (Ctrl+C to stop)
tumwater run --gui          # ... and serve the browser dashboard at http://127.0.0.1:7180 from the same process
tumwater run --tui          # ... and host the observer TUI in this same terminal (the `tumwater tui` view; quitting it stops the fleet like Ctrl+C)
tumwater run --for 2h       # run for a bounded window (capped at 90d), then drain, print a per-loop summary of the window, and exit (one window across self-redeploys); shown as `stops in …` on status, the TUI, and the dashboard
tumwater run --once         # one full round of ticks, drains its landings, and exits (for cron/CI); exits 3 if a loop's tick failed;
                            # add --role <id> to scope the round to one loop
```

`gui --all-interfaces` exposes the dashboard, and with it the director prompt, to your whole
network, so pair it with `--token <secret>`.

## Watch, check, steer, control, audit

| To | Run |
| --- | --- |
| Watch the fleet | `tumwater tui`, or the browser dashboard at http://127.0.0.1:7180 — `tumwater gui` on its own, or `tumwater run --gui` to boot the fleet and the dashboard together |
| Watch per-tick history | `tumwater history [--role <id>] [-n N] [--since <duration>] [--grep <text>] [--result <changes|none|problems>] [--summary]`, where `--summary` prints one line per loop counting its ticks by outcome class, tallying its tokens and cost, and naming its newest change (plus a total) instead of the rows, or `tumwater history --json` for the rows as JSON; `tumwater tick <role> <n>` for one tick's full event trail (a summary header — when it ran, how long, result, usage — followed by the tick's events, oldest first; a queued tick shows its landing's verdict and outcome line once the landing finishes; `--last` shows the newest completed tick's trail instead of numbering one; `--stat` appends the tick's commit's per-file `git show --stat` summary; `--json` prints the payload as JSON, `null` when the log holds no such tick) |
| Check state | `tumwater status`, `tumwater brief [--json]` (the initial prompt and the file that holds it; the TUI's Brief tab and the dashboard's Settings card show it too), `tumwater logs -f`, `tumwater logs --since <duration>`, `tumwater logs --grep <text>`, `tumwater logs --type <event type>` (only events of that exact event type; composes with `--since`), `tumwater logs --json` (the event feed as NDJSON, for scripts), `tumwater logs --role <id>`, `tumwater queue [--json]` (the durable land queue in execution order — one line per waiting landing with its position, loop, tick, pinned sha, age, and summary, plus a `[landing 2m · reviewing]` or `[vetted, awaiting merge]` label on an entry the running fleet is landing; `--json` for scripts, with an `inFlight` key then), `tumwater backlog` (planned features, open bugs, open questions as Markdown, a series with two or more blocked parts printing as one heading (`--json` still lists every entry), each held entry's heading marked `[refused]`, `[needs review]`, `[needs replan]`, or `[blocked: requires …]`, and an entry a role is working on marked `[working on it: feature #2]`), `tumwater backlog --json` (the backlog as JSON, for scripts, with `holds.plans`/`holds.bugs` and `inProgress.plans`/`inProgress.bugs` arrays parallel to `plans`/`bugs`, the latter holding runner ids or null), `tumwater backlog --ready` (only the plans and bugs no hold keeps from being picked, with entries a role is working on kept and a count of the hidden ones; composes with `--json`), `tumwater role <id>` (one loop's standing prompt — find text, `instructions` override, resolved model and interval, whether its model reads images and where a blind read reroutes (its `Images:` line), enabled/paused state, its notebook — plus its next tick's assembled prompt, which shows the oldest queued prompt without consuming it (one is dequeued per tick; `--json` for scripts); `--clear-notes` clears that loop's notebook and `--notes-file <path>` (`-` for stdin) replaces it (4 KB cap); the dashboard's loop drawer edits or clears the notebook the same way, and the TUI's notebook view (Ctrl+N) clears it with Ctrl+X pressed twice) |
| See a loop's pending change | `tumwater diff --role <id>` (`--stat` swaps each patch for its per-file `git diff --stat` summary) — that loop's branch's unlanded commits (with the patch) and its worktree's uncommitted edits (staged and unstaged); without `--role`, one line per loop holding pending work; `--json` prints the payload as data |
| Steer the project | `tumwater brief --file <path>` (`-` for stdin), or `tumwater brief --edit` (opens the prompt in `$VISUAL`/`$EDITOR`; an unchanged buffer writes nothing), replaces the initial prompt — refused when empty, over 4096 characters, or containing a prompt marker — and commits the brief file to main as `tumwater(operator): Edit brief` (the dashboard's Settings view edits it the same way, in its Initial prompt card); `tumwater prompt "prefer no third-party deps"` queues a request for the director; add `--role <id>` to aim it at one loop's next tick, `--file <path>` (`-` for stdin) to read the text from a file, or `--at <duration>` to defer it until the duration passes (45s, 90m, 1h30m, 1d; capped at 90d), `tumwater prompt --list` shows the queued prompts numbered and grouped by loop, with how long each has waited (`--json` for scripts), and `tumwater prompt --cancel <n>` removes the Nth entry as `--list` shows them, and `tumwater prompt --edit <n> "new text" [--attach <path>]` rewrites the Nth entry in place (or `--edit <n> --file <path>` takes the replacement from a file, or bare `--edit <n>` opens the prompt in `$VISUAL`/`$EDITOR`, an unchanged buffer writing nothing), keeping its position and wait time, and appends any `--attach` images after the ones it already carries (both take `--role <id>` when several loops share that number), and `--attach <path>` (repeatable, up to 4 images — png, jpg, jpeg, gif, webp, bmp, each at most 5 MiB) attaches an image the receiving loop reads at its next tick, whether it is queued or edited; when the target loop's model cannot read images the attachment is refused up front naming the fix (unless the loop reroutes a blind read to a vision tier, in which case the command says where the prompt will run — the same gate the dashboard's composer enforces); `tumwater bug "<symptom>"` files a bug into BUGS.md's Open section and wakes the bugfix loop, `tumwater plan "<title>" [body...]` — or `--file <path>` (`-` for stdin) to file one from a markdown file, its first line the title and the rest the body, kept line for line — files a plan request into PLANS.md's Planned section and wakes the feature loop — both stamped as operator-reported (the other half of `tumwater backlog`) and committed to main as `tumwater(operator): File <kind>: <title>` when the primary checkout is on the base branch, `--list` shows a command's own entries numbered with their eligibility marks and a `[working on it: …]` mark on an entry a role is working on (`--json` for scripts, each entry carrying `inProgress`; the dashboard's Plans/Bugs tabs and the TUI's backlog pane show the same marks beside each title; `plan --list` shows a series' blocked parts as one line naming their positions), `--list --done [-n <count>]` lists the newest fixed bugs or done plans instead, newest first (`--json` carries each one's `completedOn` date), `--show <n>` prints the Nth entry as the markdown file `--edit <n> --file` takes back (`--json` for scripts), and `--release <n>` lifts a Refused note and commits it on main, waking the loop, `--cancel <n>` retracts one or `--edit <n> "<text>"` rewrites one in place (or `--edit <n> --file <path>` takes the replacement from a file, keeping its lines, or bare `--edit <n>` opens the entry as `--show` prints it in `$VISUAL`/`$EDITOR` and writes the saved buffer back, an unchanged buffer writing nothing), neither with a wake, and both committed to main like a filing; the dashboard's plan/bug drawer cancels an entry the same way, after a confirming second click, and the TUI's backlog pane does too, with Ctrl+X pressed twice on the selected entry (Ctrl+E edits its title; Ctrl+N files a new plan or bug by title and wakes its loop), the drawer edits an entry's title and body in place, and the Plans/Bugs tabs' New form files one with an optional markdown body |
| Answer open questions | `tumwater questions` lists QUESTIONS.md's open questions numbered (as the loops wrote them); `tumwater questions answer <n> "decision text"` moves the Nth entry to ## Answered with your dated answer (bare `questions answer <n>` opens the question in `$VISUAL`/`$EDITOR` and records the text above the marker line; committed to main as `tumwater(operator): Answer question: <title>`; `--file <path>`, `-` for stdin, records a multiline decision with its lines kept; loops read the file back on their next tick); `--json` prints the list as data; `tumwater questions --answered [-n <count>]` lists the newest answered questions with their answer lines, newest first (`--json` carries each one's `answeredOn` date); the dashboard's question drawer records an answer with its lines kept, as `--file` does, and the TUI's backlog pane answers the selected question with Ctrl+A |
| Control the loops | `tumwater pause [--for <duration>]` / `resume [--role <id>]` (fleet or one loop; `--for 2h` auto-resumes, capped at 90d; add `--reason <text>` on a fleet pause to state why — it shows on `status`, the TUI, and the dashboard; the TUI's Ctrl+F takes a duration and reason too, and its Ctrl+P on a loop's transcript takes a duration, and its Ctrl+W takes a duration or `cancel`), `tumwater wake` (skip backoff; `wake --in 45m` schedules the wake for 45 minutes from now — the marker is written immediately but consumed no earlier than the deadline, like `pause --for`'s auto-resume, and each scheduled wake stands on its own, so later wakes do not cancel it, while `tumwater wake --cancel [--role <id>]` drops the pending scheduled wakes (or that loop's share of them), `tumwater wake --list [--role <id>] [--json]` lists them, and the dashboard's Wake later menu and loop drawer cancel pending wakes the same way; the dashboard's loop drawer schedules one loop's wake the same way ("Wake later…"); `tumwater status` and the dashboard's loop rows show the pending wake until it fires), `tumwater reclaim [--dry-run]` (drop gitignored build outputs from every harness worktree; `--dry-run` lists the candidates and cleans nothing), `tumwater retire --role <id> [--dry-run]` (remove a disabled loop's worktree, branch, and per-role state — use after setting `enabled: false` for that role; `--force` overrides the safety rails; `--dry-run` previews what would be removed and which rails would object, changing nothing), `tumwater abort --role <id>`, `tumwater stop` (drain and exit, like Ctrl+C; `stop --in 2h` schedules that drain for later and shows `stops in …` like `run --for`, `stop --cancel` drops it; the dashboard's "Stop the fleet later" control sets and cancels it too, and so does the TUI's Ctrl+Q: a duration sets it, and when one is already scheduled it cancels), `tumwater reset-counters [--role <id>]` (zero the per-loop counters the dashboards show, starting a fresh observation window — scheduling is untouched; the dashboard's Loops card and loop drawer reach the same reset) |
| Audit | `tumwater doctor` (pre-flight, naming a standing fleet or per-role pause or quiet-hours window holding now, today's spend against the daily cap, a claude subscription window holding the claude seams, the maintenance allowance's rolling-24 h use, loops failing tick after tick (and whether they are paused), code loops held by a red main, a notify command that failed to page within the last 24 h, slot waits that call for a larger `worktreeSlots`, and planned plans and open bugs held by a Refused note (released with `tumwater plan|bug --release <n>`), flagging one whose prerequisites are no longer planned, open bugs unfixed 3 days or more after their filing stamp, and backlog files or the brief with uncommitted edits in the primary checkout; `--json` prints the report as JSON, for scripts; by default it probes each claimed image-input model once (cached 7 days in `.tumwater/state/image-probes.json`) and `--reprobe` forces every one; the dashboard's Settings view runs the same checks in its Health check card and the TUI's Health tab, both reading cached image-probe verdicts only so a refresh never spends a model call), `tumwater report` (usage and cost, with landed commits by role, each role's cost per landed commit, the work/maintenance split, and ranked per-role lines for tokens, rejections (from `review_rejected` events), and revisions (rework rounds after a rejection); totals include landing runs — reviewer + conflict resolution), `tumwater report --role <id>` (scopes the day or `--since` report to one loop's ticks, tokens, cost, and commits; landing runs and backlog tallies are fleet-wide and omitted; with `--failures`, scopes the failure digest to that loop too), `tumwater report --since <duration>` (totals over a trailing window, capped at 7d; with `--failures`, the failure digest over that window instead), `tumwater report --json` (the `--days`/`--since`/`--failures` reports as JSON, for scripts), `tumwater report --failures` (the failure digest: per-role outcomes, each role's time and spend by outcome, and the top five loss causes ranked by agent-hours, with a marker naming how many were cut; `--since <duration>` windows the digest over a trailing span, capped at 7d, compared against the equal-length window before it) |

`tumwater completion bash|zsh` prints a shell completion script derived from that help (completing loop ids after `--role` and keys after `config get|set|unset`, file paths after `--file`/`--attach`/`--notes-file`, template ids after `--template`, and result classes after `--result`); install
it with `eval "$(tumwater completion zsh)"` in your shell rc.
